# 微服务

> [!abstract] 定位
> **微服务** 是把一个大系统拆成许多小而独立的服务，各自负责一块（用户、订单、支付、通知、搜索……）。这解释了「为什么会有 50 个服务 / 50 个容器」，以及为什么需要容器编排。与 [[后端基础]] 的「单服务」视角互补，向上接 [[部署方式]] 的「容器编排」。

---

## 一、为什么会有 50 个服务？

单体应用把所有功能写在一个程序里；微服务则按业务边界拆分：

```text
用户服务   订单服务   支付服务   通知服务   搜索服务   推荐服务   风控服务 ...
```

**好处**：每个服务可独立开发、独立扩容、独立部署、技术栈可不同。电商、社交、SaaS 这类大系统常见几十到上百个服务。

---

## 二、50 个服务 = 50 个容器吗？

通常是 **50 个以上容器**。因为每个服务为了高可用和扛流量，会跑 **多个副本（replica）**：

```text
订单服务 ×3 副本  ┐
支付服务 ×2 副本  ├─ 散布在多台机器上
通知服务 ×2 副本  ┘
→ 50 个服务可能对应 200 个容器
```

---

## 三、为什么需要编排（而不是 docker run）

手动 `docker run` 200 个容器、记哪台跑了什么、挂了手动拉起、流量怎么分——不可能。于是需要编排器：

- **[[Docker Compose]]**：单台机器上把多个容器一起拉起、连成网。适合小项目 / 单机。
- **Kubernetes（K8s）/ ECS / EKS**：跨很多台机器，自动调度容器、挂了重启、负载均衡、按流量扩缩副本。

> [!note] 术语关系串起来
> [[云服务模型]]（IaaS 提供机器）→ 容器是打包格式（[[Docker]]）→ 编排器（K8s）调度这几十上百个容器 → IAM / 监控等横切管理。小工具用不上这套，单机 `docker run` 或 Compose 就够了。

---

## 四、FDE 视角

- 客户系统常是「一堆已有服务」，FDE 多是**新增/连接**一个服务，而非从零设计 50 个。
- 写新服务优先用 [[FastAPI]] 做成独立容器，通过 [[REST API]] 与现有服务通信。
- 理解微服务，才能看懂客户的「服务网格 / 网关 / 注册中心」在干什么（见 [[企业系统集成]]）。
