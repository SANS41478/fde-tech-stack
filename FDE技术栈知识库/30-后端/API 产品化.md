# API 产品化

> [!abstract] 定位
> [[REST API]] 解决接口基本设计，本篇关注接口从「能返回数据」成长为「前端、客户和 AI 都能稳定使用的产品」时必须补上的契约、错误、性能和演进能力。

## 一、先判断是否需要 API

- 页面只在服务端读取一次数据：可以直接在 Server Component / 服务端函数中访问数据库。
- 多端复用、异步任务、第三方调用或权限边界明确：需要 API。
- 不要为了形式上的前后端分离，把一次简单查询拆成无价值的网络跳转。

## 二、稳定的接口契约

每个接口至少定义：

```text
Method + Path
请求参数与 JSON Schema
认证与权限
成功响应
错误响应
分页 / 排序 / 过滤
幂等性与重试
```

推荐统一错误格式：

```json
{
  "error": {
    "code": "INVALID_ARGUMENT",
    "message": "title 不能为空",
    "details": { "field": "title" },
    "request_id": "req_123"
  }
}
```

客户端依据 `code` 和状态码处理，不要只显示一个模糊的「出错了」。

## 三、列表接口的演进

### 分页

```text
GET /movies?limit=20&cursor=...
```

- `offset` 易懂，适合小数据和后台页面。
- `cursor` 更适合大数据、持续增长和稳定翻页。
- 响应返回 `items`、`next_cursor`、`has_more`。
- 明确默认排序，避免翻页时重复或漏数据。

### 过滤与排序

```text
GET /movies?tag=ai&min_rating=8&sort=-created_at
```

- 参数白名单化，不能把用户字符串直接拼进 SQL。
- 组合筛选要有索引和最大返回量。
- 复杂查询优先定义清晰的查询对象，而不是无限增加参数。

## 四、输入校验与幂等

- 前端校验只改善体验，后端校验才是安全边界。
- 使用 Zod、Pydantic 等 Schema 校验请求体、查询参数和响应。
- 创建、支付、发信等写操作支持幂等键。
- 数据库唯一约束是重复写入的最后防线。

```text
请求带 Idempotency-Key
  ↓
服务端记录 key 与结果
  ↓
重试同一 key → 返回原结果，不重复执行
```

## 五、版本与向后兼容

危险变更包括：

- 删除字段。
- 改字段类型。
- 改枚举值含义。
- 改错误码。
- 改分页默认排序。

安全演进顺序：

```text
新增字段（可选）
  ↓
客户端迁移
  ↓
标记旧字段 Deprecated
  ↓
观察使用情况
  ↓
在版本边界删除
```

保留 OpenAPI / Schema 文档，让前端和 AI 依据契约开发。

## 六、批量操作与文件上传

批量接口适合删除、更新、导入等大量同类操作，但要明确：

- 单项成功 / 失败结果。
- 最大批量大小。
- 部分失败是否整体回滚。
- 幂等和重试策略。

文件上传：

```text
multipart/form-data
  ↓
校验大小、类型、扩展名和内容
  ↓
存对象存储
  ↓
数据库只保存元数据和访问引用
```

不要把用户上传文件直接放在应用容器本地，也不要仅凭文件扩展名判断类型。

## 七、实时性选择

| 方案 | 适合 | 代价 |
| --- | --- | --- |
| Polling | 低频状态查询 | 浪费请求，有延迟 |
| SSE | 服务端持续推送、AI 流式输出 | 单向通信 |
| WebSocket | 双向实时协作、游戏、聊天 | 连接和扩展复杂 |
| Webhook | 系统间事件通知 | 需要签名、重试、幂等 |

先问「实时性是否真的影响用户价值」，再选技术。

## 八、API 上线检查

- [ ] 所有输入和输出都有 Schema。
- [ ] 错误码、状态码和 `request_id` 一致。
- [ ] 写操作具备幂等或明确不可重试。
- [ ] 列表接口有限制、排序和分页。
- [ ] 认证、授权和租户隔离在服务端执行。
- [ ] 文件不落本地容器，密钥不进响应。
- [ ] 有 API 测试和向后兼容策略。
