# Palantir Ontology 与传统方案对比

> [!abstract] 一句话
> 传统方案解决"看数据"的问题，Ontology 解决"看完数据后怎么行动"的问题。核心区别不在存储，在于**数据、操作、权限是否在同一模型里**。

---

## 一、与常见方案的逐项对比

### 1.1 vs ETL / 数据仓库

| 维度 | ETL / 数据仓库 | Palantir Ontology |
|---|---|---|
| 做了什么 | 把数据搬到一起，能看 | 把数据搬到一起，能看、能改、能控、能审 |
| 关系 | JOIN 表，用时临时关联 | **提前建好**，查询时直接遍历 |
| 操作 | 另外写代码调 API | 操作本身就是 Ontology 的一等公民（Action Type） |
| 权限 | 另外套一层权限系统 | **跟随对象走**，谁能看什么字段、能执行什么操作，在对象上定义 |
| 实时性 | 批处理为主 | 支持实时同步和流式数据 |
| 写回 | 不支持或需额外开发 | 内置回写机制，操作可写回源系统 |

### 1.2 vs BI / 数据仪表盘

| 维度 | BI / 仪表盘 | Palantir Ontology |
|---|---|---|
| 核心能力 | 可视化报表、仪表盘 | 对象化操作 + AI 推理 + 决策闭环 |
| 数据消费方式 | 看图表 | 看对象详情 + 执行操作 |
| 操作支持 | 无（看完数据另想办法执行） | 内置操作（如：一键审批、调拨、标记风险） |
| AI 集成 | 无或有限 | LLM 直接查询对象、调用函数、执行操作 |
| 权限粒度 | 报表级或数据源级 | 对象级、字段级、操作级 |
| 决策支持 | 展示历史数据 | 展示 + 推理 + 操作 + 审计闭环 |

### 1.3 vs 知识图谱（Neo4j / Stardog）

| 维度 | 传统知识图谱 | Palantir Ontology |
|---|---|---|
| 基本单元 | 三元组（Subject-Predicate-Object） | Object、Property、Link |
| Schema 灵活度 | 极高（Schema-less） | 可管理 Schema（优先稳定性） |
| 数据存储 | Triplestore（图数据库） | Object Storage V2（微服务架构） |
| 主要用途 | 知识发现、分类、互操作 | 操作应用后端、事务处理 |
| 写操作 | 有限或需特殊配置 | Action Type 作为一等公民，完整治理 |
| 权限 | 通常不内置 | 内置 Role/Classification/Purpose 三维权限 |
| AI 集成 | 有限（通常作为 RAG 数据源） | OAG（结构化对象 + 操作 + 审计） |

### 1.4 vs 传统数据中台

| 维度 | 数据中台 | Palantir Ontology |
|---|---|---|
| 设计理念 | 数据共享与复用 | 业务对象化 + 操作闭环 |
| 核心抽象 | 数据集、指标、维度 | Object Type、Link Type、Action Type |
| 操作能力 | 无（只管数据） | 有（管数据 + 管操作 + 管权限） |
| AI 就绪度 | 需要大量特征工程 | 天然结构化，AI 可直接理解 |
| 迭代方式 | 统一规划、逐步建设 | 从单个用例试点，逐步扩展 |

## 二、三种本体观的演进

| 层级 | 本体观 | 技术代表 | 主要能力 |
|---|---|---|---|
| L1 | 对象中心 | ER / OOP | 描述实体、字段、属性 |
| L2 | 对象 + 关系 | Graph / Knowledge Graph | 表达复杂关系和路径 |
| L3 | 关系 + 行为 + 约束 | Palantir Ontology | 对象、关系、动作、权限、审计 |

Palantir Ontology 属于 L3——不仅描述"有什么"，还定义"能做什么"以及"谁被允许做"。

## 三、为什么传统方案不够用

### 场景：查"哪些订单延迟了"

| 方案 | 做法 | 痛点 |
|---|---|---|
| 传统 BI | 跑 SQL，看报表 | 看到延迟后，要另想办法执行操作 |
| 数据中台 | 查数据集，看指标 | 没有操作能力，需要通知 IT 写脚本 |
| 知识图谱 | 图查询，找关系路径 | 可以分析原因，但不能直接执行操作 |
| **Ontology** | 看到 `Order` 对象列表，直接点 `Reroute Shipment` 按钮 | 数据、分析、操作、权限在同一界面 |

### 关键区别

> [!tip] 传统方案是"看完数据再想怎么行动"
> Ontology 是"数据、行动、规则、权限在同一个模型里"

---

## 四、Ontology 的局限

> [!warning] 不要过度神化 Ontology
> - **概念不新**：Ontology 理论已有 30 年历史，Palantir 只是做了工程化
> - **构建成本高**：需要大量数据清洗、映射、对齐工作
> - **维护持续**：不是建完就完了，需要持续迭代
> - **不是万能药**：如果企业数据源很少、业务流程简单，可能不需要 Ontology
> - **锁定风险**：一旦 Ontology 建好，所有应用都绑定在上面，换平台代价极大

---

## 五、何时该用、何时不该用

### 适合的场景

- 多系统、多数据源、跨部门数据需要统一
- 不仅需要"看数据"，还需要"基于数据执行操作"
- 需要 AI Agent 可靠地理解和操作业务
- 有高价值场景可以用 Ontology 闭环（如供应链、医疗、金融风控）

### 不适合的场景

- 数据源单一，已有成熟的内部系统
- 只需要报表和分析，不需要操作闭环
- 业务流程简单，不需要复杂的对象关系建模
- 预算有限，无法承受 Ontology 的构建和维护成本
