# FDE 工作方式

> [!abstract] 核心
> FDE 与普通研发最大的区别之一，不在技术栈，而在 **工作方式**。普通研发走的是「明确需求 → 设计 → 开发 → 测试 → 发布」的线性流程；FDE 走的是「模糊问题 → 快速理解 → 判断真问题 → 原型 → 现场验证 → 不断改 → 集成 → 部署 → 交付」的 **循环迭代** 流程。

---

## 一、两种流程的对照

### 普通研发（线性）

```text
明确需求
   ↓
设计
   ↓
开发
   ↓
测试
   ↓
发布
```

### FDE（循环）

```text
客户提出一个模糊问题
        ↓
快速理解业务
        ↓
判断真正问题
        ↓
快速 Prototype
        ↓
现场验证
        ↓
不断修改
        ↓
集成客户系统
        ↓
部署
        ↓
交付
```

> [!warning] 别用错流程
> 如果拿「先写详细 PRD、再排期两个月」的方式做 FDE，几乎一定会失败——因为客户在第三周就会改变想法，而你连第一个能跑的东西都还没给他们看。

---

## 二、FDE 必须接受的现实

做 FDE，要从心里接受以下常态：

- **需求经常变化** —— 客户看到 Demo 才会想清楚自己要什么。
- **信息经常不完整** —— 你常常在只有 30% 信息时就得动手。
- **技术栈经常变化** —— 今天用 LangChain，明天客户要求用别家模型。
- **客户系统经常很奇怪** —— 老旧 ERP、私有 API、手工 Excel。
- **很多问题没有标准答案** —— 能跑、能验证、能交付，就是好答案。

---

## 三、FDE 工作方式的几个原则

### 1. 先跑起来，再谈完美
> 目标不是把 UI 做到极致，而是 **尽快让客户看到「这个东西真的能工作」**。

用 [[Next.js]] + [[FastAPI]] + [[PostgreSQL]] 当天出一个能点的 Demo，比花两周写「架构文档」更有说服力。

### 2. 用最小原型验证最大假设
不要一上来就做完整系统。先验证「**最不确定的那一步**」：
- 不确定模型能不能抽对字段？先拿 10 条样例数据试 [[Prompt 工程]]。
- 不确定客户 API 能不能连？先用 [[curl]] / [[Python]] 脚本探一下。

### 3. 现场即反馈回路
FDE 的「测试」往往不是自动化测试套件，而是 **客户坐在你旁边看 Demo 时的表情**。把客户的每一次皱眉都转化成下一次修改。

### 4. 集成优先于抽象
客户不在乎你的代码多优雅，只在乎：
> 「我的 CRM 数据能不能自动进来？结果能不能自动推到 Slack？」

所以 [[企业系统集成]] 与 [[Webhook]] 往往比「代码架构」更决定项目成败。

## 四、一个真实感的工作片段

```text
周一：客户说想把邮件附件自动入库并总结
周二：Python + 邮件 API 拉附件 → 存对象存储
周三：接 LLM 总结 → 写 PostgreSQL
周四：Next.js 做查看页面，客户看后说「要按部门分」
周五：加字段、改查询、加权限，部署上线
```

> [!tip] 节奏感
> FDE 的「周」就是别人的「 sprint」。快，但不乱——靠的是 [[Debugging 与可观测性]] 兜底，出了问题能立刻定位。
