# FDE 能力模型

> [!abstract] 核心
> 一个优秀的 FDE，能力结构可以拆成三横三纵：**技术能力、业务能力、交付能力**。三者不是孤立的，而是在「快速解决问题」这个顶点上汇合。

---

## 一、能力结构图

```text
                    FDE
                     │
        ┌────────────┼────────────┐
        │            │            │
     技术能力      业务能力      交付能力
        │            │            │
   编程/API/AI     理解客户       Prototype
   数据库/云       理解业务       Integration
   Docker/Linux    找到问题       Deployment
        │            │            │
        └────────────┼────────────┘
                     │
                快速解决问题
```

---

## 二、三大支柱拆解

### 1. 技术能力
- **编程 / API / AI**：[[Python]]、[[TypeScript]]、[[FastAPI]]、[[LLM API]]
- **数据库 / 云**：[[PostgreSQL]]、[[Redis]]、[[云平台]]
- **Docker / Linux**：[[Docker]]、[[Linux]]

> 技术能力的目标不是「深」，而是 **够用且能快速组合**。

### 2. 业务能力
- **理解客户**：听得懂客户的行业黑话与痛点。
- **理解业务**：知道客户的流程、KPI、谁是决策者。
- **找到问题**：客户说的「症状」背后，真正的「病因」是什么。

> [!note] 业务能力常被技术人忽视
> 但恰恰是它决定了：你做的原型是不是在解决 **客户真正在乎的事**。

### 3. 交付能力
- **Prototype**：几天内出可运行的东西。
- **Integration**：把方案焊进客户的 [[企业系统集成]]。
- **Deployment**：不只是写出来，还能 [[Docker]] + 云上部署跑起来。

---

## 三、优秀 FDE 的判据

> [!quote] 最终判据
> 判断一个 FDE 是否优秀，不是：「会多少框架？」
> 而是：**「给他一个没有标准答案的真实问题，他能不能迅速找到可行方案，并把这个方案真正跑起来。」**

这恰好是 FDE 与传统软件开发岗位最核心的区别。

---

## 四、能力模型如何落地

把三大支柱映射到具体学习动作：

| 支柱 | 对应板块 | 怎么练 |
| --- | --- | --- |
| 技术 | [[FDE 技术栈 MOC]] 全部 | 按 [[FDE 学习路线]] 推进 |
| 业务 | 行业知识 + 客户沟通 | 多去现场，多问「为什么」 |
| 交付 | [[FDE 练习项目]] | 做端到端小项目，逼自己部署 |

> [!tip] 不要均衡用力
> 技术广度优先于单一深度；交付速度优先于代码完美；业务理解优先于炫技架构。
