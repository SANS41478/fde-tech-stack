# PRD 与技术文档

> [!abstract] 定位
> PRD 说明「为什么做、为谁做、做什么」；技术文档说明「怎么实现、如何验证、如何运行」。对 FDE 而言，文档不是流程负担，而是让客户、自己和 AI 对同一件事保持一致的共享上下文。

## 一、PRD 与技术文档的分工

| 文档 | 主要回答 | 典型读者 |
| --- | --- | --- |
| PRD | 用户问题、目标、范围、验收标准 | 客户、产品、设计、开发 |
| 技术文档 | 数据模型、API、架构、约束、部署 | 开发、运维、AI Coding Agent |
| README | 如何安装、运行、验证 | 新加入的人、客户、未来的自己 |
| ADR | 为什么选择这个方案 | 维护者、评审者 |

## 二、最小 PRD 模板

```markdown
# [产品/功能名称] PRD

## 0. 文档信息
- 状态：Draft / Review / Approved / Shipped
- 版本：0.1.0
- 作者 / 日期：
- 相关文档：
- 名词解释：

## 1. 背景与目标
- 用户是谁：
- 核心问题：
- 用户故事：
- 目标与成功指标：
- 不做什么（Out-of-Scope）：

## 2. 方案概述
- 业务流程：
- 功能流程：
- 信息架构：
- 方案取舍：

## 3. 细节方案
- 页面与交互：
- 数据与状态：
- 边缘情况：
- 非功能需求：
- 验收标准：

## 4. 上线与运营
- 排期：
- 发布策略：
- 反馈渠道：
- 监控指标：
```

### 用户故事与验收标准

```text
作为 [角色]
我希望 [动作]
从而 [价值]
```

每条故事必须配可验证条件：

```text
Given 用户已登录
When 上传一个小于 10 MB 的 PDF
Then 页面显示处理进度，并在完成后展示可检索结果
```

## 三、必须写清楚的边界

### 数据与状态

- 初始状态是什么？
- 空数据如何展示？
- 加载、成功、失败、重试分别是什么状态？
- 多个用户或多个租户之间是否隔离？
- 操作是否允许重复提交？

### 非功能需求

- 延迟和吞吐目标
- 可用性和恢复方式
- 权限与审计
- 数据保留和删除
- 浏览器、移动端和语言支持
- 成本上限

> [!warning] 最容易漏写的三件事
> 默认值、状态变化、Out-of-Scope。它们不写，AI 往往会自行补全，最后得到「看起来完整但不是你要的」实现。

## 四、从 PRD 生成技术文档

技术文档至少包含五部分：

1. **数据模型**：实体、字段、关系、唯一性、删除策略。
2. **API 设计**：路径、方法、请求/响应 Schema、错误、权限。
3. **架构和流程图**：组件边界、数据流、异步任务、外部依赖。
4. **第三方集成**：凭证、限流、重试、Webhook、失败兜底。
5. **技术决策记录（ADR）**：选择、备选方案、原因、未来触发条件。

### 最小 ADR

```markdown
# ADR-001：选择 PostgreSQL 而不是 JSON 文件
- 状态：Accepted
- 背景：需要多用户查询、约束和并发写入
- 决策：使用 PostgreSQL + ORM 迁移
- 代价：需要数据库连接和备份
- 复查条件：数据长期单用户且只读时重新评估
```

## 五、让 AI 正确消费文档

推荐顺序：

```text
读取项目结构
  ↓
阅读 PRD
  ↓
让 AI 总结理解并列出疑问
  ↓
确认数据模型 / API / 状态
  ↓
分阶段实现
  ↓
逐条按验收标准验证
```

提示词骨架：

```text
请先阅读 PRD 和现有项目结构。
不要立即写代码。
先输出：
1. 你的需求理解
2. 数据模型与状态变化
3. API / 页面边界
4. 边缘情况与风险
5. 分阶段实现计划
如果存在歧义，逐条提问，等待确认。
```

## 六、文档与代码同步

- PRD 改了目标或范围，更新版本号和更新记录。
- API、Schema、部署命令变化时同步技术文档和 README。
- 把构建、测试、Lint 命令写进项目配置，避免只存在于口头约定。
- 每次发布记录变更、迁移、回滚方式。
- 文档过期时标记 `Deprecated`，不要让 AI 把旧方案当现行方案。
