# 产品验证与用户访谈

> [!abstract] 定位
> FDE 不只是把别人说的功能做出来，还要判断「这个问题是否真实、谁最需要、最小验证是什么」。本篇把模糊想法变成可验证假设，补上从 [[FDE 工作方式]] 到 [[PRD 与技术文档]] 之间的产品发现环节。

## 一、先把想法写成假设

不要直接写「我要做一个 AI CRM」。先写成可被证伪的假设：

```text
目标用户：谁
触发场景：什么时候遇到问题
当前替代方案：现在怎么解决
痛点证据：时间、成本、错误或风险
价值假设：如果解决，用户会改变什么行为
成功信号：什么可观察行为算验证通过
```

### 灵魂三问

1. **用户是谁？** 不要用「所有人」「企业」这类没有行动意义的群体。
2. **痛点在哪？** 问正在发生的损失，不问用户是否喜欢你的想法。
3. **为什么用你？** 你的方案必须比现有替代方案更快、更便宜、更可靠或更容易。

## 二、The Mom Test：访谈问行为，不问愿望

### 三条原则

- 谈论用户过去发生的具体事情，不谈未来「会不会使用」。
- 追问现有流程、频率、花费、最近一次发生的时间。
- 多听少说，不在访谈中推销方案。

### 好问题与坏问题

| 不推荐 | 推荐 |
| --- | --- |
| 你会不会使用这个功能？ | 你上一次遇到这个问题是什么时候？ |
| 你觉得这个想法怎么样？ | 现在你是怎么解决的？ |
| 如果自动化，你愿意付费吗？ | 这个问题每周花你多少时间或成本？ |
| 我们加一个 AI 功能好不好？ | 你为什么没有继续使用现有工具？ |

### 访谈记录模板

```markdown
## 用户与场景
- 角色 / 行业：
- 触发事件：
- 现有工具或人工流程：

## 最近一次真实案例
- 发生时间：
- 用户采取的步骤：
- 花费的时间 / 金钱：
- 出错或放弃的位置：

## 证据与判断
- 可验证事实：
- 用户原话：
- 仍未回答的问题：
- 下一步实验：
```

> [!warning] 三种虚假信号
> 「听起来不错」是礼貌，不是需求；「我会用」是预测，不是行为；用户提出的功能建议通常只是对现有痛点的一个猜测，不应直接当作产品规格。

## 三、MVP 验证的层级

从成本最低、反馈最快的方式开始：

1. **手工验证**：先人工完成服务，确认用户是否真的需要结果。
2. **落地页验证**：测试用户是否点击、注册、留下联系方式。
3. **半自动原型**：只自动化最不确定的一步。
4. **可用产品**：在已有证据支持后再投入完整工程。

### 一个最小验证实验

```text
假设：销售每天需要从 CRM 中找出高风险客户
实验：人工分析 20 条客户记录，生成一页风险报告
观察：销售是否查看、转发、据此采取行动
门槛：至少 N 位目标用户完成一次真实后续动作
```

不要把「做完功能」当作「验证通过」。验证通过必须对应可观察行为，例如注册、上传数据、重复使用、邀请同事或付费。

## 四、把访谈转成产品决策

### 证据分级

```text
真实付费 / 持续使用
        ↑
重复发生的真实行为
        ↑
明确描述的现有流程与损失
        ↑
口头兴趣与功能建议
        ↑
礼貌性赞美
```

每条需求都记录：

- 证据来源和日期
- 影响的用户类型
- 问题严重程度与频率
- 现有替代方案
- 是否进入 MVP
- 暂不做的原因

## 五、FDE 的产品验证清单

- [ ] 能用一句话说清目标用户和触发场景。
- [ ] 找到至少一个真实发生过的案例。
- [ ] 记录当前替代方案，而不是只记录抱怨。
- [ ] 明确最不确定的假设。
- [ ] 选择成本最低的验证方式。
- [ ] 定义通过 / 不通过的行为门槛。
- [ ] 把结论写入 [[PRD 与技术文档]]，并明确 Out-of-Scope。
- [ ] 验证失败时缩小问题或停止投入，而不是盲目加功能。
