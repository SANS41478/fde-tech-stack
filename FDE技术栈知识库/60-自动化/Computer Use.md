# Computer Use：GUI 自动化 Agent（与机器人操作延伸）

> [!abstract] 定位
> 语音把时机轴推到了毫秒级，但它的观察仍是一维的声音流。**Computer Use 把同一个问题搬上二维的屏幕：观察变成持续变化的像素，动作变成坐标上的点击与输入**。语音场景强调"何时开口"，Computer Use 强调"下一步点哪里"，以及一个语音交互中不存在的问题——**动作执行之后，现实是否还与计划一致**。Computer Use 让 AI 像人类一样通过观察屏幕、操作鼠标键盘来使用软件——打开浏览器搜索信息、在表格软件中填写数据、在系统设置中调整配置。

---

## 一、感知-思考-行动循环

```text
① Agent 截取当前屏幕画面
② 多模态模型接收截图和任务指令，输出一段思考和一个具体动作
③ 执行层在真实环境中执行该动作（移动鼠标、点击、输入文字等）
④ 等待界面响应后再次截图，进入下一轮循环
```

**要区分"看懂界面"和"完成任务"**：前者更接近多模态理解能力，可用一次截图问答测量；后者要求模型把理解和生成动作放进闭环——处理页面加载、状态变化、误操作和不可逆后果。**Computer Use 的难点不只是让模型在截图上答对，而是让它在每一步之后重新确认现实是否仍符合计划。**典型场景：完成一个多步表单填写可能需要 10-20 轮循环；每个动作间隔 2-5 秒（串行截图-识别-思考-点击），**速度约为人类的 1/3 到 1/5**。

## 二、动作空间设计（Anthropic 参考实现）

完整交互能力分三类工具——这是一个清晰的动作空间设计，但**不是模型供应商必须遵守的私有协议**：只要 Harness 能把同样的截图、动作约束和执行结果转换成目标模型支持的消息与结构化输出，Claude、开放权重视觉模型（如 Qwen3-VL）和自托管端点都可以驱动同一个感知-思考-行动循环。

**① GUI 操作工具（computer tool）**：
- **鼠标**：移动（mouse_move）、左/右/中键点击、双击/三击（double/triple_click）、拖拽（left_click_drag）、按下/松开（left_mouse_down/up）
- **键盘**：逐字符输入（type，每个字符间隔 12ms 模拟真实打字）、组合键（key，如 Ctrl+C）、长按（hold_key）
- **滚动（scroll）**：支持四个方向并可配合修饰键
- **感知动作**：截图（screenshot）、获取光标位置（cursor_position）、等待（wait——等待界面响应）

**② 命令执行工具（bash tool）**：提供**持久的 bash 终端会话**，120 秒超时，通过**哨兵字符串**检测命令是否执行完毕，多次调用之间保持环境状态（比如 cd 到某个目录后下次调用还在那个目录）。

**③ 文件编辑工具（str_replace_editor）**：通过字符串匹配实现安全编辑——查看（view）、创建（create）、替换（str_replace）、插入（insert）、撤销（undo_edit）——比直接覆盖整个文件更精确，不容易误改其他内容。

**坐标缩放机制**：实际分辨率 ↔ 训练分辨率（XGA/WXGA/FWXGA）——截图缩小 → 模型推理 → 坐标放大 → xdotool 执行（详见视觉定位）。

**典型执行流程（填写表单）**：① screenshot 截取当前页面 → ② 模型推理识别姓名框位置 → ③ mouse_move 移动到 (324, 156) → ④ left_click 获取焦点 → ⑤ type 输入 "John Smith"。

实验 6-7 两条路径：路径 A 使用 Anthropic Computer Use Demo——容器打包完整的 Ubuntu 桌面环境（含浏览器、终端等常用工具），前端接收任务，后端把指令与截图发送给 Claude，再执行模型返回的鼠标、键盘、终端或编辑动作；路径 B 使用开放权重模型（Qwen3-VL 32B Instruct 驱动 browser-use）——可通过 OpenRouter 托管 API，也可连接自托管的 vLLM/SGLang 等服务。

## 三、视觉定位（Grounding）

循环的每一轮中，模型需要在截图中准确定位目标元素——"搜索框在哪里？""提交按钮的坐标是什么？"**两条大思路：把定位变成选择题（先标注好编号，模型从中选一个）vs 纯坐标预测（让模型像人一样直接"看"截图报坐标）。**选择题思路的共同优势：**把开放式的"在截图中找到按钮并预测坐标"转化为封闭式的"从已标注好的元素中选一个"——就像考试中选择题比填空题更容易答对**：模型只需说"点击 [123]"而不是"点击屏幕 (350, 464) 处的按钮"。输出坐标对模型挑战尤其大，需要大量训练才能做准，且在不同屏幕分辨率下容易出错。

### 3.1 Set-of-Mark（SoM）：纯视觉标注法

微软研究院 2023 年提出，最初为了释放 GPT-4V 的视觉定位能力。**纯视觉方法**：用图像分割模型（SAM、SEEM 等）在截图上自动切出候选区域，为每个区域叠加编号标记——模型看到一张带编号的图，只需报出编号，系统换算成对应区域的中心坐标。**整个过程不需要 DOM、不需要任何界面内部结构——因此原生桌面软件、游戏界面同样适用，只要分割模型能把候选区域切出来。**

### 3.2 结构化元素索引：SoM 思想在 Web 上的结构化实现

界面本身能提供结构化信息时，标注可以更精确。现代网页在渲染之前就已定义完整的元素结构（**DOM 树**）和语义角色（哪个是按钮、哪个是输入框）；**无障碍接口（Accessibility Tree）**为许多桌面应用提供类似信息。以 **browser-use** 项目为代表的 Web Agent 方案正是这样做的——四步流程：

1. 通过浏览器调试接口（**CDP，Chrome DevTools Protocol**）获取网页的结构化表示（DOM 树）和无障碍信息
2. 自动检测哪些元素可以交互（按钮、输入框、链接等）
3. 为每个可交互元素标注唯一 ID 并在截图上绘制边界框
4. 同时生成文本列表描述每个 ID 对应的元素：

```text
[1] <input type="text" placeholder="Search" aria-label="Search" />
[2] <button id="submit-btn" aria-label="Submit form" />
[3] <input type="text" placeholder="Enter your name" value="" />
[4] <a href="/docs" aria-label="Documentation" />
```

**模型只需输出一个 ID，系统自动用该元素的中心坐标执行点击**。这类方案不省 token（要把所有标注信息发给模型），但**定位准确稳定**，还免去了分割模型可能引入的漏检和误检。

### 3.3 纯坐标预测

不做任何标注，直接让模型输出坐标。以 **SeeClick** 和 **Claude 的 computer use** 为代表：在海量 GUI 截图和元素位置的配对数据上训练视觉模型，学会将自然语言描述（"点击提交按钮"）直接映射到截图中的精确坐标——**像人类用户一样纯粹靠"看"找到要点击的位置**。

**分辨率匹配与双向坐标缩放**：坐标预测模型对坐标的理解**高度依赖训练时使用的分辨率**。Claude 训练使用 XGA（1024×768）、WXGA（1280×800）、FWXGA（1366×768）——输入截图分辨率不匹配时模型预测的坐标会**系统性偏移**，就像在小地图上量距离直接用到大地图上。需要在工具层实现双向坐标缩放：

**完整流程**：①按宽高比选目标分辨率 → ②ImageMagick 缩小截图 → ③模型推理生成坐标 → ④按比例放大 → ⑤xdotool 执行。

**缩放示例（16:9 屏 → FWXGA）**：真实屏幕 2560×1440（16:9）→ 在三档里挑宽高比最接近 16:9 的 FWXGA（1366×768）→ 截图等比缩放（×0.53）送模型 → 模型输出点击坐标 (683, 384) → 反向映射 (683×2560/1366, 384×1440/768) ≈ (1280, 720)（×1.87）。**若硬把 16:9 拉伸进 4:3 的 1024×768，画面被横向压扁，模型预测的坐标就会系统性偏移——按宽高比选目标分辨率，避免非等比拉伸。**

**三条路线的选择逻辑**：
- **结构化信息可得时**（网页/有 Accessibility 接口的应用）→ 优先 DOM/Accessibility Tree 索引，定位最精确稳定
- **不可得时**（原生桌面软件如 Photoshop、Canvas/WebGL 渲染的界面、游戏）→ 视觉标注（原始 SoM 路线——对未经专门训练的通用模型更友好）或坐标预测（省去标注步骤——对做过 GUI 定位训练的模型更直接）
- 两者在小元素和密集界面上的精度都仍有差距

实验 6-8（browser-use）：基于 Playwright 浏览器自动化框架 + 多模态大模型实现自然语言驱动的浏览器操作，启用 SoM 可视化模式每次决策前保存带标注框的截图。测试任务"打开 Google 查询旧金山天气"：截图显示 Google 搜索页面，交互元素被编号 → 模型选择搜索框 → 输入 "San Francisco weather today" → 提交搜索 → 从结果页提取温度和天气状况。

## 四、能看动画、能听声音的 Computer Use Agent

到目前为止 Computer Use 的感知建立在一个隐含假设上：**屏幕是静止的**——截一张图、想一步、点一下，再截下一张。**可现实里的屏幕会放视频、会弹出转瞬即逝的通知、会播放会议里的人声。一个每 3-5 秒才睁一次眼、而且完全没有耳朵的 Agent，对这些"两帧之间发生的事"既看不见也听不到。**

**真正该被重新设计的是"观察接口"（Agent–Computer Observation Interface, AOI）**——把连续的环境观察转换成模型便于处理的离散事件。三项关键技术：

1. **屏幕关键帧截图**：用一个小模型判断屏幕是否发生了有意义的变化，只在显著变化时截图——变化频繁时每秒截图 1 次就能有不错的效果。
2. **音量门控的语音转写**：有声音时调用语音识别，把识别出的文字放入上下文——让 Agent 能够听到声音。
3. **用文字描述画面**：让模型把捕获到的屏幕截图描述成一句话——**即使原图之后被清理出上下文，这句文字仍留在上下文里**，实现多模态交互历史压缩的效果。

## 五、Computer Use 的世界模型

观察接口解决"屏幕中间发生了什么"，但**并不消除规划延迟**——Agent 仍是串行的"截图—思考—点击"循环，每执行一个动作都重新观察、思考下一步。OSWorld-Human 的效率研究显示：即使任务最终成功，**Agent 的操作步骤仍明显多于人类，等待时间也更长——准确率达到人类水平，并不等于已经足够实用。**

**人类操作电脑时并不是点击之后才开始想下一步**，而是先对动作后果作出预测：实际变化与预期一致 → 沿原定计划继续执行；发现页面状态偏离预期 → 才停下来重新观察和规划。**世界模型让 Agent 在行动前预测桌面接下来可能变成什么，实现类似人类的"推测执行"，大大提高效率。**

桌面状态不只是一张像素图——还包括窗口、焦点、滚动位置、输入框内容、加载状态、权限和网络返回；动作包括点击、键盘输入、滚动、拖拽和等待。**一个可用于 Computer Use 的世界模型至少要能**：编码当前状态、预测候选动作造成的状态变化、把预测交给规划器决定下一步：

```text
桌面状态 + click/type/scroll/wait ──> 下一状态的表示
```

**应用场景**：
- 在真正点击之前比较候选动作的后果
- 在页面加载期间准备下一步
- 在弹窗一闪而过时根据状态差异恢复
- 例："在 VS Code 新建 Python 文件并写入 hello world"——先预测文件树和编辑器在成功后的关键状态，再选择点击、输入和保存动作
- 删除文件的任务——先在**隔离的虚拟桌面**中预测是否会出现不可逆确认框，必要时请求用户确认

**重点不是让模型生成一张逼真的未来截图，而是预测完成任务所需的、可检查的状态差异。**2026 年 7 月 Induction Labs 公布的 **Photon-1** 展示了这条路线的一种实现：仅用 3 万小时的 H200 GPU 时间完成 computer use 世界模型的预训练——把每帧压缩为离散的潜在 token，自回归预测动作之后的下一状态表示（不在预训练阶段逐像素生成截图）；接入的图像生成器只用于把潜在表示可视化，并非推理必需组件。给定一张种子截图和后续动作，模型可以连续"想象"桌面状态，再通过虚拟机上的在线训练学会输出 computer-use 动作。

## 六、移动端：生态壁垒比技术更难

**技术差异**：动作空间通常不再是"鼠标坐标 + 键盘"，而是接入系统的**无障碍服务 API**（如 Android 的 AccessibilityService）来读取界面元素、下发点击与文本输入；交互方式从鼠标指针变成触摸手势，坐标的语义随之改变——**同一个 (x, y) 到底是手指的单击、长按，还是滑动手势的起点，需要额外的手势类型来界定**。AndroidWorld 等移动端基准正是在这样的动作空间上评测 Agent 完成真实应用内任务的能力。

**但真正卡住移动端的往往不是技术差异，而是生态壁垒**：曾有手机厂商尝试在消费级手机中集成 AI 助手，让它自动操作微信、淘宝、支付宝等日常应用，很快遭遇平台限制。根本原因是**商业模式冲突**——传统互联网应用的核心变现逻辑是流量与注意力：用户刷信息流时看到广告、搜索商品时跟随推荐引导、浏览页面时冲动消费；**当 Agent 代替用户操作时，这条变现链路被彻底绕过：AI 不会关注广告，也不会冲动消费，直奔目标完成任务就走**——对于靠广告和流量变现的平台，Agent 的每一次操作都在侵蚀其商业模式的根基。

**Computer Use 面对的不仅是 CAPTCHA 等技术层面的对抗，更是一个结构性的利益冲突**——这一矛盾在短期内难以调和，让 Computer Use 在消费级场景的落地面临比纯技术问题更棘手的挑战。

## 七、延伸：机器人操作（以 XLeRobot 整理桌面为例）

把同一闭环推到物理世界。机器人操作比"看图回答问题"难得多——模型不但要看懂画面，还要在真实世界里连续做出动作，**而且每个动作都会改变下一刻的情况**。贯穿任务："把红色杯子放进托盘，把黄色废纸放进垃圾盒，最后重新观察并确认桌面状态"。

### 7.1 一个能用的机器人系统要回答的四个问题

1. 人想完成什么任务？
2. 接下来先做哪个子任务？
3. 当前技能具体输出哪些动作？
4. 动作执行后，现实是否仍符合原来的计划？

四种技术各司其职：**长程规划**安排先处理杯子还是废纸；**VLA 或动作原语**完成抓取和放置；**世界模型**估计动作后果；**从仿真环境迁移到现实环境**处理训练画面和真实摄像头、执行器之间的差异。即使高层模型已具备足够的知识和规划能力，**只要缺少任何一个反馈环节，系统仍可能无法把任务做完。**

### 7.2 硬件与算法的分工：遥操作作为诊断实验

**XLeRobot 这样成本只有几百美元的机械臂，通过遥操作已经能够完成连续的多步桌面任务**——人看着摄像头画面，抓起红色杯子放进托盘，再把黄色废纸放进垃圾盒，最后重新确认状态。这一结果不只是说明"硬件勉强具备可行性"，更是一个明确的诊断证据：**对于这个任务，硬件本体不是瓶颈，算法才是瓶颈**。

诊断方法：保持摄像头、机械臂、夹爪、桌面布置和成功条件不变，先让人接管闭环。**人类操作者会自然地做很多算法必须显式实现的事**：夹爪靠近杯子时减速、杯子滑动时修正抓取点、第一次没夹住纸张时重新观察、物体放入目标区域后检查结果。**遥操作因此不只是收集演示数据，也是一种"固定硬件、替换操作者"的诊断实验**（自主系统与人的差距正体现在这些闭环能力上）。边界：这个判断仅限于桌面任务——说明硬件已跨过完成该任务所需的负载、精度和工作空间门槛，不意味着几百美元的机械臂能胜任所有开放环境或更高难度的操作。

### 7.3 机器人控制的基本结构：分层

| 层级 | 核心问题 | 输出 | 典型时间尺度 |
| --- | --- | --- | --- |
| 任务目标 | 人想完成什么 | "把杯子和废纸归位" | 分钟级 |
| **长程规划** | 先做什么、后做什么 | 先处理杯子，再处理废纸，最后检查 | 秒到分钟 |
| **基本技能** | 当前要完成哪个状态变化 | pick(red_cup)、place(red_cup, tray) | 约 1-3 秒 |
| **VLA / 技能策略** | 这个技能具体怎么动 | 夹爪的一小段动作或连续轨迹 | 约 1-10 Hz 推理 |
| **底层控制与安全层** | 如何稳定、及时地执行 | 关节或末端控制量、限速与急停 | 约 50-1000 Hz |

这是常见的工程分工，不是唯一的模型架构——VLA 可以承担一部分高层判断，规划器也可以是规则程序、VLM 或优化器。**无论哪种实现，都应把"任务顺序"和"眼前动作"分开**：否则高层模型的推理延迟会拖慢底层控制，底层的高频控制也会让高层模型处理大量无关细节。对 XLeRobot：**模型不应直接输出任意关节角**——它只选择 pick、place、verify_state 或 stop 等有边界的技能，经过标定、限速并带超时的执行器再把技能变成真实机械臂动作。

### 7.4 长程规划与任务分解

用户说"把桌面整理干净"——系统**不能把这句话直接交给动作模型**。规划器要先列出场景中的物体和目标，再决定先后顺序，并为每一步写清楚**开始条件、完成条件和风险限制**：

```text
处理红色杯子 → 清理黄色纸张 → 检查桌面
"处理红色杯子"继续拆分：pick(red_cup) → place(red_cup, tray) → verify_state()
```

**每完成一个技能就得到一个可以检查的节点**：抓取失败只重试当前这一步；物体被人挪动或用户改变目标时，只需重新规划受影响的后续步骤，不必把旧计划全部重做。给 Agent 的工具也应该足够简单：**一次调用只做一件事、动作范围固定、有超时限制、执行后立即重新观察。**

实验 6-11（真机自主整理）：保持真机遥操作实验（6-9）的硬件、布置、任务指令和成功条件不变，把人类操作者替换为 Agent——具身推理模型（如 Gemini Robotics-ER 1.5）负责观察和规划，通过智能体循环**只开放五个工具**：observe_scene、pick、place、verify_state、stop。模型先观察桌面、决定处理顺序，再调用经过标定的抓取和放置动作；**每完成一个技能都必须重新观察并检查后置条件**；抓取失败时只能重试当前技能；用户喊停、物体离开工作区或状态无法确认时必须调用 stop。**模型不能直接输出任意关节角，也不能仅凭自己先前说过"已经完成"就跳过真实检查。**人只负责启动、急停和安全监护，不能在中途代替 Agent 完成动作——这样真机遥操作与自主实验才能直接比较"同一硬件、同一任务，人类闭环与模型闭环之间还差什么"。

### 7.5 VLA 控制

**VLA（Vision-Language-Action，视觉-语言-动作模型）**：接收当前画面和一条技能指令，输出机器人接下来要执行的动作——`当前观察 + 技能指令 → 动作`。高层规划器只提交 pick(red_cup)，VLA 还要根据当前画面决定**从哪个方向接近杯子、夹爪何时闭合、手臂以什么轨迹抬起**；执行层完成这一小段运动后系统重新拍摄桌面，**只有确认杯子确实被夹住，规划器才允许提交 place(red_cup, tray)**——**工具调用定义的是期望的状态变化，VLA 定义的是如何通过连续动作实现这个状态变化。**

两种动作表示：**RT-2 和 OpenVLA** 把连续动作切成离散 token，像生成文字一样逐个输出——更容易和语言模型结合；**π₀** 直接生成连续平滑的动作轨迹——通常更适合表达平滑运动。**两种方法没有简单的高下之分。**

**动作分块（Action Chunking）**：大模型每秒通常只能推理 1-10 次，而传统控制器每秒要更新几十到上千次——模型一次生成**一小段未来动作**，控制线程按较高频率执行这一小段，模型在后台准备下一段，把一部分推理等待藏在动作执行时间里。**代价：动作段越长运动越平滑，但模型在这段时间看到的新画面越少**——如果 XLeRobot 伸手抓杯子时杯子被碰动，它可能仍在执行根据旧画面生成的动作。**动作分块是在平滑性和反应速度之间做取舍，而不是没有代价的加速。**

### 7.6 VLA 的局限

1. **训练数据有限**：机器人演示远少于互联网文本和图像数据——模型见过"杯子"这个词，不代表它见过各种材质和摩擦条件下的杯子。
2. **只学会模仿，不一定懂后果**：行为克隆主要学习"示范者下一步怎么做"，没有明确要求模型回答"这个动作会造成什么结果"。
3. **机器人各不相同**：不同机器人有不同的自由度、坐标系、夹爪和执行器延迟——同一个动作不一定能直接搬到另一台机器人上。
4. **观察可能过时**：动作块开始执行后，物体可能被移动、遮挡或碰倒，但模型仍在依据上一帧画面做决定。

**语言模型知道"杯子"是什么，并不代表它知道摩擦、接触、液体晃动和电源线会怎样改变未来状态。VLA 主要回答"现在应该做什么"，还需要另一类模型帮助判断"做了之后可能发生什么"。**

### 7.7 世界模型（机器人侧）

可以把世界模型理解成一个"**动作结果预测器**"：学习在当前状态下采取某个动作，下一刻的状态可能怎样变化。

```text
当前状态 + 候选动作
  → 预测下一状态或未来片段
  → 比较候选结果
  → 选择动作、重新规划或安全停止
```

一个能用于机器人的世界模型至少要做好三件事：看懂当前状态；预测不同动作可能带来的结果；把这些预测交给规划器或控制器帮助选择。**只会描述视频的 VLM、或只会生成画面的模型，并不会自动变成可靠的机器人世界模型**——它还必须知道动作是什么、能预测动作对物体和环境的影响（V-JEPA 2 代表在内部状态中预测未来的路线；World-Action Model 明确学习"动作-未来观察"的关系；可与 VLA 配合，不需要取代）。

**三种用法**：①**动手前**：比较抓取、推动、等待等候选动作，优先选择风险更小的方案；②**执行时**：把真实观察和预测结果对照，发现偏差就缩短动作、停止或重新规划；③**训练时**：利用视频、仿真数据和失败轨迹学习状态变化，减少真机上的试错次数。

回到桌面任务：黄色废纸被红色杯子部分遮住——系统可以比较"先抓纸""先移动杯子""换一个抓取方向"几个候选技能。**世界模型不需要生成一段逼真的机器人视频，只要能预测哪些候选动作更可能让纸张变得可抓取、哪些可能碰倒杯子，就已经能帮助规划器排序。动作执行后，真实摄像头观察仍然是最终事实——预测只能帮助选择，不能代替验收。**

**重要边界**：世界模型给出的是"如果这样做，可能会发生什么"的**可比较预测**，不是确定答案——预测得越远误差通常越大；一段看起来逼真的未来画面也可能不符合真实的接触和摩擦规律。实际系统仍需要短期预测、实时观察、对不确定性的估计，以及**独立的硬件安全控制器**。**生成式世界模型可以用来做交互式仿真或可视化，但不能把"会生成视频"和"能指导机器人动作"混为一谈。**

实验 6-12（模拟器比较三种闭环）：同一任务、对象状态、成功条件和五个工具放进桌面模拟器，执行器换成可控模拟执行器，抓取偶尔出现可恢复的瞬时失败——**开环执行**（一次生成完整动作序列，中途不重新观察：一次局部失败会带到任务末尾）、**逐步检查**（每个 pick/place 后重新读状态，失败只重试当前技能：能够恢复）、**预测式执行**（增加短期世界模型，先比较候选技能的预期结果再选择下一步：进一步帮助规划器排序）。**最终是否真的完成，仍然必须由 verify_state 的新观察确认。**

### 7.8 从仿真环境到真实机器人（Sim2Real）

模拟器里表现稳定**不能直接推出**真机会同样成功。训练时可用遥操作数据、视频数据或仿真交互数据；真正部署时，**同一个红色杯子、黄色废纸、托盘和垃圾盒会出现在不同的背景、光照、相机位置和遮挡关系中**，机械臂还会遇到不同的摩擦、传感器噪声和执行器延迟——差异足够大时，模拟中学会的动作可能在现实中失效。

实验 6-13（RGB 跨环境测试）：训练四种结构相同的视觉策略——只看固定画面 / 改变背景 / 改变物体外观 / **同时改变背景、外观、光照和噪声**（域随机化）——在原始环境和变化后的新环境中测试，比较视觉条件变化前后的动作判断准确率。**训练时主动扩大画面变化范围，有助于同一杯子-托盘、废纸-垃圾盒任务适应新的摄像头画面**；但真机部署仍然需要真实相机标定、执行器测试和完整的安全闭环。仿真环境与后训练的关系见 [[Agent 评估]] / [[模型后训练]]。

## 八、四类交互共享的控制骨架

异步事件、语音、Computer Use、机器人四节共享同一条控制骨架：

```text
持续感知 → 判断当前状态与时机 → 选择回复或动作 → 让输出进入环境
→ 观察反馈 → 继续、修正、重试、停止或重新规划
```

也共享同一组**系统原语**：**唤醒、安全点、取消、抢占、快慢分离**（例：取消——事件驱动中是用户"停止"后在安全点终止；机器人中是急停与动作分块的边界检查）。本章完成了"构建 Agent"的最后一块：观察与动作空间在**内容**（上下文与工具）、**模态**（语音、屏幕、物理世界）和**时机**（异步事件）三个方向上都已经展开。

## 九、常见坑

> [!warning]
> - **截图分辨率与训练分辨率不匹配**：坐标系统性偏移——按宽高比选目标分辨率、双向缩放，避免非等比拉伸。
> - **把"看懂界面"当"能完成任务"**：截图问答 ≠ 闭环执行；评估要走完整任务，确认"动作执行后现实是否仍与计划一致"。
> - **对"两帧之间的事"全盲**：屏幕会放视频、弹通知、播人声——观察接口三件套（关键帧、音量门控转写、文字描述画面）。
> - **串行等待**：截图-识别-思考-点击全程排队（人类速度的 1/3-1/5）——世界模型的推测执行。
> - **动作分块无视环境突变**：预生成动作序列在物体被移走后失效——短期预测 + 实时观察对照。
> - **预测代替验收**：世界模型的预测只帮助选择，最终事实仍是新观察。
> - **低估生态壁垒**：CAPTCHA 可以对抗，商业模式冲突无解——企业内部 GUI 自动化比消费级场景现实得多（对 FDE 而言）。
> - **模型直接输出关节角**：只应有边界的技能原语（pick/place/verify/stop），执行器负责标定、限速、超时与急停。
