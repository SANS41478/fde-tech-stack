# 交互：异步与事件驱动（含语音）

> [!abstract] 定位
> 第一章的论断：**底层模型固定时，提升 Agent 表现最主要的系统工程手段是重新定义或扩展观察空间与动作空间**。前五章中 Agent 与世界的交互是轮流的——用户说完一句，Agent 想一段、调用几个工具，再回一句；**在它思考的这段时间里，世界被默认为静止的**。这个前提如此自然以至于很少被当成假设写出来。本章挑战的正是它。观察空间和动作空间各有两个扩展方向：**模态**决定形式（只读文本还是也能听见声音、看见屏幕；只能输出 token 还是也能发声、点击），**触发时机**决定节奏（观察是 Agent 主动去取还是世界主动推来；动作是必须一个回合做完还是可以跨越回合、中途被打断、被更紧急的事抢占）。

---

## 一、异步与事件驱动：当世界主动找上门

### 1.1 为什么需要异步

**比喻**：同步（Synchronous）意味着"做完一件事才能做下一件"；异步（Asynchronous）意味着"多件事可以同时进行"。传统同步 Agent 像一个只会排队的柜台——每次只处理一个顾客，处理完才叫下一个号；真正智能的助手像灵活的秘书——桌上摆着多个待处理事项（邮件、电话、来访者），根据紧急程度决定先处理哪个，处理到一半有更紧急的事可以暂停切换。

同步模式无法应对真实助理场景的三项核心能力：
- **异步执行是常态**——许多任务需要长时间运行，不应阻塞用户交互；
- **事件优先级的动态判断**——不是所有事件都同等重要：取消当前操作（紧急）、加入队列（常规）、还是并行处理（独立的轻量级查询）；
- **中断和恢复的流畅性**——被打断的对话或任务应该能够自然恢复。

**根本矛盾："训练同步 / 部署异步"**——LLM 的训练范式假设同步（发出工具调用后，下一条消息必须是工具结果）；而真实部署要求异步（用户随时可能打断、多个任务可能并发推进、外部事件可能在工具尚未返回时就抵达）。这一矛盾贯穿本节所有工程取舍。

**事件驱动架构**：不再主动反复检查"有没有新消息"（轮询，效率低），而是新消息到达时自动触发处理逻辑。**所有输入、输出、思考过程和外部交互都被统一建模为事件流**——一条时间线上依次排列的事件记录。架构三部分：事件源（Email / Timer / Webhook / User）→ 事件队列（路由器 + LLM 判定紧急度）→ Agent 处理循环（取出事件 → LLM 推理：观察→思考→行动 → 工具执行：异步/同步分派 → 结果处理：通知/响应/存储）。

### 1.2 OpenClaw 的事件驱动机制

开源框架 OpenClaw 通过 **Gateway 控制平面**接收多渠道消息并路由到 Agent 运行时。三种内置事件驱动机制：

| 机制 | 说明 |
| --- | --- |
| **Hooks（事件钩子）** | 响应 Agent 生命周期中的事件（会话创建、重置等）——类似 GitHub Actions 的事件触发器 |
| **Cron（定时调度器）** | 按 cron 表达式执行周期性任务（如 `0 9 * * 5` = 每周五上午 9 点） |
| **Heartbeat（心跳守护进程）** | 每隔 N 分钟唤醒一次 Agent，检查是否有需要关注的事项 |

这三种机制赋予 Agent"自主"的外观——用户不在线时也能定时生成报告、检查系统状态、处理例行事务。**真正让 Agent 在没有用户消息时"自己动起来"的只有 Cron 和 Heartbeat，而它们都是时间驱动的**（Hooks 的事件来源是框架内部而非外部）。

**真正的短板**：对内置渠道之外的**第三方事件源**——一封新邮件到达、一个外部 API 回调推送、一个紧急通知需要立即处理——OpenClaw 缺乏即时接入通道，Agent 只能等到下一个 Cron/Heartbeat 周期才可能察觉。

**PineClaw 案例（揭示核心价值）**：PineAI 是代替用户拨打真实电话的 AI 助手（协商账单、取消订阅、处理保险理赔）。电话过程中可能随时需要用户介入：**实时身份验证**（客服要求验证账户持有人身份，Pine 需要用户立即提供安全码或 OTP）、**三方通话确认**（客服要求与账户持有人直接对话，需几秒内接听）、**进展同步与决策确认**（协商到关键节点——对方提出降价方案——需用户确认是否接受）。**依靠 Heartbeat 定时轮询，用户可能在客服等待验证码时迟迟收不到通知，导致客服挂断、通话失败。**PineClaw 的解法：引入 **Channel 机制**——在 Gateway 和 Pine API 之间建立实时事件通道，电话接通、需要用户输入、通话结束等关键事件发生时消息即时推送。**核心结论：真正的"主动服务"不仅需要 Agent 能定时检查事件，更需要事件能主动通知 Agent。**

### 1.3 事件触发工具

没有事件触发工具，Agent 只能连续循环思考、调用工具、输出结果、等待用户下一步输入。三类工具，两个时刻——**注册时**由 Agent 主动调用声明自己关心什么事件；**触发时**由外部事件异步回调唤醒 Agent：

| 工具 | 处理什么 | 细节 |
| --- | --- | --- |
| **定时器（set_timer）** | 依赖物理时间的事件 | 邮件发出去对方没回复，过一段时间再发一封询问进展；打电话时对方不在工作时间，到下一个工作时间再尝试。**一次性定时器**：明确时间点的任务（用户要求"给银行房贷部门打电话问办理进展"，当前是周六 → 设置"下周一上午 10:00 致电银行"）。**循环定时器**：周期性任务（每小时检查服务器健康状况）；**外部服务不支持主动推送、只能主动查询进展时，也需要循环定时器反复查询**（Heartbeat 正是这种机制的系统化实现，也是 OpenClaw"主动服务"能力的根源） |
| **后台任务监控（monitor_shell）** | 异步执行的命令行任务 | 一些命令行任务长时间在后台执行。让 Agent 不断"盯着命令行看"（反复调工具查进展）浪费 token；等完全结束再开始思考和行动，又无法及时发现执行过程中的严重问题，甚至命令行卡死时无法介入导致任务停滞。Claude Code 引入 monitor 工具：**允许 Agent 监控命令行的新增输出或包含特定关键词的输出** |
| **外部事件通道（connect_channel）** | 新邮件到达、API 回调、IM 消息等外部事件实时推送 | PineClaw 的 Channel 机制是典型实现 |

设计层面：**事件触发工具应定义清晰的触发条件和过滤规则**——避免无关事件唤醒 Agent 浪费算力；**事件载荷（payload）应包含足够的上下文信息**——减少 Agent 被唤醒后还需要额外查询的次数。

### 1.4 用户沟通工具

许多 Agent（Claude Code、Manus）采用原生 ReAct 循环——Agent"说"的所有话（assistant 消息）直接发送给用户，用户必须在应用中打开指定会话才能对话，会话中往往能看到 Agent 调用工具的过程。**OpenClaw 打破了这一人机沟通范式**：用户无需感知会话的存在，也无需关心 Agent 调用工具的细节；**用户和 Agent 都可以随时给对方发送消息**，而不是用户发一条、Agent 回一条——因此很多人评价 OpenClaw 具备"**活人感**"，像秘书一样通过文本消息异步沟通。OpenClaw 不是直接把模型输出的 assistant 消息呈现给用户，而是**使用专门的工具发送消息**；消息可附图片和文件，可根据紧急程度附加推送提醒。

**多渠道的用户沟通与召回**：Agent 的响应不应局限于单一渠道——**通知机制同时也是用户召回机制**。消息发送扩展到即时通讯、短信、邮件、电话、推送等多种渠道；Agent 根据紧急程度、用户状态、内容性质、用户偏好综合决定渠道选择——既保证不错过重要消息，又避免重复打扰。长时间运行的任务完成时主动通知召回注意力；定期性任务（每日总结、周报）通过通知建立固定交互习惯。设计要点：支持**异步消息模式**（用户不一定在线）、**已读/未读状态追踪**、多渠道场景下保持消息一致性。

### 1.5 虚拟身份与隔离执行环境

用户沟通解决了"如何触达用户"；Agent 以什么身份出现在这些渠道上、在什么环境中代表用户执行操作，还需要一层身份与环境基础设施。

**架构选择：直接管理用户账号 vs 独立虚拟身份**。直接管理看似便捷，但**一旦 Agent 出现错误或被攻破，用户的全部数字身份将会暴露**。更稳妥：赋予 Agent 一套独立的虚拟身份——如同秘书拥有自己的办公电话和邮箱：专属的通讯账号、存储空间、计算环境，以透明的身份代表用户工作。**身份的明确性不仅没有削弱信任，反而增强了沟通的真实性。**

**隔离执行环境**：虚拟电脑（VM/容器）和虚拟手机（Android 模拟器）提供操作系统级隔离与完整桌面/移动操作能力：①**全天候运行**——不受用户设备联网状态影响，也不影响用户正在操作的应用；②**错误隔离**——即使 Agent 执行了错误操作，最多导致虚拟环境崩溃，不影响真实设备；③**安全**——防止 Agent 随意访问用户的本地文件。

**两个现实挑战**：
- **反机器人机制**：许多网站用 CAPTCHA 和 IP 信誉检测拦截自动化访问——使用数据中心 IP 的虚拟环境很容易被识别，实践中往往需要配置**住宅代理网络**（使用真实家庭 IP）才能正常访问。
- **访问用户真实账号的场景**：任务必须以用户本人身份登录时，采用 **Human-in-the-Loop 认证**——通过 VNC/RDP 远程桌面让用户在可视化环境中亲自完成登录。用户能看到 Agent 正在操作的完整界面、理解为什么需要认证；认证后的会话令牌可在有效期内复用，避免频繁打断用户——**在自主性与安全性之间取得平衡**。

**数据交换**：Agent 与虚拟环境之间通过**共享文件系统**完成——以卷挂载的方式（如 /workspace/shared）连接 Agent、虚拟电脑和虚拟手机，**数据以文件路径引用传递而非内容拷贝，避免占用上下文窗口**。数据分析任务例：用户上传 CSV 到共享目录 → 虚拟电脑中的 Agent 读取文件、执行分析、生成图表保存回共享目录 → Agent 只需将图表的文件路径返回给用户——**各方之间传递的始终只是轻量级的路径字符串**。

### 1.6 事件处理机制

一个 Agent 实例可能同时面对多个事件：用户的新消息、工具返回的结果、定时器到期、另一个 Agent 的协作请求。**骨架是并发编程的事件循环（event loop）**——异步 Agent 看作一个长期运行的循环：每一轮从输入队列取出若干事件、追加到轨迹、调用一次 LLM、执行它决定的工具、再回到循环开头等待下一批事件（与 Go 的 goroutine 从 channel 读取消息、在 `for { select { ... } }` 中逐轮处理是同一结构）。

**关键性质：事件只在每轮循环的边界被消费**。LLM 正在推理、工具正在执行时，新到达的事件不会凭空插入打乱当前步骤——先在队列中等待，待本轮到达一个**安全点**（一段推理结束、一次工具返回）再统一处理。取消遵循同样纪律：不在任意时刻强行掐断，而是在安全点检查"是否被要求停止"——这正是 Go 中 ctx.Done() 所扮演的角色。**三种处理策略的区别只在于对待安全点的方式：让事件等到下一个自然出现的安全点（队列式）、主动提前制造一个安全点（取消式），还是干脆另起一个循环、不必等待主循环的安全点（并行式）。**

**事件的结构化建模**：通用 Agent 面对的输入不只来自用户——第三方发来的消息不是用户发给 Agent 的，但 Agent 需要理解它、评估其重要性、决定如何介入。每个输入建模为包含丰富语义的结构化事件：
- **来源（谁）**：用户本人、联系人、陌生人、系统通知
- **渠道（方式）**：电话语音、短信、即时消息、邮件、社交媒体、定时器触发、异步工具调用结果、命令行监控状态更新
- **内容（什么）**：消息文本、情感色彩、紧急程度、是否需要回复
- **上下文（背景）**：是对之前某个对话的回复还是新发起的沟通，与当前任务的关联

```json
{
  "source": {"type": "email", "sender": "client@example.com"},
  "channel": "gmail_webhook",
  "content": {"subject": "退款请求", "body": "订单 #12345 希望退款..."},
  "context": {"priority": "high", "customer_tier": "vip", "related_orders": ["#12345"]}
}
```

**只有当这些维度被清晰建模为结构化事件，Agent 才能在多方通信中保持清晰的认知——避免将用户输入误当成工具结果，或将藏有指令的工具结果误认为用户指令而导致提示注入**（见 [[提示注入]]）。多线程上下文管理还要求 Agent 理解多个对话线程之间的关联——来自第三方的消息如何影响用户的情绪、用户在不同对话中扮演什么角色、何时需要将不同线程的信息综合起来提供建议。从 n8n 等工作流平台的触发器生态可以看到：Webhook、定时器、邮件、数据库变更、文件监听——**每一种触发器都是 Agent 感知世界的一个"感官"**。

**基于紧急度的动态处理策略**（人类处理多任务的方式）：

| 策略 | 适用 | 机制 |
| --- | --- | --- |
| **取消式（Cancellation-Based）** | 紧急事件（用户点"停止"、监督系统高优先级指令） | **为紧急事件提前制造一个安全点**：①停止当前操作（LLM 正在推理→立即取消流式响应；同步工具在执行→发取消信号）；②清空待处理队列；③将队列中的事件和紧急事件一起追加到轨迹末尾；④立即重新调用 LLM 以更新后的完整轨迹评估局势。例：Agent 执行可能错误的操作时用户输入"停！我说错了"→ Agent 立即看到新输入、重新理解真实意图，避免执行错误操作 |
| **队列式（Queued）** | 常规事件（异步工具返回结果、用户补充信息） | ①事件放入队列末尾不打断当前操作；②等待当前操作完成（LLM 完成推理、同步工具执行完毕）；③**当任何工具调用完成并返回 tool.result 时检查队列**，非空则将所有事件一次性追加到轨迹；④LLM 综合处理。**批量处理提高效率**：Agent 调搜索工具后在等待期间用户补充"只看最近一个月的结果"——这条补充进入队列，搜索结果返回时两个事件一起呈现，避免不必要的往返 |
| **并行处理（Parallel）** | 独立的轻量级查询 | Agent 正在分析大量数据时用户突然问"今天天气怎么样"——三个特征：**与主任务无关、需要快速响应、执行成本低**。既不该取消式（打断重要的主任务）也不该队列式（让用户等太久）。系统判断查询的独立性和复杂度后，在**一个并行的推理会话中独立执行**，调用必要工具生成响应后立即返回；查询和响应追加到主任务轨迹并明确标记"与主任务并行执行"避免 LLM 混淆 |

**紧急度的判定**：
- 紧急事件：用户中断（user.interrupt）、监督指令（supervisor.instruction）、Agent 间中断（agent.interrupt）、标记为紧急的外部触发器（系统告警、支付失败）
- 非紧急事件：常规用户输入（user.input）、Agent 输入（agent.input）、工具结果（tool.result）、定时器触发（timer.trigger）、常规外部触发器

**硬编码的规则有其局限性，事件的语义决定了处理方式**——"马上停下来"用取消式、"今天天气怎么样"用并行式、"报告需要用中文发给我"用队列式。**建议使用轻量级的分类 LLM 作为事件路由器**，在事件到达时快速判断应采用哪种策略。**取消点必须是工具或推理能够安全收尾的位置；未完成的工具结果用显式占位符表示，不能伪造成功。**

**实验 6-1（事件驱动的邮件处理 Agent）**：最简单的事件驱动模式——自动邮件处理助手监听收件箱，新邮件自动触发处理（分类、摘要、起草回复，必要时通知用户）。统一事件源接入：邮件（on_email_received）、IM/短信、GitHub（PR review 意见、状态变化）、定时器（每日摘要周报）、Webhook、系统事件（用户不活跃/进程超时/资源告警）。验证场景：三封邮件——会议邀请（自动检查日历冲突并起草接受/拒绝回复）、客户投诉（提取关键信息标记高优先级通知用户）、营销广告（自动归档）——**整个过程无需用户介入**。

### 1.7 如何让同步模型支持异步打断

实验 6-1 只处理串行事件。回到"训练同步 / 部署异步"矛盾：工具尚未返回时用户突然打断，同步格式该如何容纳？

**具体场景**：Agent 帮用户起草邮件（工具调用 search_contacts），搜索还没返回时用户突然说"等一下，先帮我查一下明天的天气"。同步 ReAct 循环中 Agent 必须等搜索返回后才能处理下一条消息——API 要求"发出工具调用后，下一条消息必须是工具结果"。

**工程权宜之计：模拟同步的异步实现**——核心思想：**在没有打断发生的常态下，让 LLM 看到标准的同步轨迹，只在打断时才插入占位符来修复格式**。五条关键规则：

1. **LLM 输出后立即记录 assistant message**（包含 thinking、content 和 tool call）。
2. **工具调用完成时才记录 tool result**——执行中轨迹处于"部分完成"状态。
3. **工具执行中的打断需要占位符**：为未完成的工具生成占位符响应（"工具正在后台执行，请优先处理新事件"），追加打断事件，重新调用 LLM——从 LLM 的视角看，assistant message 仍然有配对的 tool result。
4. **LLM 思考中的打断直接丢弃当前思考**——不写入轨迹，新事件直接追加后启动新一轮思考。
5. **非打断事件进入队列等待批处理**——当前周期完成后才一次性追加。

**推演**（起草邮件被打断问天气）：①Agent 调用 search_contacts，assistant message 立即写入轨迹（规则 1）；②搜索工具尚未返回时用户发来"先帮我查一下明天的天气"——用户打断，系统为未完成的 search_contacts 生成占位符 tool result（规则 3），将天气查询追加到轨迹，重新调用 LLM——**此刻 LLM 看到的轨迹格式完全合法：assistant message 与 tool result 配对完好**；③天气查询完成并回复后，原先的 search_contacts 结果到达，作为新事件追加到轨迹（规则 2），Agent 读取联系人信息继续起草邮件。

**优势**：常态下 LLM 看到完美的同步轨迹——assistant message 与 tool result 严格配对、时间顺序清晰。这对当前基于同步训练范式的 LLM 最友好，最大程度保证思考质量；**只在确实需要打断时才引入占位符这个"必要的妥协"**。

> [!warning] 占位符加剧幻觉的风险
> 尽管占位符明确说明工具"尚未完成"，系统仍可能在后续思考中"编造"一个工具结果——误以为工具已返回有效数据，基于虚构结果做不恰当决策。**根源：模型训练时见到的绝大多数轨迹中，工具调用之后紧接着就是真实的结果，它从未学会处理"结果还没回来"的情况。**因此实践中**只在真正紧急时才打断**，非紧急事件放入队列批量处理。

**适合现有模型的异步工具接口**：既然模型的同步假设难以突破，更根本的策略是从**工具接口的设计层面拥抱异步语义**。传统工具设计隐含"调用即完成"（phone_call 暗示"调用将拨打电话并等待通话结束，返回通话记录"）。异步范式下将"启动"和"完成"解耦：
- `initiate_phone_call`：启动电话呼叫，立即返回任务标识符和初始状态（"呼叫已发起，正在拨号"）
- 通话进展通过事件通知（phone_call_connected、phone_call_ended）

**关键在于工具的名称和描述本身就要传达异步的语义**——模型看到 initiate_phone_call 会自然推断这是"发起"而非"完成"；工具描述进一步强化："此工具将启动由子 Agent 处理的电话任务。任务成功发起后立即返回任务 ID，你可以继续处理其他事项。通话结束后会收到单独的通知事件。"

**队列式处理中的注意力分散问题**：批量事件处理时模型往往只关注最后一个事件——**根源在于模型被训练为对最新的输入做出反应，而批量事件打破了这一假设**。两个层面干预：①提示词层面：告知模型"当收到多个连续事件时，请确保全面考虑所有信息"；②Agent 状态栏标记：每个事件前添加显式标记（`[未处理事件 1/4] Tool result from database_query：...`），末尾汇总（"上面有 4 个未处理事件，包括 1 个工具结果、2 条用户消息、1 个系统提醒。请确保回应涵盖所有信息"）。

### 1.8 深层矛盾与未来方向

归根结底，占位符、异步工具接口、状态栏标记都是在用提示工程弥补"**训练同步 / 部署异步**"的矛盾——过渡期的权宜之计。**真正的解决方案需要在模型训练层面发生范式转变。**机器人领域的 VLA 模型已经开始面对类似挑战（感知和动作之间存在不可避免的延迟），为 Agent 模型的进化指明方向——**下一代模型需要在异步环境中通过强化学习获得三种核心能力**：

1. **理解轨迹中事件的异步穿插**（最核心的能力缺陷）：当前模型期望严格的同步序列，但真实异步环境中 tool call 之后可能不是 tool result 而是新的 user 消息；thinking 进行到一半可能被打断，但中间状态应保留在轨迹中，新消息处理完后**继续思考而非从头开始**。模型需要在这种"乱序"轨迹中保持清晰认知——哪些工具调用还在等待结果、哪些思考是未完成的片段。
2. **恢复被打断的任务和思考**：被打断去处理紧急事件后仍记得未完成的任务——回答完天气问题后应自然地等待数据分析结果，而不是忘记还有工具在运行；特别要避免产生幻觉，误以为被打断的工具调用已经完成。
3. **批量事件的综合处理**：多个事件批量追加到轨迹时不能只关注最后一个，必须综合考虑所有未处理的信息。

实现异步 RL 训练需要新基础设施：**异步环境模拟器**（生成工具延迟返回、用户随机打断等场景）和**针对异步能力的专项奖励机制**（正确理解乱序轨迹、成功恢复被打断的思考、避免幻觉、综合处理批量事件）。

**"持续思考"不必等下一代模型**：用一层约两百行的编排逻辑就能让现成的文本思考模型变成**持续思考（continuous-time）的 Agent**——把整个交互建成一条不间断的思维流：随时可以强行合上模型正在写的 `<think>` 块，把新到达的观察（工具返回、用户打断、新的识别结果）作为普通消息注入，再让模型接着往下解码。利用了一个常被浪费的资源：**模型每秒能生成上百个 token，而一次工具调用、一段用户说话往往要花好几秒——这些"等待"时间都可以被模型用于思考**。由此产生两种行为：**边等边想**（不等工具返回、不等用户说完，基于已有的半截信息往下思考，甚至提前把下一步工具调起来）；**边做边想**（一边输出一边继续思考，并能在动作进行到一半时纠正自己）。

**实验 6-2（带并行执行和打断能力的异步 Agent）**：Agent 同时启动三个异步终端命令（速度每秒 3%/2%/1% 的分析脚本）；每秒 3% 的脚本约 33 秒完成时，Agent 查询剩下两个的状态（约 66% 和 33%），**取消不超过 50% 的那个**，两个终端都完成后整合结果生成报告。关键机制：占位符注入 + 异步完成事件 + cancel_tool(task_id) API。四个验证点：异步工具执行（启动后立即返回占位符，期间用户问"现在几点了"立即回应）、事件队列与批量处理（用户连发"记得用日语回复"和"整理成网页"，任务完成时一次性处理生成日语网页）、打断机制（"取消"立即终止执行流并取消异步工具）、并行工具的取消与状态查询。

## 二、语音：最自然的人机接口

语音的价值不只是把文字换成声音：**正常说话的速度约为打字的四倍，而且不占用双手与视线**——天然适合把 Agent 放进持续工作、随时可能被打断的输入输出回路。语音输入法把口述转成文字，语音 Agent 让用户直接与 Agent 协作（两者都支持 whisper coding——引言中作者用语音 Agent 协作写成本书的方式）。本节讨论两个方向：**用户对 Agent 说话**，以及 **Agent 代替用户对外部世界说话**。语音模型决定"能回答什么"，交互架构决定"能否听清、及时回应、自然换手，并在通话中完成确认和工具调用"。

### 2.1 交互时序：三种范式

| 范式 | 核心结构 | 主要优势 | 主要限制 |
| --- | --- | --- | --- |
| **级联（Cascading）** | VAD → ASR → LLM → TTS | 模块清晰、易替换、易调试 | 延迟累积，副语言信息在接口处丢失 |
| **端到端 Omni** | 原生音频输入输出，按轮次交互 | 延迟较低，能保留语气、情绪和环境声 | 仍依赖轮次，训练和调试成本较高 |
| **全双工** | 原生音频输入输出，持续听、说和决策 | 支持重叠说话、自然打断和连续流 | 模型训练、控制和评估都更复杂 |

**贯穿三种范式的主线：如何摆脱"轮流说话"和 VAD 对发言权的猜测。**级联和 Omni 仍要划分轮次，只有全双工把"该谁说话"变成模型的持续决策。

### 2.2 范式一：级联流水线（Cascading）

绝大多数商业语音助手的架构：**VAD 判断用户何时说完 → ASR 把音频转成文字 → LLM 理解并生成回复 → TTS 把文字念出来**。模块化让每个组件可独立优化，但**每一级都可能增加等待时间**。

各模块瓶颈：VAD（静音阈值带来等待和误切分）、ASR（识别延迟与上下文丢失）、LLM（首 token 延迟，开启 reasoning 后等待更长）、TTS（首包合成和播放缓冲）。

**延迟瀑布**（空载）：VAD 等待 500-800ms → ASR 转录 50-200ms → LLM TTFT 100-500ms → LLM 生成 100-300ms → TTS 合成 200-500ms——**最优 ~0.9s，最差 ~2.3s**。生产环境的排队还会进一步放大：总延迟 = S/(1−ρ)（利用率 ρ→1 时延迟发散）；**生产环境 ρ 通常 0.5-0.8 → 实际延迟 2-5 倍空载延迟**。

**完全串行的三个问题**：①延迟累积——必须等待一段静音才能确认说完；②信息丢失——有声/无声二值信号无法表达犹豫、情绪、附和环境声；③上下文被切断——邮箱、人名和专有名词可能被分片识别而出错。

**流式感知优化**（保留模块化分工的前提下各阶段尽早产出增量结果）：
- **ASR 边听边转**：VAD 检测到用户开始说话就按时间间隔调用 ASR 流式生成临时转录；VAD 检测到说完再确认最终文本。
- **LLM 推测执行**：临时转录生成后就送给 LLM；最终文本与临时转录相同则不重复调用，否则取消前序推测执行的思考重新调用。
- **LLM 分段输出**：第一段适合播报的文本生成后立即交给 TTS，不等完整回复。
- **TTS 增量合成**：持续返回音频块，让后续生成、合成和播放重叠进行。

**真正的流式 ASR 需要模型支持**：Whisper 的解码虽是自回归的，但编码器需要完整音频段——不能直接等同流式模型。基于 LLM 的流式听觉模型可从连续音频输出**文本和语义事件**：speak_start/end、interrupt（说话起止与打断意图）、emotion（情感、犹豫）、laugh/sigh/noise（副语言和环境声）——这些标记和文字 token 形成统一事件流，Agent 可识别犹豫、打断和环境变化，而不必把所有声音压成纯文本。**保留从对话开始到当前的上下文，还能利用世界知识处理品牌、人名和专有名词。**轮次判断也可做进流式识别器：模型综合语义和静音判断一句话是否表达完整——**端点判断的训练标签必须只使用决策时刻可见的信息**，否则会因"上帝视角"产生线上无法复现的判断。

### 2.3 范式二：端到端全模态模型（Omni）

级联即使流式感知，听、想、说仍通过离散接口交接——**情绪、语调和环境声可能在转成纯文本时丢失**。Omni 用同一个模型直接听音频、生成回复并输出语音：理解方面可以理解声音中的停顿；生成方面可传递更丰富的副语言信息（唱歌、用特殊语调讲一句话）。训练成本更高。**Omni 仍然假设轮流说话，通常要靠 VAD 划分发言权——用户报数字时的中途停顿仍可能被误判为说完。**代表：OpenAI Realtime（服务端 VAD + 轮次检测、异步函数调用、打断停止当前生成）、Gemini Live（VAD 敏感度可配置）、Qwen3-Omni（Thinker-Talker MoE：思考（理解）+ 表达（生成）、首包延迟 234ms）、Step-Audio 2（潜在音频编码 + RL、副语言理解、CoT 思考 + RAG + 工具）。

### 2.4 范式三：全双工交互模型

Omni 仍把对话分成"用户说"和"模型说"两个时段——但同声传译等任务要求两者重叠进行。**全双工模型不再预设轮次，而是持续听、持续说，并不断决定继续、停顿、打断或调用工具。**研究先声：Kyutai 的 **Moshi**（2024）——并行建模用户和模型的音频流，**重叠说话和打断成为模型的自然行为**。Thinking Machines Lab 称这类路线为**交互模型（Interaction Model）**：交互性不再依靠 VAD 等外部 harness 拼装实现，而是**内建在模型中**——微轮次机制以短音频块持续推进，让静音、重叠和打断都作为连续上下文保留；交互模型还可以把完整对话**委派给后台推理模型，自己继续维持话头**，后台结果返回后前台再在合适时机接入。OpenAI 的 **GPT-Live** 把全双工路线带到生产规模：模型持续处理输入并生成输出，能等待用户、附和、被打断，也能处理实时翻译。

### 2.5 认知时序：实时交互与深度思考

"交互表现"和"智能上限"是两个维度：前台模型要在用户仍然在线时回应，后台模型可以花更多时间思考。三种方案是设计取舍，不是线性迭代：

- **方案一：快思考回应，慢思考回答**——快思考几百毫秒给出即时回应，慢思考后台完成更深推导。**问题**：简单问题被重复处理（"今天星期几"快思考已对，慢思考仍运行 8 秒）；复杂问题前后不一致——快模型先建议购买，慢模型随后发现套餐缺少关键功能，**用户在几秒内听到相互冲突的答案，失去信任**（根本原因：两个实例各自完成了一次独立思考）。改进方向（慢思考作为"军师"通过状态栏幕后指导快思考）仍有本质局限：沟通间接模糊（快思考可能误解"确认价格"为"向用户确认"而非"重新计算"），无法实现"边想边说"。
- **方案二：快思考交互，慢思考提醒**——后台模型通过状态栏或专门接口向前台提供建议，前台继续维持话头并决定如何表达。比方案一稳定，但通信仍间接：前台可能误解建议、看不到后台的中间思考；后台完成前用户追问时前台只能依靠自己的能力应答。**可以自然地"等结果"，但不能真正做到边想边说。**
- **方案三：端到端思考与表达统一**——把思考能力直接内化到端到端音频模型。Step-Audio R1 的两个互补机制：**模态锚定思考蒸馏（MGRD）**让模型基于声学特征思考（理想情况下模型应从音高、节奏和语调判断情绪而不是只看转录文本；筛选真正引用声学特征的思考过程再用这些数据训练，并通过强化学习防止模型跳过思考直接猜答案）保证"想得对"；**MPS 双脑架构**让构思与表达并行（构思脑持续产出思考片段，表达脑收到片段后结合已有回复立即生成语音，流水线方式并行——不必等完整思考结束才让用户听到第一句话）解决"说得及时"。

**快慢分离与端到端的取舍**：统一模型最紧密地实现"边想边说"，代价是思考和实时表达需要一起重新训练；解耦路线更容易替换后台大脑。**快慢分离并不只是对延迟的妥协，也是一种让交互能力与智能上限分别演进的模块化选择**——更强的思考模型发布后只需替换后台模型，不必重新训练整套实时语音系统。实证：采用快慢思考分离架构的 PineAI 语音 Agent 在 τ³-Voice Leaderboard 取得第一名，超过 Grok Voice、GPT-Realtime-2 等实时语音系统——**在同时考察深度推理与实时对话的任务上，解耦架构并不天然落后于端到端模型。**

> [!note] "端到端"的两个含义要分清
> ①**语音通路的端到端**：模型直接接收音频、生成音频，不由多个模型通过离散文本串接（Omni 和交互模型都属于此，但 Omni 通常仍按轮次推进、交互模型可边听边说）；②**认知架构的端到端**：实时交互与深度思考是在同一模型内部共享状态共同训练，还是拆成前台快模型与后台慢模型。**两条轴彼此独立**——一个系统完全可以在语音通路上端到端，同时在认知架构上保持快慢分离。

### 2.6 更像人的语音合成

传统 TTS 过于流畅、零停顿，反而容易暴露机器身份——**停顿、填充词和偶尔的重复，是人类表达不确定性和思考状态的信号**。可以让主 LLM 在文本之外输出控制标记（THINKING、EMO:happy、SPEED:0.8x），由 TTS 将它们映射为停顿、韵律、语速或笑声、叹气等非语言音频。实现：自研支持控制标记的 TTS，或用语音克隆准备不同情绪和风格的参考音频（实验 6-6：Fish Audio S1 多参考语音库，比较无控制标记 / 单一参考音 / 多参考音三种配置）。

## 三、常见坑

> [!warning]
> - **轮询代替推送**：Cron/Heartbeat 定时检查第三方事件源 → 客服等验证码时通知迟到、通话失败——实时事件通道是"主动服务"的根基。
> - **事件载荷缺上下文**：唤醒后还要额外查询，浪费轮次。
> - **占位符被当真**：模型可能基于"编造的工具结果"决策——只在真正紧急时打断，非紧急入队。
> - **批量事件只看最后一个**：状态栏标记 + 末尾汇总兜底。
> - **把同步的 phone_call 工具用于长任务**：调用即阻塞——改 initiate_ + 事件通知。
> - **快慢双实例独立思考**：用户几秒内听到相互冲突的答案——快思考与慢思考的结论要对齐。
> - **级联全串行**：VAD+ASR+LLM+TTS 完全排队浪费所有时间间隙——流式感知让各阶段重叠。
> - **端点判断用了上帝视角标签**：训练标签必须只用决策时刻可见的信息。
