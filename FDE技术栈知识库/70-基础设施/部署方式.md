# 部署方式

> [!abstract] 定位
> **部署 = 让软件稳定地被人用起来**，不必然等于「上云」。本文对比六种主流形态，并回答「为什么不用闲置机器」「大/小工具部署差距」「PaaS 争议点」。向上接 [[云服务模型]]，向下接 [[Docker]] / [[CI-CD|CI/CD]] / [[云平台]]。

---

## 一、六种主流部署方式（从「重」到「轻」）

| 方式 | 大白话 | 适合 |
| --- | --- | --- |
| **裸金属 / 物理机** | 独享整台真机器，性能最高 | 数据库、AI 训练、高性能计算 |
| **虚拟机（VM）** | 一台物理机切出多台「假机器」 | 通用；云上 EC2 本质就是 VM |
| **容器 + 编排** | Docker 打包，K8s / Compose 调度 | 当今最主流应用层做法（见 [[Docker]] / [[微服务]]） |
| **PaaS** | 你只管 `git push` 代码，平台管运行 | 创业 / 个人快速上线（见下方争议） |
| **Serverless / FaaS** | 只写函数，按调用付费，无常驻机 | 事件驱动 / 突发流量（见 [[Serverless]]） |
| **静态托管 / 边缘** | 纯前端文件扔 CDN，全球分发 | 静态站 / 边缘函数（见 [[静态托管与边缘]]） |

> [!note] 容器 ≠ 必须上云
> 容器（Docker）只是一种**打包 / 交付格式**，可跑在笔记本、旧服务器、裸金属、云上任意有运行时之处。编排（K8s / Compose）才解决「很多容器怎么管」。云只是最方便的来源，不是必需。

---

## 二、为什么不直接用闲置机器当「云服务器」

云服务不是「一台 24h 运行的机器」这么简单，闲置机器通常不适合对外生产：

1. **无公网固定 IP / 端口被封**：家庭宽带多 NAT，ISP 常封 80/443。
2. **网络质量差**：上行极小、无 SLA、IP 可能被拉黑。
3. **无冗余**：断电 / 断网 / 硬盘坏 = 全挂，没有多可用区。
4. **安全与 DDoS**：家用网络无清洗能力。
5. **伸缩为零**：突发流量旧笔记本直接死。
6. **运维负担**：硬件故障、备份、系统更新全自己来。

> [!tip] 但闲置机器并非一无是处
> 个人学习、爬虫、NAS、Home Assistant、内网服务，用树莓派 / 旧 PC + 内网穿透完全合理。区别只在「能不能扛生产流量与可靠性要求」。

## 三、大型软件 vs 小型工具的部署差距

| 维度 | 小型工具 | 大型软件 |
| --- | --- | --- |
| 形态 | 单进程 / 单脚本 | 微服务集群（几十~上百服务，见 [[微服务]]） |
| 运行 | `systemd` / 一个容器 | K8s 多副本、负载均衡、服务发现 |
| 发布 | 手动跑一下 | [[CI-CD|CI/CD]]、蓝绿 / 金丝雀发布 |
| 可靠性 | 挂了重启 | 多可用区、自动恢复、SLA |
| 数据 | 本地文件 / 单库 | 主从库、缓存、消息队列、分库分表 |
| 可观测 | 日志文件 | 监控（Prometheus）、日志（ELK）、链路追踪 |
| 伸缩 | 不用 | 自动扩缩容（HPA）、弹性 |
| 协作 | 一个人 | IaC（Terraform 等基础设施即代码）、配置管理、SRE |

一句话：小工具部署是「让它跑起来」，大系统部署是「让它在任何故障下都不停、还能随时升级、被几十人协作维护」。

## 四、PaaS 的争议点（代码交上去就跑，风险怎么算）

原理：你 `git push`，PaaS（Heroku / Railway / Render / Cloud Run）在自己的集群上识别语言 → 装依赖 → 编译打包 → 启动 → 分配域名 / HTTPS。你看不到底层机器。

- **代码有 bug、打包失败**：和本地构建失败一样，平台返回错误日志，你改完重推。正常闭环，不算争议。
- **「平台打包损害源码」**：平台**不会改你的仓库**——它把代码复制进隔离构建环境产出产物，原仓库原封不动；构建沙箱隔离，风险极低。有坑时可自带 `Dockerfile` 覆盖默认构建。
- **后续打包维护**：PaaS 会自动升级运行环境 / buildpack，可能悄悄弄挂应用。应对：锁定版本（pin runtime）+ 自己跑测试。这是「便利换控制」的代价。
- **其它真实争议**：厂商锁定、看不见系统层（不能乱 `apt-get`）、平台宕机 = 你宕机、规模大了偏贵、数据落别人机器（合规）。
