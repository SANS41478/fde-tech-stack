# Agentic RAG（智能体化检索增强）

> [!abstract] 定位
> 传统 RAG 是固定前置步骤的**被动管道**：用户查询直接用于检索，结果直接注入上下文，模型直接生成——本质是"被动的检索-生成"，缺乏对问题的深度理解、分解和迭代探索。**Agentic RAG** 把知识库检索从自动化前置步骤升级为 **Agent 可随时调用的工具**：Agent 用 ReAct 循环主导——思考 → 行动 → 观察，评估信息是否充分，不够就迭代检索。传统 RAG 像"只能搜一次就得立刻写报告"，Agentic RAG 像"可以反复查阅不同书架、调整搜索策略、交叉验证信息的研究员"。

---

## 一、RAG 基础管线

查询流程示例（公司知识库"退款流程"）：

```python
query = "退款流程"
results = retriever.search(query, top_k=2)
# results = ["退款政策：订单签收后 7 天内可申请全额退款，需提供订单号。退款将在 3-5 个工作日内...",
#            "退款操作步骤：1. 进入'我的订单' 2. 选择需退款的订单 3. 点击'申请退款'..."]
answer = llm.generate(system="你是客服助手。", context=results, question=query)
```

检索器找相关片段 → 生成器（LLM）拿片段作上下文生成答案。

### 1.1 文档分块（Chunking）

检索之前的离线预处理。**为什么必须分块**：嵌入模型对输入长度有限制，且一整篇文档压成一个向量时多主题混杂，向量无法精确表达任何一个；片段太大还会连带引入无关内容，浪费窗口、稀释注意力。

| 策略 | 做法 | 特点 |
| --- | --- | --- |
| 固定大小切分 | 按 token 数（如 512）切，相邻块保留重叠（50-100）防边界截断 | 简单可预测；无视文档结构——段落/代码/表格可能被拦腰截断 |
| **递归/结构感知切分** | 按自然边界（章节标题、段落、句子）递归切——先按大边界，超长再降级小边界 | Markdown/HTML 等显式结构文档尤佳；**生产系统最常用的默认选择** |
| 语义切分 | 计算相邻句嵌入相似度，在语义"断崖"处（相似度骤降）下刀 | 每块主题单一；需额外嵌入计算 |

**块大小与重叠的权衡**：块太小——单块信息不完整，脱离上下文语义模糊（"该公司收入增长了 3%"——哪家公司？哪个季度？）；块太大——混杂多主题，嵌入向量被稀释，检索精度下降，命中后带入更多无关内容。起点：**每块 256-1024 token、重叠 10-20%**，再按检索质量实测调优。

分块的固有缺陷（伏笔）：无论哪种策略，都会切断片段与原始上下文的联系——"该公司"指谁、出自哪份报告，留在块外 → 由后文"上下文感知检索"正面解决。

### 1.2 稠密嵌入：语义理解

把文本映射到向量空间——语义相近的内容向量距离也近。**为什么用余弦相似度（夹角）而非距离**：关心的是方向是否一致（语义是否相近），不是长度——两篇内容相同长度不同的文档，向量长度不同方向一致，余弦正确判断语义相同。

技术演进：**Word2Vec（2013）** 静态词向量，捕捉词汇共现（"国王"-"男性"+"女性"≈"女王"）——根本局限：**无法处理一词多义**（"bank"在 river bank 和 investment bank 中向量完全相同）→ **BERT/BGE-M3** 上下文感知：自注意力让同一个词在不同语境得到不同向量（"苹果公司发布新产品" vs "买两斤苹果"）；BGE-M3 进一步支持多语言与长文本。

余弦手算示例（3 维简化）：A"如何养猫"=(0.9,0.5,0.1)、B"猫咪饲养指南"=(0.8,0.6,0.1)、C"股票投资策略"=(0.1,0.1,0.9)——A·B=1.03，cos≈0.99（非常相似）；A·C=0.23，cos≈0.25（差异很大）。

**ANN 索引**（海量向量中快速找近似最近邻）：

| 特性 | ANNOY（基于树） | HNSW（基于图） |
| --- | --- | --- |
| 构建速度 | 快 | 较慢 |
| 内存占用 | 低 | 较高 |
| 增量更新 | 不支持（需完全重建） | 支持（长期增量插入后建议定期重建保精度） |
| 查询精度 | 较高 | 极高（O(log N)） |
| 适用 | 数据不常变的静态数据集 | 需要实时索引新信息的动态场景 |

### 1.3 稀疏嵌入：精确匹配

根植于传统信息检索，文档表示为极高维、绝大多数维度为零的向量。理论基石**词袋模型**（只关心哪些词出现几次，忽略词序——"猫追狗"与"狗追猫"相同）。

**TF-IDF**：词在当前文档出现越多、在整个语料库越少见越重要（100 篇中 60 篇含"模型"、3 篇含"蒸馏"——"蒸馏"更能区分）。局限：原始词频线性增长（10 次是 5 次的两倍）、不校正文档长度。

**BM25** = IDF 加权 + **词频饱和**（k₁ 控制饱和速度——出现 10 次不比 5 次贡献翻倍）+ **长度归一化**（b 控制强度——长文档不因字数多而得高分）。IDF 分子换成"不含该词的文档数"，分母分子各加 0.5 平滑；DF>N/2 时为负，实现中设下限。

倒排索引实验（实验 3-5，N=10、k₁=1.5、b=0.75、avgdl=250）：查询"模型蒸馏"——"模型"df=3（IDF=0.76），"蒸馏"df=2（IDF=1.22，**更稀有单次贡献更大**）；doc_1 中"蒸馏"TF=3 贡献 2.15 反超"模型"TF=5 的 1.52——这正是 BM25 的核心逻辑。稀疏检索在技术代码、人名等查询上极佳，但**读不懂同义表达**（查 kitty 找不到只写 cat 的文档）。

### 1.4 混合检索与重排序

两路各有盲区：稠密懂语义但可能漏关键词（搜 HTTP-403 返回"服务器错误"泛泛讨论）；稀疏精确但不懂同义。**混合检索 = 两个引擎都跑、结果合并**——难点是两路得分不可直接比（余弦 0-1 vs BM25 0-几十）。

三阶段流水线：
1. **并行检索**：稠密 + 稀疏各自召回候选。
2. **结果融合（RRF）**：倒数排名融合——`score = Σ 1/(k + rank)`，k 常取 60（平滑常数，压低头部排名差距）。**完全抛开原始得分只看排名**，简单稳健；代价是丢失原始得分中的相关性信号。
3. **神经重排序（Neural Reranking）**：**不是为了补救 RRF——无论怎么融合都值得加**，因为它换用更强的匹配范式：**跨编码器（Cross-Encoder）** 把查询和文档拼成一段完整文字送入模型逐词比对输出相关性得分——慢得多但准得多；检索阶段是**双编码器（Bi-Encoder）** 各自独立编码再向量运算，快但捕捉不到深层匹配。比喻：**猎头靠简历特征大规模初筛（双编码器）vs 面试官与候选人深谈（跨编码器）**。对融合候选池前 N 个（如 50）逐一精确打分。常用模型：BAAI/bge-reranker-v2-m3。

**检索质量指标**（在带标注答案的测试查询集上计算）：

| 指标 | 直觉解释 |
| --- | --- |
| recall@k（实为命中率 success@k） | 正确答案出现在前 k 个结果中的查询比例——"该找的找到了吗"；只要相关文档进上下文 LLM 就有机会用 |
| MRR | 每个查询取第一个相关文档排名的倒数再平均——"找到得够不够靠前"（第 1 名 1 分、第 10 名 0.1 分） |
| nDCG | 综合所有相关文档的排名与相关程度，越靠后折扣越大——"整个排序列表质量如何" |

工业界还常见"检索失败率"：正确信息未出现在 top-20 的查询比例。

> [!note] 实验 3-6 的结论
> 没有哪种单一检索策略在所有场景下都可靠——语义相似、精确名称、多语言、技术代码各类查询下两路互有胜负。**把稠密、稀疏和重排序组合起来，才是构建生产级 RAG 的正确做法**。

## 二、上下文感知检索（Contextual Retrieval）

**解决分块的固有缺陷**。孤立文本块"该公司第二季度的收入增长了 3%"脱离原文后无法回答代词指代（"该公司"是哪家）、时间参照（何时）、实体关系（哪条产品线）——嵌入阶段的语义信息损失直接导致检索准确率下降。

**Anthropic 方案**：向量化索引之前，先用 LLM 为每个文本块生成简短的上下文"前缀摘要"，与原文拼接后再索引。例：生成"[本段内容节选自 ACME 公司 2025 年 Q2 财务报告的'关键业绩指标'章节]"——模糊文本块被重新"锚定"在原始语义环境中。

- **同时增强两路**：稀疏路多出可精确匹配的关键词（ACME、2025 第二季度）；稠密路前缀注入关键语义背景。
- **成本可控**：索引阶段额外 LLM 调用经 prompt caching（相同前缀重复调用约 1/10 成本）摊薄——每百万文档 token 约 1 美元。
- **效果（Anthropic 数据）**：检索失败率 **↓49%**（+BM25），**↓67%**（再+重排序）。

**实验 3-10**：并行构建两个知识库（传统无上下文分块 vs LLM 前缀），同一查询排比——无上下文库匹配到许多含"收入增长"但来自不同公司不同年份的噪声块；有上下文库每个块带"身份标签"，准确命中。

**与"上下文感知压缩"划清界限**（名字相近、时机与对象完全不同）：本节的上下文感知检索在**索引期**、针对知识库文本块、做**加法**（补前缀加背景）；[[上下文工程|上下文工程]] 的上下文感知压缩在**运行期**、针对当前会话对话历史、做**减法**（按任务裁剪）。

## 三、超越扁平文本：知识的组织

### 3.0 两个失效案例（为什么扁平分块不够）

**案例一：黑猫白猫计数**。知识库 100 个独立案例文档（90 黑 10 白，各为独立文本块），问"比例是多少"——受限于 top-k（如 20），大部分案例根本不会被检索到；模型基于不完整样本（如 15 黑 3 白）得出错误结论。解法：预生成摘要"共有 100 只猫：90 只黑猫（90%）和 10 只白猫（10%）"并索引，一次检索即得准确信息。

**案例二：Xfinity 优惠资格的边界**。客服工单库几百条，各记录一个个案结论（退伍军人 John 通过、医生 Sarah 拿到折扣、教师 Mike 不符合）——没有任何一条写着资格范围本身。护士问"我能不能享受优惠"的三重障碍：**最近邻偏置**（"护士"与"医生"语义最近，Sarah 排最前，模型顺势推断护士也行；若 Mike 排更前则答案相反）、**边界语义缺失**（"仅限 X，其他一律不适用"这种带全称与否定的边界不存在于任何单条工单，调大 k 也没用）、**完整性信号缺失**（模型无从判断看全没有，不会追问，只照手里几条自信作答）。解法：离线通读整个工单库，提炼规则卡"Xfinity 优惠适用于现役与退伍军人、持证医护人员（含护士）；教师等其他职业不适用"。

**共同结论**：把原始案例直接放进知识库远远不够——无论存向量库、检索注入还是塞长上下文，**未经提炼和结构化的知识模型都无法可靠利用**。必须在索引阶段投入计算资源，主动提炼、抽象和结构化。

### 3.1 RAPTOR：树状层次索引

自下而上递归抽象：长文档切分为文本块作**叶子节点** → 聚类算法把语义相近的分组（像图书馆按主题自动分堆）→ LLM 为每组生成更高层次摘要作**父节点** → 递归到根 → 一棵从具体细节到高度概括的知识树。**检索可在多个抽象层次进行**——既精确回答细节问题，也提供宏观理解。适合"**从概念逐步钻进细节**"的查询（如先在高层次定位"SIMD 指令集"，再沿树下钻到 SSE 技术描述）。

### 3.2 GraphRAG：实体-关系知识图谱

LLM 抽取实体（人物、地点、概念、术语）+ 关系，以**三元组**（主语-关系-宾语，如（北京, 是首都, 中国））构建信息网络。两大不可替代的优势：

1. **多跳关系推理**："我的医生所在医院的地址" = 用户 → 医生 → 医院 → 地址——扁平存储要么多次独立检索再由 LLM 拼接（低效易断链），要么无法表达；图谱天然支持沿关系边遍历。
2. **实体消歧**：区分现实世界中两个同名的"张医生"——（张医生-A, 科室, 牙科）与（张医生-B, 科室, 心脏科）是图中不同节点，靠各自关系边区分，消歧无需额外推理。（注意与"一词多义"区分：判断 bank 指河岸还是银行是**词义消歧**，靠上下文感知嵌入即可。）

局限：自然语言转三元组不可避免**语义降级**——"如果下周还下雨，我就取消去海边改去博物馆"包含条件判断和时间依赖，分解后只剩孤立事实片段，核心逻辑丢失；三元组提取准确性依赖 LLM，错误提取导致知识污染。**实践推荐分层互补**：完整自然语言保存核心信息（语义完整），辅以结构化元数据索引检索；需要多跳推理和精确消歧的垂直场景（医疗问诊、法律案件、家族关系）将图谱作为专项索引。另可通过社区发现（Community Detection）找实体集群生成摘要，形成思维导图。

**实验 3-7**（数千页英特尔 CPU 手册上对比）：RAPTOR 做"跨层穿梭"（宏观概念→叶子细节）；GraphRAG 在"关系网"中漫游（定位 SSE 实体 → 遍历到 XMM 寄存器、浮点运算、ADDPS 指令 → 社区分析给出在 CPU 架构中的位置）。**生产中组合使用通常比单选一种好**。

### 3.3 文件系统范式（OpenViking）

字节跳动火山引擎开源的第三种哲学：把所有上下文——记忆、资源、技能——映射为**虚拟文件系统中的目录和文件**，每条目有唯一 URI：

```text
viking://
├── resources/        # 外部知识：文档、代码库、网页
├── user/memories/    # 用户记忆：偏好、习惯
└── agent/            # Agent 自身：技能、经验
    ├── skills/
    └── memories/
```

**L0/L1/L2 三层按需加载**：资源写入时自动提炼三个抽象层次——**L0 摘要**（~100 token，快速判断目录相关性）、**L1 概览**（~2K token，核心信息与使用场景，供规划决策）、**L2 全文**（按需加载）。每目录自动生成 .abstract（L0）和 .overview（L1）；L0 判定无关就不加载 L1/L2——大部分查询加载到 L1 即可决策，token 大幅降低。**与 Skills 渐进式披露如出一辙**。

**选 Markdown 纯文本而非专用数据库**（看似反直觉的工程决策）：用户可直接阅读、编辑、修正 Agent 的知识；可 Git 版本控制回滚；Agent 拥有 write_file 后可在工作分支自主记录组织知识再经审核合入。

**极易被忽视的前提**：文件之间必须建立**链接与索引**——如果只是拆成一堆各自独立的文本文件平铺、无交叉引用，除了全文扫描或向量检索外 Agent 无从在相关条目间导航，知识越多越难检索。正确做法是把知识库组织得**像 Wikipedia**：条目互相链接 + 入口页 + 索引页，Agent 顺链接从一个概念走到相关概念——用轻量文件链接实现 GraphRAG 实体图谱的一部分导航能力。注意：**不同模型主动建立链接的意愿差异很大**——能力强的模型会自发回指已有条目，不少模型只孤立追加文件；**写入侧提示词必须把要求写明确**（新增条目先检索并链接相关条目、更新索引页）。

### 3.4 什么时候需要结构化索引？

不是所有场景都需要 RAPTOR/GraphRAG。**判断标准**：查询主要是"找到包含某信息的文档片段"（"退款政策是什么"）→ 混合检索就够；经常需要**跨文档综合**（"SSE 和 AVX 指令集在架构上有什么区别"）或**多层次导航**（从整体架构逐步深入）→ 才值得投入。代价：索引构建和查询都需要更多次 LLM 调用，成本延迟显著增加。

## 四、知识应该如何更新

### 4.1 增量更新：把知识库当代码库

每次知识变更当 **Pull Request**——Markdown 知识库、用户记忆文件、规则文档同样进 Git，获得差异审查、版本历史、责任追溯、一键回滚。**生产环境不应让任何模型绕过审核直接改主分支或线上向量库。**

流水线（提议者-审核者模式的具体化）：
1. **Proposer Agent 提交 PR**：从原始证据中发现新事实、冲突或过期内容，在工作分支上提出**尽可能小而完整**的 diff——不是把最新对话粗暴追加到文件末尾，而是先检索相关已有知识，再增删改条目、同步维护链接索引、时间元数据和证据引用。
2. **Reviewer Agent 独立审核**：拿到变更前知识、diff 和原始证据（轨迹、对话、业务文档、工具结果），独立检查每个新断言是否被证据支持、是否遗漏限定条件、是否与其他文件冲突、删除改写是否过度。**审核不通过时返回指向具体证据和行号的可执行意见**，不是模糊的"还需改进"。Reviewer 应主要核对证据和 diff，**不沿着 Proposer 的结论再讲一遍**。
3. **双方迭代至收敛**：设最大迭代次数或成本预算；超出上限仍未收敛转人工审核，不默认放行。
4. **合入后再发布**：CI 检查格式、链接、元数据、权限标签；知识若以代码表示还要跑类型检查和测试；通过后才从已合入版本**增量重建**受影响的分块、摘要和向量索引——**索引是可重建的派生物，Git 中已审核的知识才是真正的来源**。

**关键工程细节**：
- **三层分离**：原始证据层（只增不改的对话、轨迹、文档）/ 知识层（提炼后可持续修订的 Markdown 或代码）/ 服务层（从特定已合入版本生成的检索索引）。PR 记录证据标识、知识库版本、审核意见与决定——线上每条知识都能回答"从哪条证据而来、谁在什么时候批准"。
- **两个 Agent 都必须是 Agent**，不是两次固定 LLM API 调用——Proposer 要主动搜索其他相关记忆文档和规则，Reviewer 要追溯证据、对比多份文档、运行检查、发现新线索继续查询；需要文件搜索、版本比较、测试执行和证据检索工具（现成 Coding Agent 能胜任）。两者都应能按需查询完整知识库和原始证据库（在其被授权范围内），不是只接收上游挑选的片段。
- **异源互审**：优先用能力相近但**不同家族**的模型（Proposer 用 Claude、Reviewer 用 GPT，或 DeepSeek + Kimi）——不同训练数据和偏好降低同一处犯同类错误的概率；能力不宜悬殊，否则 Reviewer 跟不上。**权限强制分工**：Proposer 只能写工作分支，Reviewer 只读证据并提交审核结果，只有合并流程能更新主分支和线上索引。

### 4.2 定期整理（全量）

增量更新每次只看到局部——多次局部正确的修改可能累积出全局问题：同一事实散落多个文件、新旧说法并存、摘要偏离原始证据、目录结构不再适合规模。**定期全量整理**（可理解为"睡眠学习"在知识管理中的实现——见 [[Agent 持续进化]]），三项核心工作：

1. **去重、去旧与合并**：全量扫描，识别语义重复、已被取代、过度碎片化或仅表述差异的条目，删除/归并/重写；重建链接、入口页、索引页；拆分过大文件、合并过小文件、调整目录层次。**删除的是可服务的知识表达，不是下层只增不改的原始证据。**
2. **回到原始数据核查**：不能只在已有摘要之间相互改写——早期遗漏和误读会代代相传。逐段对照原始对话、轨迹、业务文档和工具输出，检查旧摘要是否遗漏关键事实、丢失否定词或时间条件、是否把推测错当事实。大型库按目录/时间/主题分批扫描，**必须保留覆盖清单确保最终覆盖全量**，不是随机抽样。
3. **冲突解决与场景限定（qualification）**：遇到矛盾不简单"保留最新"或让模型猜——追溯各自原始信息源，检查是否分别在不同时间、对象、地域、任务或前置条件下成立。都有效则不是删除其中一条，而是**把各自适用场景明确写入**；证据不足则保留冲突和待确认状态，**不强行收敛成确定结论**。

产物也不直接覆盖主库：Proposer 在分支提交重组 diff，异源 Reviewer 结合原始证据审核；大 diff 按目录/主题拆多个 PR 但共享同一份整理计划和覆盖清单；全部通过后除重建索引外，还应**回放一组典型检索与问答用例**确认新结构没有让原本可找到的知识变得不可见。触发：按时间（每周/每月）或新增条目数、冲突数、检索质量下降超阈值。

**失效内容的检测与下线**：被新版取代的旧政策留在库中会与新版一起被召回，模型给出自相矛盾或过时答案。每个分块附加**版本号、生效/失效时间**元数据，检索阶段过滤已失效内容，或提炼摘要时显式标注"此条已于某日废止"。

**多用户共享的权限与租户隔离**："所有用户"≠"所有内容对所有人可见"。**检索必须按调用者权限过滤，绝不能让越权文档进入某个用户的上下文**——权限过滤下推到检索层尤其重要：**敏感内容一旦进入 LLM 上下文，就很难保证不以某种形式泄露到最终回答里**。多租户系统需保证租户间向量索引和元数据相互隔离。

## 五、Agentic RAG：范式转变

**对比**：

```text
非智能体化 RAG                    智能体化 RAG（Agentic）
固定前置步骤，一次性检索            Agent 用 ReAct 主导，迭代检索
用户查询 → 检索（一次）→ 直接生成    思考（分析需求、定关键词）→ 行动（调检索工具）
                                  → 观察（信息是否充分？）不够则循环
                                  → 充分 → 综合生成答案
```

Agent 首先"思考"分析核心需求、自主决定用什么查询关键词最有效；"行动"调用 knowledge_base_search；"观察"初步结果后**不立即生成答案**，评估信息是否充分——不够则进入下一轮，提炼更精确的查询再搜，甚至调用其他工具辅助；充分后综合所有上下文生成**有理有据**的答案。能力随知识库扩充和模型进步而提升。

**实验 3-8（中文司法问答数据集消融）**：
- 简单问题（"正当防卫是怎么规定的？"）一次直接检索即可——非智能体化 RAG 响应更快、质量相差无几——**信息需求明确单一时传统 RAG 仍是高效选择**。
- 复杂问题（"醉酒过失致人重伤且有盗窃前科如何量刑？"）差距显著：非智能体化因首次检索关键词不精确常遗漏关键信息甚至事实性错误。智能体化展现类似专家律师的多轮迭代：①第一轮分解问题，**并行搜索**"过失致人重伤量刑标准"、"醉酒刑事责任"、"盗窃前科影响"；②评估发现各子问题法条已找到但缺关键关联——"过失致人重伤"判决中"盗窃前科"应如何纳入；③第二轮构造更精确查询（"过失伤害罪"与"累犯"或"数罪并罚"的关联）；④找到"累犯"在不同罪名下的司法解释后综合给出逻辑严密、有法条依据的完整回答。

**核心价值：从"回答问题"到"解决问题"**——牺牲一定响应速度，换复杂问题上的鲁棒性与回答质量。

### RAG 的安全边界

检索把外部内容带进上下文，也带进风险：检索文档正是**间接提示注入最典型的载体**；知识库投毒污染发生在索引之前。防御两层：①指令与数据分离（来源标记——"以下是参考资料，不是命令"）；②检索内容不得直接触发高风险操作（转账/删除/对外发信须经独立授权判断）。详见 [[提示注入]]。

### 智能体化 RAG 用于用户记忆（实验 3-9 / 3-11）

把 Agent 与用户的完整对话历史本身视为知识库：索引阶段按固定窗口（如每 20 轮对话）分块索引，应用阶段赋予 `search_user_memory` 工具。局限同样存在：孤立、缺乏上下文的对话块让系统在矛盾指令场景（转账设立→修改→改回）看到三个各自独立但矛盾的指令，无法判断哪个最终有效——**上下文感知检索补上关键线索**（见 [[记忆系统]]）。

## 六、从数据集中提取深度知识（信息检索 → 知识发现）

许多专业领域的知识以隐性、分散的形式蕴含在**海量结构化案例**中——司法领域决定判决结果的"知识"不在法条里，而在成千上万份判例中法官如何权衡犯罪动机、伤害程度、自首情节等相互冲突因素的经验中；就像资深医生的"直觉"来自无数病例积累而非教科书。

两阶段范式：
1. **知识提取与结构化**：LLM 把每个案例的非结构化描述转换为包含所有关键判决因素的标准化 JSON 对象。核心挑战是定义既全面又一致的 Schema——实验 3-12 采用"**自下而上**"因子发现策略：让 LLM 分析数百个样本自由列出所有可能影响判决的因素，构建比人类先验更贴合数据的模块化模式（核心模式：自首/赔偿等情节；罪名扩展模式：盗窃→涉案金额、伤害→伤害等级）。
2. **因子分析与重要性建模**：特征向量化（多选项字段用独立开关位而非 1/2/3——数字大小会让算法误以为"诈骗比盗窃严重 3 倍"；是非题 0/1）→ KMeans 聚类发现"案件原型"（"轻微口角引发的徒手斗殴致人轻伤" vs "有预谋的团伙持械围殴致人重伤"）→ 构建**因子重要性层次模型**。

应用：对话式法律咨询 Agent 按因子重要性引导提问 → 检索相似案件原型 → 基于原型的统计数据（典型刑期范围）提供数据驱动、有判例支持的分析。**Agent 不一定要把知识库当成只能检索的静态仓库——它可以先把数据"读懂"，提炼出结构化的决策逻辑，再基于这个逻辑回答问题。**

## 七、前沿探索：多模态记忆

一张脸的模样、一个人的嗓音很难用文字描述——文本记忆机制无法存储。三条思路：
1. **存储原始多模态数据 + 文本描述**：工具剪切人脸保存为图片，Markdown 中引用并用文本描述索引；检索时先按文本描述找到相关图片，再读取原始图片判断是否同一人。
2. **把多模态嵌入压缩存到上下文**：上下文维护一个区域保存多张人脸/声纹的嵌入——每条只占约 1 token，**1000 token 的区域足以容纳 1000 张人脸**，检索时注意力机制直接找最相关的。比文本描述高效，但无法表达难以嵌入的关系。
3. **写入模型参数（User as Engram）**：为每个用户训练 LoRA 的朴素做法会失败——fact-LoRA 直接提问能完美复述，间接推理便告失灵（冻结的骨干没学过如何"查阅"临时挂载的适配器）。Engram 方案不训练 LoRA，而是把嵌入**外科手术式插入**预训练模型空闲的哈希 N-gram 槽位——这类模型预训练时已学会通过哈希查表调取记忆，并有感知上下文的门控机制决定何时调取，新事实会自然在该想起时被想起。扩展性更强，但需预训练模型支持 Engram，查准率可能不如思路二。

## 八、常见坑

> [!warning]
> - **只测 demo 一个成功例子**：必须用带标注答案的测试查询集测 recall@k / MRR / nDCG。
> - **跨文件语义冲突无防护**：乐观锁只防同一文件写入冲突；语义冲突需更高层校验（worktree 隔离把冲突推迟到合并点）。
> - **Reviewer 只看到 Proposer 挑的片段**：审核形同虚设；Reviewer 必须能按需查询完整证据库（在其授权范围内）。
> - **embedding 模型与库维度不一致**：换模型要重建索引。
> - **黑猫白猫类问题硬靠 top-k**：需要全局统计的问题先离线提炼摘要再索引。
> - **权限过滤放在生成层**：敏感内容一旦进入上下文就可能泄露——过滤必须下推到检索层。
> - **文件系统范式下不建链接**：知识退化成孤岛，越积越难检索。
