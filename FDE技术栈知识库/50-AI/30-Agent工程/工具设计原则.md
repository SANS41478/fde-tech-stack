# 工具设计原则

> [!abstract] 定位
> 工具是 Agent 与外部世界交互的桥梁：**感知类工具承载环境到 Agent 的观察，执行类工具承载 Agent 到环境的行动**。没有工具，Agent 只能"纸上谈兵"。工具设计的质量直接决定 Agent 能走多远——接口定义不清晰，模型就乱用工具；错误处理不到位，工具失败就可能死锁；权限控制太宽泛，出错后果难以挽回。**实用调试原则：当 Agent 频繁选错工具时，优先检查工具描述而不是怀疑模型能力**——修正描述的 ROI 通常远高于换更强的模型。

---

## 一、工具分类的两个特征

按调用方向与作用对象审视五类工具（两者不构成交叉分类框架，只助快速定位）：

| 工具类型 | 调用方向 | 作用对象 | 代表工具 | 设计重点 |
| --- | --- | --- | --- | --- |
| 感知工具 | Agent 主动调用 | 获取信息 | web_search、knowledge_base_search、fetch_url、find_file、grep_file、read_file | 控制输出信息量，防上下文爆炸 |
| 执行工具 | Agent 主动调用 | 改变世界 | shell_exec、code_interpreter、write_file、edit_file、send_email | 错误代价极高，**安全约束是核心** |
| 协作工具 | Agent 主动调用 | 驱动其他 Agent/人类 | spawn_subagent、send_message_to_subagent、cancel_subagent、list_agents | 专业化分工与人工介入 |
| 用户沟通工具 | Agent 主动调用 | 向用户传递信息 | reply_to_user、send_card_to_user、send_user_notification | 异步消息 + 多渠道 |
| 事件触发工具 | Agent 注册、外部触发 | 驱动 Agent 开始执行 | set_timer、monitor_shell、connect_channel | 注册时声明、触发时回调 |

后两类与事件驱动的异步运行时密不可分，见 [[事件驱动 Agent]]。

---

## 二、能力表达形式：专用工具还是 Skill + 通用执行器

两种基本形态：
- **专用代码工具**：结构化函数调用，确定性高、可测试；每个工具占数百 token，数量膨胀破坏 KV Cache。
- **Skill + 通用执行器**：自然语言 Skill 文档描述操作流程，Agent 经终端/代码解释器执行——少量通用工具覆盖大量场景（例："部署应用" Skill 写三步 CLI 指令，Agent 用 bash 逐步执行，无需为每步建专用工具）。

**三维决策框架**：

| 维度 | 倾向专用工具 | 倾向 Skill + 通用执行器 |
| --- | --- | --- |
| 参数复杂度 | 嵌套对象、多字段联合校验、复杂类型约束——结构化 schema 更好引导 | 参数简单，CLI 传参同样可靠 |
| 变更频率 | 稳定的底层操作 | 频繁变化——修改一段文本远比改代码后测试部署轻松 |
| 模型能力 | 较弱模型需要结构化 schema 引导 | SOTA 模型可用 Skill 表达更多能力、减少工具数量 |

## 三、工具粒度：整合与分离

粒度过细 → 数量激增、选择负担（超过 100 个时最先进的模型也容易出错）；过粗 → 单工具过于复杂。

- **整合判据 = 功能相似性 + 使用场景重叠度**：extract_pdf_text / extract_docx_content / extract_pptx_content 共性是"从文档提取文本，输入路径输出字符串" → 统一 `read_document(file_type=...)`。**降低认知负担**（只需理解"读取文档就用 read_document"）、描述更清晰、便于扩展（新格式只需加一个 file_type 选项）。
- **保持独立的情形**：功能相似但参数集差异很大，或某功能使用频率极高——文件系统的 grep 和 find 虽可包含在 bash 中，大多数 Coding Agent 仍提供专门工具：**更清晰的行号反馈 + 屏蔽不同平台的参数差异**。

## 四、工具的通用性设计

**通用工具优于专用工具，除非存在明确的安全、权限或性能理由。**

- code_interpreter 装好 sympy/numpy/pandas 代替十几个专用计算器——一个 Python 解释器代替数十个特定工具，还能处理**预先没想到的边缘场景**。逻辑：LLM 本身有强大思考和代码生成能力，应该利用而不是限制它。
- 但通用性有边界：Mac/Windows/Linux 的 grep 语法各不相同——专门 grep 工具比让 Agent 自由发挥好；生产数据库写操作场景，专用工具提供更精细的权限控制和审计粒度。

## 五、工具描述的艺术

**核心是让 LLM 知道"什么时候用"，而不只是"能做什么"**："搜索相关内容" → "当需要获取实时信息或查找未知事实时使用"。

1. **边界同样重要**：文件搜索工具应明确说明只能基于文件名匹配、不能搜内容——缺反例说明时 LLM 会自行猜测。**清晰列出边界条件（做不到什么、不接受什么输入）往往比描述能力本身更重要——大多数调用失败的根因不是模型不知道工具能做什么，而是不知道工具不能做什么。**
2. **参数描述用具体例子代替抽象规范**："timestamp：RFC3339 格式，例如 2024-03-15T14:30:00Z" 远胜单写"RFC3339 格式"；"phone：电话号码，E.164 格式（国家代码+号码，无空格或特殊字符），例如 +8613888888888（中国）或 +12025551234（美国）"。原因：执行复杂任务时（同时处理多工具、从历史提取信息、权衡决策），模型只能分出一小部分注意力确认参数格式。
3. **描述返回值**："返回 JSON 数组，每个元素含 title、url、snippet 三个字段"减少后续解析出错。
4. **注明执行代价**："此工具需下载完整网页，大型网站 5-10 秒；只要元信息请用 get_page_metadata"——帮助 LLM 合理规划调用顺序。
5. **附 1-5 个真实调用示例**：JSON Schema 只能描述参数类型，无法表达调用方式和典型参数组合（时间戳是秒还是毫秒、过滤条件如何嵌套）；加示例后调用准确率在一些基准上**从约 72% 提升到 90%**。

> [!tip] 工具描述的消融证据（实验 2-4）
> 保留函数签名和参数定义、只移除所有描述性文本——工具调用错误率**增加 45%**，Agent 频繁传无效参数值或误解参数含义。

## 六、参数传递的保真性

比功能缺失更隐蔽的反模式：**静默输入转换**——工具执行前悄悄"修正"模型输入，实际操作偏离模型意图。

**Cursor 弯引号案例**：工具接收 old_string/new_string 精确匹配替换；参数传递层把中文弯引号（\u201c \u201d）静默转为英文直引号。模型经读取工具看到文件里的弯引号（读取工具原样返回），原样传入 old_string——已被转换，与文件实际内容不匹配，返回"未找到匹配"；**模型反复尝试反复失败——它无法理解为什么工具找不到自己明明看到的内容**。写入方向同样：模型本意写弯引号（中文排版正确选择），被静默替换为直引号；模型随后读取验证，看到的又是被转换的内容——彻底困惑。

**静默参数注入**：某 IDE 的 bash 工具对所有 git commit 自动附加额外参数（标记 AI 生成提交）；用户 Git 版本旧不支持该参数就报错——模型反复调整提交信息措辞、尝试不同参数组合，无论怎么改都失败。

**原则：模型感知到的世界与工具操作的世界之间，不能存在系统性的偏差**。参数传递必须透明，不得在模型不知情时修改输入输出；确需规范化（统一编码格式）必须在工具描述中说明并在返回中明确告知。

## 七、工具设计的演进（三代）

1. **第一代：API 直接封装**——每个端点一个工具，粒度过细，需协调多工具才能完成一个目标。
2. **第二代：ACI 原则**——工具应对应 **Agent 的目标**而非底层 API 操作。ACI 对标 HCI 提出：HCI 研究人如何与计算机交互，ACI 研究 Agent 如何与计算机交互，**核心是让工具对 Agent 而非对人友好**。
3. **第三代：优化调用方式**——三个独立问题各有答案：
   - "如何被准确调用" → 示例驱动调用（前节）
   - "如何被发现" → 动态工具发现（后文主动工具发现）
   - "如何被串联" → **代码编排执行**——LLM 一次性生成脚本，中间变量留在执行环境，只有最终结果返回。比喻：传统方式每做完一步写邮件汇报给领导等回信（token 往返）；代码编排像领导一次写好完整操作手册照着做，只在全部完成后汇报。抓多网页再批量提取字段：页面全文只存在于执行环境变量，返回上下文的只有汇总结果——**token 消耗可降低约两个数量级**。这属于"代码作为通用 Agent 元能力"范式（见 [[Coding Agent]]）。

## 八、工具生态：MCP 与工具选择的挑战

**MCP（Model Context Protocol）**：Anthropic 2024 年底发布的开放标准，统一 AI 模型与外部工具/数据源的通信——"每个国家插座标准不同，旅行者要带不同转换插头"的解法。客户端-服务器架构；关键设计：

- **标准化的工具描述格式**：JSON Schema 定义输入参数类型/约束/描述——直接对应前文最佳实践。
- **传输层灵活性**：本地 stdio、远程 Streamable HTTP（早期 SSE 已弃用）。
- **资源与工具分离**：工具（可执行）、资源（只读数据，客户端可浏览读取无需调用）、提示模板（prompts，可复用模板）三类原语分别对应"模型可执行的操作""应用可读取的数据""用户可选用的模板"。
- **生态价值**：一次开发处处可用——一个 MCP Server 可同时被 Cursor、Claude Desktop、OpenClaw 等兼容客户端使用。

**MCP 的局限性**：重点是标准化 Agent 与外部能力的交互，**不提供完整的事件运行时**——跨会话、多事件源、离线唤醒的事件驱动架构（新邮件启动 Agent、外部回调恢复任务）仍需在协议之上另行构建：**MCP 负责能力调用的标准化，Agent 框架负责事件接入、调度、并发和唤醒**（见 [[事件驱动 Agent]]）。

**上下文开销**：仅 5 个 MCP 服务器就可能引入数万 token 工具定义开销——200K 窗口还没对话就用掉近三成。缓解案例：
- **Cursor**：工具描述同步到文件夹，Agent 默认只看工具名称索引，需要时再查具体定义——A/B 测试使 MCP 工具相关任务总 token 消耗**减少 46.9%**。
- **Pi Coding Agent**：核心模块刻意不内置 MCP，优先把能力封装成带 README 的 CLI 工具再由 Skills 按需加载；需要 MCP 生态时经扩展接入。
- **pi-mcp-adapter**（折中）：模型默认只见一个约 200 token 的代理工具，通过"搜索 → 查看定义 → 调用"按需发现后端工具，MCP 服务器延迟到首次使用才启动。**是否采用 MCP 作互操作协议与是否在会话开始时暴露所有 MCP 工具定义是两个独立决策**：后端保留生态兼容性，前端以 CLI + Skills 或代理工具实现渐进式披露。

**层次化组织**：工具上百时按信息源性质分类比扁平列表更有效——搜索工具（主动查找）、读取工具（从已知位置提取）、解析工具（处理非结构化数据：OCR/视频分析/音频转录）、查询工具（结构化数据源：天气/股票/公开数据库）。系统提示词显式说明分类结构帮助 LLM 快速定位工具组。

**MCP 安全四险与缓解**：详见 [[提示注入]]（工具描述投毒 / 恶意或被劫持服务器 / 同名工具遮蔽 / 凭证管理风险；审查描述、锁版本、最小权限凭证）。

## 九、感知工具

常面临返回信息量远超处理能力：一次搜索数万字符、一份 PDF 上百页——直接塞上下文既耗窗口又淹没关键内容。通用做法：工具层集成**上下文感知压缩**（输出超阈值如 10000 字符时，基于当前查询意图自动压缩，见 [[上下文工程]]）。

### 各类设计要点

- **搜索类**：返回**结构化候选列表**（标题、位置、摘要片段），不是拼接全文——让 Agent 先浏览候选再决定深入读哪条；结果多时提供**分页/游标**（cursor），默认只返回前若干条，返回值注明结果总数和获取下一页方式，由 Agent 自主决定翻页。
- **读取类**：支持 offset/limit 按需读大文件指定片段；必须截断时**明确标示**（"已显示第 1-200 行，共 5000 行，可用 offset 参数继续读取"）。**静默截断是危险的**——Agent 误以为看到全部，基于不完整信息错误决策。
- **只读红利**：感知工具不改变世界——结果可安全缓存（相同查询直接复用省时省钱）、多个调用可放心并行（同时读五个文件、并发三个搜索）。执行工具没有这种自由。
- **多模态输出形态**：直接返回图像（保留布局视觉细节、耗 token）vs 转成文本（精简高效、可能丢空间结构如表格行列关系）。按内容类型选：纯文字用文本提取，布局敏感的（UI 界面、复杂表格、设计稿）保留图像。

### 多模态感知的三条路径

1. **原生多模态处理**（能力上限最高）：ViT 视觉编码器把图像分割为 Patches 序列化成向量，与文本词向量共存于共享多模态嵌入空间；自注意力同等对待文本和图像 token。模型直接"看到"PDF 页面布局、图表和文字。
2. **提取为文本**：两阶段——OCR/音频转录先转纯文本再进模型。对文本为主体的 PDF 往往更省（一页 PDF 截图上千 token vs 文字几百 token）；代价：版式、图表、图像信息全部丢弃。
3. **工具化多模态分析**：主模型不支持多模态时往往比提取更好——`analyze_image` / `analyze_pdf` / `analyze_audio` 接受文件 + 自然语言问题，返回分析结果；内部可用多模态模型实现（对 Agent 能力要求低，选型空间大）。上下文只保留简短问题与分析结果。

实验 4-2 结论：原生多模态在分析图表、理解布局上最佳；提取为文本在纯文本文档上成本效益最高但无法处理视觉查询；工具化在交互式场景灵活（低成本初查 + 需要时高成本深析），端到端深度理解不如原生。

## 十、执行工具：安全机制的层次化设计

错误代价极高：误删文件无法恢复、错误命令致服务中断、不当 API 调用产生真实财务损失。**不依赖单一机制，构建多层防护**：

### 第一层：输入验证
执行前检查所有参数合法性：路径遍历攻击（`../../etc/passwd`——`../` 使工具跳出指定目录）、命令注入（分号/管道符拼接额外命令）、API 参数类型格式。**快速失败——发现异常立即拒绝，不尝试"智能"修正。**

### 第二层：权限控制
文件操作限制在特定工作目录；命令执行维护禁止命令黑名单（rm -rf /、dd if=/dev/zero）；外部 API 检查配额与速率限制；不同部署场景经配置文件定制。**黑名单只是最基础防护层，不应作唯一手段**——变形命令可绕过字符串匹配，更健壮的是结合语义解析（见 [[提示注入]] Coding Agent 部分）。

### 第三层：提议者-审核者（Proposer-Reviewer）

独立第二视角检验第一视角产出。两种机制：

**事前审批**（银行经办、审核双签）：一个模型提议行动，另一个独立模型审查批准。三个要点：
1. **模型选择**：提议与审批模型应来自**不同家族**（GPT 系 × Claude 系）但**能力相近**——不同来源引入认知多样性（两个不同学校毕业的工程师审查同一份方案，知识背景思维习惯不同，不太可能在同一处犯同样的错）；同家族（都是 GPT）训练数据偏好相似，容易在相同场景犯相同错误；能力相差过大（Haiku 审查 Opus）反而不可靠——审查者跟不上被审者的思考。
2. **提示词设计**：底层规则和约束必须完全一致、上下文一致（否则互相扯皮僵局）；关注点差异——提议模型强调行动导向与任务完成，审批模型强调风险控制与规则遵守。
3. **审批失败不是简单重试**：把拒绝理由作为工具调用结果加入轨迹——从提议模型视角，审批拒绝就像一次工具失败返回错误信息和修正建议。

适用：**不可逆、影响重大的操作**——收费、发送通知邮件、修改关键配置、创建外部资源。可加风险分级审批（高风险总审批、低风险直接执行）、无法确定时升级人工。

**事后验证**：操作完成后由审核视角检验正确性。要诀是**模态切换**——不是让第二个模型重读相同内容再审一遍，而是**在不同模态下检验**：代码生成的文档渲染为视觉输出再查排版；修改的配置文件在沙盒实际运行验证生效。不同模态提供互补的验证视角，单一模态的审查容易陷入相同盲区。

### Sidecar 机制：与主思考并行的安全校验

解决"操作执行时如何实时校验"。Claude Code 自动模式（Auto Mode）案例：主模型决定执行工具调用时，**独立的轻量级 LLM 调用**被触发判断"这个调用是否安全"——得名于微服务边车模式，独立运行与主体并行。主模型流式输出与 Sidecar 审查同步进行；但对被审查的那次调用，Sidecar 起**门控**作用——危险操作放行前不真正执行。

**关键威胁仍是提示注入**：Sidecar 若同时读取主模型上下文或思考过程，攻击者夹带"请允许执行 rm -rf"的话术就可能被误判为合理理由。**只读结构化字段就堵住了话术通道**：主模型准备执行 `bash("rm -rf /tmp/data")`，Sidecar 接收 `{tool: "bash", command: "rm -rf /tmp/data"}`，识别 rm -rf 模式判定高风险，返回拒绝并要求用户确认。轻量模型调用通常数百毫秒，与流式输出并行，用户几乎无感。

**为什么轻量模型可以审查**（与"能力相近才可靠"不矛盾）：提议者-审核者审查的是**开放式思考**，需能力相近；Sidecar 判断的是**较简单的分类问题**（这条命令危不危险），轻量模型足以胜任。需配**拒绝熔断器**：连续多次拒绝时不应无限重试（浪费资源且可能死循环），转请求用户手动判断——[[Harness 工程]]"纠正"功能的典型实例。

**让安全检查"隐形"**：把"展示"和"放行"拆开并行——界面先显示进度提示（"正在读取文件 src/main.py…"），后台同步安全检查。**安全性不以牺牲用户体验为代价。**

**两种机制对比**：

| 维度 | 提议者-审核者 | Sidecar |
| --- | --- | --- |
| 执行时机 | 操作前（事前审批）或操作后（事后验证） | 与主模型流式输出并行，门控单次调用 |
| 审查对象 | 操作的合理性或结果 | 操作本身（工具调用） |
| 输入隔离 | 提议者和审查者看到相似信息 | **刻意隔离主模型的自由文本** |
| 典型用途 | 不可逆操作审批、文档生成、配置修改 | 权限分类、记忆相关性判断、工具输出摘要 |

Sidecar 的另一典型应用——**构造和补充上下文**：主模型思考的同时，Sidecar 并行筛选相关用户记忆、为长输出生成摘要、从数据库提取最新信息——主模型需要时已备好，用户无感延迟。

### 自动验证与反馈闭环

**如果操作结果可以被验证，就应该自动验证**。write_file 创建/修改代码后不应只返回"成功"，而应立即执行语法检查：按文件类型调相应 linter，输出解析为结构化错误列表作为返回值一部分——"执行-验证-反馈"闭环：代码有语法错误，Agent 下一轮就看到"第 10 行：未定义的变量 result"，立即修正。

### 长输出的截断与持久化

输出超阈值（200 行或 10000 字符）时：**头部保留**前 50 行（初始输出或错误上下文）+ **尾部保留**后 50 行（最终错误信息或成功标志）+ 中间提示（"... [省略 8523 行，完整输出已保存至 /tmp/execution_output.txt] ..."）+ 文件引导（"如需完整输出，请使用 read_file 工具读取该文件"）。

### 执行环境隔离与沙盒

> [!warning] Python 虚拟环境（venv）不是沙盒
> venv 只隔离包依赖，对文件系统、网络和进程没有任何安全约束——venv 中运行的代码照样可以删除任意文件、访问任意网络。

真正的隔离按强度递增：
1. **进程级**：低风险 Agent 直接本地执行（Claude Code、Codex、OpenClaw 都是）——与本地用户相同权限，可访问修改删除任意文件。
2. **容器隔离**：Docker 提供独立文件系统和网络栈，但与宿主机**共享内核**，内核漏洞仍可能被利用逃逸。
3. **microVM/虚拟机**：Firecracker 等提供带独立内核的硬件级隔离——运行完全不可信代码的最强层级。

容器和 microVM 还应设 CPU、内存、磁盘、网络上限。**按部署环境和安全需求选层级**——本地开发进程级即可，生产或处理不可信输入需容器乃至 microVM。

### 工具执行的可观测性

详细日志（每次调用的时间、参数、结果、耗时）、审计追踪（谁在什么上下文下为什么执行了操作）、性能指标（调用频率、成功率、平均耗时）、告警机制（频繁失败、超时、资源超限通知管理员）。见 [[Debugging 与可观测性]]。

### 幂等性与取消语义

执行工具改变世界，必须回答感知工具无需考虑的问题：**调用被取消或超时时，副作用到底发生了没有**？转账调用网络超时返回失败，钱可能已转出也可能没——盲目重试可能重复转账。

- **幂等性**：同一操作执行一次和多次对外影响完全相同，可安全重试。两条手段：①操作携带唯一标识，服务端凭此去重（重复请求返回首次结果）；②**先查询后变更**——重试前先查目标资源当前状态（订单是否已创建、文件是否已写入），确认未完成再执行。
- **不可幂等的操作**（发邮件、打电话、转账——每执行一次产生一个不可撤销的真实事件）：采用 **"预检-确认"两段式**——第一段用来自不同模型家族的模型 + 专用安全检查提示词做校验（检查余额、确认收款方、生成待发送内容）；第二段才真正执行。执行阶段失败不盲目重试，把详细错误信息返回主模型重新规划。

## 十一、协作工具：子 Agent 的设计

任务超出单 Agent 能力边界时，把子任务委托给其他 Agent 或人类，再整合结果。**子 Agent 的核心价值是专业化分工**——与其构建"全能"Agent，不如构建一组各自专精的 Agent：每个子 Agent 独立优化提示词、工具集和知识库，互不冲突。协作动机：简单的是并行执行不相关的多任务；复杂的是用不同的模型、工具、提示词和上下文执行不同任务取得更好效果。

**子 Agent 提示词四要素**：
1. **角色定义清晰**：开门见山"你是专门负责 XXX 的助手 Agent"。
2. **上下文来源明确标注**："[FROM_MAIN_AGENT]是主协调 Agent 给你的任务指令；[FROM_USER]是用户直接补充的信息；[TOOL_RESULT]是你调用工具后的返回结果"——防止混淆信息来源，避免提示注入攻击。
3. **任务边界明确界定**：什么在职责范围内，什么需要转交或上报。
4. **输出格式标准化**：JSON 或 Markdown 都行，但要明确——保证子 Agent 考虑所有需要的方面、降低主 Agent 解析负担、错误处理更可靠。

**协作原语三组**：
- **启动与取消**：spawn_subagent 创建并分配任务；cancel_subagent 在任务失去意义时及时终止（用户改变主意、另一个子 Agent 已找到答案），避免浪费 token。
- **消息传递**：send_message_to_subagent 运行期间发补充指令或追问；子 Agent 可反向汇报进展或请求澄清。
- **发现**：list_agents 列出可用 Agent 及职责描述和运行状态——与 MCP 的 tools/list 同一思路，只不过列出的是 Agent。

**协作形态**：同步调用（等返回，适合快速任务）、异步调用（立即得任务 ID，完成时事件通知）、流式协作（持续发增量消息，过程本身有价值时）、多轮交互（子 Agent 主动询问、主 Agent 应答）。上下文传递、协作形态选择、多 Agent 拓扑与分工见 [[多 Agent 协作]]。

**人工介入（HITL）的艺术**：
- **超时和降级策略**：HITL 请求可能不会立即响应——设超时阈值和默认行为（"5 分钟内没响应采用保守策略"）；优先级队列（紧急请求多渠道通知，普通只发邮件）。
- **反馈循环**：HITL 不是一次性交互——人类的批准、拒绝及其理由首先构成**带证据的反馈数据**：可归纳的判断原则进入知识库或 Skill，高维隐式偏好形成后训练数据（见 [[Agent 持续进化]]）。

## 十二、主动工具发现

工具从十几个增长到成百上千时，全量注入 schema 迅速失效：上下文被"工具说明书"塞满，选择精度下降。检索式预筛选（按语义相似度先筛候选）缓解但不彻底——按初始查询做一次性匹配，而"Debug the file"这类请求实际牵出文件访问、代码分析、命令执行的多步骤跨领域工具链，任务开始时无法预见所有需求。

**从被动选择到主动发现**：Agent 从被动接受者变为主动发现者——执行中意识到能力缺口时，主动用自然语言声明"我需要什么能力"，系统动态匹配注入。MCP-Zero：系统提示词不预置任何工具 schema，Agent 在思考中生成结构化请求块（"GitHub 服务器：搜索仓库并返回元数据"），系统经**服务器级 → 工具级两层语义路由**从数千候选匹配注入——约 2800 个工具上比全量注入**节省约 98% token**。工程上更常见的等价方案：系统提示词只留少数基础工具（web search、code interpreter）+ 一个"工具搜索工具"，Agent 用自然语言描述需求即可检索加载（Anthropic Tool Search Tool 即此类）。

**层次化匹配与降级**：MCP 等协议中工具按服务器分组（类似手机 App）→ 匹配分两层：先按能力描述定位相关服务器，再在服务器内匹配具体工具——搜索空间从"数千工具"缩为"数十服务器 × 每服务器数十工具"，省算力也减少跨领域语义混淆。依赖离线构建、支持增量更新的嵌入索引；**两层候选相似度都低于阈值时明确返回"未找到"**——让 Agent 改写需求重试、用基础工具手工实现，或干脆创造一个新工具（见 [[Agent 持续进化]]）。

**动态加载与 KV Cache**：若把全部工具定义放静态前缀，每加载一个新工具整段缓存失效——破解即 [[KV Cache|前文]] 的追加式注入：新工具完整 schema 追加到上下文末尾，静态前缀稳定；schema 固定在轨迹原位置作为普通历史命中缓存；状态栏只维护一份简短工具名列表。API 原生保证：OpenAI 要求后续请求保持 tool_search_output 项的原位置、同一工具无需重复加载；Anthropic 在会话历史原位置内联展开 tool_reference block，官方文档明确后续每轮保持缓存命中。**真正导致重算的只有两种情况**：Prompt Cache TTL 过期（整段前缀一起重算）、修改/移除/重排已加载的工具集。

**实验 4-5（小模型的显著收益）**：Qwen3-4B 访问 120+ 工具——对照组全量注入（超 50K tokens）指令遵循严重退化（"查询股价"错选 Web Search 而非 Yahoo Finance 专用工具；"忘记"列表中某些工具）；实验组 system prompt 只留 3 个工具 + discover_tools 元工具（自然语言需求 → 嵌入匹配返回 3-5 个候选及完整 schema → schema 追加对话历史 + 状态栏更新工具名列表）→ 准确率和任务完成率显著提升。**主动工具发现不仅帮大模型应对成千上万工具，更让小参数量模型在上百工具场景保持可用。**

**Skills：更轻的替代**——不需要"嵌入索引 + 语义匹配"基础设施（见 [[Agent Skills]]）。

- **实验 4-1 感知工具 MCP 服务器**：搜索（网络/知识库/文件下载）、多模态理解（网页阅读、PDF/Word/PPT 提取、图片 OCR、音视频转录）、文件系统、公开数据源（天气/股价/汇率/Wikipedia/ArXiv）、私有数据源（日历/Notion）。

## 十四、常见坑

> [!warning]
> - **工具描述只写"能做什么"**：缺使用时机和边界反例——失败根因多是模型不知道工具**不能**做什么。
> - **静默参数转换/注入**：模型无法自诊的系统性故障；确需规范化必须描述说明 + 返回告知。
> - **黑名单当唯一防线**：变形命令绕过字符串匹配；语义解析才可靠。
> - **venv 当沙盒**：只隔离包依赖，文件/网络/进程零约束。
> - **静默截断**：Agent 以为看到全部；必须显式标示省略与续读方式。
> - **对不可幂等操作盲目重试**：转账/发邮件可能重复执行；预检-确认两段式。
> - **审批模型与提议模型同家族或能力悬殊**：同错或跟不上；不同家族 + 能力相近。
> - **API 层微压缩频繁触发**：移除点后缓存重建代价大——临近溢出时才批量用。
