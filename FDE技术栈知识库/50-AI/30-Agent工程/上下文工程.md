# 上下文工程（Context Engineering）

> [!abstract] 定位
> **上下文**是 Agent 在每个决策点能看到的**全部信息**——Agent 只能基于它看到的信息做决策。上下文工程不是"往 prompt 里多塞点信息"，而是系统性设计、组织和提供 AI 完成任务所需的**全部背景知识**。天才工程师比喻：理论功底再深，不了解你的产品架构、业务逻辑、技术债务、团队规范，也难以发挥价值——AI Agent 就是**永远的新员工**。一个中等模型配精心组织的上下文，往往胜过顶级模型在信息匮乏下的盲目摸索。

---

## 一、上下文决定能力上限

Coding Agent 修复同一个 bug，拿到的上下文质量直接决定成败。三类最低信息需求：

```text
① 实时代码上下文   目录结构、模块职责、核心数据结构、代码规范
                  —— 缺了：代码语法正确但风格格格不入，甚至架构冲突
② 流程规范        Git 分支策略、提交规范、审查流程、CI/CD 要求
                  —— 缺了：直接往主分支提交未测试代码
③ 环境信息        开发环境配置、测试库连接、部署方式、密钥管理
                  —— 缺了：本地能跑，到测试环境立刻崩溃
```

**这不只是技术问题，更是组织问题**：多数团队的关键知识是隐性的——架构决策只有老员工记得，业务规则靠口传。对远程工作友好的团队往往也对 AI Agent 友好：Linux 内核式的高度透明、文档驱动、所有讨论公开、决策有记录——信息公开、可检索、结构化，天然 AI-ready。**构建 AI 原生团队首先是一场文档化运动**。翁家翌："人和模型一样，最重要的是 Context"；"团队合作中最大的问题也是 context 的不一致"。

ReAct 论文的定义点出本质：Agent 下一步行动取决于**截至当前的完整交互上下文**，而非眼前一条输入。模型 API 无状态，每次调用必须由框架重新构造足够上下文——所有上下文技术都在回答同一个问题：**怎样以更低成本向模型提供信息充分的 cₜ？**

## 二、上下文的构成：静态前缀 + 轨迹

```text
┌─ 静态前缀（每轮不变，KV Cache 友好）──────────────┐
│ 1. System Prompt       开发者写的"岗位说明书"      │
│ 2. Tool Definitions    名称/描述/参数 schema       │
├─ 轨迹 / 对话历史（随交互不断增长 →）──────────────┤
│ 3. 用户消息            含 RAG 检索注入的外部知识    │
│ 4. 模型回复            reasoning + content + tool_calls │
│ 5. 工具执行结果        下一步思考的直接依据         │
└─────────────────────────────────────────────────┘
窗口大小：Qwen3 = 32K | Claude = 200K | Gemini = 2M
所有内容序列化为 token 流 → 注意力机制处理
```

API 层面：**四种消息角色**（system / user / assistant / tool）+ 顶层 `tools` 字段。`tool` 消息通过 `tool_call_id` 与调用请求配对。"四种角色 + tools 字段"恰好覆盖五个组成部分。

> [!note] 模型 API 是无状态的
> 每次调用都要把完整消息历史重新发给模型；生产系统可做摘要压缩，但不能悄悄丢掉决定下一步行动所需的信息。

**为什么"前面不能动、后面可以压缩"**：静态前缀持续命中 KV Cache，轨迹可压缩——理解了这个结构就理解了全部后续技术。

## 三、Agent 核心循环（API 视角）

单轮调用：system + user → assistant。带工具调用（温哥华时间+天气例）：

```text
第 1 次调用：messages(system+user) + tools → 模型返回 tool_calls
            （get_current_time 与 get_weather 无数据依赖 → 可并行执行）
第 2 次调用：+ assistant(tool_calls 原样放回) + tool 结果 ×2
            → 模型判断信息足够 → 返回文本回复 → 循环结束
```

三个关键细节：①第二次请求包含第一次的**全部历史**（无状态）；②第一次的 assistant 消息**原样放回**（模型看到自己之前的决策）；③tool 消息靠 `tool_call_id` 关联。

完整代码循环：

```python
messages = [system, user]
while True:                              # 生产代码必须加 max_iterations
    resp = client.chat.completions.create(model=..., messages=messages, tools=tools)
    msg = resp.choices[0].message
    messages.append(msg)                 # 模型回复（含 tool_calls）追加
    if not msg.tool_calls:
        print(msg.content); break        # 无工具调用 → 最终回复
    for call in msg.tool_calls:
        result = execute_tool(call.function.name, call.function.arguments)
        messages.append({"role": "tool", "tool_call_id": call.id, "content": result})
```

**Agent 框架的核心工作就是管理这个 messages 列表**——本章后续所有技术本质上都在优化这个列表的内容与结构。

本地小模型实验（实验 2-1，vLLM/Ollama 部署 Qwen3-0.6B）：0.6B 模型在合理提示词下能可靠完成工具调用；输出顺序结构为 `<think> 思考 → 文本回复 → 工具调用`；第一个工具调用参数完整通过校验即可立即执行，无需等后续生成；**修改系统提示词几个字符后首 token 延迟明显变长**——正是 KV Cache 一节的引子。

## 四、提示工程：优化系统提示词

核心对象是 `role: "system"` 消息——Agent 的"员工手册"。**检验标准：一个聪明的新员工读完你的系统提示词还不知道该怎么做，Agent 也一样不知道。**

### 4.1 语气与风格（"人格"）

"You MUST answer concisely with fewer than 4 lines"；无法完成时"keep your response to 1-2 sentences"且**不解释为什么不能做**（避免冗长自我辩护）。大写 "NEVER do X" 比 "Please avoid" 更能引起模型注意，但过度使用会稀释效果，保留给真正关键的约束。消融实验（实验 2-4，Tau-Bench）：默认/Trump 风格/Casual 三种语气对任务完成率影响相对有限——模型有强大的风格适应能力。

### 4.2 结构化提示（"格式"）

XML 标签名称携带语义（`<working_directory>` 立刻告诉模型这是工作目录）；Markdown 提供轻量层次结构；**双层结构：XML 负责机器可解析的精确语义，Markdown 负责人机共读的组织逻辑**。

### 4.3 流程驱动 vs 规则堆砌（"组织方式"）

给新员工一份上百条零散规则的手册（没有流程图、没有优先级）——最聪明的人也会困惑：多条规则同时适用选哪条？规则未覆盖怎么办？**流程驱动 = 标准 SOP**：

```text
File Processing Standard Operating Procedure:
Step 1: Validation    Check if file exists
                      - If not found → log error and stop
Step 2: Classification Determine file type by extension/content
Step 3: Preprocessing Config files → backup; Large files(>1MB) → stream
Step 4: Execution     Execute core logic by file type
Step 5: Verification  Ensure integrity
```

模型随时知道自己在哪个阶段、当前目标、下一步去哪；异常按所处阶段处理而非遍历所有规则。**消融实验关键结论：保留全部规则内容但打乱组织结构（去标题层次、拆散流程），任务成功率下降超过 30%+，经常违反关键规则**——"先验证身份再退款"被拆散后 Agent 跳过验证直接退款。**对人类友好的信息组织方式，对模型同样友好。**

### 4.4 业务规则细化（"内容"）

最易被忽视却最关键——**产品设计问题，需要产品经理深度参与**。电话办事 Agent 的三种计费模式（按省钱提成 / 按服务收小费 / 困难任务预收款）：模糊规则（"根据任务情况选择合适的计费类型"）导致行为极不稳定——"帮我退掉上个月买的衣服"是"帮省钱"还是"取回本属于他的钱"？"取消 Netflix"算"省钱"吗？同一任务不同时间分类不同。

必须明确到可执行："**NEVER use percentage_based_one_time for refunds and service cancellations. Use fixed_fee instead.**"；成功率分步估算映射到计费模式（>60% 可退款模式、<30% 直接拒绝）；"节省"只基于现有账单计算（否则模型把"避免未来涨价"也算成省钱）。**核心设计哲学：模型的优势在遵循复杂指令和长上下文提取，不应在业务规则上被赋予过多自由裁量权**——好的新员工培训不是"你很聪明自己看着办"，而是提供详细 SOP 让员工在明确框架内发挥。提示词一般由产品经理设计迭代，工程师负责准确编码。

### 4.5 Few-shot 示例：何时给模型看例子

期望输出难以用规则精确描述时（特定风格文案、报告格式、客服语气分寸）——给 2-3 个高质量输入-输出示例，胜过等量篇幅的抽象规则；模型本来就擅长、规则又能说清的任务，示例只是浪费 token。数量：**两三个覆盖边界情况的精心示例胜过十个大同小异的**（后者稀释注意力）。

两个工程决策点：①放哪——系统提示词（成为静态前缀，全请求生效）或伪造 user/assistant 消息放首轮（适合按会话类型选示例集）；②**缓存纪律**——示例处于上下文靠前区域，一旦确定就保持字节级稳定；按请求动态检索"最相关"示例 = 每次改写前缀，缓存持续失效 → 生产系统为每类任务准备**固定示例集**。

### 4.6 工具定义的设计

与系统提示词并列的静态组成部分。Claude Code 每个工具描述都精心设计：使用边界（"NEVER invoke grep or rg as a Bash command"）、具体示例（`timezone: 'America/New_York'`）、性能提示（"Batch your tool calls together"）、工具间协作（"Use the Read tool at least once before editing"）。详见 [[工具设计原则]]。

**演进：工具定义的渐进式披露已是 API 原生能力**（2026 年起）——OpenAI Responses API 的 tool_search + defer_loading；Anthropic Tool Search（tool_reference blocks，Claude Code 对 MCP 工具默认延迟加载：会话启动只注入名称和服务器说明，完整 schema 待搜索后才注入）；Codex CLI 的 tool_search（BM25 检索）默认开启。共同思路：静态前缀只留名称简述，完整 schema 按需**追加到上下文末尾**成为轨迹一部分。

> [!note] 为什么追加末尾不破坏缓存
> 因果注意力决定每个 token 的 K/V 只依赖它之前的 token——末尾追加不改任何已缓存 K/V；新增 schema 首次出现时计算一次（一次性缓存写入），此后并入前缀持续命中。**"追加到末尾"只发生在工具被发现的那一轮**——此后 schema 固定在轨迹原位置，后续新消息追加在它之后，不是每轮重新搬运到最新末尾。约束：模型须在后训练中见过"工具定义出现在对话中间"（GPT-5.4+、Claude 4.5+ 支持；自托管开源模型需专门训练）。

### 上下文构造决策骨架

```python
stable_prefix = system_message
stable_tools = core_tool_schemas
trajectory = load_message_history(session)
status_message = make_status_message(derive_current_state(trajectory))
if estimated_tokens(...) > budget:
    trajectory = compress_old_evidence(trajectory,
        preserve=[decisions, constraints, failures, citations])
request.messages = [stable_prefix] + trajectory + [status_message]
response = call_model(request)
```

## 五、Agent 状态栏

像手机状态栏（时间、电量、信号）——不是对话主体内容，而是框架在**上下文末尾持续注入**的状态摘要："已打 3 次电话"、"当前时间 10:30"、"TODO 剩 2 项"。模型每次生成时"瞥一眼"。

### 理论基础

**上下文学习更像检索而非推理**——上下文窗口是**一台只有一半的检索引擎**：检索的一半非常强（从成千上万 token 里捞出相关原始记录，相当于内置 RAG），缺的是"提炼层"——上下文里的东西不会被自动数一遍、建索引、总结成结论；任何"关于这些内容的结论"每次都要现算，代价随内容量 N 上涨。

典型失败：系统提示要求拨打每个商家不超过 3 次，Agent 经常数不清打了几次，又打第 4 次甚至循环——"已经打了几次"的知识以原始通话记录形式分散在 KV Cache 向量中，每轮要扫描重算。**在工具结果中直接标明"本次是第 3 次呼叫"后，错误率大幅降低**——把分散的隐式状态提炼为可直接检索的显式知识。同时解决长上下文注意力衰减：末尾状态信息空间上接近生成位置，获得最高注意力权重——"强制性的注意力引导"。

**实验 2-8（注意力可视化对照）**：无状态栏——注意力分散，思考 token 在"数数"；有状态栏——注意力集中于状态信息，思考直接使用已提炼结论。小模型（Qwen3-0.6B）带状态栏后准确率可接近前沿大模型，思考 token 量、延迟和花费**降低约一个数量级**；无状态栏时思考量随上下文变长持续增长，带状态栏后基本恒定。

### 构成

1. **任务规划（TODO 列表）**：多步任务的步骤清单放轨迹末尾，防忘记原始诉求。实验数据：启用 TODO 的 Agent 平均 **15 次迭代**完成任务，禁用 **21 次**且常遗漏子任务。从认知负荷理论看，TODO 是外部记忆。借鉴 Manus"通过复述操纵注意力"，提供 rewrite_todo_list / update_todo_status 专门工具（项含唯一标识、内容、状态 pending/in_progress/completed/cancelled、时间戳）。
2. **事件的侧信道信息**：精确时间、地理位置、距上次回复的间隔——帮助理解时序与环境背景。
3. **环境状态观察摘要**：系统时间、工作目录、异常提醒（"该工具已被重复调用 N 次"）、隐式状态→显式观察的转换。

### 在上下文中的位置

状态栏在 API 层面作为一条 **user 角色消息**插入上下文末尾（`<agent_status>` 标签包裹）——**不是修改 system 消息**（那会破坏整个前缀缓存）。澄清：user 角色只是协议层技术选择，内容并非来自真实用户——Harness 在借用 user 消息槽位注入框架生成的系统状态。

### 状态更新的两种实现与缓存代价

- **实现一：每轮替换**——每次调用前移除旧状态、末尾追加最新。上下文只有一份最新状态；代价是移除点后缓存失效（与"动态时间戳"同一失效机制，区别是位于末尾、失效范围只覆盖上次注入后的短后缀）。
- **实现二：持久追加**——状态消息永久留在轨迹，每轮追加新的（Claude Code `<system-reminder>` 即此）。完全缓存友好；代价是陈旧状态累积（占 token + 模型须自己关注最新一条）。

取舍粗估：状态 S token、两次更新间新增后缀 R、更新 N 次、缓存单价为普通输入 α 倍时——**αSN/2 < (1−α)R 倾向追加，否则替换**。状态小、更新频繁、会话受控 → 追加；状态大、轨迹长 → 替换。

### 五种实用技术（实验 2-9，agent-status-bar）

1. **时间戳跟踪**：`[2025-09-14 10:30:45]` 前缀加到用户消息和工具响应（**不是系统提示词**）——理解时序、支持调试审计与时间模拟。
2. **工具调用计数器**：全局字典 + "Tool call #3 for 'read_file'"——显式计数触发模式识别（第一次失败查路径、第二次列目录、第三次主动放弃）；深层价值是**隐式成本感知**。
3. **TODO 列表管理**：见上。
4. **详细错误信息**：四层——错误类型描述 + 完整参数 JSON + 调用栈 + 针对性修复建议（FileNotFoundError → 验证路径/检查工作目录/使用绝对路径）。启用后错误场景找到替代方案的成功率 **60% → 95%**。
5. **系统状态感知**：当前时间、工作目录（cd 后自动更新）、操作系统（Linux 用 apt、macOS 用 brew）、Shell、Python 版本。

协同产生**涌现效应**：时间戳×计数器理解操作频率分布；TODO×系统状态按环境调整策略；详细错误×计数器多次失败后既换策略又理解原因。全部元信息人类可读（随时可检查 Agent 获得了什么信息）、对模型无侵入（不需微调，任何 LLM 直接起效）。

> [!warning] 状态栏维护两原则
> 1. **尽量用代码维护**；实在要用 LLM，逐条抽取再由代码汇总，绝不让它一次性批量统计——模型几乎无条件相信状态栏（写"打了 3 次"它就当真是 3 次），LLM 做数量统计本就容易错；状态栏投毒风险因此必须认真对待。
> 2. **谨慎删除原始上下文**——状态栏是对原始上下文的一次**有损投影**，只提前算了"预想会被问到"的维度；计数类任务可以整段删原始记录省 token，但只要有一个问题涉及未计算维度，准确率断崖式下降。

## 七、常见坑

> [!warning]
> - **滑动窗口截历史**：既破坏缓存前缀，又丢关键工具结果（第 2 轮读的文件第 15 轮还要用）→ Agent 反复执行相同调用（实验 2-3 中经常陷入循环）。
> - **动态时间戳塞系统提示词**：首 token 延迟 0.5s → 3-5s，月账单翻倍。
> - **工具定义按使用频率动态排序**：从首个变动工具起缓存全失效；实验表明固定顺序对模型选择能力几乎没有影响。
> - **自行拼接纯文本消息**："USER: ... ASSISTANT: ..." 偏离训练格式——重复执行已完成操作、忽略工具结果、该调工具时生成文本、格式解析错误。
> - **把工具结果混进 user 消息**：Chat Template 误判"新话题"清理思维链草稿，模型"正算到一半草稿纸被收走"。
> - **上下文无限增长**：上下文腐化比溢出更隐蔽——表面正常，决策质量悄然下降。
