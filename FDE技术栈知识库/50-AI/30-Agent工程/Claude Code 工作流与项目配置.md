# Claude Code 工作流与项目配置

> [!abstract] 定位
> [[Coding Agent]] 解释 Coding Agent 的工程原理，本篇补充用户侧如何稳定使用 Claude Code 一类工具：如何探索项目、分阶段执行、控制权限、保存项目规则并自动验证。

## 一、从开发者到编排者

```text
传统：我知道每个文件怎么改 → 手工编辑
Agent Native：我定义目标、约束和验证 → Agent 执行并汇报
```

人的核心工作从逐行输入转为：

- 明确目标和不做什么。
- 提供项目上下文和真实约束。
- 判断方案是否符合业务。
- 让外部工具验证结果。
- 决定是否继续、回滚或换方案。

## 二、五步工作流

1. **探索**：读取目录、入口、配置、测试和运行命令。
2. **规划**：列出改动文件、依赖、风险和验证方式。
3. **实现**：小批量修改，每完成一个逻辑单元就检查。
4. **验证**：运行类型检查、Lint、测试、Build 和手工路径。
5. **提交**：审查 diff，写清楚 commit，必要时开 PR。

推荐提示词：

```text
先不要改代码。请探索项目结构，找出相关入口、配置和测试。
然后给出实现计划、可能的边缘情况和验证命令，等待我确认。
```

## 三、权限与安全边界

| 模式 | 适合 | 风险 |
| --- | --- | --- |
| 只读 / Plan | 探索、方案评审 | 最安全，但不能直接修复 |
| 默认确认 | 日常开发 | 每个高影响动作可人工确认 |
| 自动执行 | 受控沙盒、重复任务 | 误删、泄密、错误部署风险高 |

- 生产数据库、支付、发信、删除、部署等操作保留人工确认。
- 把危险操作放在沙盒或临时分支。
- 不要因为 Agent 声称「已完成」就跳过外部验证。
- 外部网页、文档和工具输出都是不可信输入，见 [[提示注入]]。

## 四、项目规则文件

### `CLAUDE.md` 的最小结构

```markdown
# Project Instructions

## 项目目标
- 一句话说明产品和当前边界

## 技术栈
- Next.js / TypeScript / PostgreSQL

## 常用命令
- `pnpm dev`
- `pnpm lint`
- `pnpm test`
- `pnpm build`

## 代码约定
- 服务端密钥不能进入客户端
- 所有 API 输入必须校验
- 修改后必须运行对应测试

## 不要做的事
- 不要修改迁移历史
- 不要提交 `.env`
- 不要删除现有测试来绕过失败
```

### 模块化规则

项目较大时按领域拆到 `.claude/rules/`，例如：

```text
.claude/
├── rules/
│   ├── api.md
│   ├── database.md
│   ├── frontend.md
│   └── security.md
└── settings.json
```

规则应短、可执行、可验证；不要把整本技术文档复制进规则文件。

## 五、Hooks 与自动化

适合交给 Hook 的确定性动作：

- 提交前格式化和 Lint。
- 修改敏感文件时阻止或提醒。
- Build 后生成类型或检查产物。
- 工具调用后记录审计信息。

不要用 Hook 承担需要业务判断的复杂决策；这类逻辑放在测试、验证器或人工审批中。

## 六、MCP、插件与 Skills 如何选择

- **内置工具**：能力简单、稳定、无需额外配置。
- **插件**：编辑器或 CLI 的轻量扩展。
- **MCP**：连接数据库、浏览器、GitHub、企业系统等外部服务。
- **Skill**：把一套稳定工作流程、约束和检查清单封装起来。

选择顺序：

```text
先判断内置工具是否够用
  ↓
重复出现的流程 → Skill
需要外部服务 → MCP
需要编辑器级能力 → 插件
```

不要给 Agent 一次注入过多工具；工具描述要写清「何时使用」和「不能做什么」。

## 七、让 AI 调试而不是猜测

提供四类信息：

```text
完整错误日志
复现步骤
预期结果
实际结果与最近改动
```

然后让 AI 自己执行 `lint`、`test`、`build`，让错误由工具返回，而不是靠猜。

## 八、成本与会话管理

- 大任务先拆分，避免把整个仓库和全部日志塞进上下文。
- 先用便宜模型探索和机械修改，复杂推理再升级模型。
- 重复稳定的规则放项目配置，避免每轮重复粘贴。
- 长会话出现上下文污染时，保存决策和当前状态，重新开会话。
- 记录模型、Token、失败重试和工具调用成本，见 [[LLM API]]、[[KV Cache]]。

## 九、远程与移动端开发

当本地设备性能或在线时长不足时，可以把同一套工作流迁移到云端：

```text
浏览器 / 手机
  ↓
云开发环境或云电脑
  ↓
终端 + Claude Code
  ↓
Git 仓库 / Preview 环境
```

- Web IDE 适合临时浏览器开发、预装依赖和快速 Fork 仓库。
- 云电脑适合保持长时间会话、运行本地服务和大型构建。
- 移动端接管前先确认终端权限、网络和会话状态。
- 访问令牌只授予目标仓库所需权限，使用后撤销或轮换。
- 远程环境同样要遵守 [[提示注入]]、密钥隔离和人工审批规则。

## 十、提交前自检

- [ ] Agent 看过现有代码和测试。
- [ ] 计划包含改动边界和验证命令。
- [ ] 高风险动作经过确认。
- [ ] 代码没有硬编码密钥。
- [ ] 运行了类型检查、Lint、测试和 Build。
- [ ] 审查了 diff，而不是只看 Agent 总结。
- [ ] 规则文件和代码变更一起提交或明确说明。
