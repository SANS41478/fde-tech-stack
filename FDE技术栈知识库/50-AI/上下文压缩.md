# 上下文压缩（Context Compression）

> [!abstract] 定位
> 提示工程决定往上下文里**写什么**，Skills 决定**按需加载什么**，状态栏决定**注入什么元信息**——压缩讨论相反的方向：如何为上下文**做减法**。什么时候压、怎么压、为什么**即使上下文没满也应该压缩**。与 [[KV Cache]] 看似矛盾，实则互补。

---

## 一、为什么需要压缩：三个截然不同的动机

1. **长度与成本约束**（最直观）：窗口有限（如 128K），工具调用结果动辄数万字符，几轮交互就可能撑满，任务被迫中断；token 越多 API 成本越高、延迟急剧上升。
2. **提升思考质量**（更深、易被忽视）：即使窗口够大，把所有原始信息堆进去也不是最优——十几轮搜索的原始结果散落各处，模型每次决策要在数万 token 中反复检索，注意力被分散。**先用一次 LLM 调用把已有信息结构化总结成"目前已知：A 是……B 是……还缺 C"，后续思考直接使用这份精炼表示。**
3. **缓解上下文焦虑（Context Anxiety）**：模型认为窗口即将耗尽时，可能**在任务尚未完成前提前收尾**。在窗口尚未接近耗尽时就提前压缩，可能提升决策质量。

---

## 二、内部机制：上下文学习是检索而非推理

注意力擅长在已有内容里"查找"，不擅长在一次前向传播里"归纳统计"。状态栏是把算好的结论**加进**上下文，压缩是把臃肿的原始记录**换成**算好的结论——同一枚硬币的两面，都在给那台"只有一半"的检索引擎补上缺失的"提炼"。区别：状态栏往往由代码每步确定性维护，压缩更多是用一次 LLM 调用把大段原文蒸馏掉。

**宠物店例子**：上下文含 100 条巡查记录（笼子 1：黑猫。笼子 2：白猫……共 90 黑 10 白）。问"黑猫白猫各多少"——查找（"笼子 37 是什么猫"）是注意力的强项；统计归纳要遍历全部记录维护计数，本质是思考。启用思维链能数对，但每问一次从头数一遍；Agent 场景统计常被反复使用，累积成本极高。**提前总结写入"当前统计：黑猫 90 只，白猫 10 只"，模型立刻检索到结论。**这就是压缩的第二价值：把需要思考才能得到的结论，变成可以直接检索的知识。

**上下文腐化（Context Rot）**：明明窗口没满，Agent 突然找不到关键信息，或反复纠结早已解决的问题。与**溢出**（装不下了）不同：**腐化是"装得下但找不到了"**——更隐蔽，表面还在正常工作，决策质量悄然下降。机制：注意力权重被分散到更多 token；无关内容占大头后决策质量明显下滑；偶尔才用的知识每次都加载、稳定规则与动态状态混在一起——书越多，找到目标那本越难。

**上下文学习的临时性**：ICL 允许推理时快速适应任务，但调整是暂时的、浅层的，会话结束就消失。理论研究（Benoit Dherin et al., "Learning without training"）支持：看到上下文示例时模型行为像被"临时定制"——不是真的改参数，效果类似一次小型专项训练。这解释了 few-shot 为什么有效、也为什么**不会跨会话累积**。

## 三、压缩与 KV Cache：看似矛盾，实则互补

矛盾：KV Cache 要求前缀不变，压缩不就是要改上下文中间的内容吗？

**关键在时机与位置**——压缩不是在单次 API 调用过程中修改，而是在**两次 API 调用之间**由框架对消息列表预处理：

1. **System Prompt 和 Tool Definitions 永远不动**——静态前缀持续缓存。
2. 压缩对象是轨迹中的 **tool results**——替换位置之后的缓存失效，之前的仍有效。
3. 有意识的权衡：不压 → 溢出任务直接失败；压 → 损失部分缓存，换可控长度与更高信息密度。**频次要权衡：接近阈值时批量压，不每轮压**（频繁压缩频繁破坏缓存）。

## 四、六种压缩策略对比（实验 2-10）

任务：识别并追踪 OpenAI 联合创始人的职业状态（多步信息聚合，搜索返回长度差异大，成功标准明确）。Kimi K3，窗口刻意限制在 128K 触发压缩。7 次工具调用平均每次返回约 52K 字符（共约 367K 字符）。

| 策略 | 做法 | Token 用量 | 压缩率 | 迭代 | 结果 |
| --- | --- | --- | --- | --- | --- |
| ① 无压缩 | 原始结果完整保留 | 166,043 | 102.1% | 5 | ✗ 溢出失败 |
| ② 个体摘要 | 每个结果独立 2-3 段摘要 | 276,608 | 10.9% | 12 | ✓ 但信息碎片化（多页面重复描述同一事件） |
| ③ 组合摘要 | 所有结果合并统一摘要 | 93,449 | 4.3% | 10 | ✓ 但超长输入必须截断可能丢尾部 |
| ④ **上下文感知** | 把查询意图与已有信息纳入压缩决策（"Given the search query: {query}" + "Current context: {context}"） | **40,157** | **3.0%** | **7** | ✓ 150K 字符压到 2K 仍保住后续需要的关键信息（创始人姓名与职位变动） |
| ⑤ 感知+引用 | 智能压缩 + 每条事实附来源 URL（语义压缩有损，源链接无损索引可回溯） | 222,992 | 4.1% | 10 | ✓ |
| ⑥ 自适应窗口 | <80% 窗口保留原文；超阈值**批量**压缩全部未标记结果；`[COMPRESSED]` 标记防重复处理 | 174,601 | 102.4% | 7 | ✓ 前几轮保持完整原始信息，初期收集灵活性最大 |

②③的共同缺陷：**缺乏语义理解，无法区分信息相关性**（非任务感知压缩）。④的核心创新：**压缩决策本身考虑当前查询意图**。压缩率口径 = 压缩后体积/原文体积，数值越小压得越狠。

## 五、生产级分层压缩机制（以 Claude Code 为参照）

不同类型的信息有不同"保质期"，压缩策略应与信息生命周期匹配——五层组合：

1. **工具结果预算控制**：大体积输出存磁盘，模型只看摘要预览；替换决策一旦做出即**冻结**（保证缓存一致性）。
2. **噪声直接删除**：低价值内容（大量搜索结果中只被用到几行的）直接移除不摘要——**对噪声做摘要只是浪费 token**。
3. **API 层微压缩**：通过 API 的上下文编辑能力指示服务端从前缀移除指定工具结果，本地消息不变。零本地实现成本；但按前缀不变性，移除点后缓存同样失效——**适合上下文即将溢出、反正要付出重建代价时用，不频繁触发**。
4. **归档式摘要**：逐轮结构化摘要（像 `git log` 保留每轮独立记录，不是 `git squash` 合并成一条），保留对话逻辑脉络。
5. **全量压缩**：LLM 驱动的完整压缩，最后手段；且分两阶段（先压会话记忆，不行再全量）；配备**连续失败熔断器**——生产数据中大量会话被困在反复压缩失败的循环里，熔断避免持续烧钱（阈值"连续 3 次"来自真实统计：曾有会话在此路径连续失败三千余次，仅这类无效重试每天全球约 25 万次 API 调用浪费）。

---

## 六、压缩策略的设计原则

1. **信息价值的非均匀分布**：关键决策点（人员名单）> 支撑性证据（新闻细节）> 冗余噪声（导航栏、页脚广告）。
2. **语义完整性**："Sutskever 于 2024 年 5 月离开 OpenAI"不能压成"Sutskever 离开"——时间和公司名是不可丢失的关键信息。
3. **任务相关性**：同样内容在"查找创始人名单"与"了解个人背景"两个任务下应产生不同压缩结果。**检索类任务保广度，分析类任务保深度，创作类任务保灵感触发点**；理想 Agent 能按任务类型自适应选择压缩策略。
4. **压缩即理解**：有效压缩需要深层语义理解——压缩模块要接近主模型能力，形成"模型调用模型"的递归架构；好处是显式压缩结果可审查、可跨会话复用。

压缩有额外开销（每次压缩是一次额外 LLM 调用），但相比节省的 token 成本与提升的任务成功率 ROI 极高（上下文感知压缩 token 减少 75%+）。

> [!tip] 压缩最容易丢失的东西
> **早期的架构决策、约束背后的理由、失败的路径**。Agent 需要定期把进展记录到文档——就像公司重要信息要文档化而非存在聊天记录里；模型没有文档化习惯就用 prompt 和 skill 提醒它。

## 七、隔离优于压缩：子 Agent 上下文隔离

压缩是信息**已进入**上下文之后做减法；更釜底抽薪的思路：**让大体积的中间信息根本不进入主上下文**。

主 Agent 把"在代码库中大范围搜索"这类产生海量中间内容的任务委派给独立子 Agent；子 Agent 在自己的上下文中完成探索，**只把几百 token 的结论性摘要回传**。

同一任务对比（"找到处理支付回调的函数"）：
- 主 Agent 亲自搜：十几个文件的数万 token 原始代码进入主上下文，绝大部分在找到目标后沦为永久占窗噪声，还得靠后续压缩清理。
- 委派搜索子 Agent：主上下文只增加两条消息——任务描述 + 结论（"函数位于 src/payment/callbacks.py 的 handle_callback，另有两处调用点"）；中间数万 token 随子 Agent 上下文一起丢弃。

本质对比：
- 压缩 = 有损的、需额外 LLM 调用的**事后补救**
- 隔离 = 让噪声从一开始就与主上下文绝缘，主 Agent 的 KV Cache 前缀**完全不受影响**
- 代价：子 Agent 看不到主 Agent 完整上下文，任务描述必须**自包含、目标明确**——回到本章主题：上下文质量决定能力上限，对子 Agent 同样成立。

生产实现：Claude Code 的 Task 工具、各类 Deep Research 的检索子 Agent。子 Agent 作为协作工具的完整设计见 [[工具设计原则]]，多 Agent 上下文架构见 [[多 Agent 协作]]。

## 八、常见坑

> [!warning]
> - **无压缩硬扛**：数 次搜索就耗尽 128K 窗口（实验中 5 次迭代即溢出失败）。
> - **每轮都压**：频繁破坏缓存；应阈值触发 + 批量压缩。
> - **对噪声做摘要**：浪费 token 且没有收益——低价值内容直接删。
> - **只留状态栏不留原文**：有损投影有盲区，未计算维度被问到就断崖降准（见 [[上下文工程]] 状态栏维护原则）。
> - **压缩后不做防重复标记**：已压缩内容被再次处理；`[COMPRESSED]` 标记不可少。
> - **极端压缩不留溯源**：带引用的压缩（保留 URL）在需要回溯原始信息时是救命的。
