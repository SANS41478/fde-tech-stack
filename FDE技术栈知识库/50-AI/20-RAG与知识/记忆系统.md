# 用户记忆系统

> [!abstract] 定位
> 上一章（[[上下文工程]]）解决**单次交互**的上下文管理；本章处理更难的问题：**如何让 Agent 在对话结束后仍然记住用户、记住知识**。持久化知识分两个尺度——**用户记忆**（个体尺度：在与每位用户的交互中逐渐了解其偏好、习惯和需求，成为"懂你的助手"）与**知识库**（群体尺度：面向所有用户的集体知识，成为"领域专家"）。两者解决同一问题、共用底层技术（向量检索、知识压缩）、面临同样的麻烦（信息冲突、知识过期、检索不准）。记忆系统**不保存每句对话**，而是用额外的 LLM 调用**提取、压缩并审查**对未来有用的事实——这与只在当前窗口生效的上下文学习不同。

> [!info] 本文边界
> **负责**：通用记忆架构、存储格式、检索和更新策略。<br>
> **不负责**：DeepSeek Harness 的具体实现（见 [[10-记忆与上下文]]）和通用 RAG 基础（见 [[RAG]]）。

**提取示例**：对话结束后框架调用专门 LLM 分析对话内容（订机票场景），提取：`User prefers window seats (preference)`、`User is vegetarian, needs special meals (dietary restriction)`、`User's United MileagePlus number: 12345678 (loyalty program)`、`User has travel plans to Tokyo (recent activity)`。提取结果须满足三条规则：**选择性**（丢弃"搜索返回 3 个选项"这类短期细节）、**抽象化**（把本次"靠窗座位"归纳为长期偏好）、**结构化**（用可检索的字段保存事实）。

## 一、记忆能力的评估：三层次框架

动手设计前先回答"什么样的记忆系统算好"。学术界基准：**LoCoMo**（Long-term Conversational Memory）——平均约 300 轮、最多 35 个会话的超长多轮对话，通过问答（单跳、多跳、时间推理、开放域、对抗性）、事件摘要和多模态对话生成三类任务考察长程对话记忆。

综合各类基准与商业产品实践，用户记忆能力八项：个人信息保留、偏好追踪、上下文切换、记忆更新（矛盾新信息的正确处理）、多会话连续性、复杂思考（基于多个记忆片段联合思考——用户对花生过敏时推荐泰国菜应主动提醒）、时间感知、冲突解决。

**三层次评估框架**（贯穿全章，实验 3-9 / 3-11 用它衡量检索技术的提升）：

| 层次 | 能力 | 例子 |
| --- | --- | --- |
| 一：基础回忆 | 准确存储和检索直接提供的、结构化的、无歧义的信息 | "我的会员号是 12345"，后续精确返回 |
| 二：多会话检索 | 面对来自不同对象、不同时期的多段会话，检索出所有相关信息并推理判断 | 两辆车的用户说"为我的车预约保养"→ 找出两辆车全部信息并追问是哪辆；取消"洛杉矶之旅"需主动关联机票和酒店 |
| 三：主动服务 | 综合多个会话甚至很久以前的信息，**提供预见性的主动帮助**，从看似无关的记忆中发现深层联系 | 预订国际航班时主动关联数月前的护照信息发现即将过期；手机损坏时主动整合自带保修 + 信用卡附加保修 + 运营商保险；报税季主动整合所有税务文件 |

评估集构建（实验 3-1）：每层 20 个用例；一层的用例由单会话构成，二、三层由跨时间跨对象的会话构成（约 50 轮沟通）。评估流程：被测 Agent 根据第一个会话生成记忆 → 根据记忆和下一个会话修改记忆（**仅能访问记忆，不可回看之前会话原始对话**）→ 全部会话处理完毕后根据记忆回答新问题 → LLM-as-a-judge 对比参考答案得分。

## 二、记忆的层次结构（放哪里）

```text
轨迹（Trajectory）  单次 Agent 运行的完整历史——用户消息 + 模型回复 + 工具执行结果
                    按时间追加、只增不改（append-only）→ "流水账"
                    用于追溯/调试/审计的原始事件记录；运行时 Context 可压缩重组
用户长期记忆        跨会话、跨实例的持久化存储，键值对绑定用户 ID
                    存偏好、历史交互摘要、提取的知识点；通过特定工具显式读写 → "档案"
业务状态            开发者定义的高层状态抽象：任务逻辑阶段
                    （"需要澄清" / "处理请求中" / "等待付款" / "请求完成"）
                    在事件驱动的 Agent 架构中尤为重要
```

轨迹 vs 长期记忆：**轨迹是不可变的完整事件序列（按时间追加），工作记忆是经过筛选和激活的动态子集（按相关性裁剪）**。分层设计既保证高效处理当前任务（依赖轨迹），又具备长期个性化能力（依赖长期记忆）。

## 三、用户记忆的四种存储格式（怎么存）

四种渐进式格式，代表记忆粒度与结构复杂度的递进：

| 格式 | 形态 | 优势 ✗ 劣势 |
| --- | --- | --- |
| **Simple Notes** | 最小的、不可再分的事实键值对（"用户邮箱：john@example.com"） | ✓ 开销极低、O(1) 操作 ✗ 关联性完全丢失（"在 TechCorp 担任高级工程师负责推荐系统"被拆成三个事实，综合查询要拼碎片） |
| **Enhanced Notes** | 完整上下文段落（"用户在 TechCorp 担任高级软件工程师，专注 ML 三年，目前领导 5 人推荐系统项目"） | ✓ 语义完整丰富 ✗ 存储冗余（相同信息在多段重复）、更新复杂（属性变化要重写多段） |
| **JSON Cards** | 三层嵌套（类别→子类别→键值，如 personal.contact.email / work.position.title） | ✓ 部分更新（改 work.position.title 不影响 company.name）、可预测可扩展 ✗ 刚性分类假设信息可清晰归类（"周末用 Python 开发个人项目"同时涉及时间偏好、技术偏好、活动类型，强制归一类丢多维性） |
| **Advanced JSON Cards** | 卡片 + **backstory**（信息来源叙事）+ **person** + **relationship** + 时间戳 | ✓ **消歧**与知识管理 ✗ 生成维护成本高 |

**Advanced JSON Cards 的消歧**：同一条信息在不同场景含义不同——"张医生"可能是用户自己的牙科医生，也可能是用户父亲的心脏科医生，脱离情境无法正确理解。backstory 提供"为什么"存储这条信息；person 和 relationship 建立"为谁"存储。用户说"帮我安排家人的年度体检"→ 通过 relationship 识别所有家庭成员、通过 backstory 了解健康历史。

**实践选型**：关键且少量的数据（用户偏好、关键人物关系）用 Advanced JSON Cards 保证可检索性；大量非关键对话事实用 Simple Notes 降低成本；**多数生产系统混合**——同一 Agent 内不同类别的信息走不同路径。

**实验 3-2**（统一接口实现四种模式 + 三层次评估集）：Simple Notes 以最低成本通过第一层多数用例，但在需要综合多条信息、区分同名实体的二、三层频繁失分；Advanced JSON Cards 在消歧和跨会话关联用例上最好，代价是记忆维护调用明显更贵更慢。建议亲手切换四种模式，对比同一测试用例生成的记忆文件——差异一目了然。

## 四、进阶知识表示形态：可执行代码（User as Code）

前四种格式本质上都是文本：擅长召回单条事实，却要把聚合、冲突检测和约束执行交给 LLM"心算"。**User as Code** 把用户状态改成**带类型的可执行对象**，规则写成普通函数——"表示"和"推理"用同一种可验证介质。

借鉴"预写日志 + 检查点"：会话结束后先把事实**追加到只增日志**，再定期从完整日志**重建**带类型的状态——既保留原始证据，也得到可查询、可执行的派生状态。

```python
state = {
    passport: PassportInfo(number="AB1234567", country="US",
                           expiry_date=date(2025, 2, 18)),
    trips: [Trip(destination="Tokyo", departure_date=date(2025, 1, 15),
                 is_international=True), ...],
}
# 聚合统计交给确定性函数
count(trip for trip in state.trips
      if trip.is_international and year(trip.departure_date) == 2025)  # => 2
# 冲突发现：当前用药 × 过敏史交叉比对
def check_drug_allergy(profile):
    for medication in profile.current_medications:
        for allergy in profile.allergies:
            if medication.drug_class == allergy.drug_class:
                emit_conflict(medication, allergy)
# 约束执行：状态更新后自动检查护照有效期，不必等用户检索
def check():
    for trip in state.trips:
        if trip.is_international:
            days = date_difference(state.passport.expiry_date, trip.departure_date)
            if days < 180:
                alert("passport expires too soon", trip, days)
```

## 五、认知科学基础（存什么）

```text
工作记忆（Working Memory）= 上下文窗口——处理当前任务的临时信息空间
                            （轨迹是核心，还含从长期记忆激活加载的信息）
长期记忆 ├ 情景记忆（Episodic）：具体事件和经历
         │    人类："上周三和同事在那家意大利餐厅吃了顿很棒的晚餐"
         │    Agent："用户订了下周五去东京的 ANA 航班"——时间、对象、细节
         ├ 语义记忆（Semantic）：从具体事件抽象出的一般性知识
         │    人类："意大利的首都是罗马"
         │    Agent："用户是素食者"、"用户偏好靠窗座位"——多次交互提炼的稳定特征
         └ 程序记忆（Procedural）：行为模式和流程
              人类：骑自行车的能力
              Agent："先搜索直飞 → 确认座位偏好 → 使用常旅客号 → 订餐"
```

**三套分类体系正交**，可自由组合：

| 体系 | 回答的问题 | 类别 |
| --- | --- | --- |
| 记忆层次 | 存在哪里？ | 轨迹（当前会话）、用户长期记忆（跨会话）、业务状态（任务阶段） |
| 存储格式 | 怎么存？ | Simple Notes / Enhanced Notes / JSON Cards / Advanced JSON Cards |
| 认知类型 | 存什么？ | 情景记忆（具体事件）、语义记忆（一般知识）、程序记忆（行为流程） |

例：一条"用户偏好靠窗座位"的语义记忆可用 Simple Notes 存在长期记忆中；一段"先搜直飞→确认座位→用常旅客号"的程序记忆可用 Advanced JSON Cards 格式存储。格式取决于工程需求（简单性 vs 表达力），类型取决于业务场景。

## 六、记忆框架案例

**Mem0：从写入时消歧到检索时推理**（v2 → v3 的演进是有启发性的系统设计案例）：

- **v2（2025 论文）**：对话结束后 LLM 抽取候选事实 → 向量检索找相近已有记忆 → LLM 在 ADD/UPDATE/DELETE/NOOP 中决策。"住在北京"后来"搬到上海"→ 前一条被 UPDATE 为"住在上海"，**写入时消除冲突**。优势：记忆库始终简洁一致；风险：**一次错误的更新或删除会不可逆地丢失历史信息**，且每条候选要经历检索 + 第二次 LLM 判断。另有图记忆变体 Mem0-g（实体-关系图支持多跳与时序）。
- **v3（2026.4）**：一次 LLM 调用抽取事实，**只做 ADD**；"住在北京"与"搬到上海"作为**带时间信息的两条事实并存**。查询时融合语义相似度 + BM25 关键词 + 实体匹配，结合时间排序解决"当前事实"问题；Agent 确认完成的动作也成为一等事实。既避免错误 UPDATE/DELETE 丢历史，又减少 LLM 调用。LoCoMo **71.4 → 92.5（+21.1）**，LongMemEval **67.8 → 94.4（+26.6）**。

**Memobase**（memodb-io/memobase）：不做通用记忆流水线，聚焦"**用户画像**"形态——
- **Profile（用户画像）**：开发者可配置的槽位，按主题→子主题两级组织（basic_info→姓名 / interest→兴趣 / work→职位），存从对话提取的稳定用户属性，开发者精确控制画像范围与粒度。
- **Event Memory（事件记忆）**：按时间线记录用户经历的事件，回答"我们上次讨论预算是什么时候"这类时间问题。
- 工程：**缓冲批处理**——对话先在缓冲区累积，达到规模或时限后统一触发一次记忆提取，摊薄 LLM 调用成本；查询侧只读已整理好的画像和事件，保证低延迟。

**多类型记忆协同的参考架构**（对设计空间的概括，非具体项目）：长期记忆（情景：带元数据的事件序列，支持按时间/主题多维组合检索；语义；程序）↔ 工作记忆（当前任务状态）动态交互——重要信息选择性写入长期，相关长期记忆按需激活加载。实际框架往往只实现一两种类型——**按业务需要取舍，比追求"大而全"更符合工程现实**。

## 七、记忆压缩与整理机制

简单累积式存储导致记忆爆炸——消耗存储且降低检索准确性。三层压缩：

1. **重要性评分筛选**：综合四因素——**访问频率**（经常被检索的更重要）、**时间衰减**（越久远越易遗忘）、**情感强度**（强情感标记更易保留）、**信息独特性**（重复信息重要性降低）。低于阈值标为可压缩/可删除。例：被访问 5 次、创建于 3 天前、带强情感标记、无重复 → 高分；仅访问 1 次、创建于 90 天前、无情感标记、与其他 3 条高度重复 → 低于压缩阈值。
2. **聚类**：相似记忆分组，每组生成代表性摘要（"用户经常询问天气，特别关心降雨"）；原始详细记忆存档二级存储。
3. **抽象和泛化**：从具体情景记忆提取一般性规律，转化为语义或程序记忆——从多次购物对话学到"偏好性价比高的产品，重视用户评价"。

## 八、隐私保护：日志脱敏（实验 3-3）

核心挑战：Agent 既能利用用户信息提供个性化服务，**又不让敏感数据暴露在 LLM 上下文和系统日志中**。

log-sanitization 项目用 **Ollama + 本地 Qwen3-0.6B**（CPU/消费级设备可跑，可切 qwen3:1.7b/4b）做 PII 检测与脱敏。选本地部署的理由很明确：**日志本身可能含敏感信息，发送到云端脱敏就违背了隐私保护初衷**。识别范围：结构化信息（身份证号、银行卡号）、半结构化信息（地址）、自然语言表达的敏感内容（"我的密码是 abc123"）。结果经 JSON Schema 结构化输出（类型、位置、置信度）。对比传统正则：**LLM 方案召回率 95%+ 且显著降低假阳性**。超高吞吐场景用混合策略：正则快速过滤明显模式，LLM 深度分析剩余文本。

## 九、记忆的检索与更新 → 双层架构

记忆量到成千上万条时如何精准找回相关几条、如何辨别矛盾记录——**这正是 RAG 技术的主场**，与知识库共用检索底座（详见 [[Agentic RAG]]）：

- **Agentic RAG 用于记忆**：对话历史按固定窗口（如每 20 轮）分块索引 + `search_user_memory` 工具。第一层（基础回忆）一次搜索即可；第二层的威力在多轮迭代——初步搜索"车辆 服务 预约"只返回本田记录 → 评估时发现"还有一辆特斯拉"这条关键线索 → 二次搜索确认 → 完整回答"你是指已预约周五保养的本田 Accord，还是尚未预约的特斯拉 Model 3？"
- **上下文感知检索**（详见 [[Agentic RAG]]）：孤立的"好的，就订这个吧"毫无信息量——索引前用 LLM 生成上下文前缀后，矛盾指令场景（妻子设立转账 → 丈夫修改 → 妻子改回）的三个对话块分别带上 `[妻子正在设立初始电汇]`、`[丈夫正在修改之前的电汇]`、`[妻子在丈夫修改后再次修改]`——时间、人物、意图为判断指令优先级提供关键线索。

> [!tip] 全章汇合点：双层记忆架构
> **Advanced JSON Cards 常驻上下文**（结构化核心事实，提供随时可见的"概览"：护照 2025-02-18 过期、东京之行）+ **上下文感知检索按需取回**（从海量原始对话中取"细节"）。主动服务（第三层）之所以最难：只靠常驻上下文因容量受限丢失细节，只靠检索缺全局视野发现不了跨会话隐藏关联。落地流程：①事实回顾（审视 JSON Cards）→ ②关联推理（机票日期一月 vs 护照过期二月，发现风险）→ ③细节验证（检索"护照"和"东京机票"确认）→ ④主动服务（"护照即将过期，强烈建议加急续签"）。

**知识更新**（增量更新与定期整理）与知识库共用 Proposer-Reviewer PR 流水线与定期整理机制——详见 [[Agentic RAG]] 的知识更新一节；核心原则同样适用：来源与时间检查、冲突不强行收敛、版本化与可回滚。

## 十、常见坑

> [!warning]
> - **对话原始分块直接索引**：孤立的对话块缺上下文，检索时矛盾指令无法判断优先级——先做上下文前缀增强。
> - **矛盾信息简单保留最新**：应追溯原始信息源，判断是否不同时间/对象/地域/条件下各自成立——都有效则把适用场景写入，证据不足保留冲突与待确认状态。
> - **多用户共享库不按权限过滤**：越权文档一旦进入上下文就可能泄露——权限过滤必须下推到检索层（详见 [[Agentic RAG]]）。
> - **把轨迹当记忆存**：轨迹是流水账，记忆是档案；未经提炼的原始记录模型无法可靠利用。
> - **单一格式包打天下**：关键少量用 Advanced JSON Cards、大量非关键用 Simple Notes 的混合模式才是工程现实。
> - **保存对话 ≠ 记住了**：与 [[Agent 持续进化]] 的分工——记忆沉淀"用户与世界是什么样的"，进化沉淀"在什么条件下应该怎样行动"。
