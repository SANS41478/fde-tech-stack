# Agent Skills

> [!abstract] 定位
> 随着 Agent 覆盖的业务场景越来越多，系统提示词会不断膨胀——客服的退款规则、编程的代码规范、文档的格式要求……全部塞进一个提示词带来两个问题：**浪费 token**（大部分内容与当前任务无关）、**注意力被稀释**（无关信息过多稀释模型对关键内容的注意力）。这就是从静态提示工程到动态提示词的自然演进：**不是把所有知识一次性塞给 Agent，而是让它按需加载**。Agent Skills 是这一理念的工程化实现。

---

## 一、Skills：领域能力的可组合单元

每个 Skill 本质是**一套包含专业领域指导的提示词集合**——像为新员工准备的某个专项任务的操作手册。与把所有指令塞进单一系统提示词不同，Skills 采用**渐进式披露（Progressive Disclosure）**：先给一份目录摘要，需要时再加载完整内容——你不会把公司所有部门的操作手册都堆到新员工桌上，而是先给总目录，需要哪本再取。

### 三层结构（以 PPTX Skill 为例）

```text
第一层 元数据（启动时常驻，~300 tokens/skill）
  skills: [{name: "PPTX", desc: "Create PowerPoint presentations from content"},
           {name: "PDF",  desc: "Extract and analyze PDF documents"}, ...]
  → SKILL.md 顶部 YAML frontmatter：name + description
  → 目录在主体正文加载前对 Agent 可见：先判断任务是否需要某能力，
    不必为所有能力支付完整上下文成本

第二层 核心流程（任务匹配时才加载，~2K tokens）
  PPTX Skill 核心流程:
  1. markitdown 提取文本 → 2. 解压 PPTX 访问 XML
  3. 修改 slide{N}.xml 内容 → 4. 重新打包为 .pptx
  引用: → html2pptx.md | → reference.md | → scripts/

第三层 细则（选择性深入，按需加载）
  html2pptx.md        HTML 模板创建 PPT 的完整工作流
  reference.md        PPT XML 格式规范和技术细节
  scripts/*.py        可执行工具: thumbnail.py 等
```

**description 是路由决策的关键**——应当足够短（控制常驻 token 量），但写法要像**路由条件而非功能介绍**：明确写出"何时使用"和"何时不使用"的边界，给出典型反例，减少宽泛匹配的误触发。描述太宽泛（"help with backend"）等于任何后端工作都触发，路由失准；**"何时该用我"比"我能做什么"重要得多**。这是路由提示的写作建议，不是额外的格式字段。

### Skills 的位置与 KV Cache

**标准层**：规范规定的是**加载时序**而非消息角色——目录必须先于正文可发现，正文在 Skill 被选中后按需加载；具体消息角色与包装方式由 Harness 决定。
- **Claude Code**：目录作为运行时上下文消息提供；完整指令在 Skill 被调用的位置作为 user message 注入会话。
- **OpenAI Codex**：每轮上下文构造阶段重新渲染 Skills catalog 作为 developer 上下文片段；选中的 Skill 正文以带 `<skill>` 标记的 user 片段注入；其他来源的 Skill 经专用工具按需读取。

**缓存友好性（KV Cache 演化视角）**：元数据从 Turn 1 起在 system prompt（稳定启动前缀，可复用 Prompt Cache）；完整正文在调用位置追加进入会话历史——**调用 Skill 只在调用位置追加完整指令，不会回头改写 system prompt**。Turn 1 的 cache_creation ≈ 2.5k tokens，Turn 2 ≈ 0.5k，Turn 3 ≈ 0.4k——前缀稳定后增量极小。

> [!note] "对 KV Cache 友好"≠"零成本"
> 目录首次进入请求需要处理，完整 Skill 正文首次加载也产生新增计算；当前缀保持稳定时，后续请求才可复用缓存。不同 Harness 对目录的重建方式不同，但共同原则：**少量目录常驻、完整正文按需加载**——无需启动时加载所有正文，也无需每次调新 Skill 时回头改写已建立的上下文。

## 二、如何编写一份可用的 Skill

Skill 不应只是背景知识或一次成功对话的摘要——它要让一个刚加入团队的员工知道：**遇到什么任务时使用它、应该按什么顺序行动、哪些情况需要停下来确认、什么结果才算完成**。四部分结构（宝玉《图解 Skill》）：

1. **角色与读者**：说明这份 Skill 服务谁、面向什么任务，输出应达到什么标准。
2. **核心原则**：只保留 **3-5 条**最重要的判断，并为关键原则配**正例和反例**。
3. **禁止清单**：记录高频错误、越权动作和容易误解的表达，同时**写清合法例外**。
4. **参考资料**：术语表、模板、范文和更详细的子文档。

规则写作模式：**"作用域 + 动作 + 例外 + 验证方式"**，避免把所有可能的情况堆成一张越来越长的禁用词表。

**写作型 Skill 的迭代法**：从 3-5 篇自己最满意的原创文章开始 → 让 Agent 归纳用词、句式、段落结构和语气，生成约 20 行的初版 → 用它处理一项真实写作任务，作者逐句改稿 → **原文与修改稿的差异**比抽象地说"更自然一点"更有信息量：它告诉 Agent 哪些词被删掉、哪些长句被拆开、哪些地方需要补充事实 → 把反复出现的改动整理回 Skill，为每条规则保留正例、反例和适用范围。

**Skill 不仅包含指导性文档**，还可捆绑可执行的代码工具和模板文件——PPT Skill 可包含 PPT 模板和解析 PPT 的脚本。

**生态价值**：每个 Skill 是自包含的知识模块——独立开发、测试、版本控制、分享。Agent 能力扩展从集中式的系统提示词编辑，转变为**分布式的、社区驱动的 Skill 生态**——与 pip/npm 的包管理深刻相似：每个 Skill 封装某个领域的最佳实践。Anthropic 官方 Skills 仓库已涵盖文档处理（PPTX/PDF/DOCX）、数据分析、代码生成等领域。

> [!tip] 交互模式与模型训练保持一致
> 基础模型公司推行的 Agent 用法，本质上是它们**专门训练过**的模式——同一生态内的模型天然具有最佳表现。选择 Agent 交互模式时应与模型厂商的训练方法保持一致。

## 三、Skills 在上下文中的位置：三个实验

**实验 2-6（论文生成 PPT）**：Claude Code + Anthropic 官方 PPTX Skill，从学术论文 PDF 生成 10-15 页演示文稿。执行流程体现渐进式加载：①在元数据目录中看到 PPTX Skill 描述 → ②识别任务需要 → ③调用 Skill 加载完整指令获得核心流程 → ④选择性加载 html2pptx.md 获取详细方法 → ⑤使用捆绑脚本（thumbnail.py）生成预览、模板文件作为设计起点。Skill 的内容是实验对象，运行时可替换——只要具备「元数据目录 + 按需加载」机制即可。

**实验 2-7（"去 AI 味"写作 Skill）**：准备 3-5 篇原创文章 → Agent 生成初版 SKILL.md → 用新题目起草 → 人工修改 → 比较 before/after 并把稳定规律写回 Skill。验收：Skill 具备清晰的触发条件、3-5 条带示例的原则、作用域和例外——**不把一次主观判断当作普遍规则**。说明：Skill 的价值在于把个人经验外化为按需加载的指令；短小、可读、能通过真实任务检验的初版，比一开始罗列几十条规则更适合作为迭代起点。

## 四、Skills 与工具的关系

### 解决选择过载

Skills 对 KV Cache 极为友好：如果把所有专用代码工具的定义都放系统提示词，数量膨胀既耗 token 又干扰注意力；**Skill + 通用执行器**模式下工具数量始终很少（见 [[Coding Agent]]：仅需七个核心工具），Skill 内容经渐进式披露按需加载，不影响已缓存的前缀——**从根本上把"工具选择"问题转化为"知识检索"问题，后者正是大语言模型擅长的**。

### Skills 也可以经 MCP 被发现和传递

MCP 解决互操作（一次开发处处可用），Skills 解决组织与披露——**两者不是非此即彼**：Skills 负责组织和披露能力，也可以通过 MCP 被发现和传递；MCP 提供跨客户端互操作。一项能力做成专用 MCP 工具还是 Skill + 通用执行器，用三维决策框架（参数复杂度、变更频率、模型能力，详见 [[工具设计原则]]）。

### 模型原生工具 vs Skill：对谁友好

| | 模型原生工具发现 | Skills |
| --- | --- | --- |
| 格式 | JSON schema 规定输入输出，便于模型遵循与解析；一些推理引擎用限制采样强制格式 | 完全自然语言；模型需生成合法命令行参数并处理引号等转义（比 JSON 复杂，且 Linux/Mac/Windows 各不同） |
| 对模型 | 更友好 | 要求更高——参数复杂时更易出错；复杂结构化参数建议让 Agent 写成 JSON 文件再由命令行导入 |
| 对编写者 | 需要编程；schema 引号/花括号不匹配或缺字段会导致整个 Agent 无法运行 | **不会编程也能写**；修改是局部的，少量错误不会导致整个 Agent 崩溃 |
| 基础设施 | 需离线维护嵌入索引 + 语义匹配 | 靠通用文件阅读能力（grep、读文件）翻阅目录即可 |

**就像查工具书或维基百科**：没有人把整个维基百科从第一页读到最后一页，而是顺着索引和目录按需查阅词条。"发现"由模型在上下文里的实际需要驱动，而非任务开始时对初始查询做一次性预匹配。

**加载 Skills 后的 KV Cache**：加载 sub-skill 本质是往上下文插入一段内容，同样可放到末尾复用前缀。新特点：同一批 skill 会被反复、且在不同位置加载（跨会话、跨用户），每次随对话历史从头 prefill 成本不小——**可编辑、可组合的 KV Cache**（见 [[KV Cache]] 前沿一节）正是为此而生：每个 skill 的 KV 表示预编译缓存一次，RoPE 重定位"粘贴"到任意上下文位置，skill 从"一段每次都要重新 prefill 的文本"升级为"一个可复用、可组合的缓存对象"。

## 五、常见坑

> [!warning]
> - **description 写成功能介绍**："help with backend" 等于所有后端工作都触发，路由失准——要写成路由条件（何时用/何时不用/反例）。
> - **动态检索示例或 Skill 正文**：每次改写前缀 → 缓存持续失效；应为每类任务准备固定集合。
> - **不审查第三方 Skill**：Skills 是制度化化的注入面（见 [[提示注入]]），安装前像审查代码一样审查内容。
> - **把一次成功对话的摘要当 Skill**：Skill 是"何时用、怎么行动、何时停下确认、什么算完成"的操作手册，不是背景知识合集。
> - **规则堆成禁用词表**：应写成"作用域 + 动作 + 例外 + 验证方式"。
> - **初版贪多**：短小、可读、能通过真实任务检验的 20 行初版，胜过几十条规则的堆砌。
> - **忽略元认知问题**：渐进式披露依赖模型判断"需要什么"——如果模型不知道自己不知道什么，就无法正确触发加载；对弱模型需在 description 和路由提示上更用心。
