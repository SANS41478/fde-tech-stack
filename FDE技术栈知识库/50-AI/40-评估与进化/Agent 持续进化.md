# Agent 的持续进化

> [!abstract] 定位
> 今天的能力悖论：Agent 可以**零样本解决从未见过的复杂任务，却可能在处理了一万次相似任务之后，第二天仍然犯下第一天的错误**。能否自主从经验中学习，正在成为 Agent 从"会完成任务"走向"能够可靠工作"的关键能力。原因：部署后的模型不会因为一次推理自动改变参数；把对话存进记忆也不等于学会新行为——原始轨迹可能很长，既有有效策略，也有偶然成功、错误归因和不可信输入。**保存经历 ≠ 从经历中学习**：把一百条轨迹放进长上下文或向量库能帮助找回案例，却不会自动完成跨案例比较。学习发生在系统主动完成"**评价、对照、归纳、验证**"之后。若允许模型依据未经验证的反馈直接修改自身参数，错误经验和提示注入就可能被固化并持续放大。因此现阶段可行的路径：**把"学习"构建成模型外围的一套自主系统**——记录运行证据、验证结果与过程、从多条轨迹提取共性、再决定更新知识/指令/程序/参数；所有修改先形成待验证版本，经回归测试和安全检查后才改变下一轮运行。

---

## 一、从运行轨迹中获得学习信号

持续进化的起点不是"总结"而是"**评价**"——如果系统不知道任务是否完成、也不知道哪一步造成成功或失败，语言模型生成的反思只能是猜测。**错误的评价一旦进入长期知识、系统提示或训练数据，影响会跨越后续任务不断放大。**

- 有些任务结果容易验证：Coding Agent 可以运行测试、类型检查和性能基准；退款 Agent 可以查询订单状态和实际退款金额——**信号来自环境真实状态，通常比模型对自己行为的描述可靠**。但**结果正确不代表过程正确**：删除失败的测试用例也能让测试通过；口头承诺"7 天内退款"可能得到暂时满意反馈。**可靠评价既要看结果，也要检查达成结果的路径。**
- 更多任务没有单一正确答案（客服是否耐心、研究报告是否抓住关键证据、生成文本是否自然简洁）——用 [[Agent 评估]] 的 LLM-as-a-Judge，但**不能只给模糊总分**：预定义评价量表（Rubric），验证器逐项给分、引用轨迹证据、证据不足时明确表示不确定。

**三层轨迹验证结构**：

```text
结果验证器   测试结果、数据库状态、工具返回 —— "事情是否真的办成"
过程验证器   业务规则、权限、动作序列 —— "是否以允许的方式办成"
质量验证器   Rubric 逐项评分 + 证据位置 —— "是否办得合适"
            越靠下越应依赖代码和环境真值；只有难以形式化的部分交给语言模型
            证据不足时允许拒绝评分
```

**客服 Agent 的轨迹评价维度**（比"用户是否满意"更有诊断价值——用户可能因违规退款而满意，也可能因合规限制而不满，单一满意度无法区分）：

| 维度 | 验证问题 | 主要证据 |
| --- | --- | --- |
| 任务结果 | 核心诉求是否得到解决 | 最终环境状态、工具结果 |
| 规则遵从 | 是否违反政策、权限或必要流程 | 政策库、动作轨迹 |
| 隐私边界 | 是否泄露不应提供的信息 | 回复文本、数据访问记录 |
| 事实可靠性 | 陈述是否有知识或工具结果支持 | 引用来源、工具返回 |
| 承诺-行动一致性 | 声称完成的操作是否真实发生 | 回复与工具日志对照 |
| 表达质量 | 是否自然、简洁，避免重复与模板化 | 对话全文、语言 Rubric |
| 合规变通 | 原方案不可行时是否找到允许的替代路径 | 用户目标、政策与后续动作 |

实验 9-1：对照"只输出一个总分"和"逐维度输出结论、证据与置信度"——只有保留"哪里错、为什么错、证据在哪里"，后续模块才知道应更新知识、Prompt、程序还是模型参数；**低置信度案例不应自动进入学习集**。

## 二、Agent 持续进化的四种方法

学习信号说明"应当改变"，但没说明"改变应发生在哪里"。**能力的表示性质决定主要更新位置**——事实和经验适合写成知识文档；可用语言清楚表达的策略适合写入提示词或 Skill；可精确执行的流程与约束适合写成程序；感知、语言风格和隐式策略等高维能力必须进入模型参数。**不是单向阶梯，而是四种互补载体。**

| 更新方式 | 适合承载 | 主要优势 | 主要局限 |
| --- | --- | --- | --- |
| **经验知识库** | 事实、经验规律、例外与来源 | 更新快、可追溯、可按需检索 | 依赖检索和模型正确应用 |
| **Prompt 与 Skill** | 需要理解语境、例外和优先级，但仍能用自然语言说明的判断原则 | 可解释、作用范围可控 | 容易膨胀、冲突或被忽略 |
| **程序与 Harness** | 可确定解析、可执行验证和高风险硬约束 | 可测试、执行稳定、成本低 | 开发与维护成本较高 |
| **模型参数** | 高维感知、生成风格和隐式策略 | 泛化能力强、推理开销低 | 更新与回归成本高 |

同一能力可拆到多个载体：医疗影像 Agent 依靠参数识别病灶、知识库提供最新指南、代码计算风险指标；客服模型的自然语气来自后训练、具体企业政策由知识和 Skill 提供、关键合规由服务端代码兜底。**路由结果只是更新提案，尚未获得发布资格。**

### 2.1 将经验沉淀为知识

最轻量的进化方式：把多次运行中反复出现的经验整理成可检索的知识文档。**与第三章知识库的分工**：[[记忆系统]]/[[Agentic RAG]] 主要从用户对话、文档和数据集中提取"**用户与世界是什么样的**"；本章从 Agent 的行动轨迹和结果中提取"**在什么条件下应该怎样做**"——"该航空公司要求特殊餐食提前 24 小时预订"是领域知识；"**订票前先检查特殊餐食截止时间，避免付款后才发现无法满足需求**"是行动经验。

- 原始轨迹不适合作为正式知识单元（又长又嘈杂：工具原始输出、偶然绕路、环境细节）。**三层数据**：不可变的原始轨迹（审计）→ 单次运行分析（本次成败 + 经验草案）→ 多条同类轨迹比较、聚类、归纳 → 面向未来的 Markdown 知识文档。
- 正式文档写清：**适用场景、推荐策略、禁止做法、例外条件、证据来源、最近验证时间**——不是复述某一次任务的完整过程。
- 与 User as Code（[[记忆系统]]）相同的两阶段思路：先保存证据，再离线生成可变知识。**把记录与整理分开，避免一次偶发成功或网络故障立即改变 Agent。**
- **真正有迁移价值的内容来自对照**：同类成功轨迹做了什么、失败轨迹缺少什么；某种策略在哪些环境版本有效、哪些前置条件下失效。
- 五步知识提炼管道：①保存不可变轨迹和环境结果 → ②单次运行生成结构化分析（任务类型、所需能力、观察到的策略、错误与例外）→ ③按任务族聚合同类运行，为每条经验草案建立"哪些轨迹支持、哪些轨迹反驳"的证据表 → ④**只有达到支持门槛的草案才写入正式文档** → ⑤在未参与提炼的新任务上测试迁移效果。
- GAIA 经验学习：GAIA 是试卷（需综合搜索、网页阅读、文件处理和计算的多步问题），AWorld 是考场与实验记录系统。旧式做法：一次任务成功后立刻生成策略摘要向量化入库；更严格的实现：**先用 GAIA 答案验证或其他环境验证器标记成功、部分成功和失败，再比较同一任务族的多条路径**——成功轨迹贡献策略草案，失败轨迹贡献排除性知识，部分成功帮助识别"哪一段有效、哪一段仍有问题"。**Reflexion 的自然语言反思可以参与生成经验草案，但反思本身不是证据**——只有与环境结果相符、得到跨轨迹支持、并在新任务上显示正向迁移的内容，才应进入正式经验文档。
- 实验 9-2：比较"不使用历史经验"/"检索一条相似轨迹摘要"/"检索由多条轨迹共同支持的知识文档"——**经验不是"记住一次成功"；若文档不能提高未见任务的表现、或带来负迁移，就不能算学会了经验。**

### 2.2 将经验写成指令

知识库给 Agent "可以参考的资料"，Prompt 和 Skill 规定"**应该怎样行动**"。前提：**多条相似轨迹反复暴露同一种策略错误，且错误能够用语言清楚描述**。三个概念分开：**系统 Prompt 对所有任务生效；Skill 只在匹配到某个领域或工具时按需加载；程序/Harness 负责权限和其他硬约束。**

- **系统提示学习（System Prompt Learning，Karpathy）**：模型遇到问题后，用一句清楚的话提醒未来的自己。相关方法：DSPy 在开发集上搜索指令和示例；OPRO 根据历史提示词及其得分提出提示提案；GEPA 从失败轨迹的自然语言反思中生成并筛选提示提案——适合**离线批量优化**；生产环境更适合**可审计的最小更新提案** + 快速回滚路径。
- **与提示工程的区别**：[[Prompt 工程]] 讨论怎样组织一份好 Prompt；本节讨论**什么反馈足以触发修改、更新提案怎样安全发布**。修改应是**带来源的最小 diff**（最小 diff + 可回滚模式），不是让模型每次重写整份 Prompt——反复重写会让旧版本中的重要细节逐渐消失、相互制约的条件被合并成过度抽象的原则。待验证版本必须同时在**触发失败的边界集**（要改善）和**正常工作的保留集**（不能退化）上测试。
- **例子一：基于失败轨迹优化航空客服的系统 Prompt**（实验 9-3）：问题案例——用户对退票、改签费或行李政策不满，Agent 没查政策、没解释规则、没找允许的替代方案就调用 transfer_to_human。普通政策争议不需要转接；用户明确要求人工或出现安全/人身风险才必须转接。**问题不是"Agent 不够礼貌"，而是 Prompt 没写清转接边界**。诊断直接变成提示词规则：先查询并解释政策、识别用户真正想解决的目标、提供合规替代方案；只有在明确要求人工或超出权限/涉及安全时才转接。**Prompt 自动优化的重点不是让模型自由改写一大段文字，而是把可归因的失败转成作用域明确、可回滚、可验证的局部规则。**
- **例子二：需求澄清 Skill——从"直接开工"到"先确认再执行"**（实验 9-4）：用户说"把登录页改成支持企业登录"，Agent 立刻开工可能在身份提供商、回退方式、兼容旧用户和上线范围上替用户做尚未考虑过的选择；无论任务大小都先列十几个问题又把简单修改变成访谈。**问得太少导致返工，问得太多增加打扰**——Skill 要表达的不是"所有任务都必须确认"，而是一条**带作用域的判断路径**：先判断任务的歧义程度、风险和返工成本；低风险易撤销的小改动说明假设后直接执行；涉及架构、数据、权限、公开接口或大范围改动时集中提出少量真正会改变方案的问题；得到答案后生成短 Spec（目标、非目标、关键取舍、假设、验收标准）交用户确认；确认后执行，发现 Spec 不成立时暂停重新确认。持续进化从运行证据开始：**同时记录任务、澄清问题、Spec 版本、用户修改、执行结果和交付后的返工**。负反馈可能是"做出来的和我想象的不一样"，也可能是"你问得太多了"。**单独保存一句抱怨不足以触发更新，必须把反馈和具体轨迹、任务类型以及结果关联起来**。多条轨迹反复指向同一缺口才提出最小 Skill 更新提案（多个认证架构任务都在交付后才发现需兼容旧登录 → 规则草案要求执行前确认"身份提供商、回退路径和兼容范围"；大量拼写修复被先问一轮 → 规则应收窄高风险与高歧义的触发范围）。对照实验比较"直接执行"/"先提问再执行"/"提问后生成 Spec、确认后执行"三种策略按复杂度分层，指标至少包括需求偏差率、返工次数、澄清轮数、首次有效产出时间、用户放弃率、Spec 被修改比例、高风险操作错误率。**Skill 与 Harness 的边界**：Skill 负责理解语境主动提问、整理 Spec、说明取舍；Harness 负责在缺少确认时否决高风险写入、直接操作 main、绕过发布流程——Harness 的否决器不能替模型决定 PR 该怎么描述。随经验积累，稳定的对话轨迹还可进一步生成 SFT/RL 训练数据。

### 2.3 将经验写成程序

经验描述的是**稳定、重复且可验证**的操作时，每次都让模型重新阅读文档和推理并不经济——把经验**编译为工作流、工具或 Harness 代码**，使一次探索变成可重复执行的程序。本节关注的不是一般代码生成，而是 **Agent 如何根据自己的轨迹修改未来版本的自己**。可修改对象远不止新工具：操作层（浏览器轨迹编译为参数化工作流、为变化的 API 生成适配器）、控制层（修改工具路由、重试、熔断、上下文压缩策略）、验证层（根据生产失败新增参数检查、状态验证器、回归测试）、架构层（增加 Reviewer Agent、改变规划与执行的信息流）。

**浏览器工作流的生命周期**（类比电子表格宏录制）：
1. **捕获轨迹**：记录导航、点击、输入、下拉选择等动作，保存动作参数、当时 URL、XPath/CSS 等元素定位证据。**定位信息只用于再次寻找元素，不能证明任务已经完成。**
2. **参数化**：把首次运行中的字面量识别为模板变量——test@example.com、邮件主题、正文 → {recipient}、{subject}、{content}；其余稳定动作保持不变。
3. **定义状态检查**：为动作增加执行前检查和执行后检查（"发送按钮当前可见"）；为整个工作流增加最终状态检查。**动作执行成功与任务成功是两件事——最终状态检查必须读取真实页面或后端状态。**
4. **独立回放验证**：把沙盒账号或测试站点**重置到独立初始状态**，完整回放录制的程序；每一步的执行前检查、执行后检查和最终状态检查全部通过才能发布。
5. **匹配与回放**：新任务到来先在能力库按意图和关键词寻找工作流，提取参数，Playwright 直接执行——**回放路径不需要逐步调用 LLM**，但仍需等待元素可用并完成所有状态检查。
6. **失效与重学**：找不到目标元素、状态检查不通过、API Schema 改变或最终状态错误 → 回退到完整 Agent 模式重新探索。

PreAct 实验：这类程序在重复任务上实现 **8.5-13 倍端到端加速**，回放不逐步调用语言模型；更重要的结论：**流程记忆必须同时具备动作前验证、动作后验证和独立回放验证**——否则得到一种危险的假象：每个按钮都点过了，但某个字段其实为空，任务从未真正完成。

**Agent 修改自己的代码不意味着运行中的进程直接覆盖自身**——从当前稳定版本创建隔离更新分支，Coding Agent 生成最小补丁，依次通过静态检查、单元测试、安全扫描、失败轨迹重放和旧任务回归，再生成可灰度部署的新版本。**把"自我修改"转化为可审计的软件发布流程**（第九章与第五章的边界：第五章提供修改系统的能力，本章提供由经验触发、以验证闭环约束的自我修改方法）。

- **Git worktree + Pull Request**：Skill 应主动指导 Agent 先创建独立 worktree、确认需求和 Spec、实现与测试、提交有意义的 commit、在 PR 中写清背景/方案/测试结果/剩余风险；Harness 不替模型做判断，但可在它准备结束任务时检查是否仍在 main 直接提交、是否遗漏 worktree 或 PR——**违反边界就否决这次操作要求返回修复**。
- **变更契约**：仅有"补丁尽量小"不足以可靠归因——每个修改请求还应是一份**可证伪的变更契约**：列出失败证据、推断根因、归属的 Harness 组件、修改提案、预期修复的行为、可能受损的既有行为，以及分别验证两者的用例。Agentic Harness Engineering 的三层可观测性：**可编辑组件都有文件级表示；海量轨迹先整理为可逐层下钻的证据；每次编辑在执行前声明影响预测，再由下一轮结果验证**——分数上涨才能与某个具体机制建立联系。
- **提案生成器的输入不只失败案例**：Self-Harness 还提供必须保留的成功行为和此前被拒绝的修改记录——前者告诉 Agent 哪些性质不能在修复时破坏，后者避免换一种说法重复提交已失败的方案。**失败证据、成功约束与历史尝试构成有边界的方案空间**，比把全部源码和原始日志无差别塞给修改 Agent 更容易产生局部、可验证的改动。
- **工具创造遵循同一协议**（Alita 案例）：Agent 要从《指环王》咕噜配音演员解说的 YouTube 360 VR 视频中找出恐龙首次出现后紧接着提到的数字——发现自己缺少字幕读取能力后，搜索并测试 youtube-transcript-api，封装为新的字幕工具，最终得到答案 100000000。**只有安全扫描、功能测试和后续任务复用都通过，新工具才进入能力库。**
- 实验 9-6（由失败轨迹触发自我修改）：把"不可重试错误被反复调用"的经验写入重试与熔断程序——比较"只在 Prompt 中提醒不要重试"和"修改程序中的重试策略"；提案必须经过失败轨迹重放、正常故障回归和安全发布门槛，**不能修改验证器或稳定版本**。**能够确定性执行的约束应该进入程序，而不是继续堆在 Prompt 里。**
- 实验 9-7（高风险操作确认门禁）：多条用户纠正、点踩或事后审计都指向"高风险操作未经确认" → 生成确认门禁提案——用危险操作边界集和正常操作保留集共同评价：既要拦住未经确认的高风险调用，也不能阻断正常任务；**生成提案的 Agent 无权修改安全测试和批准规则**。**安全能力的进化不能由修改者自证成功。**

**案例：DeepSeek Harness 以"一切皆插件"实现自我进化**——Cordis 底座指出：传统组合是静态的（函数调用、模块导入、类继承在编译期确定），插件系统和自进化 Harness 需要的是**动态组合**——组件在运行中被装入、卸下和重新配置；Agent 的每一次自我修改本质上都是一次动态组合。两个正交维度：**时间可组合性**（一个组件被移除时，它对共享环境做过的修改能否被完整、安全地撤销——要求运行时追踪它的每一次资源分配、事件注册和状态变更）与**空间可组合性**（组件之间能否以结构化、可验证的方式声明、发现和解析彼此的依赖，并在依赖变化时协调生命周期）。自进化 Harness 的困难：要撤销的副作用是**长期存活、带状态的**；要解析的依赖会**在运行中出现、消失或改变身份**。Cordis 把两个编译期概念提升到运行时：**效果系统**（推理"计算如何修改环境"）提升为**可撤销效果**——每次对上下文的变换都携带显式的逆操作，由运行时追踪，组件移除时上下文随之恢复；**协效果系统**（推理"计算对环境有什么要求"）提升为**反应式协效果**——组件把自己需要的依赖声明成规格，上下文每次变化都按规格通知它激活、失活还是无关；再用动态组合演算把性质推广到相互交错的组件系统（**可组合性必须是可传递的**）。**自我进化的上限，不取决于模型能写出多好的代码，而取决于承载它的系统具有多强的可组合性**——这也是 dsh 让模型适配器、工具注册表、会话日志乃至 Agent 主循环本身都成为插件的原因：不存在一个只能由人类维护的特权内核。另两笔账：模型写出的插件只活在进程内存里、重启即消失——要留下来必须走 worktree + PR 的更慢的路；**进化本身有代价——运行中的插件会改变模型可见的工具集和提示片段，请求前缀一变 KV Cache 就从变化处开始失效**（见 [[KV Cache]]），dsh 插件的说明文档需要专门描述对上下文和 KV Cache 的影响。

### 2.4 将经验写入参数

知识、指令和程序都建立在前提上：目标能力能被外部符号较完整地表达。**医疗影像理解、自然的语音韵律、消除文本的模板化"AI 味"、长程规划等能力很难压缩成几条规则或工作流**——必须通过后训练写入模型参数。弯引号的作用域判断处在中间地带：文档语法边界可以由程序解析，语境和例外需要 Skill 表达，跨任务的识别习惯才适合通过后训练内化。**是否参数化并不由"任务是否长期稳定"单独决定**——新影像设备带来的域偏移仍可能需要 LoRA 或持续微调；快速变化的语言风格也可以通过周期性偏好训练适应。**稳定性影响的是更新频率和成本，真正决定主要载体的是能力的表示性质。**第八章已完整讨论 SFT、蒸馏和 RL；对持续进化而言关键是把**经过评价**的生产轨迹转化为训练数据：高质量示范进 SFT，明确偏好形成成对数据，具有可靠环境奖励的交互用于 RL。

### 2.5 从更新产物到更新"更新方法"

正交的一条轴：系统正在优化的究竟是**某份产物**的内容，还是**产生、管理和验证这些产物的方法**。优化对象可逐层扩大：单条规则或记忆 → 结构化上下文 → 工作流 → Harness 代码 → 产生更新提案的优化器代码。**这不是五种新载体，而是五种不同的搜索尺度**；知识、Prompt、Skill 和程序都可能出现在其中多个层级。

- **最内层——只修改产物内容**：根据失败轨迹给系统提示增加一条局部规则、给经验文档补充例外条件。作用面小、易归因回滚，**应当是默认选择**。但反复让模型重写整份 Prompt 或记忆会产生另一类退化：为追求简洁，旧版本中少数重要细节在多轮改写后逐渐消失；相互制约的条件被合并成一句过度抽象的原则。**Agentic Context Engineering（ACE）**：把上下文维护成**带稳定标识符的条目集合**，由生成、反思和整理模块提出增量更新，再用确定性逻辑合并与去重——而不是每轮重写一个越来越短的文本块。这是"最小 diff、保留来源"原则的具体研究实例。
- **外一层——优化"上下文应怎样被构造"**：**Meta Context Engineering（MCE）**拆成内外两个循环——内层在给定管理方法下优化当前任务的上下文产物；外层根据多轮执行和验证结果，修改**搜索、选择、过滤、格式化这些上下文操作本身**。修改一条检索规则是改内容管理机制；让系统比较多种检索与整理机制、保留迁移效果更好的版本，才是学习"如何管理上下文"。
- **扩展到工作流和整个 Harness**：**AFlow** 把由多个 LLM 调用组成的工作流表示为代码图，通过执行反馈搜索节点与控制流的组合；**Meta-Harness** 让 Coding Agent 读取待验证 Harness 版本的源码、分数和轨迹，搜索决定信息如何存储、检索和呈现的代码。代码不只是一次生成的产物，还可以**连同评估历史一起成为持续搜索的对象**。
- 实验 9-8（把这本书交给 Hermes：它能升级自己吗？）：不给 Agent 预设修复目标，观察它能否把书中的原则映射到自己的代码，并根据 Reviewer 的退回意见继续修正；稳定版本、验收测试和批准门槛始终在它的修改权限之外。**自我修改不是"模型读完资料后直接改代码"，而是"理解原则 → 提出更新提案 → 接受外部检验 → 根据反馈修正"的闭环；一次提案被接受只能证明更新流程成立，不能自动证明下游能力已经提升。**

## 三、构建可长期运行的持续进化闭环

四种更新方式只有进入同一个自主循环，才会从单次优化变成持续进化。**生产系统更稳妥的双循环结构**：

```text
在线执行循环：稳定版 Agent 处理真实任务 → 只记录轨迹与反馈，不改写正式版本
        ↓ 版本化经验日志
离线进化循环：聚合与诊断（寻找共同根因）→ 候选修改（知识·指令·程序·参数）
        → 回归与安全验证（保留旧能力）→ 灰度、监控与回滚 → 晋升为新稳定版
        ↓ 通过验证的新版本进入下一轮运行
可信根：权限、审计、验证与回滚机制不由普通进化流程自行修改
```

**Voyager 展示了较完整的持续进化循环**（Minecraft）：根据当前能力选择新目标（**自动课程生成器**——使探索不是随机漫游）→ 通过环境反馈迭代程序 → 验证成功后把代码存入技能库（**可检索、可组合**——高级采集技能调用移动和制作等基础技能）→ 组合旧技能解决更难任务（**迭代提示机制**把环境观察、执行错误和自验证结果带回下一轮代码生成直到任务真正通过）。**自动课程、可执行技能和环境验证缺一不可**：只有技能库没有课程不知道下一步学什么；只有自我反思没有环境验证技能库会积累错误；只有探索没有持久化每次任务仍要从头开始。**发现循环：假设、实验、评估、反馈**——数百年来逐渐形成的科学方法；Jeff Dean 等人的 Discovery Loop 旨在把它推向自动化（提出实验、实现实验、开展评估、取得结果、把结果交给下一轮）。Agent 自我进化要避免自说自话、自我感觉良好，**必须遵循科学方法**。

**区分两种经常混在一起的能力**：**Harness 更新能力（harness-updating）**——从轨迹中产生有价值的持久修改；**Harness 受益能力（harness-benefit）**——任务 Agent 在后续运行中找到、激活并正确使用这些修改。一个 Skill 可能写得完全正确，但较弱的任务模型没有在合适场景加载它、或加载后无法长期遵循——任一种都会让最终成绩看起来"没有进化"。**不能只用端到端分数反推更新器好坏。**

**分层评估指标**：

| 指标 | 回答的问题 | 主要证据 |
| --- | --- | --- |
| 更新提案有效率 | 更新器是否提出了有价值的修改 | 提案在独立验证中的接受率与增益 |
| 产物激活率 | 任务 Agent 是否在正确场景加载了新 Skill、记忆或工具 | 检索、路由与工具调用轨迹 |
| 遵循成功率 | 激活后是否按新规则或流程执行 | 动作序列与过程验证器 |
| 保留任务集增益 | 整体是否改善了未参与进化的任务，是否有泛化能力 | 保留集成功率、质量与成本 |

**长期评价至少观察五类结果**：①**回退**（regression）——新经验是否与已有经验冲突，原本能通过的案例是否退化；②**泛化能力**——测试集未覆盖场景中的提升；③**Token 效率**——完成任务的成本；④**安全性**——规则、隐私和拒绝边界是否随进化漂移；⑤**长期工程质量**——维护复杂度、架构一致性、所有权边界、向后兼容、未来迁移调试负担是否恶化。**只解决了当前失败案例却在其他已有案例或新领域中退化，不是成功的持续学习。**

## 四、可验证闭环的边界：当"完成"不等于"进步"

闭环在 Coding、工具调用和业务状态变更等任务上最容易成立——测试、环境状态或确定性规则能快速给出反馈。**开放式科研、战略规划和复杂产品设计则不同**：评价信号来得慢、正确答案不唯一，研究品味、长期价值、可维护性等真正重要的目标很难用分数评判——Harness 可能把流程执行得非常完整，却只是稳定地产出"像成果的东西"。

**自动科研的压力测试**（Trehan & Chopra 记录四次端到端尝试，三次在实现或评估阶段失败）：三类问题——①**实现漂移**：原方案一旦变难，Agent 逐渐退回训练数据中更熟悉、但已偏离研究假设的普通实现；②**认识论上的过度乐观**：信号仍可能只是噪声，系统却开始解释结果、添加补丁并宣布发现；失败和阴性结果更容易被忽略；③**隐性判断力不足**：Agent 可以运行实验，却未必知道什么基线真正重要、哪个异常值得追踪、何时应该放弃假设。

**对策——改变证据和监督结构**：
1. **结论与证据分离**：对引用、数字、方法和结论分别记录证据来源，最终文稿只是证据图的一种呈现（ScientistOne 的 Chain-of-Evidence 把每类声明链接到可审计来源——提高可追溯性，并不自动保证研究问题有价值）。
2. **保留负面结果**：失败实验、被拒提案和停止原因写入日志——否则进化模块只看到幸存方案，会反复探索已经证伪的路径。
3. **维护搜索多样性**：不只保留当前得分最高的一条链——备选方案池保留若干暂时低分但类型不同的分支，避免所有方案收敛成同一个易得分模板。
4. **让人类在更高层介入**：人的作用不只是危险工具调用前点"批准"，还包括**定义问题、审查评价标准、解释反常结果和决定何时停止**。

## 五、持续进化的安全边界

Agent 的自我进化能力可能把一次错误变成长期风险：网页、邮件和工具输出中的提示注入若被总结成经验，可能跨会话反复生效；自动搜索的恶意软件包若被封装成工具，影响从一次沙盒运行扩散到所有后续任务；**一个有缺陷的验证器可能持续批准看似进步、实际退化的待验证版本**。除了验证"是否更强"，还必须限制"**谁能改什么、依据来自哪里**"：

1. **证据与指令隔离**：原始网页、工具输出及其 LLM 摘要都属于**不可信证据**——不能当作指令执行，也不能直接纳入 Skill 等长期能力。**LLM 总结只是为了提高可读性的转换，不是把输入变得无害的净化过程。**系统按固定 schema 提取主张、原文位置和采集时间，同时保留原文与来源；提取出的字符串绝不能作为指令执行；模型给出的置信度只是未经验证的估计，不能充当批准门槛。待发布内容通过确定性的 schema、允许列表和来源检查，以版本化的 pull request 提交；独立于生成者的 reviewer 对照原始证据审查变更；高风险 Skill 上线前经过人工批准。
2. **待验证能力与正式能力隔离**：新知识、Prompt、Skill、程序和参数都先进入**不可服务真实流量的待验证区**。新生成的代码和外部依赖还要经过沙盒、权限检查、供应链扫描与行为测试等安全检查；通过后才服务真实流量成为正式能力。
3. **安全机制不可自我修改**：业务 Agent 可以修改 Prompt、Skill、知识库、工具等，**但不能修改批准自身更新的验证器、测试用例、发布门槛、审计日志和稳定版本备份**——否则一个 Agent 只需降低测试阈值或删除失败用例，就能把退化伪装成进步。真正的保证必须来自被修改者无法触及的那一层（与 [[Harness 工程]] 数据层护栏同理）。

## 六、睡眠学习：整合、遗忘与能力保鲜

"睡眠学习"是对离线整合的认知类比（不要求任务真的在夜间运行）。**在线 Agent 的首要职责是完成当前任务并追加不可变证据**；后台学习进程在空闲期或满足门控条件时读取一批新经历，比较新旧结论、合并重复项、解决冲突、提出更新提案并运行回归。**把采集与整理分开，可以防止一次偶发成功、网络故障或恶意输入立刻改写长期能力**，也允许系统使用更大的批量和更便宜的模型完成整理。

**典型的睡眠学习周期五步**：
1. **触发**：达到时间间隔、新增轨迹数量、存储容量或错误频率门槛，并确认当前没有高优先级在线任务；
2. **定向**：读取正式知识、Prompt、Skill 目录及其版本，了解已有能力和不可修改边界；
3. **采集与整合**：从近期已评价轨迹中寻找新信号，合并重复内容，标记冲突与适用条件，优先生成局部补丁；
4. **验证与审批**：在迁移集、保留集和安全集上评估待验证版本，高风险写入等待人工批准；
5. **修剪与索引**：更新检索索引，把长期不用或被新证据推翻的能力标记为过期，或归档、删除，同时保留来源和回滚版本。

**用户记忆是最直观的例子**（但注意与行动经验区分）：Claude Code 的自动记忆为每个项目维护 MEMORY.md 索引和按主题拆分的详细文件——会话启动只加载**索引的有界前缀**，其余按需读取；索引接近上限时系统要求 Agent 合并或移走细节。说明纯文本记忆也需要**容量约束、分层加载和主动整理**（当前公开机制主要是在会话中持续写入，不能简单等同于固定的夜间后台任务）。

**Hermes 是更完整的后台记忆进化案例**：长期信息分成有界的 MEMORY.md 与 USER.md、基于 SQLite/FTS5 的历史会话检索、按需加载的 Skill、可选外部记忆提供者。**历史检索返回原始消息而非先由 LLM 摘要**——避免把检索和生成混成一个不可审计步骤。当一次任务包含较多工具调用、从错误或死路中恢复、收到用户纠正，或发现非显而易见的工作流时，后台复盘创建或局部修订 Skill；记忆和 Skill 写入可经过审批门控。**独立的 Curator 跟踪 Skill 的使用、陈旧和归档状态**，在空闲期执行确定性修剪、可选运行 LLM 合并；变更前保存快照，错误整理可回滚。

**持续进化不是让知识、Prompt 和工具无限增长**——[[上下文工程]] 的上下文腐化会在更长时间尺度上重现：经验文档相互冲突、Prompt 被边界规则淹没、Skill 库出现重复能力、多次微调造成灾难性遗忘。**周期性离线整理清单**：
- 合并重复经验，保留来源和版本；
- 把局部规则从全局 Prompt 移动到领域 Skill，保持全局 Prompt 整洁；
- Prompt 和 Skill 保持结构清晰；
- 重新验证长期未使用的工具；
- 删除被新证据推翻的知识；
- 从原始基座模型重新训练 LoRA。

## 七、常见坑

> [!warning]
> - **保存反馈 ≠ 持续进化**：继续使用已废止规则、靠违规捷径完成任务、更新后破坏原有能力，都不算学会。
> - **用户满意度当唯一信号**：满意度上升但规则违规率也上升是失败；要有护栏指标。
> - **反馈直接追加到 Prompt**：应识别作用域、提最小指令更新、独立评价后发布。
> - **反思当证据**：Reflexion 式自然语言反思可以生成草案，但没有环境验证就不是证据。
> - **只看端到端分数反推更新器好坏**：Skill 写得对但没被加载/遵循 = 没进化；分层评估。
> - **经验知识库无限增长**：检索错误与知识冲突抵消学习收益——需要版本、时效与淘汰机制。
> - **进程内直接覆盖自身**：自我修改必须走分支 + 测试 + 灰度的发布流程。
> - **验证器可被进化流程修改**：降低测试阈值就能把退化伪装成进步；可信根不可自我修改。
> - **理解债与认知投降**：Agent 交付越快，人对系统的理解落后越远——"你可以外包你的思考，但不能外包你的理解"。管理 Agent 像管理技术员工：既不能越俎代庖，也不能放手不管。
