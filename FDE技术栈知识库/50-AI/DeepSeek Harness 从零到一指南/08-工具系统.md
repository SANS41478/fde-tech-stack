# 工具系统 — 工具注册、调度、执行

> [!tip] 目标
> 理解工具如何被注册、LLM 如何选择工具、工具如何被安全执行。

---

## 1. 工具是什么

> [!tip] 类比
> 工具 = 一个**有说明书的函数**
>
> 说明书告诉 LLM："我能做什么，你需要提供什么参数"
>
> 函数体告诉程序："收到参数后，具体执行什么操作"

每个工具由两部分组成：

```
工具 = Schema（说明书）+ Execute（执行函数）

Schema:
{
  "name": "bash",
  "description": "在终端中执行命令",
  "parameters": {
    "command": { "type": "string", "description": "要执行的命令" }
  }
}

Execute:
async function bash执行(command) {
  // 实际在终端执行命令
  return 执行结果
}
```

---

## 2. 工具注册表（ctx.tools）

> [!tip] 类比
> 工具注册表 = 工具箱里的**清单**
>
> 清单上写着：这个工具箱里有哪些工具，每个工具能做什么

注册一个工具：

```typescript
ctx.tools.register('bash', {
  schema: {
    name: 'bash',
    description: '在终端中执行命令',
    parameters: {
      command: { type: 'string', description: '要执行的命令' }
    }
  },
  execute: async (args) => {
    const result = await 执行命令(args.command)
    return { content: result }
  }
})
```

注册后，LLM 就能看到这个工具：

```
LLM 收到的工具列表：
├── bash - 在终端中执行命令
├── read_file - 读取文件内容
├── write_file - 写入文件内容
├── search - 搜索网页
└── ... 其他工具
```

---

## 3. 工具如何被 LLM 调用

LLM 看到工具列表后，决定使用哪个工具：

```
用户："帮我查看当前目录的文件"
  │
  ├─ LLM 分析：需要执行 ls 命令
  │
  ├─ LLM 生成工具调用：
  │  {
  │    "type": "tool-call",
  │    "name": "bash",
  │    "arguments": "{\"command\": \"ls\"}"
  │  }
  │
  └─ 这个调用被发送给 Agent Loop 执行
```

> [!note] LLM 不直接执行工具
> LLM 只是**生成一个工具调用请求**，实际执行由 Harness 的工具系统完成。这是安全隔离的关键。

---

## 4. 工具执行 Pipeline

工具执行不是简单的"调用函数"，而是一个完整的 pipeline：

```
LLM: "请执行 bash 命令 ls"
  │
  ├─ [1] 解析参数
  │      arguments: { command: "ls" }
  │
  ├─ [2] 检查执行模式
  │      ctx.tools.executionMode() → exclusive（串行）
  │      意味着不能和其他工具并行执行
  │
  ├─ [3] pre-execute（执行前检查）
  │      │
  │      ├─ 审批系统：这个命令需要人类确认吗？
  │      │   → 如果是危险命令，暂停等待用户批准
  │      │
  │      ├─ 沙箱系统：这个命令在什么环境中执行？
  │      │   → 本地 / Docker / 远程沙箱
  │      │
  │      └─ 策略检查：这个命令被允许吗？
  │          → 文件系统策略、网络策略等
  │
  ├─ [4] dispatch（实际执行）
  │      在终端执行 ls 命令
  │
  ├─ [5] post-execute（执行后处理）
  │      │
  │      ├─ 记录执行结果到 Session Log
  │      ├─ 更新工具状态
  │      └─ 生成额外上下文（如文件变化）
  │
  └─ [6] 返回结果
         content: "file1.py  file2.py  folder1/"
         isError: false
         meta: { ... }  // 工具私有的展示数据
```

---

## 5. 执行模式：Exclusive vs Parallel

工具执行有两种模式，就像交通规则：

### Exclusive（串行）— 单行道

```
工具 A 执行 ──────→ 完成
                      工具 B 执行 ──────→ 完成
                                        工具 C 执行 ──────→ 完成
```

**适用场景**：
- Bash 命令（不能同时执行两个命令）
- 文件写入（避免竞争条件）
- 任何有副作用的操作

### Parallel（并行）— 多车道

```
工具 A 执行 ──────→ 完成
工具 B 执行 ──────→ 完成
工具 C 执行 ──────→ 完成
```

**适用场景**：
- 读取操作（读文件、读数据库）
- 网络请求（搜索多个网站）
- 无副作用的操作

**控制参数**：`maxParallelToolCalls`（最大并行工具调用数）

---

## 6. 工具调度器

> [!tip] 类比
> 工具调度器 = 交通指挥中心
>
> 它决定：
> - 哪些工具可以同时执行（parallel）
> - 哪些工具必须排队（exclusive）
> - 并行执行时最多同时跑几个（maxParallelToolCalls）

在源码中（`tool-calls.ts:121-246`），调度器的工作：

```
runGroup()
  │
  ├─ 如果是 parallel 模式：
  │   启动多个工具（受 maxParallelToolCalls 限制）
  │   等待任意一个完成
  │   按顺序提交结果（模型顺序）
  │   继续启动下一个
  │
  └─ 如果是 exclusive 模式：
      等待当前工具完成
      等待 pool 清空
      执行下一个工具
```

## 7. 工具结果的处理

工具执行完成后，结果通过以下路径返回：

```
工具执行完成
  │
  ├─ [1] 记录 tool/result 到 Session Log
  │      包含：内容、是否错误、元数据
  │
  ├─ [2] 生成 ToolResultMessage
  │      这是 LLM 能理解的格式
  │
  ├─ [3] 通过 acceptContext 放入 next-step 队列
  │      等待 Agent Loop 在下一步处理
  │
  └─ [4] Agent Loop 在下一步取出结果
         作为上下文发送给 LLM
         LLM 看到结果后决定下一步
```

## 8. 工具的 UI 展示

每个工具有一个**展示意图**（presentation intent），告诉 UI 如何显示结果：

| 展示类型 | 用途 | 例子 |
|---|---|---|
| `generic` | 通用展示 | 搜索结果 |
| `terminal` | 终端输出 | bash 命令结果 |
| `diff` | 代码差异 | 文件编辑结果 |
| `locations` | 位置列表 | 搜索文件位置 |

## 9. Code Mode — 批量工具调用

Harness 有一个特殊模式叫 **Code Mode**，模型不是逐轮调用工具，而是生成一段**多步程序**：

```
普通模式：
  LLM: "执行 bash 命令 A"
  执行 A → 结果返回
  LLM: "执行 bash 命令 B"
  执行 B → 结果返回
  LLM: "执行 bash 命令 C"
  执行 C → 结果返回

Code Mode：
  LLM: "执行以下程序："
  {
    "steps": [
      { "tool": "bash", "args": "命令 A" },
      { "tool": "bash", "args": "命令 B" },
      { "tool": "bash", "args": "命令 C" }
    ]
  }
  → 一次性执行 A、B、C
  → 结果一起返回
```

> [!note] 源码位置
> `packages/core/tools/src/code-mode.ts` — Code Mode 的实现

每个子调用有独立的事件记录：

```
tool/code-dispatch-start → 子调用开始
tool/code-dispatch       → 子调用完成
```

## 10. 安全机制

工具系统有多层安全机制：

```
用户请求
  │
  ├─ [1] 审批系统
  │      危险操作 → 暂停 → 等待用户批准
  │
  ├─ [2] 沙箱隔离
  │      所有操作在沙箱中执行
  │      限制文件访问、网络访问等
  │
  ├─ [3] 策略检查
  │      文件系统策略：只能访问工作目录
  │      网络策略：只能访问白名单域名
  │      进程策略：不能嵌套执行
  │
  └─ [4] 超时控制
      工具执行超时 → 自动终止
```

> [!warning] 安全第一
> 工具系统的设计原则是**默认安全**：不确定的操作会被拒绝，而不是被允许。

## 小结

| 概念 | 一句话解释 |
|---|---|
| 工具 | 有说明书的函数 |
| 注册表 | 工具箱清单 |

| 调度器 | 决定工具执行顺序的指挥中心 |
| 执行 Pipeline | 检查 → 执行 → 记录 → 返回 |
| Code Mode | 批量执行多步操作 |
| 安全机制 | 审批 + 沙箱 + 策略 + 超时 |
