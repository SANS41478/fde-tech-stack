# 理解你每天在用的东西

> [!tip] 目标
> 从你作为**用户**的体验出发，倒推 Agent 工具内部在做什么。让你建立"我打字时，背后发生了什么"的直觉。

---

## 1. 你打字时发生了什么

当你在 Agent 工具（比如 Claude Code、Cursor、DeepSeek Chat）里输入一句话并按回车，发生了以下事情：

```
你输入："帮我修复 login 函数的 bug"
         │
         ▼
┌─────────────────────────────────────────────┐
│  第 1 步：消息进入队列                         │
│  你的文字被放入一个"待处理消息队列"              │
└────────────────────┬────────────────────────┘
                     ▼
┌─────────────────────────────────────────────┐
│  第 2 步：组装上下文                           │
│  把以下内容拼在一起：                          │
│  - 系统提示（Agent 的人格和规则）               │
│  - 历史消息（之前你说过什么、Agent 做过什么）     │
│  - 你的新消息                                 │
│  - 可用工具列表（每个工具的名称和描述）          │
└────────────────────┬────────────────────────┘
                     ▼
┌─────────────────────────────────────────────┐
│  第 3 步：发送给 LLM                          │
│  把组装好的上下文发给 DeepSeek/OpenAI 的服务器  │
│  （这一步需要几秒钟）                          │
└────────────────────┬────────────────────────┘
                     ▼
┌─────────────────────────────────────────────┐
│  第 4 步：LLM 返回回复                        │
│  可能是：                                     │
│  A. 直接文字回答                              │
│  B. 工具调用请求（"我需要用 bash 执行..."）     │
│  C. 混合（一部分文字 + 一部分工具调用）          │
└────────────────────┬────────────────────────┘
                     ▼
         ┌───────────┴───────────┐
         │                       │
         ▼                       ▼
    直接回答                  工具调用
    → 返回给你                → 执行工具
                               → 拿到结果
                               → 回到第 2 步
```

## 2. Agent 工具的四种运行模式

DeepSeek Harness 有四种模式，对应不同复杂度的使用场景：

### 模式 1：Standard（标准模式）

> [!tip] 类比：全功能 IDE
> 就像 Visual Studio Code——什么都能做：
> - 完整的工具集（bash、文件编辑、搜索、终端...）
> - 可以创建子 Agent
> - 可以加载 Skill
> - 有 Goal 追踪
> - 有审批系统

**适合**：日常开发、复杂任务

### 模式 2：Code（代码模式）

> [!tip] 类比：批量处理
> 就像写了一个脚本一次性执行多个步骤：
> - 模型生成一段**多步程序**
> - 程序一次性编排多轮工具调用
> - 不需要逐轮交互

**适合**：重复性任务、批量处理

### 模式 3：Minimal（最小模式）

> [!tip] 类比：只给一支笔和一张纸
> 只有最基本的工具：
> - Bash（执行命令）
> - 文本编辑器
> - 没有技能、没有子 Agent、没有 Goal

**适合**：测试模型本身的推理能力

### 模式 4：Creator（创建者模式）

> [!tip] 类比：开发者调试模式
> 可以实时检查和实验插件：
> - 运行时检查 Agent 状态
> - 实时挂载/卸载插件
> - 调试工具执行流程

**适合**：开发者调试 Harness 本身

## 3. 一条消息的完整生命周期

让我们跟踪一条消息从输入到输出的完整过程：

```
用户输入："帮我创建一个 Python 脚本"
  │
  ├─ [1] 消息进入 Inbox（消息队列）
  │      存储在 next-turn 队列中
  │
  ├─ [2] Agent Loop 唤醒
  │      检测到有新消息，启动一个"轮次"（turn）
  │
  ├─ [3] preStep：组装上下文
  │      系统提示 + 历史 + 工具列表 + 新消息
  │      插件可以在这一步注入额外上下文
  │
  ├─ [4] 调用 LLM
  │      发送组装好的上下文给 DeepSeek API
  │      流式接收 token（逐字显示）
  │
  ├─ [5] LLM 返回：工具调用
  │      "我需要使用 bash 工具创建文件"
  │      参数：command = "echo 'print(1)' > hello.py"
  │
  ├─ [6] 执行工具
  │      在终端执行命令
  │      结果：文件创建成功
  │
  ├─ [7] 工具结果放入 next-step 队列
  │      等待下一步处理
  │
  ├─ [8] 回到第 3 步（新一步）
  │      组装上下文（包含工具结果）
  │
  ├─ [9] 调用 LLM
  │      LLM 看到工具结果
  │
  ├─ [10] LLM 返回：直接回答
  │       "我已经创建了 hello.py 文件，内容是 print(1)"
  │       没有工具调用 → 循环结束
  │
  └─ [11] 回复返回给用户
```

## 4. 你在屏幕上看到的 vs 实际发生的

| 你看到的           | 实际发生的                         |
| -------------- | ----------------------------- |
| "思考中..."       | Agent 正在组装上下文并调用 LLM          |
| 逐字出现的文字        | LLM 流式返回 token，每个 token 是一个事件 |
| "正在执行 bash..." | 工具执行 pipeline 正在运行            |
| 最终回复           | LLM 在看到工具结果后生成的最终回答           |

> [!note] 源码对应
> - 逐字显示 → `assistant/chunk` 事件（每个 token 一个事件）
> - "正在执行" → `tool/call` 事件
> - 工具结果 → `tool/result` 事件
> - 最终回复 → `assistant/message` 事件

## 5. Session Log：你可能没注意到的细节

每次你和 Agent 对话，Harness 都在后台记录一个**完整的事件日志**：

```
事件 1: turn/start     { turn: 1 }
事件 2: user/message   { content: "帮我创建一个 Python 脚本" }
事件 3: step/start     { turn: 1, step: 1 }
事件 4: assistant/chunk { chunk: "我" }
事件 5: assistant/chunk { chunk: "需要" }
事件 6: assistant/chunk { chunk: "使用" }
...
事件 N: assistant/message { message: {内容} }
事件 N+1: tool/call    { name: "bash", arguments: "..." }
事件 N+2: tool/result  { content: "文件创建成功" }
事件 N+3: step/end     { turn: 1, step: 1 }
事件 N+4: step/start   { turn: 1, step: 2 }
...
事件 M: turn/end       { turn: 1, reason: "completed" }
```

**为什么要记录这么详细？**
1. **回放**：可以重放整个对话，精确到每个 token
2. **恢复**：程序崩溃后可以从日志恢复
3. **调试**：出了问题可以看日志找出哪一步出错
4. **分析**：可以分析 Agent 的行为模式

> [!abstract] 核心不变量
> **Model-visible ⟺ logged**：模型看到的每一样东西，都必须记录在日志里。这是 Harness 的核心设计原则。

## 6. 工具执行的细节

当 LLM 请求使用工具时，发生了什么：

```
LLM: "我需要用 bash 工具执行 ls 命令"
  │
  ├─ [1] 解析工具调用
  │      name: "bash"
  │      arguments: { command: "ls" }
  │
  ├─ [2] 检查执行模式
  │      exclusive（串行）还是 parallel（并行）？
  │      bash 工具通常是 exclusive（不能同时执行两个命令）
  │
  ├─ [3] pre-execute（执行前检查）
  │      审批系统：这个命令安全吗？需要人类确认吗？
  │      沙箱系统：这个命令在隔离环境中执行吗？
  │
  ├─ [4] 执行
  │      在终端实际执行 ls 命令
  │
  ├─ [5] post-execute（执行后处理）
  │      记录执行结果
  │      更新工具状态
  │
  └─ [6] 结果返回
         content: "file1.py  file2.py  folder1/"
         isError: false
```

## 7. 为什么 Harness 这么复杂

你可能会问：一个聊天工具为什么需要 54 个包？

答案是：**因为真正的 Agent 需要处理的问题比你想象的多得多**：

| 问题 | 简单聊天工具 | DeepSeek Harness |
|---|---|---|
| 对话中断怎么办 | 丢失 | 从 Session Log 恢复 |
| Agent 做了危险操作 | 无法阻止 | Sandbox + 审批系统 |
| 任务太复杂做不完 | 放弃 | Goal 系统追踪进度 |
| 需要不同类型的 Agent | 不支持 | Preset 系统组合不同配置 |
| 工具执行失败 | 报错 | 重试 + 错误恢复 |
| 上下文太长 | 截断 | Compaction 压缩 |
| 多人协作 | 不支持 | 子 Agent 委派 |
| 模型换了 | 不支持 | Provider 适配器 |

> [!tip] 简单类比
> 简单聊天工具 = 功能手机（只能打电话发短信）
>
> DeepSeek Harness = 智能手机（可以装任何 App）

## 小结

- 你输入的每一句话，都经过了：消息队列 → 上下文组装 → LLM 调用 → 工具执行 → 结果返回
- Session Log 记录了每一步，确保可回放、可恢复
- 工具执行有完整的 pipeline：检查 → 执行 → 记录
- Harness 的复杂性来自于它要处理的真实世界问题
