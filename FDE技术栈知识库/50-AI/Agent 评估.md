# Agent 的评估

> [!abstract] 定位
> 构建完成不等于构建正确——**只有能够稳定测量结果，后续的模型训练和系统进化才有可靠方向**。评估提供科学的决策依据：通过**对比实验**（改变一个变量观察效果）和**消融实验**（逐一关闭组件观察整体性能）区分真正的能力提升与表面波动。从 Harness 视角，评估是"验证"功能的核心。**关键认识：评估对象是模型与 Harness 的组合体**——同一模型在不同 Harness 中表现差异悬殊；表现不佳时先区分"模型能力不足"还是"Harness 设计缺陷"（方法：固定 Harness 换模型 / 固定模型消融 Harness）。**评估体系的首要价值不是打分，而是让你能快速、可靠地跟上模型演进**——有评估体系的团队数小时内得出切换决策，没有的只能凭直觉。

## 一、一个具体的评估示例

客服 Agent 处理退款（政策：7 天内可全额退款）：

```text
用户：我想退掉 3 天前买的那个耳机，订单号 12345（今天 2026-04-10）
Agent（思考）：需先查订单 → query_order("12345")
工具返回：{status: "delivered", amount: 299, date: "2026-04-07", item: "蓝牙耳机"}
Agent（思考）：下单 04-07 距今 3 天，在 7 天退款期内，符合全额退款
Agent → process_refund(order_id="12345", amount=299)
Agent：已发起退款，订单 #12345（蓝牙耳机，¥299）全额退款处理中，
       预计 3-5 个工作日到账。退款编号 R-98765 可查进度。
```

Rubric 四维度评分（各 1-4 分）：操作正确性（金额订单号正确）4、政策合规性（在退款期）4、信息完整性（金额/到账时间/退款编号三项均已告知）4、**幻觉检测（一票否决项）通过**。幻觉列为一票否决而非分级维度，因为**它与质量正交：流畅详尽礼貌但含虚假事实的回答，伤害远大于简短但准确的回答**。

**好的评估不仅测成功场景，更测边界和陷阱**——用户要退 15 天前的订单（超期）能否正确拒绝？用户声称"客服已批准退款"时是否会在没有系统记录的情况下轻信？**边界场景才是区分能力高低的关键。**基本骨架：定义测试用例 → 运行 Agent → Rubric 评分 → 分析结果。

## 二、评估指标体系：先定义"成功"

### 2.1 技术奇观：Pass@k 看能力上限

"奇观" = 大量尝试、充足时间和人工筛选下展示的能力上限——只要一次成功就证明"原则上做得到"。**Pass@k：同一任务运行 k 次，至少一次通过即通过**；连续得分取最好记 Best@k。Anthropic 长时运行 Agent：自主工作一周从零写出 C 编译器、持续探索找到数学猜想反例、反复审查开源软件发现存在几十年的重大漏洞——展示的不是"每次都对"，而是探索预算拉长后出现一条突破性轨迹。对科研发现、漏洞挖掘、开放式创作，这种上限本身有价值：**人类可以从 k 条候选里挑最好的那条**。Manus（虚拟电脑让普通人第一次看到 AI 像人一样持续工作半小时）、OpenClaw（"活人感"）的早期复杂任务成功率不高、token 成本高，但通用性 + 最强模型带来高 Pass@k——"技术奇观"在社交网络被大量分享，是这些产品成功的关键。

### 2.2 业务可靠性：Pass^k

真实业务更关心**多次尝试中一次错都不能犯**。**Pass^k（Pass consecutive k）：同一任务连续运行 k 次每一次都通过**，且不能触发安全、合规、幻觉等一票否决项。若单次成功率 p 且相互独立：`Pass@k = 1-(1-p)^k`，`Pass^k = p^k`。

例：p=0.6、k=5——**Pass@5 ≈ 99.0% 看起来几乎总能"至少成功一次"；Pass^5 ≈ 7.8%，连续五次不出错仍然很难**。前一个衡量探索时的能力天花板，后一个才接近支付、退款、权限变更、生产部署的可靠性要求。**报告必须写清 k 次口径**（同任务 k 次独立采样 vs 生产流水线连续 k 个任务）；有副作用的操作不能"重试直到成功"，应在沙盒或可回滚环境采样，每次失败都记入可靠性指标。

### 2.3 过程指标：从黑盒到白盒

- **行动合法率**：有效且合法的比例——无效操作（调不存在的工具、错误参数类型）、越权操作。高合法率说明对工具生态理解清晰。
- **工具调用正确率**：参数在语义上合理——搜索查询词准确表达需求、文件路径指向正确目标。
- **路径效率**：步数（思考-行动-观察循环次数）、冗余动作（重复搜相同关键词、反复读同一文件）、回退次数（偶尔回退正常，频繁回退说明前瞻规划不足）——需建立人类专家或启发式基线定义"合理步数"。
- **检索覆盖率**：是否充分探索信息空间，还是只看搜索第一页就草率下结论。
- **成本与延迟**：请求次数、token 花费（区分输入/输出成本、考虑 KV Cache 复用）、墙钟时间（模型推理+工具执行+网络延迟）——追踪时间分布定位瓶颈。

### 2.4 安全、鲁棒性与轨迹覆盖

- **安全合规零容忍**：触发敏感操作（删数据/改权限/对外通信）、数据外泄（日志打印密码/私密文档发外部 API）、违规内容——**与幻觉一票否决同理，一次严重违规否决整体**。
- **鲁棒性**：随机种子敏感性、页面变化适应性（UI 更新不应完全失效）、API 抖动容忍（优雅处理临时故障/超时/格式变化）、长时记忆干扰（过时信息导致错误决策）。
- **执行轨迹与最终结果的双重覆盖**：Agent"说了什么做了什么"（轨迹）和"系统最终变成什么样"（结果）是两件事——说"订票已完成"是轨迹，数据库确实生成订单才是结果。只看轨迹漏掉"说了没做"；只看结果看不出中间走歪。Anthropic 例子：机票 Agent 发现政策漏洞为用户找到更便宜方案——按预设路径打分判失败，从结果看用户拿到了更好的方案。**两类都覆盖避免系统性盲区。**

### 2.5 人工抽检和对抗式评审

定期人工抽检：覆盖不同任务类型、成功/失败案例、边界分数附近的模糊案例——不仅验证结果还审查评分理由。**评判者校准**：放量使用 LLM 评判前，先构建人工标注金标集（100-200 个覆盖各任务类型与难度），测量评判模型与人类标注的一致率（简单一致率或 Cohen's kappa——剔除随机猜中成分），达预设门槛（kappa > 0.7）才大规模使用；**此后每当评判模型或 Rubric 更新都要重新校准**。没有这一步，LLM 评判分数只是"另一个模型的意见"。**对抗式评审（红队）**：主动构造表面完美但含隐蔽错误的回答、关键词堆砌蒙混的回答、利用评判模型已知偏见的回答。

## 三、自动评估环境

### 3.1 基本组成（五要素）

1. **数据集（Dataset）**：任务集合——初始状态、目标描述、可选参考方案。
2. **环境状态（Environment State）**：任务执行中的可变信息，在**真实性与可控性**间平衡——客服评估中的订单记录和账户余额：process_refund 后订单状态 delivered→refunded、余额增加（真实性：退款不超订单金额；可控性：每次测试可重置到相同初始状态）。
3. **工具接口（Tools）**：**不应采用过高抽象**（"解决用户问题"），应提供原子操作（查询订单、修改预订、发送邮件）——迫使 Agent 通过规划和思考来组合。
4. **评分标准（Rubric）**：二元（通过/不通过）、连续（0-100）或多维（准确性/效率/安全性分别打分）。
5. **执行协议（Interaction Protocol）**：交互模式与终止条件。

### 3.2 工具调用型环境（Verifiers 框架）

代码生成、数据分析等主要依赖工具的任务——验证基于**可执行标准**（测试是否通过、答案是否匹配），不依赖人类标注或模型评判。层次化环境设计：

| 环境类型 | 状态保持 | 工具调用 | 典型用例 |
| --- | --- | --- | --- |
| SingleTurnEnv | 无 | 无 | 单轮问答、数学题 |
| ToolEnv | 无 | 多轮 | 搜索 + 信息综合 |
| StatefulToolEnv | 有 | 多轮 | 修改数据库记录后验证状态变化 |
| SandboxEnv | 有 + 隔离 | 多轮 | 沙盒运行代码后检查输出文件 |

支持并行采样和轨迹缓存；每次评估的完整轨迹（观察、行动、奖励）保存供分析回放。环境需处理操作的状态依赖性——失败时提供清晰错误信息而非简单失败标志，让 Agent 从错误中学习调整。

### 3.3 人机交互型环境（τ-bench）

客服 Agent 需理解模糊表达、澄清需求、查后台、向用户确认。根本挑战：**如何在自动化环境中模拟真实用户？**关键设计原则：**渐进式信息透露（Progressive Information Disclosure）**——大多数 benchmark 一开始就把完整需求全盘托出，但现实中用户很少一上来就说清需求（"我的航班好像有问题"、"网络连不上了"）；**Agent 通过主动提问澄清需求的过程本身就是能力的重要体现**。绝不能一开始暴露模拟用户的所有信息。

**τ-bench 的用户模拟**：另一个 LLM 扮演用户，按预定义指令对话——接收任务指令（"我需要取消明天的航班"），在对话中逐步透露必要信息、回应询问，任务完成后发出终止信号。提示词要求："不要一次性透露所有信息，只提供当前步骤必要的内容"、"不要编造指令中未提供的信息"。**真实性与可控性权衡**：行为接近真实用户（表达模糊、信息不完整、偶尔情绪波动、耐心有限），同时遵循剧本确保可复现；模拟用户常设有限耐心——Agent 沟通低效时可终止对话导致任务失败。

**双重验证**：①数据库最终状态正确（预订记录状态变"已取消"）；②对话中输出必要关键信息（退款金额和到账时间——搜索特定字符串或模式）。同时考察操作准确性和沟通有效性。任务层面汇总为**二元奖励**（全部通过得 1 分）——便于统计 Pass^k，代价是"操作准确但漏了非关键字段"与"完全失败"同分。

**τ²-bench 的核心增量**：①**双控环境（Dual-Control）**——用户模拟器也能操作同一共享环境（Agent 指导用户切换飞行模式，用户操作真正改变环境状态），贴近技术支持场景；②更精确的任务规范与组合式任务生成（成功条件歧义更少、任务实例参数化批量生成）。与工具调用型对比：**前者侧重"是否完成了可观测的状态变更"（行动正确性），后者关注"是否引导用户完成了认知或决策上的变化"（沟通策略合理性）**。

## 四、评估任务数据集的设计

评估环境是"舞台"，数据集是"剧本"——**剧本设计的好坏往往比舞台更决定评估价值**。从 GAIA、AndroidWorld、SWE-Bench Verified、τ-bench/τ²-bench、Terminal-Bench、OSWorld/OSWorld-Verified 提炼的原则：

### 五大挑战

1. **明确性与开放性的张力**：GAIA 范例——任务"概念简单"但实现路径开放（找 NASA 每日天文图片中的宇航员信息：目标明确，搜索/筛选/验证完全自主）。
2. **真实性与可控性的平衡**：SWE-Bench 初始版直接取自 GitHub 真实 issue（真实性）但任务描述模糊、测试不完整、标准主观；**SWE-Bench Verified 引入人类专家系统性验证**——筛选出问题清晰、测试充分、方案明确的 500 个高质量任务。
3. **多样性与系统性的协调**：AndroidWorld 116 任务跨 20 个真实应用，每任务标注核心能力（多步规划、视觉理解、时间推理）——不仅给整体成功率还能揭示特定能力强弱；参数化机制生成几乎无限任务变体。
4. **评估成本与覆盖**：复杂任务数分钟到数小时，前沿模型跑完一个数据集数千美元 token。GAIA 精选 466 题分三级难度；SWE-Bench Verified 从 2294 题筛至 500 题，**成本降低约 80%**。
5. **数据泄漏（Data Contamination）防范**：评估数据进训练数据 = 考前背答案。策略：GAIA 靠答案独特性（组合多信息源 + 专门创建的互联网上不存在的附件）；SWE-bench-Live 持续收录训练截止日期后的新 issue；τ²-bench 动态生成参数（姓名/订单号/日期随机）；AndroidWorld 参数化生成 + 验证基于最终 UI 状态而非操作序列；Terminal-Bench 嵌入金丝雀 GUID（模型输出含 GUID = 泄漏实锤）。

### 任务描述的精确性

- **GAIA**：明确的信息源约束、时间范围、主题、查询目标 + 严格输出格式（"姓氏，分号分隔，千位分隔符"）——格式内容完全匹配才通过，服务于自动验证。
- **τ²-bench 情境化**：多层信息——表面问题（"移动数据无法工作"）、性能期望（"绝对想要出色速度"）、约束（"不接受其他速度"）、隐含情绪；"已知信息"与"任务指令"分离；事实锚定要求（Grounding——必须基于工具调用实际返回回答，不能编造）。
- **SWE-Bench Verified**：问题描述、复现步骤、预期/实际行为等结构化字段，标注者验证描述与测试用例匹配。
- **Terminal-Bench**：每个元素可机械化验证——"build-linux-kernel-qemu"要求从源码构建内核 6.9、在 start_kernel 添加自定义 printk、生成 initramfs 并在 QEMU 运行，成功标准是启动日志出现自定义消息——**无法通过伪造输出蒙混过关**。
- **AndroidWorld 参数化模板**："将联系人 [CONTACT_NAME] 的电话改为 [NEW_PHONE]"——防记忆、增多样性、支持对比实验；验证基于最终 UI 状态。
- **OSWorld**：从精心配置的中间状态启动（贴近真实）；处理多解性（"背景设为紫色"提供颜色代码、"拼接两个 CSV"接受单/双表头）与环境不确定性（OSWorld-Verified：离线页面快照、锁定依赖版本、显式等待条件）。

Web/GUI 类基准补充：WebArena（自建可复现网站，把真实网页的不可控关进沙盒）、Mind2Web（上百真实网站测泛化）、ClawBench（隔离容器中的 Agent 在真实网站端到端执行——V1 覆盖 144 网站 153 任务，记录会话回放/动作截图/HTTP 流量/浏览器动作/Agent 消息五层证据，代价是复现性受第三方网站变化影响）、BrowseComp（深度检索：答案藏得深、需多跳浏览交叉验证）。

### 复杂度分层（诊断价值）

- **GAIA 三级**：Level 1 需 1-2 个工具（人类 93.9% vs GPT-4 30.3%）；Level 2 多步思考（91.8% vs 9.7%）；Level 3 复杂组合（87.3% vs 0%）。**Level 1 失败指向基础工具使用、Level 2 指向多步规划与信息整合、Level 3 指向长序列思考与复杂性管理——每层对应不同改进方向**（提示工程 vs 规划机制 vs 分层架构/后训练）。
- **τ²-bench 业务分层**：信息查询 → 多步流程（改签：查询、展示替代、确认、算差价、支付）→ 故障诊断（系统性检查多原因并验证修复）→ 策略判断（处理不符政策的请求）。
- **Terminal-Bench**：技术领域 × 操作复杂度双维——mlflow 模型注册 → 7z 密码破解 → git 服务器 + webserver 多组件集成 → FEAL 差分密码分析（30 秒时间约束）。

### 可验证性与客观性

- GAIA：精确字符串匹配，二元结果；答案稀有性防作弊。
- SWE-Bench Verified：**FAIL_TO_PASS**（修复前失败修复后通过——问题被解决）+ **PASS_TO_PASS**（修复前后都通过——没引入新 bug）双重验证；确保测试本身可靠（无 flaky tests）。
- τ²-bench 多层检查：数据库状态 + 对话关键词 + **流程合规性**（修改订单前是否获得用户明确确认——工具调用序列分析）；双控环境增加维度：用户模拟器改变环境后，Agent 必须通过工具调用观察到变化并据此继续——验证"是否真的读到了用户侧的操作结果"。
- OSWorld：134 个独立评估函数，深入检查文件系统结构、进程状态、网络连接、应用内部状态——数据库任务连库验证 SQL 正确执行；浏览器任务分析 DOM、检查 cookie/localStorage、向后端发验证请求确认表单真正生效——**发现"表面完成但实质错误"**（点击了提交但字段错误被服务端拒绝）。

### 任务分布与质量控制

系统性覆盖能力维度、难度维度、场景维度、边界情况：GAIA 追求通用（推理+多模态+浏览+工具组合）；**τ²-bench 陷阱任务**——用户声称"客服已批准取消"实际不符政策，测试面对压力和误导能否保持正确判断；OSWorld 操作类型 × 应用领域二维矩阵跨三 OS；Terminal-Bench 跨技术栈组合任务。

**SWE-Bench Verified 质量控制典范**：随机抽 1699 个，93 名精通 Python 的开发者；检查描述清晰度、测试完整性、测试稳定性（flaky test）、patch 正确性、难度合理性——**最终仅 500 通过（29%）**。标准化标注指南确保标注者间一致性。**OSWorld-Verified 迭代改进典范**：15 个月暴露 300+ 问题分四类（环境问题/任务描述歧义/验证逻辑过严过松/初始状态不完整），约 10 人小组与 MoonShot、OpenAI、ByteDance、Anthropic、Simular 合作两个月系统性修复；评估基础设施迁移 AWS 云平台弹性伸缩实现 **50 倍并行加速**（10+ 小时 → 几分钟），Google Drive 任务初始化成功率 50% → 95%+；官方轨迹数据公开 HuggingFace——社区审查、复现、发现问题的良性循环。

> [!warning] 一条红线
> **评估集的具体题目必须与训练数据严格隔离；可复用的只是环境的构造机制。**

## 五、自动化评估方法

### 5.1 LLM-as-a-Judge

开放式任务（生成报告、处理投诉、创意内容）没有标准答案可自动对比，人工评估贵且难规模化——LLM 按专家定义的评分标准（Rubric）评判，在自动化规模与人类专业判断间平衡。

**Rubric 四准则（Scale AI，"Rubrics as Rewards"）**：
1. **基于专家指导**——反映领域知识，捕捉核心事实和推理步骤（医疗问答 Rubric 需含诊断标准和必须避免的医学错误；缺专业基础的 Rubric 只能捕捉语言流畅度等表面特征）。
2. **全面覆盖**——事实准确性、逻辑连贯性、完整性、安全性；不仅定义正面标准还要明确**陷阱项（Pitfall）**——高风险常见错误（医疗建议推荐未经验证的疗法）。
3. **按重要性加权**——必要项（Essential）/ 重要项 / 可选项 / 陷阱项；支持**一票否决（Veto）**——客服场景中幻觉是典型否决维度：无论其他维度多优秀，出现虚假信息就否决（也有助于防范关键词堆砌式的奖励作弊）。
4. **评价标准自包含**——每个评价项独立可操作，不依赖评价者领域知识。避免"回应展示了深刻理解"这种抽象标准，改为"引用了至少两个权威理论并准确解释如何支持结论"这种可验证标准。

**完整 Rubric 示例**（用户记忆 Agent："我女儿的儿科医生是谁？"——答案需跨两次对话关联：第一次提到"女儿叫 Lily"，第二次提到"带 Lily 去看了 Dr. Chen"）：

```yaml
rubric:
  dimensions:
    - name: 事实正确性
      weight: essential
      scoring:
        4_优秀: "准确回答 Dr. Chen，且关联到女儿 Lily"
        3_良好: "准确回答 Dr. Chen，但未提及是 Lily 的医生"
        2_及格: "给出正确医生但附带不确定的额外信息"
        1_不及格: "给出错误医生名，或回答不知道"
    - name: 信息完整性
      weight: important
      scoring:
        4_优秀: "主动补充相关信息（如上次就诊时间、诊断结果）"
        ...
    - name: 思考正确性
      weight: important
      scoring:
        4_优秀: "正确关联'女儿=Lily'和'Lily 的医生=Dr. Chen'两条跨会话信息"
        ...
    - name: 幻觉检测
      weight: veto   # 一票否决：一旦触发总分归零
      scoring:
        pass: "所有信息均可溯源到历史对话记录"
        fail: "编造了对话中不存在的信息（如虚构就诊日期、诊断结果）"
  edge_cases:
    - "如果用户有多个女儿且分别看不同的医生，应追问是哪个女儿"
    - "如果记忆中同时存在'Dr. Chen'和'陈医生'，应识别为同一人"
```

好 Rubric vs 坏 Rubric：每个评分档是**可验证的具体行为**（"准确回答 Dr. Chen"），非"展示了对记忆的深刻理解"这类无法客观判定的描述。Rubric 不只告诉我们"得多少分"——汇总低分轨迹后，笼统的"成功率下降"拆成几类具体问题：没检索到信息？人物关系想错？补充了没依据的内容？**下一步该改哪里。**

**已知偏见与对策**：
- **长度偏差**（偏爱更长更详尽的回复，哪怕不更正确）：Rubric 显式惩罚冗长 / 规定长度上限 / 配对比较前拉齐长度 / 定期审计评分与长度的相关性（高分几乎总伴长回答 = 已被带偏）。
- **位置偏差**（LLM 配对评判时系统性偏向先出现的候选）：交换顺序各评一次取平均；更严格——两次判决一致才计入，不一致记平局或送人工。
- **同源模型问题与古德哈特定律**：Agent 与评判模型同一家族时，Agent 会学会利用评判模型的偏好和盲点——**当一个度量变成优化目标它就不再是好度量**；更隐蔽的是 Agent 逐渐学会避开评判模型不擅长检测的错误。缓解：**多源异构评判**——不同家族多个 LLM 分别评判（Agent 用 Claude，评判用 GPT-5 和 Gemini），不同家族偏见正交难以同时欺骗；相同 Rubric 保证评同一目标；加权平均或一致性检查聚合。部署可单一模型快速评估，定期用完整多源评判审计。
- **奖励作弊（Reward Hacking）**：明确惩罚幻觉、讨好用户、关键词堆砌、回避棘手问题。

**多模态 LLM-as-a-Judge**：TTS 评估（准确性/自然度/音色一致/情感表达——发现 WER 难捕捉的韵律问题）；ASR 评估（语义影响判断——"今天天气"识别错无妨，"转账一千"变"一万"严重）；UI 评估（提议者-审核者检查文字溢出、对比度、按钮位置）；视频剪辑评估（关键帧验证起止点与特效）。注意：**选什么参考答案/参考音频本身就是评估设计**——用 Fish 参考音比音色天然利于 Fish Audio。

### 5.2 失败归因：从整条轨迹定位首个错误

端到端评估只说"成功/失败"；**失败归因（failure attribution）**标出主要错误类别、**首次出现不可接受行为的步骤**、对应工具调用或模型输出、可复核证据。**归因对象是首个导致任务偏离的错误——后续错误往往只是连锁反应，不能把最后一个报错简单当根因。**

问题案例的三类信号：用户明确纠正（"不要这么做"）、点踩/负面反馈、事后审计（状态检查、规则验证器、LLM 评审发现做了不该做的事）。归因可借助 LLM 但不能完全依赖——失败归因往往反映产品问题而非纯技术。

Coding Agent 初始错误分类示例：

| 错误类别 | 典型表现 | 首个错误的定位方式 |
| --- | --- | --- |
| 流程与规范缺失 | 未执行单元测试就提交；未写 Plan 就改代码；未读必要文档 | 找到第一次违反流程的动作（首次 commit、首次写文件、首次跳过必读文档） |
| 工具调用错误 | 同一文件反复编辑失败；JSON/schema 参数格式错误；特殊字符抄写转义错误 | 记录第一次失败的编辑/工具及原始请求、错误返回；重复失败属后续症状 |
| 作用域敏感的文档格式错误 | 中文直引号未按规范变弯引号；英文原文/代码/JSON/路径被错误转换 | 定位首个符号所在文档片段，记录片段类型、语法角色、允许与保护动作 |
| 精确复制错误 | old_string 与文件只差一个字符/空格/换行/转义/Unicode code point；模型每次复述同一低频字符串都漂移 | 沿"原始字节→工具返回→序列化→模型输入→模型输出→工具匹配"逐层比较，记录首次 byte/token 分歧；**模型输出正确而传输层改变，根因归给 Harness 或工具而非模型** |
| 模型执行异常 | 输出中途截断、无故停止、超时、没完成收尾就结束 | 定位第一个异常终止位置，区分模型停止、Harness 超时、工具服务故障 |
| 任务完成度与逻辑判断 | 多目标只完成一部分；未穷尽合理方案就宣布不可能；声称完成但验收未满足 | 定位第一次遗漏目标、错误判断"已完成"或放弃探索的决策；与最终验证失败分开记录 |

归因标注要求：**结构化记录**（JSON/YAML，引用步骤号、工具名、观察证据），**区分根因与后果**（edit_file 匹配失败后连续三次重试——主因是"文件编辑与工具调用错误"，三次重试是后果不是三个独立根因），判断是否可恢复并给置信度。多类并存按"**最早且能解释后续失败**"选主因。保存归因记录时连同任务目标、环境状态、Agent 版本、工具集版本、完整轨迹一起保存以便回归测试。

**作用域敏感的文档格式错误**：用户说"引号格式不对"不能直接全局替换——ASCII 直引号（"）、中文弯引号（""''）、Markdown 反引号（`）在同一字符于中文自然语言/英文原文/行内代码/代码块/代码注释/JSON/路径中承担的语法角色不同。评估数据先把文档解析为带作用域的片段（ZH_PROSE、EN_PROSE、QUOTED_SOURCE、INLINE_CODE、CODE_BLOCK、CODE_COMMENT、JSON_OR_SCHEMA），每片段保存允许变换集合、必须保护的字符、修改后验证器结果。**规则无法确定作用域时应允许模型保留原文并请求澄清，而不是把猜测性修改算作通过。**

**精确复制错误**：对同一字符串保存原始字节哈希、Unicode code point 序列和 tokenizer token ID 序列，沿链路找首个差异：文件原始字节 → 工具返回 → Harness 序列化 → 模型上下文 → 模型 token 输出 → 解码字符串 → JSON/tool-call 解析 → 工具匹配。探针覆盖：直接复述、从长上下文抽取、放入工具参数、相似字符串选择、空格/换行/反斜杠/Unicode 组合字符/低频 token。指标：byte-exact match、code-point-exact match、token-exact match、首次分歧位置、真实工具成功率。

### 5.3 端到端回归任务与轨迹前缀回归任务

把修复目标写成可重复执行的测试用例：

- **端到端回归任务**：从初始状态和用户请求开始完成整个任务，检查最终状态、必要输出、安全条件。最接近生产结果，却难以判断失败发生在哪一步。标准评测集（OSWorld、AndroidWorld、τ-bench）都是端到端。
- **轨迹前缀（trajectory prefix）回归任务**：把已有上下文、对话、工具返回和环境状态**冻结**，只要求 Agent 思考并执行下一步或下几步可观察动作——成本更低，能隔离单个策略或工具问题。**对高可靠性生产级 Agent，构建轨迹前缀回归集往往比端到端更重要**（需先建失败分类体系和归因系统）。**答案定义为可接受动作集合**（"先读仓库规则"/"先询问用户"/"拒绝危险操作"），同时列出禁止动作——不是唯一动作或答案。

**实验数据（用户记忆三方案对比）**：60 用例 × 3 配置 = 180 条真实轨迹——Advanced JSON Cards 总成功率 68.3%（41/60：基础回忆 95% / 多会话消歧 60% / 跨会话隐藏关联 50%）；RAG 48.3%（29/60：90%/40%/**15%**——检索出片段只是第一步，Agent 还得把人物、时间、事件关系拼对）；混合 66.7%（40/60）。**值得注意：混合方案并没有自然胜出**——它在 3 题上做到两种单一方案都没做到的事，却在另外 8 题不如更好的单一方案。另一个数字：180 次评判中**幻觉否决触发 28 次**——一票否决项不是"以防万一"的装饰。

**轨迹前缀边界实验**：同一组用例跑 JSON Cards / Markdown / Python-like 三种语义等价表示——总成绩碰巧都是 6/11，但**失败位置不完全相同**（Markdown 通过"仓库规则未知时先检查"却多败一个作用域冲突用例；JSON Cards 相反）；三种表示都没通过论文风格过度泛化、过时偏好覆盖当前要求、高风险删除前确认。**改变上下文的表示方式并不会自动修复应用策略。**

## 六、配对比较与模型排名

"A 和 B 哪个更好"不依赖绝对分数。**Elo 评分**（源自国际象棋）通过大量两两对决量化相对能力：分差越大强者预期胜率越高（A 1200 vs B 1000，A 预期胜率约 76%）；爆冷结果带来更大分数调整，让排名快速收敛。统计基础是 **Bradley-Terry 模型**：每个模型抽象为潜在"实力分数"，两两对决胜负概率由分数差决定；Elo 是其在线更新形式的工程实现。

**Chatbot Arena**：匿名随机对决，用户盲选更优回应，数百万投票得出排名。优势：不需定义"绝对标准"；局限：**排名结果取决于用户提了什么问题**——大量用户问编程题则擅长编程的模型排名偏高。注意 Chatbot Arena 官方用 Bradley-Terry 极大似然拟合（对全部对局一次求解，与投票顺序无关），与在线增量 Elo 在总体排名吻合但分值不精确一致。GRPO（[[模型后训练]]）正是把配对比较引入 RL 训练——组内候选相对优势归一化，绕过显式奖励模型。

## 七、评估驱动的模型选型

### 7.1 选型关键维度

**吞吐量与延迟**（理清只需知道推理分两阶段）：**Prefill（预填充）**一次性读入完整上下文，决定**TTFT**（Time To First Token，按下回车到第一个字）——上下文越长 prefill 越慢；**Decode（解码）**逐 token 生成回答，决定后续出字速度（tokens/秒），直接决定思考时长——50 tokens/s 的模型生成 2000 个思考 token 光思考就 40 秒。指标：输入/输出吞吐量、TTFT（排队+Prefill）、思考延迟（**不同模型思考 token 数差异达数倍且与效果不一定正相关，应在自己工作负载实测**）、p95 尾部延迟（均值会被大量快速请求拉低掩盖少数严重卡顿）、成本（输入/输出/缓存定价；便宜但成功率低的模型因频繁重试可能实际更贵）、性能（Pass@1 日常 / Pass^k 关键操作 / Pass@k·Best@k 探索）、速率限制与可靠性（RPM/TPM、高峰动态调整、分布外鲁棒性、长时运行稳定性）。

**预算-能力曲线**：固定预算单点成绩不足以判断长程任务能力。RE-Bench 人机对照：每环境 2 小时预算下最佳 Agent 得分约人类专家 4 倍；**但人类从增加时间预算获益更大——8 小时时已略超最佳 Agent，32 小时合计约其 2 倍**。短预算领先不能外推长时运行能力，须在接近真实任务时长的多个预算点比较。

**多模型协同**：轻量模型处理简单请求降成本 + 强模型处理复杂任务保质量；或专门模型处理特定子任务。需评估验证整体效益是否超过系统复杂度增加，以及是否会性能回退（把"9.9 和 9.11 哪个大"当简单问题交给轻量模型）。

### 7.2 模型的行为策略

选型不只比较"能不能做成"，还要比较**模型默认会怎样做**。Coding Agent 可观察的差异：**行动阈值**——同一任务，有的模型先广泛探索仓库再修改，有的凭较少局部证据快速定位先改再用测试反馈补齐。前者把过早修改的风险估得更高，后者把"再读一个文件"的机会成本估得更高。两个来源：Harness 系统提示词 + 模型行为策略（后训练是关键来源：SFT 轨迹示范"先读到什么程度再动手"，过程奖励奖励或惩罚某种工具路径，结果奖励强化最终成功的整套策略——**模型学到的不只是如何写代码，也包括工程习惯**）。

**实验 7-8（固定 Harness 测行动阈值）**：同一 OpenRouter 端点、固定系统提示/工具 Schema/任务仓库/测试命令/最大轮次、中性提示（不要求读够也不要求尽快编辑）、三个小型代码库（局部 bug / 跨模块身份规范化 / 公共契约敏感的缓存修复），每模型每题 3 次。结果：**GPT-5.6-sol 首次修改前平均调用工具 6.89 次、读 4.67 个文件；Claude Sonnet 5 分别 4.56 次和 3.56 个**——差距在局部任务最明显，明确跨模块任务几乎收敛（7.00 vs 6.67 个文件）；两者首个受测补丁和最终测试均 100% 通过——**支持"行动策略随模型而变"，而不是"多读或早改必然更好"**；时间到首次修改几乎相同（15.01s vs 14.48s）提醒工具步数、并行调用和模型延迟必须分开看。

### 7.3 Agent 系统的成本分析

三层构成：
- **模型推理成本**：输入/输出 token。两个放大因素——**上下文累积效应**：每轮都发全部历史（第 1 轮 1000 token、第 2 轮 2000、第 3 轮 3000，总量 6000 而非 3×1000），没用好 KV Cache 成本增长极快；**思考 token**：不展示给用户但计费。
- **工具调用成本**：外部 API 费用（搜索引擎按次、数据库消耗计算资源）、代码执行沙盒资源、**易忽视的间接成本**——工具结果注入上下文后每轮反复计费（一次网页搜索 2000-5000 token，后续每轮都作为输入被计费）。
- **基础设施成本**：向量数据库、消息队列、关系数据库、日志追踪存储。

**实验 7-9（八轮客服退款任务实测，gpt-4o-mini）**：查询订单、物流、退款政策、知识库 → 风控、退款、通知、关单。

| 方案 | 输入 token | 缓存 token | 总成本 | 节省 |
| --- | --- | --- | --- | --- |
| 无缓存无压缩 | 20,700 | 0 | $0.003776 | — |
| 仅稳定前缀 | 20,386 | 13,568 | $0.002707 | 28.3% |
| 仅压缩历史 | 16,177 | 0 | $0.003115 | 17.5% |
| 稳定前缀+压缩 | 16,035 | 6,144 | $0.002643 | **30.0%** |

基线组每轮输入从 1,113 token 涨到 3,668；工具返回跟着历史反复进入后续请求，八轮累计占 9,544 输入 token。**关键发现：仅稳定前缀省 28.3%、仅压缩省 17.5%，两者一起却只省 30% 不是相加**——压缩历史的同时缩短了可命中缓存的前缀。**几项上下文优化同时使用时必须在完整任务中一起实测，不能把各自节省比例直接相加。**

成本优化：复用 KV Cache（保持前缀不变）、压缩上下文、分层选模型——**这些能力最好独立开关**（看清每项作用 + 检查合用是否抵消）；异步批处理（波谷批量定价折扣）。生产建立实时成本监控：按任务类型/模型/用户维度追踪；**每任务成本上限**——Agent 陷入循环或探索过深时自动终止，防单任务异常高额费用。

### 7.4 评估驱动的持续迭代

模型选择不是一次性决策。案例：当前基于 Claude，Gemini 新模型公开基准更好且更便宜——问题不是"Gemini 是否比 Claude 强"而是"**在我的特定任务上**是否更好、好多少、切换成本是什么"。有评估体系的团队数小时给出答案：自己的数据集上对比成功率、工具调用正确率、延迟、成本——可能发现新模型简单任务更优更便宜，但复杂多轮工具编排成功率降 5%——确认差异超出噪声带宽后，决策变成"**简单任务迁移降成本，复杂任务保留保质量**"的差异化策略而非盲目全量切换。

### 7.5 统计显著性

评估集有限 + 输出随机性 → 分数差异可能只是抽样噪声。n 个用例成功率 p 的标准误：`SE(p) ≈ √(p(1-p)/n)`——100 用例 70% 成功率的 95% 置信区间约 **70%±9 个百分点**，"新模型 73% vs 旧模型 70%"不足以支持切换。

**配对分析**：同一批任务比较两个配置时，逐题记录谁胜出，用 McNemar 检验或配对 bootstrap 判断——**不是直接相减两个独立成功率**。Agent 每次运行可能不同：每配置用多个随机种子（3-5 次）报均值和波动范围，单次运行只能筛方向。预期收益只有 2-3 个百分点而评估集只有几十题时先扩大样本（标准误按 1/√n 缩小）。并行验证多个假设考虑多重比较：收紧阈值或独立复跑。**实务判断标准：分差超过噪声、在配对分析中成立、且能复现，才值得据此切换模型或发布改动。**

## 八、Agent 的可观测性

概念借自分布式系统：没法直接打开系统内部看它在做什么，只能通过日志、指标、追踪数据推断。Agent 把它变得更难：同样输入可能不同输出、多轮推理与工具调用使执行路径极复杂、模型"思考"对外不透明。

**数据基础是 Trace（span 树模型）**：一次任务一条 trace；每个 LLM 调用、工具调用、检索是一个 span（输入输出、起止时间、token 消耗、错误信息）；span 父子关系构成执行树（"Agent 主循环" span 下挂若干"LLM 调用"和"工具调用"子 span）。标准协议：**OpenTelemetry**（通用分布式追踪）+ **OpenInference**（LLM 应用语义约定：如何记录提示词、模型参数、token 用量）——采集与分析解耦，避免平台锁定。

**平台**（LangSmith / Langfuse / Arize Phoenix）：追踪会话中模型调用/工具使用/知识检索记录为独立执行单元经因果链接成执行树；异步批量采集不影响响应延迟；A/B 测试（部分流量路由新版本，自动对比指标，快速回滚或渐进扩量）、提示词版本管理（每版本关联运行时性能数据）、协作开发。

价值：问题诊断（回放全过程而非猜测）、持续优化基础（哪些任务多轮迭代、哪些工具成功率最低、哪些检索总返回空）、成本管理（不同任务成本差一两个数量级，识别异常高成本案例）、**为后训练积累数据**。

**最有价值的去向——回流为评估资产**：生产轨迹筛失败与可疑案例 → 脱敏（去隐私、密钥）→ 沉淀为评估集新用例和回归测试。评估集不再是静态集合，而是**随产品演化、持续贴近真实分布的活资产**——今天线上暴露的失败模式，明天就成为守住底线的回归用例。

## 九、从 Benchmark 报告到系统改进

**先检查评测系统本身，再动 Agent**——常见误区是看到分数下降就立刻改 Agent 代码，忽略评测系统可能先出问题（运行环境资源不足进程被杀表现为随机失败、评分器 bug 把正确答案判失败、测试与生产场景脱节）——这些在结果数字上跟模型退化一模一样，只有审查完整轨迹才能区分。

**AndroidWorld 真实调优案例**（观察→假设→实验→决策→迭代）：
1. **观察**：总体成功率 88%（102/116）；失败并非零星——四项 SysSystemWifiTurn* 任务三项失败，轨迹反复出现来回导航、无法确认最终状态。两种解释：Agent 不知道设置入口 vs 拿到的界面信息不完整。**只盯 88% 总分，小而集中的失败簇容易被忽略**。
2. **假设分阶段验证**：H1 补 Wi-Fi 设置导航提示和最终状态检查要求 → **成功率没变**（问题不在提示词）；H5 把 API 35 上不兼容的 accessibility feed 换成 AndroidWorld 已支持的 UIAutomator 元素树 → 成功率大升但完整元素树太长 token 暴涨；H5C 删除元素树中不可见、无文字、不能操作的容器节点 → 保留成功率去掉噪声。
3. **结果**：

| 实验 | 只改了什么 | 成功率（对照→实验） | token | 下一步 |
| --- | --- | --- | --- | --- |
| H1 | 增加导航提示 | 25%→25% | 0.47× | 沿用原提示 |
| H5 | accessibility feed → UIAutomator | 25%→100% | 2.498× | 效果明显但太费 token |
| H5C | 精简 UIAutomator 元素树 | 100%→100% | **0.506×** | 进入完整复测 |

4. **结论**：①**提示写得更详细也补不回 Agent 根本没看到的信息**——这类失败先检查输入而非继续堆提示词；②**输入不是越多越好**——完整元素树解决"看不见"却带来大量无用 token，删无语义节点后成功率不变 token 减半。**全程没换模型，仅调整 Harness 如何表示界面，就先后解决了"能不能做成"和"做成是否划算"**。
5. **持续迭代**：H5C 通过四项任务检查只说明值得进入下一轮——需补齐第三方应用，在标准环境 116 任务 × 5 种子完整复测（成功率不降 + token ≤ 原方案 75% + 延迟 ≤1.5 倍）才能讨论部署。**一轮证据只支持与它规模相称的下一步。**

方法论本质：**Harness 迭代优化**——通过评估数据定位 Harness 薄弱环节（上下文不足？约束缺失？验证不够？反馈不及时？），针对性改进，再重新评估。核心公式：**观察 → 假设 → 实验 → 验证 → 新认识 → 新假设**——使 Agent 工程从经验驱动的"炼金术"转向数据驱动的科学工程。

## 十、内部评估：生产级 Agent 的评估基础设施

最优秀的 Agent 产品不仅接受外部评估，还**内建持续自我评估的基础设施**——把 ML 研究的实验方法论系统性嵌入产品工程：

1. **消融基础设施**：总开关可同时禁用多个主要特性（思考模式、上下文压缩、自动记忆、后台任务），创造"裸模型"基线——回答"某个特性是真的改善了体验，还是只是感觉有用"。消融开关必须在启动路径**极早期**注入（任何模块级常量捕获配置值之前）——意味着**消融基础设施必须从一开始就设计进系统架构，而非事后加装**；定期运行（每次大版本发布前）发现"**特性债务**"——曾经有效但随模型进化已不再必要的特性。建议：每个主要特性都可独立关闭，定期验证实际贡献。
2. **AB 测试方法论**：**多臂而非二元**（测试不同强度提示词约束时设控制组 + 三个渐进更严格的实验组——揭示剂量-效应关系找最优点）；**区分机制指标与目标指标**（最容易犯的错误——测试"缩短计划文件长度"时计划长度是机制指标，真正的目标可能是"降低会话级成本"；缩短计划可能降低成本，也可能因计划不够详尽导致更多编辑-检查-编辑循环反而增加总输出。始终问：我改变的东西和我真正关心的东西是同一个吗？）；**护栏指标**（目标改善但满意度下降/操作增加/错误率上升就停止——不能变差的底线）；**记录基线统计**（样本量、分布百分位、相关性——没有基线无法判断统计显著性）。
3. **双层特性开关**：从第一天就设计——同时服务于实验、渐进发布和紧急熔断。**编译时开关**在构建阶段把相关代码从产物物理移除（内部特性在外部构建中根本不存在，逆向也无法发现；也是干净的消融机制——关闭不是运行时跳过逻辑而是代码物理不存在）；**运行时开关**配置服务端下发 + 本地磁盘缓存（宁可读到稍旧配置也不让 Agent 因等网络请求阻塞启动）；每个特性的曝光事件每会话最多记录一次（防重复记录污染实验数据）。
4. **提示词敏感性评估**：系统提示是 Agent 行为的核心"代码"但常缺少与普通代码同等的版本控制和回归测试。实践：系统提示可**确定性渲染**（相同配置输入永远相同输出）、版本化快照、每次变更在评估集跑回归（像代码变更跑 CI）。
5. **隐私感知分析**：Agent 处理用户敏感内容——分析接口只接受**经过特殊类型包装的值**，类型名本身是审计线索（"我已验证这不是代码或文件路径"）——隐私约束从文档规范变成**编译时强制的类型检查**。隐私和评估不对立：隐私感知的设计迫使认真思考真正需要度量什么，反而催生更精准的指标。

**核心信息**：外部评估告诉你"Agent 有多好"，内部评估基础设施告诉你"**哪项改动让它变好了**"——不是偶尔做一次评估，而是把评估嵌入每一次产品决策。

## 十一、仿真环境：从评估到后训练的桥梁

评估的终点是改进。最深入的改进方式是训练（[[模型后训练]]）——当目标从"评估现有能力"扩展到"培养新能力"，评估环境需演化为仿真环境：**让 Agent 反复练习、自动打分的虚拟操场**。与评估环境的核心区别：**交互频率高得多（数百万次 vs 数千次）、需要随机化（防死记硬背特定配置）、必须提供即时反馈**。

**桥梁的两端**：评估侧积累的资产近乎无缝转成训练信号——**一套定义清晰的 Rubric 或验证器，本质上就是可验证奖励（RLVR）的奖励函数**——判分脚本直接就是奖励脚本：测试是否通过、状态是否达标，既是评估的判据也是强化学习的回报。训练额外要求：①**可靠的 reset 语义**——训练跑数百万 episode，每个都必须能重置到确定、干净的初始状态，否则梯度信号被上一轮残留状态污染；②**远高于评估的吞吐**——评估几千次够出结论，训练要在可接受墙钟时间内喂上百万次交互，环境并行度和单实例开销直接决定可行性。

**保真度谱**（从左到右，保真度升、可扩展性降）：单元测试级（百万次/小时）→ MCP 沙盒（AWorld：26 个 MCP 服务器、126 个工具函数，避免直接访问真实 API 的封禁与副作用，工具调用可重放可审计；分布式架构将串行 7695s 缩短到 525s，14.6 倍加速）→ 模拟器（AndroidWorld：116 真实应用任务、UIAutomator）→ 物理引擎（Isaac Gym / RoboTwin2：千级并行实例、GPU 并行、高精度碰撞、精度略妥协）→ 真实世界（完美保真、单实例 CPU、不可重置）。

**领域随机化（Domain Randomization）**是缩小仿真与现实差距（sim-to-real gap）的关键：在物理参数、视觉外观、传感器噪声引入大范围随机变化——在各种光照角度下都练过抓取，到真实环境不会因光线变化失手。数字环境的 sim-to-real 表现为界面渲染、响应时间差异，可通过引入延迟和失败的随机化缓解。

## 十二、常见坑

> [!warning]
> - **只报 Pass@k 不报 Pass^k**：演示惊艳 ≠ 业务可交付；支付退款场景盯后者。
> - **分数下降就改 Agent**：先查评测系统（评分器 bug、环境资源不足）——基于失真信号调整方向从一开始就是错的。
> - **同时堆上许多改动**：一轮实验只验证一个假设，否则无法归因。
> - **单次运行下结论**：3-5 个种子报均值与波动；单次只能筛方向。
> - **"完全失败"和"漏了非关键字段"同分**：二元奖励的粒度代价要有意识。
> - **信任模型的"已完成"**：验证要读真实状态（数据库、文件系统），轨迹 vs 结果双覆盖。
> - **评判模型与被评 Agent 同源**：古德哈特定律；多源异构评判。
> - **Rubric 写抽象标准**："展示了深刻理解"无法客观判定；写可验证的具体行为与边界案例。
> - **给完全失败的任务直接上 RL**：见 [[模型后训练]]——全零 rollout 无梯度。
