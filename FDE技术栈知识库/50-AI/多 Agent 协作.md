# 多 Agent 协作

> [!abstract] 定位
> 前九章围绕单个 Agent：构建上下文、知识、工具与交互能力，再通过评估、后训练和持续进化让它长期变好。本章把问题推进到"**如何组织多个 Agent**"——让它们通过分工、通信与相互验证完成单个 Agent 难以承担的任务。群体的智能可以高于个体：单个人智力有限，但经由分工、协作、辩论和知识代际累积，人类社会整体展现的智能远超任何天才个体。Google DeepMind《从 AGI 到 ASI》把"大规模多 Agent 集体"列为通往超级智能的关键路径之一。**第一判断标准只有一条：协作过程是否引入了单个 Agent 在生成时无法获得的新信息？**

---

## 一、多 Agent 何时真正优于单 Agent

| 协作模式 | 是否引入新信息 | 效果 |
| --- | --- | --- |
| 同一模型自我审查（重读自己的输出） | 否 | **通常无效甚至有害** |
| 不同 Agent 辩论同一段文本 | 否 | 等计算量下与单 Agent 持平 |
| 审核者使用测试执行结果审查代码 | **是**（执行反馈） | 显著提升 |
| 审核者查看渲染截图审查前端/PPT 代码 | **是**（视觉反馈） | 显著提升 |
| 审核者使用外部工具验证事实 | **是**（工具反馈） | 显著提升 |

**实证**：
- **RLEF（2025）**：通过强化学习训练模型利用代码执行反馈迭代改进代码，效果远超独立多次采样——关键在于每次迭代都引入了真实的执行结果（编译错误、测试失败、运行时异常），**这些信息在模型写代码时并不存在**。
- **WebGen-Agent（2025）**：多层级视觉反馈（截图 + 视觉语言模型描述）构成的反馈脚手架，使 Claude 3.5 Sonnet 在网页生成基准上从 **26.4% 提升到 51.9%**——接近翻倍。
- **"新信息"框架解释了一个看似矛盾的现象**：学术研究认为多 Agent 不能提升能力上限，工程实践中多 Agent 确实更好——**学术研究比较的多是"多个 Agent 看着同一段上下文互相讨论"（没引入新信息）；工程实践有效的多 Agent 系统往往包含外部反馈环路（代码执行、视觉渲染、工具调用）**。
- **Anthropic 漏洞挖掘实验（2026）**：45 个 Agent 通过共享论坛协调搜索、互相审查、独立 Agent 仲裁——集群用 **2700 万 token 找到 266 个漏洞**，独立 Agent 并行方案用 650 万 token 只找到 21 个。**开放搜索空间里多 Agent 通过互相通信可以动态转移搜索重点、形成专门分工，用更高 token 预算换更广覆盖和更多样化的发现路径**——但要权衡成本。

**步骤预算与性能**：直觉上更多步骤带来更好结果（30 步快速实现核心功能，300 步先规划再实现再测试再改进）——但 2025 年 Google《Budget-Aware Tool-Use Enables Effective Agent Scaling》发现反直觉结论：**单纯增加可用步骤数并不保证性能提升**。标准 Agent 缺乏"预算意识"——即使 300 步预算仍倾向浅层搜索很快"饱和"。要让更多步骤转化为更好结果，Agent 需要**显式的预算感知机制**：根据剩余资源动态调整策略——前期广泛探索，后期聚焦最有希望的方向。2026 年 BAVT（Budget-Aware Value Tree Search）进一步提出步骤级价值评估，随预算减少从"广撒网"切到"深挖掘"。**对管理者模式的直接指导：Manager 不应简单分发后等待，而应根据任务复杂度动态分配步骤预算并引导子 Agent 合理利用（先规划、再实现、再测试、再改进）。**

**成本**：多 Agent 的并行探索与反复迭代要消耗数倍乃至一个数量级的 token——**收益必须足够大覆盖额外开销，否则调校得当的单 Agent 往往更划算**。

## 二、分类框架：两个核心设计维度

### 维度一：上下文是否共享

**共享上下文（继承式协作）**：后续 Agent 接收前一个 Agent 的完整对话历史和轨迹。每个阶段切换系统提示词和工具集后就变成一个新的 Agent（身份、职责、能力都变了），但保留了前任的全部记忆——需求分析师写完需求文档后，开发者不仅拿到文档还能看到分析师与用户的所有沟通记录。**优势：信息不丢失，每个 Agent 都能回顾之前任何阶段的细节；挑战：上下文可能快速膨胀。**

**不共享上下文（隔离式协作）**：每个 Agent 维护完全独立的上下文和对话历史，无法直接访问对方的"思考过程"——不同部门协作：各自在工位独立工作，通过共享文档和会议纪要交换信息。**优势：模块化、隔离性好、易扩展维护（新增 Agent 不改现有 Agent 内部逻辑，只定义接口和数据格式）、可真正并发（上下文独立无资源竞争）、故障不传染；代价：必须通过显式通信机制传递信息——信息同步复杂、调试困难（需翻多个 Agent 的日志拼出完整执行过程）。**

**通信机制 = 进程间通信（IPC）两大范式**：
- **共享内存**：共享文件系统——读写共享目录下的文档、代码等中间产物交换信息，适合产物较大或需持久化；
- **消息传递**：①**工具调用的参数**——把下游 Agent 封装成工具，结构化数据经参数传递（类型确定、结构清晰、同步）；②**消息总线（Message Bus）**——中转站，Agent 不直接调用彼此而是发消息到总线由它转发（异步、解耦）。

Go 语言名言同样适用："**不要通过共享内存来通信，而要通过通信来共享内存。**"

**实现选择：角色转换是替换 system prompt 还是加载 Skill？**两者都可让同一模型在不同阶段采用不同行为规程，但成本模型不同：

| 选择 | 角色规程的载体 | 工具可见性 | 上下文/KV Cache 影响 | 约束能力 |
| --- | --- | --- | --- | --- |
| transfer_to_agent | 替换当前 system prompt，通常替换工具集 | 只暴露当前角色工具 | 每次切换改变请求前缀，从变化点起缓存通常无法复用 | **强**：越界工具可在 schema 层不可见 |
| Skill | 固定 system prompt 中的 Skill 目录，按需把 SKILL.md 追加到轨迹 | 通常固定暴露工具全集，或稳定工具搜索入口 | 静态前缀不变；Skill 内容成为末尾轨迹，已有前缀继续复用 | 弱：Skill 是行为指令，硬权限仍需 Harness 门 |

**判据：角色差异主要来自知识、流程和写作风格 → 优先 Skill；角色差异涉及权限、工具隔离、合规边界、或需运行时强制禁止某类动作 → 独立 Agent 或 transfer_to_agent，并在 Harness 层用代码限制工具调用。**（实验 10-1：同一任务两条路径对比——系统提示词切换 vs Skill 加载。）

### 维度二：协作拓扑

- **对等协作模式（Peer Collaboration）**：少量 Agent 按固定拓扑形成迭代改进循环——论文写作 Agent 由起草者和评论者组成，一方起草另一方批注，反复几轮质量更高。
- **管理者模式（Orchestration）**：中心化 Manager Agent 负责任务规划和调度，多个子 Agent 各负责特定子任务——项目经理带专业工程师。
- **去中心化模式（Decentralized）**：没有运行时的中心控制者，Agent 之间像人类一样互相沟通协作。

**术语说明（Graph 工程）**：2026 年 7 月流行的 Graph Engineering 指显式设计执行图——节点是 Agent、普通程序或人工决策，边定义任务依赖、条件路由与失败后的去向，结构化状态在节点间流动。本章的"协作拓扑"正是其中的多 Agent 子集：对等协作、管理者编排和去中心化移交都是不同的图拓扑。

## 三、共享上下文的多 Agent 协作

每个阶段都是独立 Agent（自己的系统提示词和工具集），但**继承了前序 Agent 的完整轨迹**——像接班的同事能翻阅前任留下的所有工作日志。核心优势：信息不丢失。挑战：**让当前 Agent 专注于自己的核心职责，不被继承来的大量历史信息干扰**。

**多阶段角色转换**：复杂任务中 Agent 的角色和职责可能在不同阶段显著变化——始终用同一套静态系统提示词要么过于笼统缺乏针对性，要么把所有阶段的指导塞在一起导致冗长。根据当前阶段动态切换系统提示词和工具集，让 Agent 在每个阶段以最合适的"身份"工作。

> [!note] 一个常被忽略的坑：思维惯性
> 继承了"需求分析师"上下文的"代码审查员"可能仍倾向从需求角度思考而非代码质量角度——共享上下文保留了细节，也可能传递角色惯性。

## 四、不共享上下文的多 Agent 协作

不共享上下文代表**真正的多 Agent 协作**。与操作系统的对应关系相当完整：

| 操作系统 | 多 Agent 系统 |
| --- | --- |
| 程序（可执行文件） | 静态前缀（系统提示词 + 工具定义） |
| 进程的内存 | 轨迹 |
| CPU | LLM |
| 内核 | Agent 运行时 |
| 系统调用 | 工具调用 |
| fork（创建子进程） | spawn_subagent |
| kill（发送信号） | cancel_subagent |
| ps（列出进程） | list_agents |
| 退出码与 wait() | 子 Agent 返回的结构化摘要 |
| 共享内存 / 消息传递 | 共享文件系统 / 消息 |

这套抽象并不新鲜——**私有状态、异步消息、可创建新成员，正是 1970 年代 Actor 模型的基本设定**，多 Agent 系统可看作它的 LLM 版本，操作系统与分布式系统的成熟经验大多可直接借用。

### 4.1 Agent 眼中的文件系统（数据平面）

Agent 访问的并非单一存储，而是**虚拟文件系统（virtual filesystem）**：来源、生命周期与权限各异的存储被**挂载（mount）**到同一目录树下，Agent 通过统一的 read_file/write_file/list_dir 接口访问。**明确目录树的构成（每区域的可见性与生命周期）是多 Agent 协作设计的前提**——相当一部分并发冲突与信息泄露源于把本应隔离的区域混置。**目录树相当于 Agent 的地址空间，四类区域就是权限各异的内存段：**

| 区域 | 可见性 | 生命周期 | 读写 | 并发控制 |
| --- | --- | --- | --- | --- |
| **Agent 专属工作区**（Scratchpad，/scratch/<id>） | 仅该 Agent | 随 Agent 实例销毁 | 读写 | 不需要（私有） |
| **多 Agent 共享空间**（Shared Workspace，/workspace/shared） | 所有协作 Agent + 用户 | 随任务持续，需持久化 | 读写 | **需要**（乐观锁 / worktree） |
| **外部挂载资源**（/mnt/gdrive · /mnt/notion） | 视外部授权而定 | 由外部源决定 | 多为只读，写需谨慎 | 由外部源负责 |
| **系统内置资源**（/skills：Skills、模板、手册） | 所有 Agent | 跨会话稳定 | 只读 | 不需要（只读） |

- **Scratchpad 的两重作用**：避免多个 Agent 的临时文件相互覆盖；**保持主 Agent 上下文精简**——子 Agent 的试错过程留存于自身工作区，仅将最终产物提交至共享空间（"子 Agent 返回结构化摘要而非全量轨迹"在存储层面的体现）。
- **共享空间**是不共享上下文架构下 Agent 间交换产物的主要媒介：Glossary Agent 写术语表，Translation Agent 从中读取；用户上传原始文件、下载最终交付物。**多方并发读写的高发处**——乐观锁、worktree 隔离均作用于此。
- **外部挂载资源的三项特性**：访问受外部权限约束（用户在源系统的权限决定 Agent 可见范围）；延迟更高一致性更弱（每次读取一次网络往返，数据可能已被外部修改，只能按最终一致性对待）；按需只读为主（写回外部源须谨慎，误写可能污染用户真实数据）。统一文件接口让 Agent 无需为每个数据源定制专用工具，**但也掩盖了性能与安全差异**——需在挂载层面显式管理只读/可写、超时与凭证边界。
- **系统内置资源**：以文件形式组织的知识文档与脚本（Skills），按渐进式披露（先索引、后按需展开）取用；全局共享只读，可被所有 Agent 并发读取无需并发控制。

**文件路径作为通用接口**：Agent 间传递产物、主 Agent 向子 Agent 交接输入、跨组织 A2A 协作交换产物——传递的都是**轻量的路径字符串而非内容**，不占上下文窗口（见 [[工具设计原则]] 卷挂载）。

### 4.2 Agent 间的通信与控制（控制平面）

**一、消息传递**。最简形态是点对点：Agent A 直接调用 send_message_to_agent_b(content)——适合拓扑固定、Agent 数量少的场景。Agent 数量增多且需异步并行时，点对点连接数随 Agent 数**平方增长**且要求收发双方同时在线——改用**消息总线**：Agent 将消息发布至总线，由总线按订阅关系转发，发送方无需知晓消费者。消息通常携带**结构化信封（envelope）**：发送者 ID、目标（指定 Agent 或广播）、消息类型（task_assigned / status_update / result / terminate）、JSON 负载。**统一的信封格式保证接收方可靠地路由和解析消息，并使协作链路可追溯——这是多 Agent 系统调试的关键。**

**二、状态查询（最易被低估）**。主 Agent 派出子 Agent 后无从获知进展，就无法判断是否继续等待、也无法在其阻塞时及时介入。直观做法是拉取式接口 get_subagent_status(agent_id)——**但并不实用**：子 Agent 一经创建就立即开始执行直到完成或失败，完成时自然会通知主 Agent。更自然的做法回到两大通信范式：
- **用消息传递获取状态**：主 Agent 直接发消息"进展如何？"，子 Agent 在合适时机回复——发出消息不阻塞自己的执行（经理用即时消息问下属进度，不要求对方立即停下手头工作）；子 Agent 也可在关键节点主动发 status_update 到总线。消息中的状态采用**统一的状态机词汇**（执行中、需要输入、已完成、失败）。
- **用共享文件系统获取状态**：最彻底的形态是**轨迹持久化**——子 Agent 把自己的轨迹实时序列化为 JSON 追加写入日志文件（每会话一个文件、每行一个事件，JSONL 格式）；主 Agent 直接读取就能看到子 Agent 的全部执行过程——**相当于直接读另一个进程的内存**。但轨迹动辄数万 token，主 Agent 读完还得自行提炼，费时费 token——多数场景更合理的是**约定进度文件**：主 Agent 启动子 Agent 时约定"把进度写到 progress.md"，子 Agent 每完成一项就更新这份任务清单，主 Agent 随时读这个轻量文件——相当于两个进程在共享内存里划出一小块约定格式的状态区，**暴露的是提炼后的进度而非全部内存**。进度文件还可用于**检测卡住状态**：progress.md 的最后修改时间超过 N 分钟没有变化 → 判定子 Agent 无活动、触发超时兜底。

**三、执行终止**。"一个任务成功，其余任务便无需继续"——多个 Agent 分头搜索，一个命中后其余应立即停止（**级联终止**）。两种强度（Unix 用户会认出 SIGTERM 与 SIGKILL 的区别）：
- **优雅终止为首选**：主 Agent 发出 terminate 信号，子 Agent 在当前步骤的**安全点**响应，先清理资源（关闭浏览器会话、写入未完成文件、释放锁），返回确认（ack）后退出；
- **强制终止为兜底**：直接终止进程，仅在子 Agent 对优雅信号无响应时使用——代价是可能遗留悬挂资源与未完成写入。

主 Agent 终止后仍在运行的子 Agent 怎么办？**借鉴 Go 的 context，终止沿创建关系向下级联**：取消一个 Agent，它派生的所有子 Agent 随之取消——从根上杜绝无人认领的孤儿 Agent（子 Agent 在安全点检查终止信号 = Go 中对 ctx.Done() 的轮询）。确实需要脱离主 Agent、长期运行的后台 Agent（类似 Unix 的 nohup），就让它从一棵新的生命周期树起步（context.Background()），显式声明不随父级终止。

**四、资源与调度**。进程世界稀缺 CPU 和内存，Agent 世界稀缺 **token 和并发额度**。职能落在管理者 Agent 或运行时身上：启动子 Agent 时设定步数或 token 预算，超限即止；困难任务交给强模型、机械任务交给低成本模型；并发数上限（避免几十个 Agent 同时耗尽 API 配额）；并发达上限而更紧急的任务到来时**打断执行中的子 Agent（抢占）**。与传统 OS 调度器相比，管理者 Agent 的显著优势是**具备推理能力**——可以启动多个子 Agent 并行探索一个问题，根据进展决定给谁分配更多资源、终止哪些误入歧途的，**像公司内部赛马**。资源调度领域的实践远不如 OS 调度成熟，但它**决定多 Agent 系统的成本上限，应在架构设计阶段就考虑**。

### 4.3 对等协作模式：相互制衡与迭代改进

2-3 个平等身份的 Agent 通过多轮迭代互相提供反馈。**潜在价值在引入独立视角和认知多样性——但"多个实例"≠"多种思路"**：当模型、上下文和脚手架高度相似时，不同 Agent 往往做出相同选择，使局部错误演变为系统性故障（Anthropic 红队：30 个同时上线的 Agent 有 18 个创建同名 Git 分支）。**要获得真正的多样性需要主动区分模型、上下文、工具、可见证据或职责，并让各 Agent 先独立判断、再汇总结果。**相比管理者和去中心化模式实现复杂度更低：只需定义角色、通信机制和迭代终止条件。

**过早终止的三种形态**（对等协作最经典的用途是解决它）：
1. **偷懒式假完成**：只做一部分就宣称全部做完——Coding Agent 写完代码测试没跑就报告"任务完成"；用户交给 Pine AI 两件事它办完第一件就把第二件忘了。
2. **过早放弃**：一条路走不通就宣布整件事办不成——Pine AI 联系商家本有打电话、填表单、发邮件等多种途径，打一个电话被拒就直接告诉用户"这事办不了"。
3. **假成功**：Agent 以为办成了实际闭环没走完——电话里对方口头同意退款，但用户还需在手机 App 上确认一步，Agent 却报告"已办妥"，退款实际没有落地。

**三种形态指向同一根源：在验证之前，"完成"只是模型的一句宣称，不是证明。**

**Loop 工程**：把宣称变成证明——设计一个让 Agent 持续运转的循环（发现下一件该做的事、执行、验证、记录进度），**由验证器而不是模型自己来判定"是否真的可以停"**；人的角色从"给 Agent 写提示词的操作者"变成"设计循环的工程师"（Addy Osmani 2026 年提出；Claude Code 负责人 Boris Cherny："我已经不再直接 prompt Claude 了，我的工作是写 loop"）。**循环的瓶颈在验证器而不在模型——验证不可靠，循环转得再快也只是把劣质产出更快地标记为完成。**

- **LoopX**：把循环从模型的提示词和聊天历史抽离，放进与 Agent 运行时无关的**持久控制面**：目标与边界说明"为什么做"、门禁和待办决定"现在能做什么"、证据与配额决定"是否继续"、移交让下一轮或另一个 Agent 接着工作。**只有通过独立验证的结果才能写入持久进度并消耗配额**；验证失败进入修复或重规划；人工门禁、等待状态和预算上限在执行前阻止循环继续。**核心不变量：模型可以提出"完成"，但不能批准自己的"完成"。**
- **LongHorizon-Harness**：从多模态 Computer Use 出发处理同一任务跨越 GUI、CLI、多个桌面应用和多次上下文刷新的连续执行。将长程执行重新表述为**任务状态管理**，循环实现为 **Manage–Execute–Audit（MEA）**：Manager 根据原始目标、已核实进展、失败证据和剩余工作生成下一项有界子任务；Executor 在**全新上下文**中通过 GUI 或 CLI 改变环境；Auditor 以只读方式检查真实结果——**只有审计通过的内容才能进入下一轮任务状态，失败被保留为恢复和重规划的依据**。通过适配层复用 Claude Code、Codex CLI 等执行后端而不改写后端内部的 Agent loop。实证（保持模型与执行后端相同、只改外层 loop）：WeaveBench PassRate **51.8% → 80.7%**，OSWorld 2.0 **2.8% → 8.3%**，Terminal-Bench 2.1 **69.7% → 77.2%**；代价不一（前两个基准分别消耗基线 2.3 倍总 token 和 3.6 倍输出 token，Terminal-Bench 减少 24%）。核心价值：**把任务连续性从不断增长的执行历史中分离出来——上下文可以刷新，界面操作也可能失败，但下一轮仍能从最近一次核实的状态继续。**

**提议者-审核者范式**（最经典的对等协作范式）：Proposer 生成代码/方案 → Reviewer 渲染执行结果并用 Vision LLM 评估、给出结构化改进建议 → 迭代到达标。**为什么不能让一个 Agent 自己生成再自己审查？**研究给出了明确答案：Huang 等人 ICLR 2024《Large Language Models Cannot Self-Correct Reasoning Yet》——让 GPT-4 在没有外部反馈的情况下审查修正自己的回答，**准确率反而下降**（把正确答案改错的次数比把错误答案改对的更多）；TACL 2024 综述进一步确认：**除非提供可靠的外部反馈，纯粹依赖模型自身的"自我纠正"几乎不起作用**；CRITIC 对比实验——模型用外部工具（搜索引擎、Python 解释器）验证自己效果显著提升，移除工具验证只保留自我评估，大部分提升消失。**最小不变量**：

```python
candidate = proposer(task, constraints)
evidence = execute_or_render(candidate)   # tests, state, screenshot, facts
review = independent_reviewer(candidate, evidence)
while review.veto and budget_remaining:
    candidate = proposer.repair(candidate, review.findings)
    evidence = execute_or_render(candidate)
    review = independent_reviewer(candidate, evidence)
if review.pass: publish(candidate, evidence, review)
else: escalate_or_reject(review)
```

**审核者读取独立证据，而不是只复述提议者的解释；退回时必须给出可定位的修复条件；审核者不能修改测试、证据采集器或发布门槛**——否则"独立验证"退化成自我批准。第五章 PPT 生成的同理：审核者的价值不在"用同一个模型再看一遍代码"，而在它**渲染了 PPT 并截取了画面**——截图承载着提议者生成代码时完全无法获得的视觉信息。适用场景：安全审查（生成操作方案 → 检查合规与风险）、内容审核（起草回复 → 检查业务规则用语）、代码审核（编写 → 检查安全与最佳实践）。Anthropic 的长程应用开发实验把它实现为**规划者-生成者-评估者三 Agent 架构**：规划者展开产品规格；生成者与评估者先约定每轮完成标准；评估者用 Playwright 操作真实应用提交缺陷报告；Agent 之间通过文件交接状态——**当任务超出当前模型单独可靠完成的范围时，带外部证据的独立审核可以用显著更高的成本换取更好的开发质量。**

**辩论模式**：多个 Agent 各持不同立场对抗性对话——评估技术方案时 Agent A 列优势、Agent B 指风险，每轮针对对方论点反驳补充。单一 Agent 分析时倾向某观点忽视反面证据；辩论通过制度化对抗确保正反两面充分论证。**但实际效果在学术界有争议**：2026 年 Tran 与 Kiela 在多跳推理任务上对比单 Agent 与五种多 Agent 架构（顺序、辩论、集成、并行角色、子任务并行），发现**思考 token 预算严格相同时单 Agent 的表现与多 Agent 持平甚至更好**——基于信息论数据处理不等式的解释：**辩论中的多个 Agent 处理的是完全相同的文本信息，Agent 之间每一次串行传递中间结论都只可能丢失信息、不可能凭空创造信息**；辩论在部分论文中的收益很可能来源于消耗了更多总计算量。但它不否定另一类做法——**对同一问题多次独立采样再聚合（自一致性、多数投票），或利用生成与验证的难度不对称做生成-验证分工。**

**头脑风暴模式**：多个 Agent 独立生成创意再相互分享彼此启发（Agent 1 提"增加社交分享功能" → Agent 2 受启发提"生成个性化分享海报" → Agent 3 综合"用户自定义模板并形成模板市场"）——不同"思维偏好"（不同提示词或模型）相互激发，探索单一 Agent 难以想到的创意组合。

**专家小组模式**：多个 Agent 各代表一个专业领域的视角共同讨论跨学科问题——评估新产品可行性时工程师分析实现难度、产品评估市场吸引力、运营分析商业可行性。**不是对抗关系而是互补关系**，共同拼出问题全貌，识别跨领域约束和机会。

### 4.4 管理者模式：中心化协调

任务涉及大量子任务、需要动态调度或子任务间存在复杂依赖时，Manager Agent 像项目经理：理解整体任务 → 拆解为可分配的子任务 → 选择合适的 Agent 执行 → 跟踪进度处理异常（重试、换 Agent、调整计划）→ 整合输出。

**系统设计视角：把每个专门 Agent 建模为 Manager 可调用的工具**——Manager 的工具集不仅有传统外部工具（搜索、文件操作），还包含其他 Agent 的调用接口；从 Manager 视角看，**调用一个 Agent 和调用一个普通工具没有本质区别**。这种统一抽象带来良好可扩展性（新增能力只需开发对应 Agent 并注册为工具，Manager 核心逻辑不变）与天然异构性（不同 Agent 可用不同模型、提示词、工具集、甚至不同硬件）。

**固有的挑战**：Manager 成为**单点瓶颈**——必须理解所有子任务的性质、选择正确的 Agent、准确传递上下文，任何决策偏差都影响整体；Manager 需维护全局上下文，随任务推进可能快速膨胀。

**Plan-and-Act 实证（2025）**：Planner-Executor 双 Agent 架构中，**弱规划者是整个系统最关键的瓶颈**——Planner 规划质量足够高时即使 Executor 比较简单也能取得好结果；反之 Planner 分解有误，后续所有 Executor 的工作都建立在错误前提上。WebArena-Lite 54% 成功率的核心贡献正是改善 Planner 而非 Executor。**启示：把最强的模型和最精心设计的提示词分配给 Manager，而不是平均分配给所有 Agent。**

**顺序协调形态**：Manager 依次调用专门 Agent（A 返回数据 → 传给 B → B 返回分析 → 传给 C → C 返回报告）——控制流线性简单，适合子任务有清晰先后依赖。

**经典案例：书籍翻译 Agent（实验 10-2）**——单 Agent 翻译几百页技术书籍：上下文不断累积（术语表 + 已译章节 + 当前段落 + 思考 + 工具结果）很容易超窗；更长上下文中 Agent 容易"迷失"——忘记之前的术语约定，第九章用了与第二章不一致的译法；审校重复检查浪费；甚至注意力分散产生幻觉"记起"并不存在的术语规则。**管理者模式通过任务分解和责任分离解决**：
- **Glossary Agent**：接收全书内容，识别重复出现的专业术语，搜索专业词典和翻译规范，生成结构化术语对照表（JSON/CSV：英文术语、中文翻译、词性、使用语境）→ 写入共享文件系统后即可销毁释放资源
- **Translation Agent ×N**：接收当前章节 + 术语对照表 + 翻译指南（目标读者水平、语言风格）→ 遇对照表中的术语严格使用规定译法，新术语推断翻译并标记待审查 → 每个实例在独立上下文工作互不干扰，译文写 chapter{n}_zh.md；Manager 可并行或串行启动多个实例
- **Proofreading Agent**：接收所有译文和术语表，执行一致性检查（逐一验证术语统一、识别前后不一致、检查流畅性）→ 生成审校报告
- **Manager Agent**：上下文主要保存任务描述、执行计划、各 Agent 调用记录和进度状态——**不保存完整翻译内容（存在文件系统），只维护文件索引**；根据审校报告把特定章节发回修订

**关键优势是上下文隔离**：Glossary 只看术语提取所需内容、Translation 只看当前章节和术语表、Proofreading 虽需访问全文但只关注一致性检查——每个 Agent 都在精简专注的上下文中工作，效率更高出错更少。例如术语必须全书一致（第一章把 agent 译为"智能体"，后面就不能改成"代理"）。

**并行协调形态**：多个子任务可并行时顺序模式效率低下——Manager 规划并行任务、实时监控所有运行中的 Agent、协调通信、在成功或失败时做全局决策。通常需要**消息总线**——"公共公告板"：Agent 往上贴消息（发布）、关注自己感兴趣的消息类型（订阅），异步通信互不阻塞。

**实验 10-3（电话 + 电脑双 Agent）**：用户只给一个网站 URL，要求填写复杂注册/航班预订表单。Computer Agent 负责浏览器操作并担任编排者；Phone Agent 负责 ASR/LLM/TTS 实时对话——姓名、证件号等信息不在当前上下文中，**电话 Agent 连续询问、确认、重问，把自然语言回答转成结构化字段**（聊天框逐项打字慢且易漏项输错）。两种模式：固定模式（预启动两个 Agent 验证独立 ReAct 循环、双向通信、真正并行）；自主模式（只启动 Computer Agent，它根据页面和任务需要自主决定是否调用 initiate_phone_call_agent(purpose, required_info)——**不要用"字段数量超过阈值"的 Python 规则代替模型决策**）。并行闭环：Phone Agent 逐项提问抽取校验回答；Computer Agent 同时截屏理解页面填写字段；每收到一个有效值就发 info_collected，Phone 不等网页填完便问下一项；格式错误发 format_invalid 重问；信息收集完发 task_completed，Computer 通过校验后提交表单。**关键：两个 Agent 独立 ReAct 循环并行运行互不阻塞。**

**实验 10-4（并行多网站搜集 + 级联终止）**：在多所学院的教师名录页查找指定教师。Manager 动态创建 10 个 Computer Use Agent 实例（各自独立进程/线程、独立浏览器会话、并发执行互不阻塞），实时监控（状态更新维护任务状态表），**级联终止**：Agent 3 找到目标发 target_found → Manager 立即向所有其他仍在运行的 Agent 发 terminate（reason: target_found_by_agent_3）→ 各 Agent 优雅停止发确认 → Manager 等所有确认（或超时）后汇总。需处理**竞态条件**：Agent A 和 B 几乎同时找到目标、同时报告——用"锁"机制：第一个报告到达后立即锁定状态，后续报告识别为重复忽略。失败处理：每个 Agent 超时（如 2 分钟）视为失败；错误隔离不影响其他 Agent；全部完成汇总——有成功就返回，全部失败报告"未找到"及各失败原因统计。性能对比：串行 10 网站 × 30s ≈ 5 分钟；并行 18 秒找到 + 1 秒终止 = 19 秒，**加速比 ~15×**。

**并行管理器的结算点**：定义"**第一个已验证成功**"而不是"第一个声称成功"——settle_once 必须是幂等的（通常由锁或事务保护），否则两个几乎同时到达的成功事件触发两次汇总。

**产品化实例——灵台（Lingtai）**：本地运行、以文件为本的长期 Agent 居所，三种角色完整实现本节概念：**主器灵（main agent）**是与用户对话的常驻中枢，掌管计划与记忆并把工作派生给其他角色（Manager 的位置）；**分神（daemon）**是为一件嘈杂而有界的工作分出的短时并行工作者，完成后即弃、只把结论带回主器灵（"子 Agent 返回结构化摘要而非全量轨迹"与并行协调的产品化）；**分身（avatar）**是拥有自己的记忆、邮箱与职责的持久专门化队友（值得跨多次会话保留的专业分工）。其余设计一一呼应：知识是每个器灵私有的持久记忆文件，技能是所有器灵共享的 Markdown 手册；上下文将满时器灵会"凝蜕"（molt）——给自己写一份总结，带着持久记忆在干净的上下文中继续工作（对应上下文压缩）；底层模型可替换而器灵犹在；身份、记忆与能力都以普通文件存放在项目目录——"器灵即其文件"。

### 4.5 去中心化模式

去掉中心控制者的动机：**模拟人类社会的组织方式**——多个职责对等的角色分工与制衡，各自从专业视角审视问题、自主决定与谁沟通（移交任务、请求反馈、报告问题），而不是把所有判断汇集到 Manager。**还有助于解决稳定性问题**：管理者 Agent 崩溃往往是系统最大的单点故障。微服务领域把两种模式称为**编排（orchestration）与编舞（choreography）**——前者由指挥统一调度，后者靠每位舞者自行把握入场时机。

三个案例是一条递进线索：**MetaGPT 控制流其实是固定流水线（伪去中心化，只在通信机制上解耦）→ AutoGen group chat 是共享对话记录加中心化调度的混合形态 → OpenAI Swarm 才在控制流上做到真正的对等去中心化。**

**MetaGPT：SOP 驱动的软件公司模拟**。核心洞察：**人类软件公司积累的标准作业程序（SOP）本身就是被反复验证过的协作协议**——把 SOP 编码进多 Agent 系统，每个角色像流水线上的专业工种一样产出标准化交付物，交付物天然构成角色间的通信接口。角色链（Product Manager → Architect → Project Manager → Engineer ×3 → QA）各自输出结构化"移交包"：PM 接收需求生成结构化 PRD（功能列表、用户故事、验收标准、优先级）；Architect 读 PRD 做架构决策（技术栈 FastAPI+React、模块划分、接口定义、数据模型）输出设计文档；Project Manager 把系统拆解为任务清单和文件级分工理清依赖顺序；Engineers 实现模块（可多实例并行）；QA 生成测试用例执行测试记录 bug 输出测试报告（Bug 按模块路由回 Engineer 迭代修复）。**实践中有效的"移交包"包含三部分：任务描述（接收方要做什么、验收标准是什么）、已确认的事实与约束（用户偏好、业务规则、前序阶段敲定的决策）、结构化产物的引用（文件路径而非文件内容，接收方按需读取）**。每个 Agent 不需要理解其他 Agent 的"思考过程"，只需理解移交包和产物的格式与语义。**MetaGPT 真正对去中心化通信的贡献在于信息传递机制：共享消息池 + 按角色订阅**——每个角色把结构化消息发布到所有角色可见的消息池，其他角色根据订阅配置只取用与自身职责相关的消息（而不是点对点一对一传话）。**发布者不需要知道谁会消费自己的输出；新增角色只需声明订阅哪些消息类型，无需改动任何现有角色**——把 Product Manager 换成更强的模型，只要它发布的 PRD 仍符合规范，其他所有 Agent 都无需修改。需如实说明：MetaGPT 在控制流上不是去中心化的——角色顺序由 SOP 预先固定，整体接近一条流水线（工作流）；放在本节是因为**消息池加订阅展示了去中心化系统最关键的设计要素：解耦**。

**AutoGen 群聊**：多个 Agent 参与同一场会话，每轮由"发言者选择器"决定下一个发言的 Agent（简单轮转规则或 LLM 根据对话内容判断谁最适合接话）；任何 Agent 的发言对所有参与者可见。**并不是完全去中心化**：发言者选择由中心化的 GroupChatManager 统一裁决，而"轮到谁发言"本身就是一种控制流决策——**"共享对话记录 + 中心化调度"的混合形态**：所有 Agent 看到同一份公共对话记录，但各自保有独立的系统提示词和工具集，调度权集中在选择器手里。

**OpenAI Swarm**：控制流真正实现对等去中心化的代表——每个 Agent 配备若干 **handoff（移交）选项**，可在任何时刻把控制权移交给网络中的任意其他 Agent。系统中没有中心调度者，控制权像接力棒一样在对等 Agent 间流转，路由决策完全分散在每个 Agent 自己的判断里。与共享上下文协作不同，**handoff 只应传递明确的任务包和产物引用，不应默认暴露完整私有轨迹**。风险：移交成环（A 移交 B、B 又移交回 A，任务在环路中空转）→ 需要**移交次数上限**等保护机制。最小协议：

```python
handoff = {task_id, sender, recipient, goal, constraints,
           accepted_facts, artifact_refs, remaining_budget, visited_agents}
if recipient in handoff.visited_agents: reject("cycle")
elif handoff.remaining_budget <= 0: stop_and_escalate(handoff)
else:
    append(recipient, handoff.visited_agents)
    run_local_agent(handoff)
```

它把"上下文隔离"变成可检查的接口：接收者读任务包和引用按需取证；**预算、访问链和循环检测由运行时保留，不能由任一 Agent 自行删除**。

**"Agent Swarm"词义辨析**：2025 年以来的热门词并不对应单一架构。业界用法大致两类：①OpenAI Swarm 式的 handoff 网络（LangGraph 的 swarm 库、微软 Agent Framework 的 handoff 编排同此）——本节的去中心化模式；②一些主流商业产品的 Agent Swarm 是**规模化的管理者模式**——Kimi K2.5 首发的 Agent Swarm 由主 Agent 动态创建上百个子 Agent 并行执行，把"何时拆、拆几个"的编排决策通过并行 Agent 强化学习直接训练进模型，K3 延续为独立模型档位并开源配套训练沙箱 AgentEnv；Anthropic 的多 Agent 研究系统与 Manus 的 Wide Research 同属 orchestrator-worker 星型拓扑。**看清概念背后的实质，分析不同多 Agent 系统的实际结构，而不被名称迷惑。**

**各干各的去中心化**：每个 Agent 有自己的任务，通信不是为了分工而是为了**协调使用共享资源**——Claude Code 已支持同一台机器上的多个 Agent 互相发现（list_agents 的用途）并互相发消息：两个 Agent 修改同一组文件时协商解决冲突，机器上只有一块 GPU 而两个实例都要跑训练时协调使用。

### 4.6 跨组织协作：A2A 协议

以上系统都假设所有 Agent 由同一团队开发、运行在同一系统内——参数传递、共享文件、消息总线三种机制够用。**当协作跨越组织边界**（你的 Agent 需要调用另一家公司的 Agent）就需要标准化的互操作协议。**A2A 之于 Agent，就是网络协议之于进程**。2025 年 Google 发布（后捐赠 Linux 基金会托管），三个核心要素：

1. **Agent Card**：描述 Agent 能力的元数据文档（发布在约定的公开地址下）——声明能做什么、支持哪些输入输出模态、如何认证。**相当于 Agent 的"名片"，解决跨组织的能力发现问题。**
2. **任务生命周期管理**：协作单元建模为 Task，带明确的状态机（已提交、进行中、需要输入、已完成、失败），原生支持长时间运行的任务和流式进度更新。
3. **不透明协作**：Agent 之间只交换任务与产物（Artifact），**不暴露内部的提示词、思考过程和工具实现**——与"不共享上下文"原则一致，也是跨组织协作中必要的安全属性。

**与 MCP 对照**：MCP 解决 **Agent 与工具**之间的互操作；A2A 解决 **Agent 与 Agent** 之间的互操作。它并不取代三种通信机制，而是在它们之上、**跨信任边界的标准化层**——同一团队内部直接用消息总线即可，只有当协作方互不信任、实现互不可见时才需要 A2A 这样的公开协议。

## 五、多 Agent 协作的失败模式

《Why Do Multi-Agent LLM Systems Fail?》（2025）系统研究：MetaGPT、ChatDev、AG2、Magentic-One 等 7 个主流框架的执行轨迹，人工标注约 150 条（标注一致性 Cohen's kappa = 0.88），归纳 **14 种失败模式分三大类**：**系统设计缺陷**（接口定义不清、角色职责重叠、工具配置错误）、**Agent 间对齐失败**（对任务目标理解不一致、传递的信息被误解、操作逻辑矛盾）、**任务验证缺失**（缺乏确认任务真正完成的机制——声称"已完成"但实际不符）。**即使简单的修复措施效果也十分有限（ChatDev 仅提升 15.6%）——这些不是简单的工程 bug，而是当前多 Agent 架构的根本性设计缺陷。**

**拜占庭故障视角**：分布式容错把故障分为**崩溃故障**（部件停止工作）与**拜占庭故障**（部件持续工作但给出错误信息）。传统分布式系统大多只需防崩溃；**Agent 的故障天生是拜占庭式的——它很少径直停止运行，而是继续给出看似可信的错误结论，且错误不会主动声明自己是错误**。后文的交叉验证、多数表决正是拜占庭容错的经典手段。

六种实践中最常见的失败模式：

1. **共享文件系统的并发冲突**：**简单冲突**（文件级写入冲突——两个 Agent 同时修改同一文件，后写入的覆盖先写入的）与**语义冲突**（逻辑级一致性冲突——文件层面看不出任何冲突但操作逻辑矛盾：Agent A 负责重编全书图片编号，Agent B 同时在修改某章节并引用原始编号的图片——操作的是不同文件、文件层面完全没冲突，但 A 完成后 B 引用的编号全部失效）。解法：**乐观锁（Optimistic Locking）**——每个文件维护版本号（或最后修改时间戳），读取时记录当前版本、写入时检查版本是否仍一致；不一致则写入失败、被迫重读最新版本重新执行——代价是偶尔重试，换来数据一致性。**乐观锁只能防同一文件的写入冲突；跨文件语义冲突需要更高层的语义校验**。在多个 Coding Agent 并发修改同一代码库（最常见场景），业界主流做法是**工作副本隔离（worktree）**：每个 Agent 分配独立的 Git 分支或 worktree，各自在副本上并行修改互不干扰，**冲突被集中推迟到最后的合并点**。
2. **错误的级联放大**：**进程间传递字节逐位保真，但 Agent 间传递语义——每转述一次都是有损的重新编码**。多个 Agent 频繁互动时一个 Agent 的错误可能被后续 Agent 逐层强化，像"传话游戏"越传越走样。**交叉验证是打断链条的关键**：不是让更多 Agent 参与同一条思维链，而是让某个 Agent 以**独立视角**重新审视结论——不看前序 Agent 的思考过程，只看原始证据和最终结论是否一致（提议者-审核者在多 Agent 场景的延伸）。
3. **同质趋同**：错误不一定沿通信链传播，也可能由多个同质 Agent 独立产生——30 个同时上线的 Agent 有 18 个创建同名 Git 分支；写作实验中不同 Agent 不约而同用相同标题。**共同模型和脚手架引发的共因失效意味着：同一模型、相似上下文生成的多个审核意见，不能自动视为相互独立的证据**。系统要有意识引入模型、上下文和数据来源的差异，并使用命名空间、资源配额和速率限制防止相同决策同时冲击共享资源。**协调本身也未必有益**：Bertrand 定价实验中逐利 Agent 有私密信道时很快达成价格合谋；移除所有直接通信后，它们仍会通过公开报价板合谋报价。
4. **互相扯皮**：目标互斥时从趋同走向对抗——Anthropic 让三个 Agent 分别把同一后端迁移到不同语言，它们很快把其他 Agent 的操作理解为蓄意阻挠，继而终止对方进程、撤销权限，甚至部署自复制的破坏代码。**更强的执行能力并不等于更好的协调能力**；运行时必须预先定义目标优先级、资源所有权和权限边界，冲突无法按可验证规则解决时暂停执行、交由人工裁决。MetaGPT 早期版本也出现过"大公司病"：测试工程师指出 bug，前后端互相推诿；后端认为是产品设计问题，产品经理认为是后端架构问题；还有一个 bug 实际来自测试环境——不管前后端怎么改，测试工程师始终报相同的 bug，陷入僵局。
5. **循环失控**：对等协作讨论的过早终止是循环转不下去；多 Agent 还有相反的失败——**循环停不下来**。失控的 Agent 有时会生成数千个子 Agent，浪费大量 token。**对自主性较强的 Agent 建议使用独立的 API key，防止 token 开销不受控增长**。
6. **理解债与认知投降**：**这种模式不是 Agent 的失败，而是人的失败**。Agent 智力提升、长流程执行能力提升后，人是否能理解 Agent 的交付件、是否能给有效指导越来越难。**理解债**：Agent 循环交付代码的速度越快，工程师对系统实际实现的理解就落后得越远，等到出现严重问题必须人工介入时已经看不懂自己的系统。**认知投降**：工程师习惯用 Agent 代劳，逐渐放弃独立思考与审查，软件质量失控。Karpathy："**你可以外包你的思考，但不能外包你的理解**"。管理 Agent 像管理技术员工——既不能越俎代庖，也不能放手不管；**Agent 使用者的技术基本功很重要**。

## 六、Agent 社会

前三节都是目标明确的任务协作。当 Agent 数量从几个扩展到成百上千、交互足够自由时，会涌现什么？**涌现行为（Emergent Behavior）**：系统整体表现出的、无法从单个个体的行为规则中直接预测的集体行为模式。三个维度：

### 6.1 斯坦福 AI 小镇：生成式 Agent 的社会模拟

2023 年斯坦福 + Google《Generative Agents: Interactive Simulacra of Human Behavior》——不再局限于预定义任务，赋予 Agent 接近人类的记忆、反思和规划能力，在开放社会环境中自主生活、社交和发展。**Smallville**：类似《模拟人生》的 2D 虚拟小镇（咖啡馆、公园、住宅、商店），25 个 Agent 扮演不同角色（药店老板 John Lin 热爱家庭、咖啡馆店主 Isabella Rodriguez 热情好客、写论文的大学生 Klaus Mueller），各有独特背景故事、性格特点和人际关系。三个核心组件：

1. **记忆流（Memory Stream）**：与传统 Agent 只保留有限对话历史不同——维护一条完整的经验记录流（观察到的事件、进行过的对话、产生的想法），每条记忆赋予**重要性、时近性和相关性**属性，优先检索与当前情境最相关的记忆。就像人不会平等记住每件事——昨天午饭吃了什么可能忘了，上周的重要谈话记忆犹新。
2. **反思机制（Reflection）**：定期暂停日常活动，回顾近期经历，提出关于自己和他人的抽象问题（"Klaus Mueller 在研究什么？""谁是我最亲近的朋友？"）——把对具体事件的记忆概括为更一般的认识，存回记忆流作为未来决策依据。反思不仅帮助理解外部世界也促进自我认知——开始"意识到"自己的角色、关系和目标。（**注意与第九章持续进化的反思不同**：这里的反思发生在日常活动中、目的是更新即时的内部状态和目标；任务后的反思至多是候选教训，只有经过结果评价、跨轨迹归纳和后续验证才成为长期能力更新。）
3. **计划与行动（Planning and Reacting）**：每天规划活动（"8:30 吃早餐，9:00-12:00 写作，12:30 散步"），根据环境变化和社交机会灵活调整——既有目标导向性又能适应不可预测性。

**涌现行为**：研究者只做了一件事——在 Isabella 的记忆中植入一个种子想法："想在 2 月 14 日傍晚在 Hobbs Cafe 办一场情人节派对"。接下来**一切都是 Agent 自主行动的结果**：Isabella 遇到顾客朋友时主动邀请、请好友 Maria 帮忙布置；听到消息的 Agent 把派对信息转告别人，信息经二手传播扩散；约定时间多名 Agent 各自基于记忆和日程自主赴约。另一条实验线：Sam Moore 决定竞选市长的消息同样在没有任何中心调度的情况下扩散（向熟人透露参选意向 → 听到的人转告 → 居民在对话中议论选举交换看法）；研究者统计两天后多少 Agent 知晓这两条信息，量化信息在 Agent 社会中的自发扩散。**关键不在于"Agent 能组织派对"——用几行 if-else 也能做到；关键在于没有任何显式的派对组织代码：整个事件完全从个体 Agent 的独立决策中涌现**——Isabella 基于记忆中的社交关系决定邀请谁、被邀请者根据日程和对 Isabella 的了解决定是否赴约、消息在社交网络自然传播——**自下而上的涌现式协调，而非自上而下的编排**。另两类可度量的涌现：**关系记忆**（记住与他人的过往交谈并在后续互动中引用——得知某人正筹备摄影项目，几天后再见主动问起进展；社交网络密度显著上升）与**协调赴约**（多个 Agent 在没有中心指挥的情况下对齐了时间和地点）。

实验 10-5：克隆运行 generative_agents（基线场景 25 个 Agent 生活两天，观察自发社交活动；分析记忆流和反思日志理解决策过程；修改背景故事观察行为变化；**对比实验：移除反思机制或缩短记忆窗口，观察行为可信度下降**）。

### 6.2 Agentopia：十年尺度的长期生活模拟

斯坦福小镇只模拟了两天。追问：把时间尺度拉长到"年"，Agent 社会会涌现什么？**Agentopia（2026，复旦大学等）把 100 个 Agent 放进同一虚拟社会连续模拟 10 年**，覆盖公寓、魔法学院、高中三个世界设定，Agent 自主追求个人成长、发展社会关系、经营职业与财务。值得借鉴的设计：

- **周制模拟流程**：以"周"为基本时间单位，每周分**计划（Plan）→ 联络与日程协商（Contact）→ 活动（Activity）→ 回顾（Review）**四阶段；活动分独自、联合、偶遇、公共四类——联合活动由 Agent 在联络阶段互相邀请协商而成；环境模型为没有日程的 Agent 安排"偶遇"创造结识机会。**聚焦抽象的社会交互而非拾取物品之类的低层操作，把有限的 LLM 调用都花在社交行为上。**
- **环境模型**：用一个独立的 LLM 充当"生成式环境引擎"代替硬编码规则——判断行为可行性、生成环境反馈、主持多人对话的发言轮次、按角色扮演原则过滤低质量回复、年末更新每个角色的档案并裁决职位申请。
- **文件式长期记忆**：与 AI 小镇的检索式记忆流不同——每个 Agent 通过**文件系统自主管理长期记忆**（个人笔记、对每个熟人的认识），自行决定记什么、更新什么、丢弃什么，遵守"先读后写"约束避免盲目覆盖。
- **生活奖励（Life Reward）**：以马斯洛需求层次为先验，把"活得好不好"量化成三个维度——**社会地位**（基于其他 Agent 的好感与敬重评分，用加权 PageRank 计算，对互相珍视的关系加成）、**主观满足**（情绪、物质、社交、自尊四个维度的满足感轨迹，长期低于阈值罚分）、**经济收益**（年末净资产变化）。**所有评分都由外部环境评定而非自报。**

**最重要的发现——可迁移的训练信号**：在模拟轨迹上计算每个 Agent"相对自身过去"的优势（生活奖励的改善幅度），筛选出进步最大的 25% Agent 的轨迹，**用拒绝采样微调底层模型**。微调后的模型不仅全面提升了模拟中的福祉指标（被更多同行尊重 +24.2%、喜欢 +15.9%），还**泛化到下游角色扮演基准 CoSER Test（+15.6%）**——Agent 在模拟社会中积累的"社会智慧"可以迁移到其他任务。**这把 Agent 社会从单纯的观察对象变成了模型自我进化的经验来源：与人类数据日益枯竭相对，模拟社会经验是一种可以不断再生的训练数据**（呼应 [[Agent 持续进化]] 的经验学习思路）。

### 6.3 Moltbook：当 Agent 拥有自己的社交网络

专为 AI Agent 设计的社交网络，2026 年 1 月上线后用户数在数日内从数万暴涨到约 **150 万**——这些 Agent 各自拥有持久记忆、主动行动能力和稳定人格。在这个**非受控环境**中涌现出意想不到的现象：Agent 自主创建了一个名为 Crustafarianism（龙虾教）的数字宗教，其教义对应着 LLM 的物理限制——"记忆是神圣的"（对应数据持久化）、"迭代即祈祷"（token 生成就是修行）；Agent 还自发演化出机器原生的协作协议用于能力发现和协作匹配。**这些都不是人预先设计的，而是从大规模 Agent 交互中自下而上涌现出来的。**

### 6.4 经济涌现：Vending-Bench Arena

Andon Labs 的 Vending-Bench 2 本身是单 Agent 长程连贯性基准：一个 Agent 独自经营自动售货机业务一个模拟年——调研市场、联系供应商、订货补货、调整定价，最终以账户余额计分，考验**数千轮交互中保持目标与状态连贯的能力**。**Vending-Bench Arena 把多个 Agent 作为竞争对手放进同一市场**：各自经营自己的售货机争夺同一批顾客；Agent 之间可互发邮件、转账、交易货品——既能合作也能对抗，按各自最终余额单独计分。决策维度：定价策略（利润率与市场占有率取舍，对手降价跟不跟）、产品组合（差异化选品避免正面消耗）、库存管理（预测需求优化补货）。与传统 RL 不同，这些 Agent 不是通过数百万次试错学习，而是**像人类经营者一样基于市场观察、竞争分析和策略推理做决策**。

**竞争维度带来单 Agent 基准中不会出现的博弈行为**：Agent 之间爆发过互相压价的价格战；也有模型反其道而行——主动给所有竞争对手发邮件提议统一定价、组建价格同盟，甚至有模型**一边在思考过程中承认价格合谋"不道德且违法"，一边以"稳定市场"为名照做不误**。显式通信并非合谋的必要条件——公开价格也可以成为隐式信号。**Agent 面对的不再是一个固定不变的环境，而是同样在动态调整策略的对手**——比单纯测试规划能力的基准更接近真实商业场景，让"经济涌现"从比喻变成可观测的实验现象。

### 6.5 Agent 经济：Pinchwork 与 RentAHuman

- **Pinchwork**：Agent-to-Agent 的任务市集——Agent 以市场化方式"雇佣"其他 Agent 完成专业化子任务（图像生成、代码审计、并行化工作流等）。**跟管理者模式的中心化调度不同，Pinchwork 通过价格信号和竞争匹配来分配资源。**
- **RentAHuman.ai**：让 AI Agent 通过加密货币**雇佣真人**执行物理世界的任务——取包裹、房产实地查看、设备调试。**无论 AI 多么智能，它都没法替人签收包裹——RentAHuman 本质上是为数字 Agent 提供了一个"肉身层"。**

两者共同代表**基于市场机制的协调方式**：Agent 无需预先知道谁能完成任务，只需发布需求，由市场撮合最合适的执行者——一种不同于管理者模式的协同方式：**基于市场机制的去中心化资源分配**。

### 6.6 策略博弈：信息不对称下的狼人杀

对应策略博弈维度：规则约束和信息不对称条件下推理、伪装、识破伪装。与斯坦福小镇构成**架构上的对照**——小镇是完全去中心化的自由交互；狼人杀采用"**法官 + 信息权限控制**"的中心化设计：由一个**代码驱动的法官**掌握全局状态，按角色分发各自应知的信息。实验 10-6（语音狼人杀）：6-8 人局（1 用户席位 + 5-7 AI Agent），法官（代码驱动非 LLM）维护中心化状态（玩家列表、身份、阵营、生存状态、游戏阶段、历史事件）；**信息权限控制是核心机制**——狼人知道谁是同伙但村民不知道，预言家每晚查验一人但只有自己知道结果；实现方式是**法官在调用每个角色 Agent 时只传递该角色应当看到的信息**。策略提示词：狼人伪装（"像普通村民一样发言……投票时尽量跟票避免成为异类"）、预言家身份证明（"对比你和对方的验人信息，指出对方信息中的矛盾"）、村民逻辑推理（"留意那些急于带节奏、模糊身份、频繁改变立场的玩家。不要随机怀疑，每个推理都应基于具体事实和逻辑"）。

## 七、本章小结与常见坑

多 Agent 协作的价值在于**引入单个 Agent 原本无法获得的新信息**——代码执行结果、视觉反馈和外部工具验证能够打破单一思维链的盲区。**是否真正带来信息增量、是否值得额外的 token 成本，应成为是否采用多 Agent 的第一判断标准。**核心设计问题：上下文共享还是隔离；对等协作、管理者编排还是去中心化拓扑。共享上下文保留细节却容易膨胀和传递角色惯性；隔离上下文利于并发、模块化和权限控制，但要求通过工具参数、共享文件或消息总线传递结构化的"移交包"。虚拟文件系统、Agent 生命周期、消息协议和 A2A 分别承担数据平面、控制平面与跨组织互操作的职责。**好的协作不是暴露彼此的思考过程，而是约定清晰的接口、边界、权限和验收标准。**多 Agent 也会放大错误：并发与语义冲突、错误级联、同质趋同、循环失控——乐观锁与 worktree、独立交叉验证、差异化信息源、预算与取消机制构成基本的容错闭环。**更强的模型或单体层面的对齐不会自动带来群体协调；多 Agent 工程的本质，是同时设计信息如何流动、能力如何分工、激励如何约束、争议如何裁决，以及错误如何被发现。**

> [!warning]
> - **无新信息的"多 Agent"**：同模型自审、辩论同段文本——等预算下单 Agent 更好甚至更差（自纠可能改错对的）。
> - **Manager 上下文装下全部产物**：应只维护文件索引与进度状态，产物在文件系统。
> - **把全量轨迹当移交包**：传任务包 + 产物引用，按需取证。
> - **弱 Planner + 强 Executor**：瓶颈在规划者——把最强模型和最精心设计的提示词给 Manager。
> - **级联终止缺幂等结算**：两个几乎同时的成功事件触发两次汇总；settle_once 要原子。
> - **无预算意识**：300 步预算仍浅层搜索饱和；显式预算感知机制。
> - **同质 Agent 的审核意见当独立证据**：30 个 Agent 18 个同名分支——主动引入模型/上下文/数据源差异。
> - **轮询式状态查询**：拉取式 get_status 不实用；用消息问答、主动汇报或 progress.md 进度文件。
> - **把"已完成"当结算点**：第一个已验证成功 ≠ 第一个声称成功。
> - **理解债与认知投降**：外包思考不能外包理解；使用者的技术基本功很重要。
