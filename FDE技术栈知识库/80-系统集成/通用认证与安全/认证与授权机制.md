# 认证与授权机制（总览）

> [!abstract] 定位
> 本篇把企业集成里反复出现的 **API Key / OAuth / JWT / Webhook / Token 生命周期 / Rate Limit / Permission** 串成一张总图。FDE 接任何客户系统都要过这一关：先想清楚「谁在调、凭什么调、能调什么、调的频率」。本篇是 [[企业系统集成]] 与 [[SaaS 集成]] 的「认证授权地基」，并与 [[后端基础]] 的「运行时 / 框架 / API 风格」分层互补。

---

## 一、概念地基：认证 vs 授权

很多人把两者混用，但差很远：

| 词 | 回答的问题 | 例子 |
|---|---|---|
| **认证 Authentication** | 「你是谁」 | 登录、密码、验证码 |
| **授权 Authorization** | 「你能干啥」 | 权限、角色、scope |

- **OAuth 是授权框架**（ delegation：把「某系统在某某范围内」的访问权授予第三方），它默认不解决「你是谁」——要做登录得在其上加 **OIDC（OpenID Connect）** 身份层。
- 记忆口诀：**认证 = 进门刷脸；授权 = 进门后能进哪些房间。**

---

## 二、六种集成机制总览

| 机制 | 是什么 | 解决什么 | 详见 |
|---|---|---|---|
| **API Key** | 一串静态密钥，放 Header/Query | 最简地标识「你是谁」，server-to-server | 本节三 |
| **OAuth** | 委托授权框架 | 用户不交密码，授权第三方有限访问 | [[OAuth]] |
| **JWT** | 自包含签名令牌 | 无状态地携带「谁/范围/过期」并可本地验真 | [[JWT]] |
| **Webhook** | 事件回调（对方主动推） | 实时接收事件，而非轮询 | [[Webhook]] |
| **Access/Refresh Token** | 令牌生命周期 | 短时访问 + 长时刷新，缩小泄漏面 | 本节六 |
| **Rate Limit / Permission** | 限流 / 最小权限 | 配额管控 + 只给够用的 scope/角色 | 本节七 |

> [!note] 它们不是并列清单
> API Key 与 JWT 是「凭证形态」；OAuth 是「发凭证的流程」；Webhook 是「触发方向」；Rate Limit / Permission 是「约束」。实际一个集成往往是「OAuth 发 JWT → 带 Bearer 调 REST API → Webhook 收事件 → 遵守限流与权限」的组合。

---

## 三、API Key 与 JWT 根本不是一回事

这是最常见的误解。两者都能塞进 `Authorization: Bearer <xxx>` 头，所以容易混，但本质不同：

| | API Key | JWT |
|---|---|---|
| 形态 | 随机不透明字符串（`sk_live_xxx`） | 结构化、可解码的签名 JSON（`header.payload.signature`） |
| 验证方式 | **必须查库/查服务**知道「这串对应谁」 | 拿公钥**本地验签名**即可，无需查库 |
| 携带信息 | 本身不含（都在服务端记录） | 自带 `sub` / `scope` / `exp` 等声明 |
| 吊销 | 删库里那行记录 | 等过期或加黑名单 |
| 状态 | 有状态 | **无状态** |

- **类比**：API Key 像「门禁卡号」——前台查表才知道你是谁；JWT 像「带照片和有效期的水印证件」——看一眼就知道真假和权限，不用打电话问前台。
- 所以「普通 API Key 不就是 JWT 吗」——**不是**。一个是裸密钥，一个是自描述的签名票据。

---

## 四、OAuth 是框架，JWT 是令牌载体

一个关键澄清（也是很多人绕不过去的弯）：

- **OAuth 定义「如何拿到授权的流程」**：用户跳授权页 → 点允许 → 你的应用拿到 Authorization Code → 用 Code 换 Token。它是一套**协议/框架**。
- **JWT 定义「那张票长什么样」**：`Header.Payload.Signature` 三段，payload 里是 claims。它是一種**令牌格式**。
- **关系**：JWT **通常就是 OAuth 流程发出来的 Access Token 的载体**。OAuth 不强制 JWT（也可以发不透明随机串），但现代实现（Azure AD、Auth0、多数 SaaS）普遍用 JWT 当 access token。

> [!tip] 一句话
> **OAuth 是「舞步」，JWT 是「舞步结束时递给你的那张票」**。JWT 不是脱离 OAuth 独立做验证的东西，而是配合框架、在框架之内被签发与校验的。

## 五、scope：把权限做成「可定义分块字段」，跨公司怎么定制？

你之前有个很漂亮的判断：**「限制范围只用一个字段就能装下，说明各模块事先就做好了权限隔离，做成可定义分块字段，互相调用时只需在 JWT 里简单带一下。」** 完全正确。展开：

- **资源服务器预先**把自己的能力切成细粒度 scope（如 `read:orders`、`write:invoice`）。调用方申请哪些 scope，token 里就装一个 `scope` 字段，资源服务器据此放行。
- **调用方与被调用方解耦**：被调用方定义好权限边界，调用方只管在 token 里带对应 scope。这就是「分块权限字段」的威力。

**那不同公司模块天差地别，OAuth 怎么定制隔离？** 答案是「**机制标准化 + 词汇表各家自定**」：

- 框架规定：`scope` 是一串字符串、授权时申请、token 里携带、资源服务器据此放行——**机制是通用的**。
- 但具体有哪些 scope、叫什么名字，**由每家厂商自己设计**：Microsoft Graph 用 `https://graph.microsoft.com/Mail.Read`，Salesforce 用 `api` / `refresh_token`，你的内部系统用 `order:read`。
- 所以集成 Salesforce 和 SAP，**走的是同一套 OAuth 舞步，但 scope 取值不同**。框架提供「通用语言」（consent、token、scope、refresh），各厂商填充自己的「权限词典」。

> [!note] 框架的定位
> OAuth 主要就是「**授权这一层**」的设计规范（RFC 6749 等）；JWT 是配套的便携式令牌格式（RFC 7519）。二者合起来，本质就是**在裸 API Key 之上，封装出一套 scoped + delegated + stateless + revocable + 标准化 的凭证体系**。

## 六、Access Token / Refresh Token 生命周期

- **Access Token**：短命（分钟级），每次 API 调用带上，证明「此刻我有这些权限」。
- **Refresh Token**：长命（天/月级），用来换新的 Access Token，避免用户反复登录。
- **为什么分开**：缩小「爆炸半径」——Access Token 泄漏，窗口很短；Refresh Token 泄漏，服务端可吊销。
- **混合策略（实战最常见）**：Access Token 用 **JWT**（无状态、资源服务器可本地验，不必每请求查库）；Refresh Token 用 **不透明随机串**（存在服务端，可随时吊销）。两者各取所长。

## 七、无状态登录态（Stateless Session）详解

对比两种模式：

| | 有状态（Session） | 无状态（JWT） |
|---|---|---|
| 登录后 | 服务端存 session（Redis/DB），发你 sessionId cookie | 服务端**签一个 JWT 给你**，自己不留底 |
| 每次请求 | 带 cookie → 服务端查 session 表确认身份 | 带 JWT → 服务端**验签名 + 过期**即可，不查库 |
| 依赖 | 必须有共享的 session 存储 | 只要有**公钥/密钥**就能验 |
| 扩展 | 多实例要共享 session 集群 | 任意实例独立验，天然水平扩展 |

**「无状态」的含义**：服务端**不保存你的登录上下文**，你的「登录态」整个被编码进那张签名令牌里（`sub`=你是谁、`scope`=能干啥、`exp`=到几点）。服务端验证令牌本身就能确认，不依赖任何内存/数据库状态。

- **为什么好**：水平扩展（100 个服务实例任意一台都能独立验，不用共享 session 集群）；跨服务/跨域（微服务 A 调 B，B 自己验 JWT 就行）；移动端 / SPA 友好（没有 cookie 会话也能维持登录）。
- **代价**：令牌发出去就「飞了」，在 `exp` 之前难单方面吊销（除非加黑名单或把 TTL 设很短 + refresh）。实践上 JWT 通常短命（几分钟），靠 Refresh Token 续命。

> [!tip] 一句话
> 「无状态登录态」= **登录信息存在令牌里而不是服务器里**，服务器靠密码学验真伪，不查库。

## 八、授权框架是不是多余？（核心哲学）

你提过一个很尖锐的方案：**「给 FDE 建个定时过期的账号，到期 cron 删掉；要限位就给账号打标记」**。方向完全正确——而 OAuth / Permission 框架恰恰是这套思路的**标准化、自动化、可扩展版本**，不是多余。逐条回应：

1. **「删账号太暴力 / 粗粒度」到底粗在哪？**
   删账号是**全有或全无**：删掉的是「这个人的整个身份」，他所有授权、所有集成、所有数据访问一并消失；你没法「只废掉这次 FDE 集成、保留他别的正常使用」。而 **JWT 吊销是外科手术**：只废那一张令牌（甚至只废某个 scope），用户账号、其他集成毫发无损，且一键 API 完成。

2. **删/建账号是人工运维，不可 API 化**：慢、易错；token 吊销是瞬间、程序化的。

3. **建账号就得把密码交给 FDE**：FDE 一旦被攻破，攻击者拿到能登录的凭据，在到期删除之前可滥用。OAuth 里 FDE **从没拿到用户密码**，只拿到一个 scoped token；就算 token 泄漏，窗口短且可即时吊销。

4. **「打标记限位」本质就是 Permission / Scope 机制**：框架就是把这个「标记 + 限制」正式化、可在 API 网关统一强制、可程序化发放与吊销的版本。手工给每个账号打标记无法扩展到成百上千的集成/合作伙伴，框架让你用一行 scope 声明 + 一次 API 调用完成，且跨厂商一致。

5. **框架由谁建？** 企业（或其 SaaS 厂商）提供并运行授权框架（IdP：如 Okta、Entra ID、Auth0），FDE 是**消费者，不是建设者**。但 FDE 必须「会」：走 OAuth 授权码流程拿 token、申请正确 scope、安全存 token、处理过期与刷新、调 API 时守限流、校验 Webhook 签名——不会这些就接不上客户系统。这正是 FDE 的价值。

> [!note] 你的判断成真
> 你手动描述的「临时账号 + 到期删除 + 打标记限位」= OAuth / Permission 框架的**人肉版**。框架不是凭空多出来的累赘，而是把这套逻辑变成标准化、自动发放/吊销、跨厂商互通、不共享密码、可分布式验真的生产机制。

## 九、匿名化实战案例：某本地「任务型 CLI」的 OAuth2 + JWT 实测

> [!warning] 匿名约定
> 以下案例用于印证上述理论，**不出现任何具体产品名、域名、账号标识或个人姓名**。所有名称、邮箱、ID 均已替换为代称，仅保留技术结构。

**背景**：某云端任务平台提供一个**本地 CLI 客户端**（schema 驱动的任务执行工具）。它默认连一个云端 API（`https://api.example-task-platform.com`），用来发现任务、提交任务、拉结果。我们直接看它的鉴权实现。

**1. 登录流程（OAuth2 浏览器流）**
```bash
<cli> auth login        # 打开浏览器做登录（不向 CLI 交密码）
<cli> auth whoami       # 显示当前登录主体
<cli> auth logout       # 清掉本地令牌
```
它还支持 `--token` 用一次性登录令牌交换——典型的 OAuth2 授权码 / 设备流特征。

**2. 令牌落盘结构**（本地 `~/.config/<cli>/profiles/default.json`）
```json
{
  "server": "https://api.example-task-platform.com",
  "profile": "default",
  "principal_id": "user_abc123",
  "principal_email": "user@example.com",
  "principal_name": "某用户",
  "access_token": "<JWT>",
  "access_token_expires_at": "2026-08-28T10:33:00Z",
  "refresh_token": "<不透明随机串>",
  "refresh_token_expires_at": "2026-09-27T10:18:00Z"
}
```
注意：**`access_token` 是 JWT，`refresh_token` 是不透明随机串**——正是第六节讲的混合策略。

**3. 把 access_token 解码（只展示声明，不重放密钥）**

Header：
```json
{"alg":"EdDSA","kid":"backend-auth-key-1","typ":"JWT"}
```
Payload（claims，值已代称）：
```json
{
  "iss": "http://localhost:8765",        // 签发者：本地登录回调服务
  "aud": "task-cli",                     // 受众：仅限该 CLI 使用
  "sub": "user_abc123",                  // 主体（你是谁）
  "user_id": "uuid-1111",
  "sid": "uuid-2222",                    // 会话 ID
  "email": "user@example.com",
  "name": "某用户",
  "roles": [],                           // ← 权限/角色声明位（分块权限字段）
  "provider": "frontend",
  "iat": 1787912280,                      // 签发时间
  "exp": 1787913180                      // 过期时间（iat + 900s = 15 分钟）
}
```

**4. 这案例逐条印证了我们的理论**
- ✅ **OAuth2 框架**：浏览器登录 + Access/Refresh 生命周期 + `expires_at` 字段。
- ✅ **JWT 是 OAuth 的令牌载体**：access token 三段结构、`typ:"JWT"`。
- ✅ **JWT 自带 sub / roles(=scope) / exp / aud**：你猜的「限制范围只用一个字段装」正是 `roles` / `aud` 这一层（此账号 `roles:[]`，但槽位已就位）。
- ✅ **Access 短时（15 分钟）、Refresh 长时（约 30 天）**：标准混合策略。
- ✅ **无状态登录态**：JWT 自包含 sub/exp/roles，云端验签名即可，不依赖会话存储。
- ✅ **aud 受众隔离**：`aud:"task-cli"` 限制令牌只能被该客户端使用。

> [!tip] 结论
> 你这几轮在抽象层推演出的模型，在一台真实机器上的某个 CLI 里被一行不差地实现了：浏览器登录（OAuth2）→ 签发 JWT（EdDSA 签名、带 sub/roles/exp/aud）→ 本地存混合令牌 → 每次调用带 Bearer 访问云端多租户后端。这也顺带回答了「SaaS 怎么判定」：该 CLI 背后的平台核心算力在厂商云上、多租户、你只调用——正是 SaaS。

## 十、FDE 实战 checklist

- [ ] 调客户系统前，先搞清楚它用哪种凭证：API Key / OAuth / JWT？
- [ ] OAuth 走标准流程，**绝不收集用户密码**；scope 按最小需要申请。
- [ ] Access Token 过期用 Refresh Token 换，流程不能断。
- [ ] JWT 必须验签名 + 验 `exp`，别把敏感数据放 payload。
- [ ] Webhook 必须校验签名、做幂等、立刻回 200 再异步处理。
- [ ] 尊重 Rate Limit，退避重试、分页、缓存。
- [ ] 密钥/令牌绝不硬编码、不进仓库（见 [[Git]]、[[Docker]]）。
