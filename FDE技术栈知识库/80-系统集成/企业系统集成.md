# 企业系统集成

> [!abstract] 定位
> **企业系统集成** 是 FDE 非常核心的能力：把你的方案连进客户真实的业务系统——CRM、ERP、内部数据库、企业 API，甚至「只有 Excel 和老 Web 后台」的奇怪环境。集成的成败，往往决定项目能不能真正交付。

---

## 一、企业要集成的对象

```text
Salesforce / HubSpot   # CRM
Slack / 飞书 / 企微      # 协作
Jira                   # 研发协作
Notion / 文档           # 知识
Google Workspace / M365 # 办公套件
ERP                    # 财务/供应链
CRM                    # 客户管理
内部数据库              # 私有数据
企业 API               # 自建系统接口
```

> [!note] SaaS vs 内部系统
> [[SaaS 集成]] 是标准云应用的连接；本篇更强调「客户自有 / 老旧 / 非标准」系统的对接，两者手段相通。

### 一·补一、谁在维护这些系统（角色表）

企业系统不是「一个人搞定」，而是分层负责：

| 角色 | 干什么 | 例子 |
|---|---|---|
| **业务 owner（业务部门）** | 定义流程、提需求、验收 | 销售总监定 CRM 销售阶段；CFO 定 ERP 财务规则 |
| **IT / 运维 / 系统管理员** | 账号、权限、配置、升级、可用性 | 给员工开 CRM 账号、配角色、管沙箱 |
| **实施顾问 / 集成工程师** | 把系统配到贴合企业、做对接 | Salesforce 实施商、SAP 顾问 |
| **开发 / 内部平台组** | 写定制代码、接 API、做集成 | 用 CRM/ERP 的 API 拉数据进数仓、接 FDE 方案 |
| **厂商支持** | 云端 SaaS 的底层运维由厂商负责 | Salesforce 的 SRE 管平台本身 |

> [!tip] FDE 打交道的通常是谁？
> SaaS 化之后，底层硬件/数据库/可用性由厂商负责，企业自己只管「配置 + 权限 + 集成」。所以 FDE 通常对接的是**有 API 权限的集成开发者 / 管理员**——这正是 OAuth / JWT 这套授权机制存在的土壤（见 [[认证与授权机制]]）。

### 一·补二、CRM / ERP 是什么，与「内部 DB / 企业 API」的层级关系

- **CRM（客户关系管理）**：管理客户与销售全生命周期——线索、商机、客户、合同、客服。属前台。代表：Salesforce、HubSpot、Dynamics 365。
- **ERP（企业资源计划）**：管理核心业务流程——财务、采购、库存、生产、HR。属后台。代表：SAP、Oracle ERP、NetSuite、用友/金蝶。
- 两者关系：CRM 赢下商机 → 推 ERP 生成订单 → ERP 出财务凭证/发票，数据要双向同步。

**关键层级（务必分清）：**

```text
┌─ 业务系统（CRM / ERP / 自研）
│     ├─ 内部数据库  ← 厂商托管，你基本碰不到（不直接连）
│     └─ 企业 API    ← 厂商开给你的「受控窗口」(REST/SOAP)
│            │
│            ▼
└─ 你的集成代码（FDE 写的中间件 / 连接器）
```

要点：
- **你几乎从不直接连 CRM/ERP 的数据库**：那是厂商托管、schema 私有、动一发全身；SaaS 场景下物理上你就没那台库的主机。
- **企业 API 才是 sanctioned（官方允许）的集成面**：所有读写走 API，受权限、限流、审计约束。
- 层级即：**业务系统 ⊃ 其内部 DB（碰不到） ⊃ 企业 API（唯一窗口） ⊃ 你的集成层**。

### 一·补三、为什么本篇要提「SaaS 集成」

因为今天的 CRM/ERP **大多本身就是 SaaS**（Salesforce、NetSuite 都是云上多租户）。所以：

- **企业系统集成** = 从「系统类型」视角（CRM/ERP/内部系统怎么连）。
- **SaaS 集成** = 从「交付形态」视角（云上多租户、API-First、OAuth/Webhook 原生）。

两者关系：**SaaS 集成 ⊂ 企业系统集成的实际子集**。FDE 接的客户系统 90% 是 SaaS，所以两个角度都要会（[[SaaS 集成]] 里还详述了 SaaS 的本质判定）。

## 二、必须理解的集成机制

这七种机制（API Key / OAuth / JWT / Webhook / Access·Refresh Token / Rate Limit / Permission）的完整定义、相互关系与「授权框架为何不多余」的哲学，已单独整理到 **[[认证与授权机制]]**。这里只点一句各自角色：

- **API Key**：最简标识「你是谁」，但长期不变、无 scope、泄漏即全权。
- **OAuth**：委托授权框架，用户不交密码即可授予第三方有限访问（见 [[OAuth]]）。
- **JWT**：常作为 OAuth 发出的 Access Token 载体，自包含 sub/scope/exp 声明（见 [[JWT]]）。
- **Webhook**：事件反向推送，实时省资源（见 [[Webhook]]）。
- **Access / Refresh Token**：短时访问 + 长时刷新，缩小泄漏面。
- **Rate Limit / Permission**：配额管控 + 最小权限原则。

> [!tip] 一个真实集成的样子
> 往往是「OAuth 发 JWT → 带 Bearer 调 [[REST API]] → Webhook 收事件 → 守限流与权限」的组合，而非单个机制单打独斗。

典型场景：
```text
客户 CRM
   ↓ API（鉴权）
FDE Solution
   ↓ AI 处理
CRM / Slack / Email
```

## 三、FDE 集成的现实挑战

- **系统很老**：没有 REST，只有 SOAP / 数据库直连 / 网页后台（用 [[Playwright]] 顶上）。
- **文档缺失**：靠抓包、试错理解接口。
- **安全审查严**：客户要你证明 Token 不泄露、数据不越权。
- **数据脏**：真实业务数据充满异常，清洗靠 [[ETL 与数据管道]] 与 [[SQL]]。
- **权限复杂**：跨部门数据要按角色过滤（[[RAG]] 的 metadata 过滤也同理）。

## 四、安全是底线

> [!warning] 企业集成安全红线
> - **密钥绝不硬编码 / 进仓库**：用密钥管理 + 环境变量（见 [[Git]]、[[Docker]]）。
> - **最小权限**：只申请必要范围与字段。
> - **传输加密**：全程 HTTPS，内网也要考虑。
> - **审计与脱敏**：日志别打全量敏感数据；留操作痕迹。
> - **可逆**：集成要能随时断开，不影响客户主干系统。

---

## 五、常见坑

> [!warning]
> - **低估对接成本**：「调个 API 而已」往往变成数周适配，提前排期。
> - **不处理限流 / 重试**：生产一跑就 429 或重复写。
> - **忽略数据权限**：检索/展示越权，触碰合规红线。
> - **没有降级**：客户系统挂了，你的方案也挂，要有兜底与队列（[[Redis]]）。

---

## 六、延伸：授权框架是不是多余？

常有人问：「给 FDE 建个定时过期的账号、到期删掉、打标记限位不就行了，何必 OAuth/JWT？」

答案：**OAuth / Permission 正是这套思路的标准化、自动化、可扩展版本**——删账号是粗粒度（连真人其他正常使用一起删），JWT 吊销是外科手术；建账号就得交密码，OAuth 从不交密码；「打标记限位」本质就是 scope/permission 机制。框架由企业/厂商建好，FDE 是消费者。完整论证见 **[[认证与授权机制]]** 第八节。
